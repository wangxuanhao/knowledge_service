# 旧后台与新增服务：能力对标与修正

## 结论

用户目标是原项目能力的增量提升，而不是用简化后台替代原有能力。此前将“不改命名、向后兼容”解释为“不兼容编号脚本与旧数据格式”不符合当前明确要求。此前设计中的不兼容前提撤回；新服务暂不能替代旧后台。

此文为源码核查结果与待确认修正方向，不表示以下缺失功能已经补回。

## 实际实现对照

| 能力 | 原后台实现依据 | 新增 knowledge_service 状态 |
|---|---|---|
| 本地项目列表、加载 | `kgcore/kg_project.py`、16 的 `api_projects/api_load`，读取 data/projects | 只列 SQLite 项目，没有旧项目适配 |
| 导入已有抽取结果 | 16 的 `api_import/run_import_job` | 缺失；只能上传文本或结构化记录 |
| 交互图谱、节点定位、邻域 | 原 app.js 的 ECharts graph/force；16 的 graph/node/subgraph | 只有图 JSON 与关系列表，无图谱画布 |
| 看板与统计 | `api_dashboard` + ECharts 图表 | 缺失 |
| 原文数据源浏览 | `api_sources` + 数据源页 | 缺少原有专门浏览页 |
| 脑图 | `api_mindmap/api_roots` + 卡片树 | 缺失 |
| 实体治理 | 添加/改类型/删除、别名维护 | 仅创建/修订，不完整 |
| 消歧候选 | `api_resolve`：别名、同名、向量候选 | 缺失 |
| 人工融合 | `api_merge_entities`：边迁移、别名合并、索引重建 | 缺失 |
| 增量自动融合 | `_upsert_meta_into_project/_fuzzy_resolve`，类型一致，相似度阈值 | 缺失；目前按文档/块生成独立实体 ID |
| 增量任务与进度日志 | `run_upsert_job`、jobs 接口 | 同步摄取，未保留任务进度面板 |
| 项目快照回滚 | `_snapshot_project/api_history/api_restore` | 记录级系统历史不能替代项目包回滚 |
| 多通道图问答 | 实体 + 原文双路检索、邻域扩展、流式答案/证据跳图 | 单候选集检索 + 非流式答案，缺图扩展 |
| 本体与 SPARQL | ontology_owl + 原本体页与编辑器 | 新增不可变版本、写入 SHACL；不是原来完全没有本体 |
| 评测 | gold/eval API 与界面 | 缺失 |
| 双时态、metadata 前置筛选 | 原代码未提供统一查询契约 | 新增服务已有，可作为增量模块接回 |

## Semantica 实际参与点

旧 16 并非只使用 15 或只使用 17：它复用 15 的部分构建/检索辅助实现，但 `_new_extractor()` 默认使用 17 的 `SemanticaLLMExtractor`；设置 `KG_EXTRACTOR=15` 或 17 初始化失败时回退 15。17 调用 Semantica 的 NER/关系抽取，另有标题分块、偏移修复及本地 embedding 适配。

旧消歧和融合接口主要是项目自实现的别名/向量/NetworkX 逻辑，不能声称它们已经调用 Semantica 原生融合引擎。新版适配只实际调用了 Semantica LLM 抽取方法及 ContextGraph.state_at，没有接入其 deduplication 或 conflicts 能力。显示安装版本也不是这些能力实际启用的证据。

## prompt 错误

`knowledge_service/web/app.js` 创建项目直接调用 `prompt('项目名称')`，当前内嵌浏览器不支持该原生对话框。应改成页面内表单或 dialog，覆盖取消、空名称、提交失败和成功创建；不能依靠换浏览器掩盖问题。此次核查只确认根因，尚未修改页面实现。

## 推荐的增量修正方向（待确认）

**用户已选择另一方案：以新版为基础，逐项重建旧能力。** 以下推荐仅保留为决策历史；当前执行以 `docs/superpowers/plans/2026-09-09-rebuild-feature-parity.md` 为准，不退回旧后台。旧项目仍需非破坏性导入与名字保留。

1. 以旧后台完整交互与 API 能力为验收基线；保留项目名、数据、旧加载方式，不删除旧实现。
2. 修正启动环境与 prompt 兼容问题；先验证四个旧项目加载及真实图谱渲染。
3. 从 16 的现有逻辑逐步抽取项目、抽取、检索、治理、任务等服务模块，保持原页面契约；不是给新页面仅加旧后台链接冒充恢复。
4. 时间和 metadata 接入原有实体/段落/图扩展/问答全链路；旧记录缺失的业务时间保留未知，不伪造上传或生效时间。新存储适配需要显式映射、备份、数量和来源核对。
5. 保留并增强别名、候选消歧、人工融合和增量融合，再适配 Semantica DuplicateDetector/EntityMerger/冲突处理；合并须保留多来源、关系、有效区间、审计与可恢复性，不能无条件取第一条覆盖。
6. 验收覆盖旧能力清单与新增时间/筛选；单独通过新服务单元测试不能证明原项目功能无回退。

另一方案是继续以新增服务重建全部旧页面和行为，但迁移面更大、恢复旧能力更慢，不推荐作为当前修正路线。
