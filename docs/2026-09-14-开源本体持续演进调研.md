# 开源本体持续演进与抽取控制调研

调研日期：2026-09-14

## 结论先行

当前项目**需要调整，但不需要立刻重构成一套复杂的“自动持续学习平台”**。

“多次开放发现 → 汇总全部候选 → 本体趋稳后发布一次 → 用已发布本体做受控提取”是一条合理的本体冷启动路线。真正会造成异常的不是多次开放，而是把每次开放结果都当成正式本体、正式实体和正式关系发布。

开源生态的共同规律是：

1. 抽取器负责产出候选，最多通过类型清单、Prompt、阈值控制召回范围；
2. 本体发布依赖稳定术语标识、版本差异、校验和人工治理；
3. 实体去重是独立的数据质量流程，不能用“本体版本相同”代替实体身份判断；
4. 增量摄取不等于本体自动演进；新增文档可以自动处理，新增概念通常仍要审核；
5. 没有发现某个主流开源方案能够安全地、端到端自动完成“开放发现候选累积 → 同义本体融合 → 本体发布 → 跨版本实体融合”。这部分仍需应用层编排。

因此，当前项目的最佳策略不是照搬某个框架，而是保留现有 Semantica 适配器、OWL/SHACL、审核和图谱能力，补齐候选生命周期、本体差异发布和稳定身份三条边界。

## “Open Foundry”名称歧义

用户所说的 “Open Foundry”至少可能指两个不同对象：

- [syzygyhack/open-foundry](https://github.com/syzygyhack/open-foundry)：一个面向 operational digital twin 的开源本体运行平台，使用 ODL（扩展的 GraphQL SDL）、版本化 schema registry、对象/链接生命周期和同步引擎。它是 schema-first 系统，不是从非结构化文档中自动学习本体的工具。
- [OBO Foundry](https://obofoundry.org/)：生物医学本体社区及其治理原则集合，不是一套“Open Foundry”应用。它对永久标识、版本发布、术语稳定、弃用和协作维护的规范非常适合借鉴。

下文分别分析两者。

## 1. Semantica：能力齐全但模块彼此独立，流程需要项目自己编排

当前项目环境安装的是 Semantica 0.6.7；官方仓库为 [semantica-agi/semantica](https://github.com/semantica-agi/semantica)。

### 抽取如何控制

Semantica 的 `NERExtractor` 接受 `entity_types`、`min_confidence`、抽取方法与 `fallback / union / consensus` 合并策略。值得注意的是，官方源码对 `entity_types` 的表述是让抽取方法“try to limit/focus”，它不是数据库级硬约束；最终是否严格拒绝未知类型仍由调用方决定。[NERExtractor 官方源码](https://github.com/semantica-agi/semantica/blob/main/semantica/semantic_extract/ner_extractor.py#L82-L160)

`RelationExtractor`同样接受 `relation_types`、置信度阈值和抽取方法；官方实现会把类型清单传给方法做相似度匹配并重算置信度，但这仍不是 OWL/SHACL 意义上的强制 domain/range 校验。[RelationExtractor 官方源码](https://github.com/semantica-agi/semantica/blob/main/semantica/semantic_extract/relation_extractor.py#L73-L123) [关系抽取处理逻辑](https://github.com/semantica-agi/semantica/blob/main/semantica/semantic_extract/relation_extractor.py#L345-L425)

这意味着当前项目在 `semantica_adapter.py` 中做的两层控制是必要的：

- 开放模式使用自定义 Prompt 产生领域类型和关系候选；
- 受控模式把本体类/关系传给模型，并在返回后再次解析 IRI、拒绝未知类型、检查关系 domain/range、把异常送入审核。

这些严格行为主要是**本项目的适配器策略**，不能简单归因于 Semantica 原生抽取器。

### 本体生成和版本

Semantica 可以从实体及关系集合推导类、对象属性、数据属性和层次，也可以用 `LLMOntologyGenerator` 从文本冷启动本体；官方建议有图以后优先使用确定性的 `OntologyGenerator.generate_from_graph()`，避免每次都依赖 LLM 重生成。[本体管理指南](https://github.com/semantica-agi/semantica/blob/main/docs/guides/ontology.md) [本体 API 参考](https://github.com/semantica-agi/semantica/blob/main/docs/reference/ontology.md)

Semantica 也提供本体版本、diff、快照和回滚。其版本管理源码明确采用“本体 IRI 带版本、元素 IRI 不带版本”的设计，使类和属性标识跨版本稳定；但快照何时建立、如何审核变化、如何迁移实例仍由调用方编排。[OntologyVersionManager 官方源码](https://github.com/semantica-agi/semantica/blob/main/semantica/change_management/ontology_version_manager.py#L1-L64) [变更管理参考](https://github.com/semantica-agi/semantica/blob/main/docs/reference/change_management.md)

### 去重和增量

Semantica 把实体解析作为独立模块，支持字符串、属性、关系、向量等信号，能够增量比较新实体与已有实体，并在合并时保存来源和重定向关系。官方同时明确提示：低阈值会误合并；可靠主键优先于模糊相似；大规模全对比较存在 O(n²) 成本；合并结果需要抽样验证。[去重指南](https://github.com/semantica-agi/semantica/blob/main/docs/guides/deduplication.md) [DuplicateDetector 官方源码](https://github.com/semantica-agi/semantica/blob/main/semantica/deduplication/duplicate_detector.py)

Semantica 的批量抽取会保留 `document_id` 与批次来源，但官方 API 展示的是每批结果、图构建、去重、本体生成和版本管理等独立步骤，并未提供一个自动维护“本体候选出现池及审核状态”的端到端产品流程。[Semantic Extract 使用指南](https://github.com/semantica-agi/semantica/blob/main/semantica/semantic_extract/semantic_extract_usage.md) [模块总览](https://github.com/semantica-agi/semantica/blob/main/docs/modules.md)

### 对当前项目的含义

Semantica 已经提供可复用的底层能力，但不能通过简单打开某个参数就获得持续本体学习。当前项目应继续负责：候选生命周期、与当前本体对齐、发布审批、实例迁移和正式图谱投影。

## 2. syzygyhack/Open Foundry：先定 schema，再治理版本和数据同步

Open Foundry 的定位是“用一个 schema 定义对象类型、链接、动作和权限，然后编译为受治理运行系统”。领域模型通过 Domain Packs 中的 ODL 文件显式提供；官方仓库把成熟度标为 pre-1.0，适合评估、原型和受控试点。[Open Foundry README](https://github.com/syzygyhack/open-foundry)

其 schema registry 的关键机制是：

- 每次保存完整、不可变的 schema 快照；
- 使用单调递增版本号；
- 自动计算与上一版本的 diff；
- 将变化分类；
- breaking change 必须附带且通过审核的 migration plan；
- PostgreSQL 实现用事务与 advisory lock 串行化多实例并发发布。[Schema Registry 接口](https://github.com/syzygyhack/open-foundry/blob/main/packages/odl/src/registry/types.ts) [内存注册表](https://github.com/syzygyhack/open-foundry/blob/main/packages/odl/src/registry/index.ts) [PostgreSQL 注册表](https://github.com/syzygyhack/open-foundry/blob/main/packages/storage-postgres/src/schema-registry/postgres-schema-registry.ts)

它通过 JDBC/Debezium CDC 将已有业务系统数据映射到已经定义的对象和链接类型，并提供历史、软删除、冲突处理和 lineage。它没有把非结构化文档开放抽取、本体候选聚类或 LLM 自动合并术语作为核心流程。[Domain Pack/schema loader](https://github.com/syzygyhack/open-foundry/blob/main/packages/api/src/schema-loader.ts)

可借鉴的是其**发布闸门**，不是它的抽取方式：完整快照可以保留，但发布前必须对比当前版本；破坏性变化必须有明确迁移方案。

## 3. Microsoft GraphRAG：抽取可配置、增量索引可用，但不是本体治理系统

GraphRAG 的标准索引流程以 TextUnit 为粒度提取实体与关系。`extract_graph.entity_types` 控制要识别的实体类型，`max_gleanings` 控制补提轮次，Prompt 文件可以替换；关系输出主要是端点和自然语言描述，并非严格受控的 OWL 对象属性体系。[配置参考](https://microsoft.github.io/graphrag/config/yaml/) [索引数据流](https://microsoft.github.io/graphrag/index/default_dataflow/)

标准数据流把同 `title + type` 的实体聚合，把同 `source + target` 的关系描述聚合，再用 LLM 摘要多条描述。当前增量实现中，旧实体和增量实体首先按 `title` 对齐并复用旧 ID；这适合检索索引，但不能可靠处理别名、同名异人或类型演进。[增量实体合并源码](https://github.com/microsoft/graphrag/blob/main/packages/graphrag/graphrag/index/update/entities.py) [输出数据模型](https://microsoft.github.io/graphrag/index/outputs/)

GraphRAG 已提供 `update` 命令来更新已有索引，但其目标是避免全量重做并更新社区、摘要和嵌入，不是维护候选本体、术语审批或实例迁移。[CLI update](https://microsoft.github.io/graphrag/cli/)

可借鉴的是：分块抽取、来源绑定、同实体描述聚合、缓存和增量重算。不可直接照搬的是：只按名称合并实体，以及把开放关系描述当作正式本体关系。

## 4. OBO Foundry + WebProtégé：成熟本体治理，不负责文档自动抽取

OBO Foundry 强调稳定术语身份和可追溯发布：每个本体有永久 IRI；正式发布版本有唯一、可永久解析的版本 IRI；术语标识使用稳定 PURL/CURIE。[OBO 标识原则](https://obofoundry.org/principles/fp-003-uris.html) [OBO 版本原则](https://obofoundry.org/principles/fp-004-versioning.html) [OBO 标识政策](https://obofoundry.org/id-policy.html)

术语含义不能在保留同一 IRI 的情况下实质改变；如果 referent 改变，应创建新术语并弃用旧术语，同时提供 `replaced_by` 或 `consider` 指引。这直接支持“本体升级但实例不因版本号自动换身份”的设计。[术语语义稳定原则](https://obofoundry.org/principles/fp-019-term-stability.html)

WebProtégé提供 OWL/OBO 协同编辑、权限、讨论、完整变更跟踪和版本历史，可以下载历史快照；它解决的是人工本体工程和审核，不解决文档抽取及实体消歧。[WebProtégé 官方仓库](https://github.com/protegeproject/webprotege) [WebProtégé 用户指南](https://protegewiki.stanford.edu/wiki/WebProtegeUsersGuide)

可借鉴的是：稳定术语 IRI、弃用而非复用标识、每次发布可回溯、变更由人审。无需为了这些原则直接部署 WebProtégé；当前项目可以先在自己的审核工作台实现同样的最小契约。

## 横向对比

| 方案 | 开放候选累积 | 本体/Schema 版本 | 实体融合 | 增量数据 | 人工审核 |
|---|---|---|---|---|---|
| Semantica | 能批量抽取并保留来源；没有集成候选状态机 | 有快照、diff、回滚和稳定元素 IRI，但需应用编排 | 独立 dedup 模块，支持多信号和增量比较 | 支持批处理/增量去重；不等于本体自动演进 | 库层未提供完整发布工作流 |
| Open Foundry | 不以 LLM 候选发现为目标 | 强：不可变快照、diff、SAFE/BREAKING、迁移闸门 | 依赖业务对象 ID、连接器映射和冲突策略 | 强：JDBC/CDC、历史和 lineage | 破坏性 schema 变化必须批准迁移计划 |
| GraphRAG | 每 TextUnit 提取，结果进入索引；不是本体候选池 | 无正式本体治理模型 | 主要按名称/title 聚合，适合 RAG，不够严格 | 有 update、缓存和下游重算 | 非核心能力 |
| OBO Foundry + WebProtégé | 不负责自动发现 | 强：永久标识、正式版本 IRI、术语弃用与历史 | 不负责实例实体解析 | 本体编辑和发布可持续演进 | 强：协同、讨论、权限、历史 |

## 当前项目的现状判断

当前服务已具备不少正确基础：

- 开放模式产生候选，受控模式使用已发布本体；
- OWL/SHACL 校验与关系 domain/range 审核；
- 候选保存在文档来源中；
- 有本体变更提案、版本冲突检查和高影响确认；
- 有实体融合、来源和图谱展示。

但“连续多次开放后再整体整合”目前仍存在四个边界风险：

1. `ontology_discovery._candidates()`每次读取所有文档的全部发现候选；创建草案也是全量消费，但候选没有独立、明确的 `pending / included / rejected / materialized` 生命周期。
2. 发现草案发布时会同时保存新本体并把候选直接写成正式实体/关系，因而“发布本体”和“按正式本体构图”没有解耦。
3. 本体记录当前主要使用新 UUID 标识版本，缺少明确 `parent_version_id`、版本差异和稳定术语身份契约。
4. 正式实体仍携带 `ontology_id`；若多次发布发现草案，跨版本融合和关系端点统一会变复杂。

对应代码：`knowledge_service/ontology_discovery.py`、`knowledge_service/ontology_changes.py`、`knowledge_service/repository.py`、`knowledge_service/reconciliation.py`。

## 推荐操作流程

### 本体冷启动期

1. 持续上传文档；每篇文档只需做一次开放发现。
2. 保留每个候选出现及来源，不要把同名候选出现直接覆盖。
3. “全量整合”应重新汇总已保存的候选，不必反复让 LLM 重抽全部旧文档。
4. 可以多次生成候选草案预览，但不要每次都发布到正式层。
5. 观察新类型增长率、未知概念率、同义/冲突数量和在留出文档上的覆盖率；达到业务可接受范围后发布 V1。
6. 用 V1 对全部历史文档做一次受控重提取，生成正式实体和关系并执行实体融合。

### 稳定期

1. 新文档默认执行“本体约束提取”。
2. 无法映射的类型、关系和属性进入增量候选池，不进入正式图谱。
3. 候选积累到一定规模后，基于当前版本生成 V1 → V2 差异提案。
4. 兼容新增可直接审核发布；删除、改义、拆分、合并必须附带实例迁移方案。

## 最小调整边界

不建议立即引入全新的 Canonical Entity/Mention/Assertion 大模型；先做以下小到中型调整即可支撑用户当前路线：

### 必须做

1. **候选出现独立化**：候选 ID 包含 `document_id + document_version_id + chunk_id + kind + local extraction key`；另设 `normalized_signature` 用于聚合，避免同一实体在多篇文档的证据被字典覆盖。
2. **候选状态**：至少增加 `pending / included_in_draft / rejected / materialized`，并记录 `draft_id`、处理时间和决策人。
3. **草案是快照而非发布**：允许从“全部有效候选”生成累计草案，但默认只把它作为预览；本体发布与实例物化拆成两个按钮或两个事务步骤。
4. **发布前 diff**：新草案必须与当前本体比较，显示新增、复用、改名、删除和约束变化；不得直接把一份全新生成结果视为无关联的新本体。
5. **稳定术语 IRI**：同一类/关系/属性跨版本复用同一 IRI；版本号属于 ontology IRI/版本记录，而不是术语身份。改义时创建新 IRI并弃用旧 IRI。
6. **发布后统一重提取**：V1 发布后使用它处理所有历史文档，再开启正式脑图；不要把冷启动候选直接当作最终图谱。

### 可以后置

- 全功能的规范实体/mention/assertion 分层；
- 自动语义聚类和本体术语推荐；
- 跨版本自动迁移所有历史实例；
- WebProtégé 集成；
- 大规模向量实体消歧平台。

### 已发布 V0 的处理

目前已经发布的版本可视为实验 V0。后续继续开放发现没有问题，但不要再次把全量发现草案直接发布并与 V0 图谱并存。候选稳定后应选择一种明确路径：

- 推荐：以 V0 为基线生成差异化 V1，复用未变术语 IRI，然后统一重提取历史文档；
- 更简单的试验期方案：保留 V0 快照供回溯，但把 V0 实例图标记为 trial/non-current，V1 构图后正式视图只读 V1。

## 最终建议

当前项目应调整，但调整目标要收敛为：

> 让多次开放发现可以安全累计，让本体只在明确审核后发布，让发布版本之间复用稳定术语身份，让正式图谱只由受控提取产生。

这比一次性建设完整持续学习架构小很多，也与 Semantica 的模块化能力、Open Foundry 的 schema 发布闸门、GraphRAG 的批量/增量处理方法，以及 OBO Foundry 的稳定术语治理原则一致。

如果完全不调整，也可以依靠操作纪律完成一次冷启动，但只要用户误操作第二次“发布发现草案”，就仍有本体版本、实体和关系割裂风险。因此至少应完成上述六项“必须做”中的前五项，再把“多次开放 → 一次发布”作为正式产品流程。
