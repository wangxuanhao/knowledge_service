# 本体利用深化规划（2026-09-20）

> 范围：基于现有架构的最小调整，不引入新平台、不大兴土木。
> 前置事实均来自源码实证（见 §1.3 证据行号），非推断。

## 0. 结论

你的本体"治理半边深、理解半边空"：写路径（受控抽取→校验→发布→物化）很完整，但
读路径（检索/问答）零使用，且本体层级因两步断层而丢失、呈现平铺。

本规划分 4 个可独立交付的阶段，P0 半小时、P1/P2 各半天量级，全部落在现有
`knowledge_service/services/` 与 `knowledge_service/web/` 内，不动存储结构、不动 API 契约。

## 1. 现状实证（源码定位）

### 1.1 写路径已深入（不重复建设）
- 受控抽取 guidance + 类型/关系约束检查：`integrations/semantica_adapter.py:355-487`
- 写入前时态校验 + SHACL：`services/service.py:106-122`、`services/ontology.py:201-252`
- 开放归纳→草稿→审核→发布→物化校验：`services/ontology_discovery.py:317/35/80`
- 受治理本体变更 + 影响评估：`services/ontology_changes.py:65-133`
- 实体融合按稳定类型 IRI：`services/reconciliation.py:7-102`

### 1.2 读路径空窗（检索/问答零本体）
- `services/retrieval.py`：`ontolog` 出现 **0 次**
- `services/answers.py`：`ontolog` 出现 **0 次**
- 唯一沾边：`services/explorer.py:175` 把类型标签塞进 `_lexical_aliases` 当检索别名（最浅层）
- 后果：问"快驴传媒合作过哪些主播"，系统不知道"签约 ⊑ 合作"、不知道"主播"是类、
  不会做类型下推，只拿原文去跑向量/关键词。

### 1.3 层级断层（平铺的两个根因，均实证）
1. **归纳结果丢字段**：`services/ontology_discovery.py:_induce:354-368` 只把
   `RDF.type/label/comment` 写进 turtle，Semantica 返回的 `subClassOf`/`parent` 字段
   **没落图** → 即使归纳出层级也被丢掉。
2. **归纳方法对中文无效**：Semantica `class_inferrer.py:324 _find_parent_class` 按
   `class_name.split()`（英文空格分词）+ 常见父类名（Entity/Thing/Resource）推断层级，
   中文类名（"主播""带货主播"）吃不到该逻辑。
3. 手动编辑已支持 class 的 parent（`services/ontology.py:set_term_constraints:316-332`
   有 RDFS.subClassOf + 循环检测），读取端 `Ontology.parents()` 子类闭包已实现
   （`ontology.py:145`），图谱探索也已用子类扩展（`services/explorer.py:146-159`）。

## 2. 原则：不引入开源本体平台（回应疑虑）

已有调研（`docs/2026-09-14-开源本体持续演进调研.md`）的结论与本规划一致：
WebProtégé、Open Foundry、GraphRAG 各自解决的是「人工本体治理 / schema 发布闸门 /
批量抽取索引」，**没有哪个能安全端到端自动完成"候选累积→本体发布→实例融合"**。
你的架构缺的不是"本体配置平台"，而是：①把归纳出的层级保住；②给中文一个有效的层级
来源（LLM 草稿）；③让本体参与读取。这三点都是现有代码内的增量，不需要换地基。

## 3. 分阶段改动方案

### P0 修复层级丢失（约 0.5h，纯止损）
**文件**：`knowledge_service/services/ontology_discovery.py`
**函数**：`_induce`（`:_induce:317`）内 classes 落图循环（354-368 行）
**改动**：循环里补
```python
parent = item.get('subClassOf') or item.get('parent')
if parent:
    parent_uri = class_lookup.get(str(parent).strip().casefold()) or _iri(base, parent)
    if parent_uri != uri and uri not in Ontology(graph).parents(parent_uri):
        graph.add((uri, RDFS.subClassOf, parent_uri))
```
**注意**：P0 单独上对中文产出的层级可能很少（Semantica 英文启发式），
它真正的价值是"不再丢弃已有结果 + 给 P1 铺路"。
**风险**：低。循环检测复用现有 `Ontology.parents`；只影响下次归纳/发布，不动存量。
**测试**：`tests/service/test_ontology_discovery.py` 补"归纳结果含 subClassOf 时 turtle 保留层级"。

### P1 LLM 层级归纳草稿（约 0.5 天，中文有效路径）
**目标**：给"本体平铺"一个中文可用的层级来源，且保持"草稿→人审→发布"现有治理纪律。
**文件**：`knowledge_service/services/ontology_discovery.py`（新增函数）、
`knowledge_service/web/`（审核界面加层级建议展示，后置）
**设计**：
1. 在生成发现草案（create draft）时，对候选类型清单（`_summary` 的 entity_types）调用
   一次 LLM（复用 `KG_LLM_*` 通道，JSON 输出），产出 `{"类A": ["父类X", ...], ...}` 的
   **subClassOf 建议**，存入草案的 `hierarchy_suggestions` 字段。
2. 审核界面（复用现有草案审核面板）把建议渲染为"可勾选/可修改"的层级树。
3. 发布时把审核确认后的 subClassOf 通过 P0 的落图逻辑写进 turtle。
4. LLM 只产出**建议**，不直接进正式本体——延续你现有"候选→人审→发布"纪律。
**风险**：中（LLM 可能建议错误父子关系，靠人审兜底）；草案结构新增一个可选字段，向后兼容。
**测试**：mock LLM 返回层级 JSON，断言草案字段 + 发布后 turtle 含 subClassOf。

### P2 读路径：本体感知查询扩展（约 0.5-1 天，核心价值）
**目标**：让本体参与检索/问答，不做大改，沿用现有 `scope` 传参模式
（先例：`explorer.py:175` 的 `_lexical_aliases`）。
**文件**：
- `knowledge_service/services/retrieval.py`：`search()`（176 行）解析新 scope 字段
- `knowledge_service/services/answers.py`：`question_context()`（8 行）构造扩展
- `knowledge_service/services/ontology.py`：新增 `query_expansion(ontology, labels, query)`
**设计**（保守版，分两小步）：
1. **术语命中 + 子类扩展**：把查询词与 `ontology.summary()` 的 term label/name 做匹配，
   命中术语时扩展出：术语 label、术语的所有子类 label（走现有 `Ontology.parents` 反推）。
   例：查询"主播" → 扩展词 {"主播", "带货主播", "娱乐主播", ...}。
2. **keyword 通道 OR 化**：扩展词与原文用 OR 组合进 FTS/BM25 查询（中文场景 keyword
   本来就是痛点，见 skill 的 bigram 记录，扩展词能缓解）。
3. **semantic 通道（后置小步）**：不做多向量融合（复杂、易回归），改为把扩展词拼进
   query 做一次"查询改写"再编码，或暂时只在 `question_context` 的上下文补充扩展命中的
   实体——保证语义通道行为不变。
4. 开关：默认关闭，`extraction_mode=ontology` 的项目请求里显式开启（`scope['_ontology_expansion']`）。
**风险**：中低。不改变存储、不改 API 契约、可开关回退；keyword 通道 OR 化需回归测试
防召回爆炸。
**测试**：`tests/service/test_retrieval.py` 补"开启扩展后 keyword 命中子类实体"。

### P3 最小公理 disjointWith（可选，约 0.5 天）
**目标**：用最小成本堵住 LLM 抽取最常见错误——"同一实体被标成两个不相交类实例"。
**文件**：`knowledge_service/services/ontology.py`（`validate`/`validate_timeline` 加一项检查）
**设计**：`Ontology` 支持读取 `owl:disjointWith` 三元组；`validate` 中检测
`entity.type` 与其 parents 闭包与另一不相交类的 parents 闭包相交 → 报错进审核。
**风险**：低；不新增存储字段（turtle 内表达），旧本体无此公理则检查空转。
**测试**：构造含 disjointWith 的 turtle，断言冲突实体被拒。

## 5. 明确不做（排除项）

- ❌ 引入 WebProtégé / Open Foundry / GraphRAG 全量（已有调研支持排除）
- ❌ 完整 OWL 推理机（HermiT/Pellet/owlrl）——P3 之前没有可推理的公理，上了也是空转
- ❌ 属性特征公理（functional/inverseOf/transitive/subPropertyOf）——依赖推理机与检索
  架构升级，属于下一轮
- ❌ 跨项目本体共享 / 外部词汇对齐（schema.org/SKOS）——涉及 IRI 命名与权限，单独议题
- ❌ 改动存储表结构、SQLite/Milvus/Neo4j 写入链路

## 6. 验收标准

- P0：归纳草案发布后，`GET .../ontology` 的 summary 里 classes 带非空 `parents`
- P1：审核界面可见层级建议且可勾选；发布后 turtle 含 subClassOf
- P2：构造含父子类的测试项目，keyword 检索父类词能命中只有子类类型的实体；开关关闭时
  行为与改动前逐字节一致（回归基线）
- P3：含 disjointWith 冲突的写入被拒并进入审核
- 全量 `pytest tests/service -q` 失败数 0（改动前先跑基线）
