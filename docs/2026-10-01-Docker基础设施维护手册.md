# Docker 基础设施维护手册（PostgreSQL / Milvus / etcd / minio / Attu）

> 范围：仓库根目录 `docker-compose.yml` 定义的全部基础设施容器。本文只描述**当前已验证可用**的操作，
> 验证脚本为 `scripts/verify-compose-stack.sh`。
> 最后验证时间：2026-10-01，测得 5 个容器冷启动 60s 内全部 healthy。

## 1. 服务清单

| 服务名 | 容器名 | 镜像 | 宿主端口 | 数据目录 | 职责 |
|---|---|---|---|---|---|
| `postgres` | `knowledge-postgres` | `postgres:18.6-bookworm` | `127.0.0.1:5432` | `volumes/postgres` | 权威关系库 |
| `etcd` | `milvus-etcd` | `quay.io/coreos/etcd:v3.5.25` | `127.0.0.1:2379` | `volumes/etcd` | Milvus 元数据（唯一写者） |
| `minio` | `milvus-minio` | `milvusdb/minio:RELEASE.2024-12-18T13-15-44Z` | `127.0.0.1:9000/9001` | `volumes/minio` | Milvus 对象存储 |
| `milvus` | `milvus-standalone` | `milvusdb/milvus:v3.0.2` | `127.0.0.1:19530/9091` | `volumes/milvus` | 向量检索 |
| `attu` | `attu` | `zilliz/attu:v3.0.0-beta.6` | `127.0.0.1:30001` | 无（无状态） | Milvus 可视化控制台 |
| `milvus-volume-init` | — | `milvusdb/milvus:v3.0.2` | 无 | 复用 `volumes/milvus` | 一次性修正卷属主后退出 |

所有端口只绑 `127.0.0.1`，不对局域网暴露。Attu 宿主端口是 **30001**（映射到容器内 3000，避开常被占用的 3000）。

## 2. 日常操作

```bash
# 启动全部（--wait 会等到 healthcheck 通过，失败即非零退出，适合放脚本里）
docker compose up -d --wait --wait-timeout 420

# 查看状态
docker compose ps

# 看日志
docker compose logs -f milvus          # 或 etcd / minio / postgres / attu

# 只重启某一个
docker compose restart milvus

# 停止并删除容器（数据保留在 ./volumes，volume-init 会在下次启动时补齐卷属主）
docker compose down
```

**禁止事项**

- 不要用 `docker compose down -v`：虽然数据在 bind 目录里、`-v` 删不到它，但会连带删除 minio 镜像声明的匿名卷，属于无意义副作用。
- 不要在 `etcd` 服务运行的同时启动任何「内嵌 etcd」的 Milvus 容器：两个进程会写同一份 etcd 数据目录。

## 3. 数据目录：一个目录即可整体迁移

所有持久化数据都在 `./volumes`（可用 `.env` 的 `DOCKER_VOLUME_DIRECTORY` 改成绝对路径）：

```
volumes/
├── postgres/   # PG18 集群（PGDATA = volumes/postgres/18/docker）
├── etcd/       # Milvus 元数据（member/ 下的 WAL 与快照）
├── minio/      # Milvus 对象存储（a-bucket/）
└── milvus/     # Milvus 本地数据 + .milvus-volume-owner-* 属主标记
```

**迁移到另一台机器**

```bash
# 1) 源机：停容器，保证落盘一致
docker compose down

# 2) 拷贝 ./volumes 与 .env 到目标机对应位置

# 3) 目标机（Linux 宿主）：PG 数据目录属主必须是 uid 999（Debian 镜像内 postgres 用户）
docker run --rm --user 0:0 -v "$PWD/volumes/postgres:/to" postgres:18.6-bookworm \
  sh -c 'chown -R 999:999 /to && chmod 700 /to/18/docker'

# 4) 目标机：启动
docker compose up -d --wait --wait-timeout 420
```

Milvus 的 `volumes/milvus` 属主由 `milvus-volume-init` 自动处理：标记文件 `.milvus-volume-owner-<uid>-<gid>` 把 uid/gid 编进文件名，换了机器用户后标记名不匹配，会自动重跑 `chown`，无需手工干预。

> 迁移前的旧 Docker 命名卷 `knowledge-postgres-data` 已不再被 compose 引用，其内容已复制到 `volumes/postgres`。
> 确认新目录工作正常、且不再需要回滚后，可手工 `docker volume rm knowledge-postgres-data` 释放约 47MB。

## 4. PostgreSQL 维护

**进入 psql**（本地 socket 免密）：

```bash
docker exec -it knowledge-postgres psql -U postgres -d knowledge
```

**备份 / 恢复**

```bash
# 逻辑备份（推荐，跨版本可用）
docker exec knowledge-postgres pg_dump -U postgres -Fc knowledge > backup-$(date +%F).dump
# 恢复
docker exec -i knowledge-postgres pg_restore -U postgres -d knowledge --clean < backup-2026-10-01.dump
```

**升级大版本**：`postgres:18` 的数据目录与 17 及以下不兼容。必须走 `pg_dump` + 新建卷导入，不要只改镜像 tag。

### 应用角色 `knowledge_app`

`POSTGRES_APP_USER` / `POSTGRES_APP_PASSWORD` **不是** postgres 官方镜像认识的变量（镜像只读 `POSTGRES_DB/USER/PASSWORD/INITDB_ARGS/INITDB_WALDIR/HOST_AUTH_METHOD`），
所以 compose 把 `.env` 注入容器并不等于角色被创建——必须由 initdb 脚本执行 SQL。脚本在 `docker/postgres/initdb/10-app-role.sh`，已挂载到 `/docker-entrypoint-initdb.d/`。

- **新装**：数据目录为空时镜像自动执行该脚本，无需干预。
- **已有集群**：initdb 不会再跑，手工执行一次同一脚本（幂等，重复执行只同步口令）：

```bash
docker exec knowledge-postgres bash /docker-entrypoint-initdb.d/10-app-role.sh
```

权限口径（依据 `docs/2026-09-30-PostgreSQL替换与本体知识服务优化规划.md` §154「应用角色无建库/DDL/superuser 权限」）：
可登录、`NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`、无 `public` schema 的 `CREATE`（试建表会被拒），只拿 `CONNECT` + `USAGE` + 已有表的增删改查与序列用法。
**DDL 由单独的迁移角色负责**，该角色尚未创建，属于规划中未完成部分。

> ⚠️ **noop 陷阱**：镜像默认 `pg_hba.conf` 对 `127.0.0.1` / `::1` 是 `trust`，只有来自其他地址的连接才命中 `all/all/scram-sha-256`。
> 因此「在宿主机用 psql 连 127.0.0.1 能登录」**不能**证明口令正确（任意口令都能进）；要验证口令必须从容器网络内连接。
> `scripts/verify-compose-stack.sh` 就是按这个口径做的：跨容器连接 + 错误口令必须被拒。

## 5. Attu 维护

- **无状态**：不挂任何数据卷，`docker rm -f attu` 或 `docker compose up -d --force-recreate attu` 都不影响 Milvus 数据，出问题直接重建即可。
- **升级**：改 `image` tag 后 `docker compose up -d attu`。
- **访问**：<http://127.0.0.1:30001>（Attu 自带登录页，直接访问根路径返回 401 属正常）。
- **连不上 Milvus 时**：Attu 的地址固定为 `milvus:19530`（走 compose 网络，不是宿主端口）；先确认 `docker compose ps` 中 `milvus-standalone` 是 `healthy`，再 `docker compose restart attu`。

## 6. Milvus / etcd / minio 维护

**启动依赖链**（由 compose 保证，不需要人工排序）：

```
milvus-volume-init（跑完退出）
        ↓
etcd healthy ─┐
              ├─→ milvus healthy ─→ attu
minio healthy ┘
```

与 Milvus 官方 `docker-compose.yml` 的差别，以及为什么：

| 项 | 官方 | 本仓库 | 原因 |
|---|---|---|---|
| milvus 依赖 etcd | `service_started` | `service_healthy` + `restart: true` | 官方只保证「容器已创建」不保证「已可服务」；用 healthy 消除启动竞争窗口。`restart: true` 只在**用 compose 命令**重启 etcd 时传播（`docker compose restart etcd`），用原生 `docker restart milvus-etcd` 不会传播——后者场景下 Milvus 会自行重连恢复（已实测） |
| etcd healthcheck 间隔 | 30s | 5s | milvus 依赖 healthy，30s 会让它最多白等 30s |
| minio 凭证 | 写死 `minioadmin` | 取 `.env` 的 `MINIO_ACCESS_KEY/SECRET_KEY` | 避免默认弱口令被扫；凭证同时注入 milvus（`MINIO_ACCESS_KEY_ID` / `MINIO_SECRET_ACCESS_KEY`），两处必须一致 |
| minio/etcd 端口 | 不发布 / 全接口 | 只绑 `127.0.0.1` | 减少暴露面 |
| 数据目录 | `${DOCKER_VOLUME_DIRECTORY:-.}/volumes/...` | `${DOCKER_VOLUME_DIRECTORY:-./volumes}/...` | 官方变量语义是「volumes 的父目录」，容易写成 `./volumes` 后变成 `volumes/volumes`；本仓库变量即数据根目录 |

**etcd 快照**（改 Milvus schema 前建议先打）：

```bash
docker exec milvus-etcd etcdctl --endpoints=http://127.0.0.1:2379 snapshot save /tmp/etcd-$(date +%F).db
docker cp milvus-etcd:/tmp/etcd-$(date +%F).db ./etcd-$(date +%F).db
```

**minio bucket**：Milvus 首次启动会自动创建 `a-bucket`。凭证一旦更换，Milvus 读不到旧 bucket，必须用原凭证启动。

## 7. 常见故障处置

| 现象 | 原因 | 处置 |
|---|---|---|
| milvus 反复重启，日志报 `/var/lib/milvus` 不可写 | bind 目录属主与容器内 `milvus` 用户不符 | 删掉 `volumes/milvus/.milvus-volume-owner-*` 后 `docker compose up -d milvus`，让 volume-init 重跑 |
| milvus 报 etcd 连接失败 | etcd 未就绪或未启动 | `docker compose ps` 确认 `milvus-etcd` healthy；`docker compose restart etcd milvus` |
| milvus 日志大量 `authentication is not enabled` 告警 | Milvus 会先探测 etcd 是否开启鉴权，属正常噪声 | 无需处理（验证脚本已把它排除在故障计数外） |
| attu 报无法连接 | milvus 未 healthy 或 attu 先启动了 | 等 milvus healthy 后 `docker compose restart attu` |
| 端口 5432/19530/30001 被占 | 宿主已有其他服务 | 改 `ports` 左侧端口；`netstat -ano \| grep LISTENING` 定位占用进程 |
| `docker compose config` 报变量未设置 | `.env` 缺 `POSTGRES_*` / `MINIO_*` | 按 `.env.example` 补齐 `.env` |

## 8. 验证

```bash
bash scripts/verify-compose-stack.sh
```

脚本会依次校验：渲染配置（端口绑定、无内嵌 etcd、数据目录位置、无命名卷）→ 五服务功能连通与
应用角色最小权限（存在性、无 DDL、SCRAM 存储、跨容器登录成功、错误口令被拒）→
`down + up` 冷启动两轮（etcd 真实连接故障必须为 0）→ etcd 单独重启（compose 命令触发 `restart: true` 传播 /
原生 `docker restart` 触发自愈）→ milvus 单独重启 → postgres 探针表与 milvus 集合在全程保持不变。
只做 `down`，不做 `down -v`。

脚本会在库里留下两类探针，属预期，不要误删：

- PostgreSQL：`knowledge` 库中的 `_compose_probe` 表（每次执行插入一行，用于证明数据未被重建）
- Milvus：`knowledge_records` 集合（1024 维、COSINE，与应用 `KG_MILVUS_DIM` / 检索集合名一致）
