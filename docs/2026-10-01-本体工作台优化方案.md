## 0. 一句话结论

**工作台的「治理外壳」已经成型，「本体论内核」还很薄。**

已落地：五阶段 UI（发现/设计/审核/校验/发布）、统一草案内核（`ontology_drafts` 1786 行）、层级与矩阵接口、
服务端风险地板、批量批准门槛、草案 CAS 与原子发布。抽查测试 `338 passed`（详见 §1.3）。

真正待补的是三件事，按「价值 / 成本」排序：

1. **读路径零本体**（最高价值，最低成本）。`services/retrieval.py` 与 `services/answers.py` 中 `ontolog` 命中 **0 次** ——
   本体论最直接的语义能力（子类蕴含）完全没有参与检索与问答。工作台再精致，本体也只是「被治理的文档」。
2. **TBox 公理只有 3 条**（subClassOf、domain/range、SHACL）。没有 disjointWith / functional / inverse / transitive，
   推不出新事实，也拦不住「同一实体落在两个不相交类」这类最常见的 LLM 抽取错误。
3. **Semantica 只用了 4 / 27 模块族，且运行时版本与契约标签漂移**。实测已装 `semantica 0.7.0`，
   `conflicts` / `ontology.quality_gate` / `reasoning` / `evals` / `provenance` 全部可导入，一个都没接；
   而 `api/ontology_discovery.py:49` 仍把生成器契约写成 `semantica-0.6.7+...`（详见 §1.1-⑥）。

**明确下调优先级：React + `@xyflow/react` + `elkjs` 画布迁移（规划 §6.4/T10）应排到最后。**
当前 467 行手写 JS 已能跑通五阶段与草案闭环，画布重写的收益是「手感」，而上面三条的收益是「本体到底有没有用」。

## 3. 本体论视角：让「本体」真的参与推理与检索

把工作台的能力按本体论的三层分开看，缺口就清楚了：

```text
TBox（术语层：类 / 关系 / 属性 / 公理）
  现状：subClassOf ✅、domain/range（OR 集合）✅、SHACL ✅、datatype ✅
  缺口：disjointWith ❌、functional/inverse/transitive ❌、等价类 ❌  → 所以"推理"无处可推

ABox（事实层：实体 / 关系 / 属性值，双时态）
  现状：受控写入 + 时态 + 证据 + 事实键 ✅
  缺口：类型语义未参与读（子类蕴含不生效）❌ → P0-1

治理层（草案 / 审核 / 发布 / 溯源）
  现状：草案内核 + 逐项审核 + 原子发布 + 版本 ✅
  缺口：服务端 review_plan ❌、质量门 ❌、冲突报告 ❌、PROV-O 链 ❌ → P1 / P2
```

**核心判断：先补 ABox→TBox 的读路径连接（P0-1），再补治理层算法（P1/P2），公理与推理放最后（P3）。**
理由：公理再多，如果读路径不看本体，对本体的投入都无法体现在回答质量上；反过来，
读路径接通后，用户能立刻感知「查父类词命中子类实体」，这才是本体的可见价值。

## 5. 搭建方案（按顺序，不要跳）

### P0 —— 让本体进入读路径（约 1 天，最高性价比）

#### P0-1 本体感知的查询扩展与类型下推

**目标**：查「合作方」能命中 `type=签约主播` 的实体（子类蕴含生效），且**默认关闭、关闭时逐字节等价**。

**改动点**：

| 文件 | 位置 | 内容 |
|---|---|---|
| `knowledge_service/services/ontology.py` | 新增 `query_expansion(query)` | 返回 `{'terms':[IRI], 'labels':[...], 'subclasses':[...], 'type_iris':[...]}`；术语匹配用 `summary()` 的 label/name/local-name **子串匹配**（中文无空格），并做长度阈值与最长匹配 |
| `knowledge_service/services/retrieval.py` | `search()` `:179` | 解析 `scope['_ontology_expansion']`（默认 False）；命中时：① keyword 通道把扩展词 OR 进 FTS/BM25；② 用 `type_iris`（命中类 + 其子类）做类型下推过滤 |
| `knowledge_service/services/answers.py` | `question_context()` `:12` | 打开开关时把扩展命中的实体补进候选集与上下文；**不改排序** |

**硬约束**：扩展词**不得改变「哪些记录可见」** —— 权限、时态、project 过滤仍由 `QueryScope` 唯一裁决；
这是防止「检索扩展变成越权入口」的关键。

- 验收：契约标签与 `importlib.metadata.version('semantica')` 一致；fixture 断言失败即说明上游结构变了。

### P1 —— 服务端审查计划与发布门禁（约 2 天，对齐规划 §6.6 / T09）

**关键动机**：前端 `ontology-workbench.js:424` 已经**复刻了一份风险规则**（`isBatchEligible`），
与服务端 `ontology_operations.py:163` 是两套实现 —— 迟早漂移，且漂移时前端会「显示可批准但服务端拒绝」。

**改动点**：

| 接口 | 返回 | 说明 |
|---|---|---|
| `GET .../ontology-drafts/{draft_id}/review-plan` | `{classification: safe/manual/blocked, reason_codes[], risk, operation_ids[], impact{}, policy_version, fingerprint}` | 服务端唯一裁决；前端**只渲染**，删除本地风险复刻 |
| `GET .../ontology-drafts/{draft_id}/publish-readiness` | `[{code, message, severity, operation_ids[], remediation}]` | 发布按钮旁**始终列出全部未满足条件**并可定位，不得只置灰 |
| `POST .../ontology-drafts/{draft_id}/decisions/batch-safe` | 一次事务复核 plan fingerprint → 写入全部安全项决定 | actor 取自认证上下文；任一项失效则整批拒绝，不产生部分决定 |

**验收**：`manual`/`blocked` 永不被批量批准；每个发布阻断原因可复现、可定位；
`tests/contracts/test_ontology_review_plan.py`（待建）覆盖「plan fingerprint 变化 → 整批拒绝」。

### P2 —— 用 Semantica 补治理算法（约 2–3 天）

1. **冲突报告**（`conflicts`）：新增离线任务，按 canonical entity × 属性调 `detect_property_conflicts` /
   `detect_value_conflicts`，结果写成**审核候选**（复用 `resolution_reviews` / `governance` 队列），绝不自动覆盖。
2. **本体质量门**（`ontology.quality_gate`）：草案 `submit` 时对覆盖图调 `ontology_quality_check(..., competency_questions=[...])`，
   报告存入草案只读字段，工作台「校验」阶段与 SHACL 报告并列展示。**只报告，不修改，不降低已有阻断项等级。**
3. **回归评测**（`evals`）：固定留出文档集，比较 prompt / 模型 / 本体版本，产出可复跑报告（替代「单次演示」判断）。
4. 三者共同要求：严格 DTO 白名单 + 组件版本/模板版本记录 + 日志脱敏（§8.2 适配器契约）。

### P3 —— 公理、推理分层、PROV-O、React（最后）

1. **最小公理集**：`owl:disjointWith` 先落 —— 在 `services/ontology.py:290 validate()` 加一项检查
   （实体类型的 `parents()` 闭包与不相交类的闭包相交 → 报错进审核）；旧本体无该公理则自然空转。
   之后再评估 `functional` / `inverseOf` / `transitive`。
2. **推理分层**：公理足够后再接 `semantica.reasoning`；推导事实必须 `derived=true` 标记、与显式事实分开存储/展示、

3. **PROV-O 只读导出**：`repository/provenance_*` → W3C PROV-O；用 `verify_checksum` 做完整性校验。
4. **React 画布**：只挂载工作台 island（`@xyflow/react` + `elkjs`），其余页面保持原生 JS。
   **排在最后**：当前五阶段已可跑通，收益集中在手感而非能力。

### 10.6 顺带修掉一个换库遗留的并发缺陷（本轮实测发现）

全量套件本轮出现一次偶发红：`test_operation_reservations_are_atomic_across_repository_connections[True]`
→ `UniqueViolation: record_operation_reservations_project_id_recorded_at_key`。

- **复现与定位（先证因果）**：单独跑该文件 16 passed ×2，单用例连跑 8 次全绿 → 不是恒定失败；
  读代码发现 `_reserve_record_operation()` 在**裸 `BEGIN`（READ COMMITTED）**下
  「先 `SELECT MAX(recorded_at)` 再 `INSERT`」，跨连接没有互斥 —— 两个连接会算出同一时间点。
- **根因**：SQLite 的 `BEGIN IMMEDIATE` 会拿库级写锁，把这段读-写变成了原子操作；
  切到 PostgreSQL 后这层隐含串行化消失，而 `Repository._lock` 只是**进程内**锁，
  对两个连接无效。于是 `(project_id, recorded_at)` 唯一约束把其中一个连接打成原始驱动异常。
- **修法**：在事务内先取**项目级事务咨询锁**
  `SELECT pg_advisory_xact_lock(hashtextextended(?, 0))`，把「读高水位 + 预留」串成临界区，
  锁随事务提交自动释放（`repository/core.py:_reserve_record_operation`）。
- **回归测试**：`test_concurrent_reservations_are_serialized_per_project`（确定性、非碰运气）——
  外部先持有项目锁，另一次预留必须阻塞；去掉修复后该用例**立即转红**（已做变异验证）。

### 10.8 阶段门禁真的生效了 + 画布失败可诊断（用户反馈的两个问题）

**问题一：流程步骤锁定没生效。** 旧判据只有一句
`hasDrafts===false && !draftId` —— 只要项目里**有任意一个草案**，五个阶段就全解锁，
用户可以跳过审核直接进"发布"。现在判据收敛到 `stageRules()`（唯一出处）：

| 阶段 | 可进入条件 | 锁定时给用户的话 |
| --- | --- | --- |
| 发现 | 永远可进（入口） | — |
| 设计 | 有草案（含"草案列表还没加载完"时不预判） | 还没有草案 → 到发现生成，或点状态条的「新建手工草案」 |
| 审核 / 校验 | 草案状态 ∈ {submitted, reviewed, published, closed} | 草案还是「编辑中」：先「提交审核」 |
| 发布 | 草案状态 ∈ {reviewed, published, closed} | 还有变更没有审核决定：先到审核逐条批准/拒绝 |

- 锁定的按钮：`disabled` + `data-locked="true"`（CSS 变灰 + 🔒）+ `title` 写明原因 + `aria-disabled`；
- **按钮与 `setStage()` 共用同一份判据**：程序化调用（含 URL、外部脚本）也绕不过去；
- 刷新时机收口在 `renderStatusbar()`（状态→视图的统一出口）与 `setStage()` 末尾，
  审核/校验/发布在草案状态变化（提交、逐条决定）后立刻解锁；
- 锁住不能是死路：没有草案时状态条给出唯一的「新建手工草案」出口（否则设计阶段所有写操作都会被门禁拒绝）。

**问题二：画布数据加载失败：Failed to fetch。** 实测确认这个英文串只会在
**请求根本没到达服务端**时出现（端口没监听/进程退出/被代理或扩展拦掉）；abort 抛的是
`AbortError`，HTTP 错误抛的是中文消息（已在浏览器里逐一实测对照）。所以：

- `request()` 现在把 fetch 的 `TypeError` 翻译成「无法连接服务端：请确认服务在运行、地址端口正确，
  本地请求没有被代理拦截（接口 …）」，并保留 `path`/`cause` 供上层使用；
- 新增 `requestRead()`：**读操作**允许一次退避重试（偶发抖动不该让画布永远空着）；
  **写操作一律不重试**（重试写入可能造成重复变更）；
- 画布失败时不再只在顶部闪一行提示，而是在画布原位渲染失败卡片：原因 + **具体接口** +
  可能原因（服务未运行/端口不对/被代理拦截）+「重试」按钮；
- 顺手消掉一个隐蔽 bug：画布读分页的变量名叫 `page`，把工作台根节点 `page` 遮蔽了（现改名 `result`）；
  并把 `el(tag, class, text)` 的第三参收口为"支持节点/数组"——之前传节点会渲染出
  `[object HTMLButtonElement]`（本工作台已经因此出过 3 次问题）。

**回归测试（每条都做过变异验证：去掉修复即转红）**：
`test_review_validate_publish_unlock_only_after_draft_reaches_the_state`（编辑中锁定 → 提交后
审核/校验解锁 → 决定做完后发布解锁）、`test_canvas_network_failure_explains_the_endpoint_and_offers_retry`
（失败文案含接口名、无英文原文、可重试恢复）、以及两个空草案用例改为断言"4 阶段锁定 + 有出口"。

**匹配规则**（中文没有空格，所以用子串匹配而不是分词）

* 类的表层形式取 `label_zh / label / label_en / local-name`，**长度阈值** `min_length=2`（单字"方""人"必然误命中）；
* **最长匹配**：命中形式互相包含时只留最长的（查"合作方有哪些"命中"合作方"，被它包含的"合作"不再单独成词）；
* 命中类 → 收集**闭包内全部子类** → `type_iris = 命中类 + 子类`；
* 只读**当前（最新）版本**本体，且**跳过被废弃的类**（`owl:deprecated`）—— 扩展不该把用户引向停用的术语。

**与方案的偏差（有意为之，改进了原设计）**：§5-P0-1 写的是"用 `type_iris` 做类型下推**过滤**"。
实测下来严格过滤只会**减少**召回（本体外的实体被剔掉），而验收要的是"查「合作方」能命中
`type=签约主播` 的实体"。所以实现为**类型召回通道**：命中类与其子类的实体即使文本里没有查询词
也被召回，按 id 给确定顺序后与关键词/语义通道一起走 RRF 融合。

**两条纪律**

1. **不改变"哪些记录可见"**：类型通道只在 `scope` 已经过滤出的候选集里挑，权限/时态/project
   过滤仍由 `QueryScope` 唯一裁决 —— 扩展不会变成越权入口；
2. **额外召回不算降级**：`active_mode` / `degraded` 只由关键词/语义后端决定，本体通道单独记在
   `backends.ontology` 与 `ontology_expansion` 里（否则纯 keyword 请求会被误报成混合模式）。

**性能**：开了扩展就不走 Milvus 排名快路径（类型通道是本地按已过滤候选算的，交给 Milvus 会
静默丢掉子类命中）；扩展默认关，所以默认路径零影响。索引按本体版本签名缓存，与
`ontology_labels` 同一套失效规则。

### 11.2 P0-2 生成器契约标签对齐（修标签漂移 + 兼容读路径）

**问题**：`GENERATOR_CONTRACT` 写死 `semantica-0.6.7+materialization-context-v2`，而实际运行的是
0.7.0；它同时还是 source fingerprint 的输入，于是"改标签"= 把所有在飞的 run 判成 stale。

**改法**

* 拆成两个概念：
  * `ADAPTER_CONTRACT = 'ontology-discovery/2'` —— **本项目适配层的语义版本**，只有本项目
    生成管线语义变化时才递增，是 fingerprint 的身份来源；
  * `generator_contract(runtime)` —— 对外曝光的标签，从运行时版本派生：
    `semantica-0.7.0+materialization-context-v2`（验收：等于 `importlib.metadata.version('semantica')`）；
* provenance 同时记三个字段：`generator_version`（标签）+ `adapter_contract` + `runtime_version`；
* `discovery_source_fingerprint(generator_contract=...)` 改为**必填**（原来那个写死的默认值正是漂移来源）；
* **兼容读路径**：收尾校验不再比对单一指纹，而是比对**等价指纹集合** = {当前契约 + 历史契约} ×
  {当前运行时 + 该 run 记录的运行时}。差异只在两个"版本标签"上，指纹真正的载荷（候选、基线
  哈希、生成选项、请求名）必须逐字节相等才可能匹配 —— 放宽的是标签，不是数据。
  没有这一步，任何一次升级都会让在飞的 run 永远收不了尾。

**用真实 0.7.0 重锁上游结构**（`tests/service/test_generator_contract.py`，真跑 `OntologyGenerator`）：

| 探到的上游事实 | 影响 |
| --- | --- |
| `classes[].parent` 与 `subClassOf` 同值同时给出（0.6.x 只有 `parent`） | 读取逻辑的 `parent` 优先 + `subClassOf` 别名两条路都必须留着 |
| 类名被规范化：`EntityType_5b0d…` → `Entitytype5b0d…`（下划线被吃、首字母小写） | **不能靠类名回推来源**，必须走 `metadata.inferred_from`（已锁死：中文标签仍原样落 Turtle） |
| 通用父类自环：`Entity` 的 `parent` 是 `Entity` 自己 | 读取逻辑里 `parent != child` 那行守卫是必需的，否则会往本体里写 `C rdfs:subClassOf C`（已锁死，去掉守卫即转红） |

### 11.4 P0-3 层级建议：让发现出来的本体不再"永远是平的"

**问题（实测确认）**：开放发现**从来没抽过父子层级** —— `SemanticaExtractor.discover()` 只出实体/
关系/属性；而 Semantica 自己的层级推断只看**类名**（通用父类名单 Entity/Thing/Resource + 英文词前缀），
我们的机器名是哈希串（`EntityType_5b0d46251aa1`），实测**一条父类都推不出来**。所以历史上每份发现
草案都是平的，"查父类命中子类"的层级语义无从谈起。

**做法**（`services/hierarchy_suggestion.py`，新文件）：

* 生成发现草案时，对**候选类清单**调一次 LLM（走既有 `KG_LLM_*` 通道，`temperature=0`，要求纯 JSON）
  产出 `{"子类": ["父类"]}`；提示词版本 `hierarchy-suggestion/1`；
* 输出是**不可信输入**，入库前收口：只认清单里的类名（大小写/空白归一）、去自环、去重复、
  每个子类最多 3 个父类、总边数上限 200、**丢掉会成环的边**（环会让本体自相矛盾 `A ⊑ B ⊑ A`）、
  结果按确定性顺序排序；
* 规范化后的边在 `_induce()` 里写进**同一张图**，于是走的是**既有**路径：
  `canonical_turtle_diff` → `add_parent` 操作 → 审查计划 → 发布门禁。**没有旁路、不自动改本体**；
* 台账存进 run 的 `hierarchy_suggestions`（`discovery_run_store` 做形状校验），
  但**刻意不进 `_expected_run_snapshot`** —— LLM 输出不是"已存输入"的确定函数，
  进了比对集会让"重跑同一个 run id"因模型抖动而报 snapshot 冲突；
* **降级**：LLM 没配/超时/返回垃圾 → 只记日志、按"本次无层级"继续，发现照常完成
  （层级是增强，不是正确性前提）。

**前端**：`renderHierarchySuggestions()` 在工作台「发现」结果区与「设计 → 层级」视图都渲染
"层级建议 · N 条父子关系" + 一句人话解释（父子关系是什么、开启"本体扩展"后有什么效果、
这些边要逐项审核后随版本发布）；没有建议时整块不出现。

**未做（下一步可选）**：把建议渲染成"可勾选/可勾掉"的层级树（现在会全部进草案，用户靠审核阶段
逐条批准/驳回 `add_parent`）；以及给建议加"证据片段"引用。

### 11.4b 本体扩展的入口与解释（回应"这个词不明确"）

「本体扩展」＝ **本体层级感知的检索扩展**，属于本方案 §5 的 P0-1，不是一个独立的东西。它做两件事：

1. 查询串里出现类名（或业务标签）时，**命中该类的全部子类**，子类实例即使正文没有查询词也被召回；
2. 关键词通道按类名/别名**多词 OR 扩召回**（同一条记录取最高分，不累加 —— 扩展只补召回，不改相关性直觉）。

它**只补召回、不放宽可见范围**：权限与时态仍由 `scope` 唯一裁决，关掉时检索路径与响应字段和改前
逐字节一致。现在它有：中文 `Field(description=...)`（OpenAPI 可见）、检索栏勾选项（默认关）+ 悬停说明、
结果栏"本体扩展：命中 X，带出 N 个子类"的结果说明、代码注释与本文档。
