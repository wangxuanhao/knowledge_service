# 本体治理操作手册（审核台 · 编辑台 · 档案）

> 入口：左侧菜单「建模与治理」下的三个并列入口
> - **本体审核台**：收件箱（机器抽的候选 / 业务方的申请 / 你自己的改动待确认）→ 逐条**收下 / 退回让对方改 / 不收** → 收完自动发布。整页只读。
> - **本体编辑台**：主动改本体结构（新增/改/停用术语、改父类与 domain/range），改完提交审核。（A2 起由「本体编辑台」改名，只变了名字与定位口径）
> - **本体档案**：已发布本体与版本的只读账本（目录 / 版本对比 / Turtle / SPARQL / 发布记录）
>
> 文件名保留历史名（`2026-10-01-本体工作台操作手册.md`），内容已覆盖三个页面。
> 为什么拆成三页：`docs/2026-10-01-本体治理模块拆分设计.md`；历史改造依据：`docs/2026-10-01-本体工作台优化方案.md`
> A2 收窄审核台的设计理由：`docs/2026-10-02-审核逻辑-知识输入到发布.md`；分期与依赖：`docs/2026-10-02-完整落地规划.md`

## 0. 三个页面各做什么、不做什么

一句话记法：**审核台管"收不收"，编辑台管"应该长什么样"，档案管"现在是什么、怎么变的"。**

| 页面 | 做什么 | 不做什么 |
|---|---|---|
| **本体审核台** | ①收件箱看三格（机器抽的候选 / 业务方的申请 / 你自己的改动待确认）；②对草案逐条**收下 / 退回让对方改 / 不收**（含一键收下）；③全部有决定后**自动发布**为不可变版本；④只读地看结构（画布 / 层级树 / 关系矩阵） | **整页只读**：不新增/改结构（去「本体编辑台」）；没有"发布"按钮（发布是"收下"的结果）；不展示历史版本、Diff、Turtle、SPARQL、已发布目录（去档案页） |
| **本体编辑台** | 新增实体类/关系类型/属性；改父类（多继承）、domain/range、数据类型、中英文标签与说明；停用/恢复；查影响面；存为草案；**提交审核**（冻结快照） | 不发布（发布是收下的结果）；不处理"别人提的申请"（那是审核台的收件箱）；不做历史版本浏览 |
| **本体档案** | 版本概览、本体类别目录、版本历史与结构对比、Turtle 只读查看、SPARQL 查询台、发布记录与逐条决定 | 整页只读。唯一写操作是「基于此版本新建草案」→ 交编辑台 |
| **项目与运行**（运行层，不属上面三个本体页面） | 一页四个分区，每个分区回答一个问题：①**项目设置**——我有哪些项目（新建 / 改名 / 删除 / 切换当前项目）；②**运行总览**——这个项目现在有多少知识、有哪些分布；③**后台任务**——解析任务跑到哪一步了、失败在哪；④**快照与评测**——存档 / 恢复 / 按标准答案打分 | 不改知识、不改本体结构（改结构去编辑台，收知识去审核台）；不在这里读原文（去「原文数据源」或「知识台账」）；评测只按标准答案打分，不改任何知识 |

**唯一路径不变**：`候选/申请 → 草案 → 逐条收下 → 不可变本体版本`。
编辑台不是第二个写入口——它产出的仍然是草案，同样要经收下才能发布。

**关键不变量**：

- 不直接改正式本体。所有编辑都落在**草案**里，只有走完审核 + 发布才成为真相源。
- 删除术语不是物理删除，而是**在当前版本停用**；历史版本和引用旧版本的知识继续保留。
- 不做知识迁移。改了 IRI 或类型后，已有知识不会自动重分类（要迁移得走「新增新术语 → 迁移 → 停用旧术语」）。

## 1. 审核台的两个视图：收件箱 + 逐项收下

A2 起审核台不再是"四站流水线"，只剩两个视图。**视图回答的是"我现在在看哪一类事"，不是"流水线走到第几站"。**

| 视图 | 看什么 | 什么时候能进 |
|---|---|---|
| ① **收件箱** | 三格并列，每格带服务端给的真实计数与一句话说明 | 永远可进（入口） |
| ② **逐项收下** | 一条一条决定：收下 / 退回让对方改 / 不收；全部有决定后自动发布 | 草案状态 = **待审核**（已提交）或已审核 |

收件箱三格（**按"谁提的"分**，不是按阶段分）：

| 格子 | 里面是什么 | 一句话 |
|---|---|---|
| 机器抽的候选 | 从文档里抽出来、还不是本体的新概念 | 先看候选与证据，满意就生成草案 |
| 业务方的申请 | 别人要求改本体 | **只有这一类才叫「审核」** |
| 你自己的改动待确认 | 你自己改动里，系统不肯替你自动确认的项（高风险 / 需要写理由） | 收下就是发布，收完自动生效 |

「发现 / 设计 / 校验 / 发布」这四个词去哪了（用户最容易问的一个）：

- **设计（改结构）→ 去「本体编辑台」**。同一件事以前有两个入口（审核台浮动条的「＋子类 / 改父类 / 补定义 / 停用」和编辑台的保存并生效），这是"环节冲突"：审核台现在恒定只读。
- **校验 → 不是阶段**：进入"逐项收下"时自动跑一遍（图完整性 / 新写入约束 / 历史影响），报告摆在变更详情里。
- **发布 → 不是阶段、也没有按钮**：**"收下"就是发布**。全部变更都有决定后服务端自动发布为不可变版本；只在收尾失败时，状态条才出现一个"收下并发布（重试）"。

顶部**状态条**永远告诉你三件事：「草案现在什么状态」「下一步点哪里」「为什么现在不能点」。
**门禁判据只来自服务端**（`GET /api/projects/{id}/ontology-drafts/stage-availability`）：前端只渲染它给的"能不能进 + 为什么 + 下一步"，程序化调用（URL / 外部脚本）也绕不过去。

> 常见误解：看不到「一键收下」，**先看状态条**——多数情况是草案还没提交（待审核），或还有变更没有决定。
>
> **查已发布版本、类别目录、历史对比**请去「本体档案」；**改本体结构**请去「本体编辑台」。

## 2. 改结构：去「本体编辑台」

审核台里的结构视图（画布 / 层级树 / 关系矩阵）**只读**：点节点＝看详情，用来判断"这条变更放进去之后长什么样"。

要动手改，去「本体编辑台」（左侧菜单同一组里的第二个入口）：
新增对象、改父类、补定义、停用/恢复、多继承、domain/range、标签与说明，都在那里，**保存即生效（落进草案）**，然后「提交审核」。

编辑台的操作细节见本手册 §5。

## 3. 逐项收下（审核台的主场）

### 3.1 界面分区

- **左栏**：收件箱模式下是三格；逐项收下模式下是**变更队列** —— 每条显示：风险（低/中/高）、动作（新增对象 / 添加父级 / …）、对象（例如「对象 价格类型」）、当前决定、**判定**（可一键收下 / 需逐条看 / 被阻断）、判定依据。
- **中栏上：变更详情** —— 第一行是 `第 N / M 条 · 中风险 · 来源 … · 判定 …`，标题写明对象，紧跟一句 **「收下后：……会发生什么」**（这是判断依据，JSON 只是原始数据，在下面，可以跳过）。
- **中栏下：结构视图** —— 画布 / 层级树 / 关系矩阵（只读，会高亮当前变更的目标节点）。
- **右栏：来源证据 + 审核决策**（三颗按钮：`A · 收下` / `E · 退回让对方改` / `R · 不收`）。

### 3.2 一键收下：覆盖什么、不覆盖什么

按钮：`一键收下 N 条`（没有可收下项时**仍然显示**，置灰并写明原因，不会"消失让你找不到"）。

- **覆盖**：低/中风险、无阻断、无警告、**不需要写理由**的变更。
- **不覆盖**：高风险、被阻断、需要写明理由的变更——这些必须逐条看。
- 请求体里**不带条目清单**：收哪些由服务端用同一份审查计划（`ontology-review-plan/1`）算，前端不挑。
- 点完会如实汇报：`一键收下完成：收下 52 条；还剩 0 条需要你逐条看。`

> 数字口径全站只有一套：`可一键收下 N · 需逐条看 M · 被阻断 K`。你不会再看到"需人工 0（需人工 52）"这种自相矛盾。

### 3.3 逐条决策

- 按钮：`A · 收下` / `E · 退回让对方改` / `R · 不收`；快捷键 `A / E / R` 执行当前决策，`J / K` 切换变更。
- 三个动作对本体做了什么，说清楚（这是 A2-b 的全部要点）：

| 动作 | 对本体做了什么 |
|---|---|
| **收下**（approve） | 这条变更**进本体**。收完最后一条，草案自动发布为不可变版本 |
| **退回让对方改**（request_changes） | 打回编辑态：草案回到"编辑中"，提出人接着改（自己改的草案叫「退回继续编辑」） |
| **不收**（reject） | 关门：这条变更**不进本体**，草案照常收尾 |

- 决定**立即自动保存**；需要写理由的（高风险、带警告、非收下动作）会弹表单，必须填理由并勾掉相关警告。
- 全部变更都有决定后，草案变成 **已审核**，并**自动发布**（同步索引/向量失败也不会回滚已发布版本——只在状态条上提示重试）。
- 审核人要先改回来：对任意一条选「退回让对方改」，草案回到**编辑中**。

### 3.4 来源证据怎么读

右栏「来源证据 N」是**发现阶段冻结的原文**，不是模型复述。每张卡片给：哪份文档、命中位置（字符区间）、置信度、片段 ID、**原句**。

顶部那行数字是**如实拆分**的：

> 共 56 条：能在原文里找到句子的 55 条，只留下文档与位置、没有原句的 1 条，原文无法还原的 0 条。

- `已还原原文` = 有原句可核验；`已还原·无原句` = 只有文档与位置（常见于表格/字段名/纯符号）；`仅引用` = 连文档都还原不了，会保留原始引用串。
- 一条变更可能引用同一份文档的多处命中，默认只展开前 12 条，其余折成「展开其余 N 条来源」。

## 4. 校验与发布（发布是"收下"的结果）

- **校验**：进入"逐项收下"时自动跑：图结构完整性 / 新写入约束 / 历史数据影响。报告里有阻断问题，那一条就**收不下**（只能「退回让对方改」或「不收」）。
- **发布**：没有独立的发布表单，也不填发布人——**收下最后一条变更时服务端自动发布**。
  - 冻结 provenance 链：`来源快照 → 统一草案 → 原子变更 → 审核决定 → 不可变版本`。
  - 发布**不可回滚**（同步任务失败也不会回滚已发布版本）；要再改，基于它新建草案。
  - 发布后状态条会写清结果：`已发布为不可变版本 vX：这批收下已经写进本体，检索、问答与交互图谱立刻读得到。`

## 5. 本体编辑台（主动设计本体）

> 入口：`建模与治理 → 本体编辑台`。这里画的是"本体**应该**长什么样"。

### 5.1 一次完整的设计流程

1. **选基线版本**：顶部「基线版本（新草案基于它）」。默认是最新版本。
2. **新建草案开始设计**：草案是这个页面的工作对象。
3. **编辑**：三个视图任选（表格 / 层级树 / 画布）+ 右侧检查器。
4. **提交审核**：冻结草案交审核台逐条批准。
5. 单人项目还有 **提交并自审**（见 5.4）。

### 5.2 三个编辑视图

| 视图 | 适合做什么 | 怎么用 |
|---|---|---|
| **表格** | 逐条整理、批量核对 | 每行有「编辑」；改哪条点哪条，字段在右侧检查器 |
| **层级树** | 看父子结构、重排继承 | **把一个类拖到另一个类上＝加父类**（追加，允许多继承）；按住 `Alt` 拖＝替换全部父类；拖到"变成根类"区域＝去掉所有父类 |
| **画布** | 看整体连接 | 节点＝实体类，实线＝继承（子→父），虚线＝关系（起点→终点）；滚轮缩放、拖拽平移；点节点或连线切到它 |

> 新建关系请在**检查器**里填起点 domain / 终点 range，比在画布上拉线更不容易连错。

### 5.3 检查器能改什么

- **标签与说明**：中文名、英文名、说明（`rdfs:comment`）。改中文名会**先删旧值再写新值**（否则会留下两条标注）；把输入框清空再保存＝删掉这条标注。
- **结构**：类的上级类（可加减，多继承）；关系的起点/终点；属性的所属实体与**数据类型**（文本/整数/小数/是-否/日期/日期时间/链接）。
- **停用 / 恢复**：停用只影响新版本，历史知识与历史版本保留；停用前可以点**查影响面**看有多少知识用到它。
- **新增术语**：填中文名（必填）、英文名、说明、父类/domain/range/数据类型。IRI 由服务端按名称生成并固定，**不用手写**，也不在前端拼。

### 5.4 提交审核 vs 提交并自审

| 按钮 | 做什么 | 边界 |
|---|---|---|
| **提交审核** | 校验 → 冻结草案 → 交审核台逐条收下/不收 | 适合有人复核的项目；提交后编辑台不能再改 |
| **提交并自审** | 校验 → 提交 → 自动批准"服务端判定可自动批准"的变更 → 若全部有决定则直接发布 | **跳过他人复核**，会在版本里留下操作人（`designer@design`）与时间；高风险/被阻断/需要写理由的变更**不会被自动批准**，此时会停下并把你送到审核台 |

> 「提交并自审」不会替你做判断：它只做服务端允许的那部分，剩下的仍然要逐条看。

### 5.5 已提交/已发布的草案

编辑台只编辑**编辑中**的草案。已提交的要改，去审核台让审核人「退回让对方改」，把它退回编辑态；已发布/已关闭的只能**基于当前版本新建草案**。

## 6. 本体档案（已发布本体的只读账本）

> 入口：`建模与治理 → 本体档案`。整页只读。

| 区块 | 看什么 |
|---|---|
| ① 版本概览 | 版本号与 id、发布时间、发布人、规模（类/关系/属性/三元组）、写入路径（`governed_publish`＝走的是受治理发布） |
| ② 本体类别目录 | 实体类 / 关系类型 / 实体属性三张表：中文名、标识 IRI、上级类或 domain/range、数据类型、状态。可以搜名称或 IRI；点一行看详情（上级/下级、被哪些关系或属性引用、原始说明） |
| ③ 版本历史与变更 | 版本账本（谁、何时、来自哪个草案、规模）+ **结构对比**（与上一版比：新增/移除/改动） |
| ④ 发布记录 | 这个版本的来源：发布人、来源草案、基线版本、**校验指纹**；可展开该草案当时的**逐条决定**（收下/不收/理由/操作人/时间） |
| 底部 维护入口 | 旧的「本体源码与版本」+「本体与知识查询」（Turtle 查看、SPARQL 查询、结构化新增术语）。**这里保存的也是草案**，不是正式本体 |

- 「基于此版本新建草案」＝唯一写操作：新建草案后自动跳到**本体编辑台**编辑它。
- **结构对比的口径**：按标识 IRI 比"类别增删 + 父类变化 + domain/range 变化 + 停用/恢复"。改说明文字、换前缀、调整顺序**不算**改动。
- 校验指纹：发布那一刻校验快照的摘要；内容或校验条件变了指纹就不同，用它确认"发布的确实是校验过的那份"。

## 7. 常见问题

| 现象 | 原因 / 怎么办 |
|---|---|
| 一键收下是灰的 | 当前没有"可一键收下"的变更：剩下的都是高风险/被阻断/需要写理由。按提示逐条处理。 |
| 「提交审核」按钮找不到了 | 审核台不再有提交按钮（A2-c）：继续改与提交都在「本体编辑台」；状态条上的「下一步」会把你送过去。 |
| 收完最后一条变更却没发布 | 草案里还有没决定的变更（或被阻断的那几条）。看状态条那句"还剩 N 条没有决定"和校验报告。 |
| 画布上的节点数比左侧清单少 | 画布按层加载，节点上会写 `已展开 6 / 共 8 个子类`；点「多展开一层」。 |
| 虚线卡片是什么 | 只存在于当前草案、还没发布的类（正是这轮要审核的对象）。 |
| 改了样式/脚本没生效 | 静态资源带 `?v=` 版本号；改完必须一起 bump（`index.html`），否则浏览器用缓存。 |
| 新建草案报 409 `new draft must use the current ontology as its base` | 工作台会自己读项目当前本体；若仍出现，先刷新页面并确认项目已选。 |
| 服务端改了 Python 但界面没变 | **必须重启服务**（Python 模块在启动时加载）。 |

## 12. 向量维度（1024）为什么会出现"256 != 预期 1024"

用户问"维度的问题，看下改成1024啊"。结论：**应用侧本来就是 1024，报错来自两处，都已处理。**

### 12.1 事实核对（真机）

| 项 | 值 | 来源 |
|---|---|---|
| 生产编码器 | `sentence-transformers:data/model:normalized-v1`，`semantic=true` | `GET /api/health` |
| 该模型输出维度 | **1024**（xlm-roberta，`data/model/config.json` 的 `hidden_size`） | 读模型配置 |
| Milvus collection 实际维度 | **1024** | `describe_collection('knowledge_records')` |
| 真实重建结果 | `{"indexed": 56, "dim": 1024, "recreated": false, "elapsed": 4.13s}` | `POST /api/projects/{p}/indexes/rebuild` |
| 语义检索 | 9 条命中（此前是 0 命中） | `POST /search {retrieval_mode:'semantic'}` |

### 12.2 那 256 是从哪来的

测试用的 `demo` 哈希编码器（`HashingEncoder`）产出 **256** 维；把它的向量写进 1024 维的
collection，就会抛 `向量维度 256 != 预期 1024`。而测试本该在密闭环境跑（`tests/conftest.py`
设 `KG_SKIP_DOTENV=1`，pg_support 自己从 `.env` 取 PG 凭据）——如果跑 pytest 之前手写
`set -a; . ./.env`，`KG_VECTOR_BACKEND=milvus`+`KG_MILVUS_DIM=1024`+`KG_EMBEDDING_BACKEND=local`
就会渗进测试进程，于是十几个用例集体报维度错，看起来像"环境数据坏了"。

**正确命令**（不要 source `.env`）：

```bash
cd /d/workspace/knowledge_service
/d/Anaconda3/envs/model_agent/python.exe -m pytest -q      # 实测 1364 passed
```

### 12.3 代码侧的三处加固（防止这类错配再发生）

1. **维度只有一个出处**：编码器声明自己的维度（demo=256、本地模型读 `config.json` 的
   `hidden_size`=1024），`_resolve_milvus_dim()` 按 `KG_MILVUS_DIM` > 编码器 > 1024 兜底解析。
   以前 1024 是硬编码在建表处的，换编码器必然错配。
2. **错配在启动就喊，并说清怎么改**：显式配置与编码器矛盾时打印
   「…把 KG_MILVUS_DIM 改成 256 并重建索引；或换回对应维度的编码器」。
3. **重建接口能自愈**：`POST /indexes/rebuild` 检测到表维度 != 当前维度时，删表按当前维度重建
   （Milvus 里全是派生数据，随后全量重编码补回），返回里带 `recreated` 与 `dim`。
   维度是建表时固定的、事后改不了，所以"换了模型"只能删表——放在这个显式动作里做，
   不在检索路径上偷偷改表。

回归被锁在 `tests/service/test_vector_dimension.py`（11 个用例：维度声明、解析顺序、
错配告警文案、可执行的异常、重建接口的删表/不删表两条路径）。


## 13. 图谱怎么操作（平移 / 缩放 / 适应画布 / 点节点看详情）与颜色规则

用户问："知识图谱的画布不能平移，能不能用外部的一些现有的框架呀，现在节点底下类型颜色和实体类型颜色都不统一。"

### 13.1 平移：不用换框架，是拖动被节点吃掉了

**结论先说**：ECharts 的 `roam` 本身就是现成的平移+缩放能力（ECharts 就是"外部现成的框架"，图谱本来就跑在它上面），
所以这里**不引入第二个图谱库**。真正的问题是：`series.draggable:true` 会让**拖动先落到节点上**——
图谱被铺满时几乎每次按下都压在某个节点/标签上，节点又被力导向布局拉回原位，
于是屏幕几乎不动：实测拖 180px，画面只抖了 21px。用户看到的就是"不能平移"。

现在的行为（图谱是**只读画布**，节点不可拖动）：

| 你的动作 | 结果 |
| --- | --- |
| 按住空白处拖动 | **平移**画布（roam） |
| 滚轮 | 缩放（0.2×~4×），中心点保持在你指着的位置 |
| 双击空白处 | 等效点「适应画布」 |
| 点节点或连线 | 看详情（来源、版本、有效期） |
| 点「适应画布」 | 重新铺开 + 缩放复位（图被缩没了/挤成一团就点它） |

**没有「移动节点」按钮**：节点不可拖动，位置由力导向布局决定（节点位置不承载任何编辑语义）。
画布光标在手形（`grab`）与拖动中（`grabbing`）之间切换，工具栏下方常驻一行提示：
`拖动空白处平移 · 滚轮缩放 · 双击空白处适应画布 · 点节点或连线看详情`。

**没有做**：没有加入 Cytoscape.js / G6 等第二套图谱库。理由是现有 ECharts 已覆盖平移、缩放、力导向布局、
邻居聚焦，换库只换实现不增能力，却要多维护一份依赖和一套适配层。

### 13.2 颜色：类型颜色现在只有一个出处

同一个实体类型在**节点、图例、"按实体类型查看"那排圆点、跨页面**必须是同一个颜色。以前不统一有两个原因：

1. 颜色按"在数组里的下标"取（`palette[index % 9]`）：换个加载顺序就换颜色；而筛选条那排圆点用的是按钮下标，
   第 0 项还是「全部类型」，于是**每个类型的圆点正好错位一格**，和节点颜色差一位。
2. 有的地方传的是原始 `type`、有的地方传的是显示名 (label)，同一个类型算出来两种颜色。

现在统一到 `knowledge_service/web/graph-palette.js`：

- `GraphPalette.colorFor(类型名)`——按类型名做 FNV-1a 哈希取色，**同名必同色**，与顺序、页面、结果集无关；
- `GraphPalette.colorMap(视图内全部类型名)`——一张图里两个类型撞到同一色概率很高（16 色放 8 个类型），
  所以按类型名排序后依次取色、撞了就往后挪一格，保证**同屏不重色**且同一批类型在任何页面颜色一致；
- 保留色：`属性值` 固定 `#8c7b68`（它不是实体类型，不参与哈希），空类型中性灰。
- 取色 key 一律是"页面上显示的那个类型名"（label），页面各处不得再传原始 type。

验证（Playwright 真机，25 实体 / 8 类型）：节点色 = 图例色 = 圆点色，8 个类型 8 个颜色，零重复；
空白处拖动＝平移画布（roam）；节点不可拖动，布局由力导向决定。

## 14. 阶段门禁搬到服务端 + 四个架构性问题的答复（2026-10-02）

用户原话（一次问了四件事）：

> 刚刷新的时候 本体审核台 打不开审核 检验 发布 ，点击了设计就可以查看了，但是当前是没新的审核任务的，
> 你这个状态是维护在后端的吗，要后端控制状态吧，发现时候 是不是也不能看设计呢。
> 要区分本体审核台是在知识写入时候触发吧，还是怎么，本体审核台-发现的已生成治理草案
> 如果按照 审核流程的话是不是不应该出现

### 14.1 逐条答复

| 用户的问题 | 结论 |
|---|---|
| 状态是维护在后端的吗，要后端控制状态吧 | **状态本来就在后端**（`ontology_drafts.status` 存 PG，`submit/decisions/publish` 的顺序由服务端 `_status_guard` 拒绝，前端放开也绕不过）。但"哪个阶段现在能进"以前是**浏览器现算**的 —— 已按用户拍板搬到服务端：新增只读接口 `GET /api/projects/{p}/ontology-drafts/stage-availability`，返回每阶段 `allowed + reason` 与唯一的 `next_action`，前端只渲染 |
| 发现时候是不是也不能看设计 | 现在的规则：**没有任何草案时设计也进不去**；一旦有草案（任何状态）设计就可进 —— 五阶段不是流水线，而是"同一份草案的不同视图"（设计＝看/改结构、审核＝逐条决策、校验＝约束快照、发布＝确认版本）。已提交的草案在设计里是只读的，保留可进是为了审核时能看图判断影响面 |
| 本体审核台是在知识写入时触发吗 | **不是自动触发**。链路是：知识写入/开放解析 → 产出候选（候选区，不碰正式本体）→ 在「发现」里**显式点「生成草案」** → 才有草案进设计/审核/发布。入口三处：左侧导航「本体审核台」、「候选脑图」页的「进入本体工作台」、检索/脑图页顶部"还有 N 条候选待审核"提示条 |
| 发现里的「已生成治理草案」是不是不该出现 | 上一轮已按"留在发现、但自己说清身份"改过（见 §11 第 1 条）：它是"上次点发现跑出了什么"的任务报告，不是草案列表；眉题写着「发现任务的结果（这里只是报告，不是草案列表）」，并给「去本体审核台审核这个草案 →」按钮。删掉它就没法解释"发现跑完到底做了什么" |

### 14.2 刷新后"三个阶段点不开"的真因与修法

三个缺陷叠在一起（前两个已在前一轮修掉）：

1. 打开审核台**没人替你选草案**（`selectDraft` 只在走设计阶段的路径上被触发）→ 草案为空 → 审核/校验/发布全灰。
   修法：`ensureDraftSelected` + **唯一一条**选草案规则 `pickDraft()`＝编辑中 > 待审核 > 已审核 > 已发布 > 已关闭。
2. 状态条只刷门禁不重渲染 → 左边列着草案、状态条还写"还没有草案"。修法：`renderDraftList` 里重渲染状态条。
3. 灰掉的阶段只在 `title` 里说原因（disabled 按钮点了没有任何反应）。修法：阶段条下面一行可见文字
   （`[data-stage-lock]`，黄底），**只写第一条可执行的原因**。

### 14.3 服务端接口的形状（前端只渲染）

```
GET /api/projects/{p}/ontology-drafts/stage-availability[?draft_id=<id>]
{
  "draft_id": "528fc7ec-…", "draft_count": 3,
  "status": "editing", "status_label": "编辑中",
  "status_copy": "可以自由增删改；改完点「提交审核」冻结快照。",
  "stages": {
    "discover": {"allowed": true,  "reason": ""},
    "design":   {"allowed": true,  "reason": ""},
    "review":   {"allowed": false, "reason": "草案还是「编辑中」：先在设计里点「提交审核」冻结变更集合，再逐项审核。"},
    "validate": {"allowed": false, "reason": "（同上）"},
    "publish":  {"allowed": false, "reason": "（同上：没提交的草案到不了发布，所以指向同一步）"}
  },
  "next_action": {"kind": "submit", "label": "提交审核", "stage": "review",
                  "enabled": true, "title": "冻结当前快照并进入审核（修订 2）"}
}
```

- 判定规则与写操作守卫同源：发现永远可进；设计＝项目里有草案；审核/校验＝草案已提交；发布＝审核已完成。
- `reason` 是**给用户看的下一步**，不是日志：只写当前真正该做的那一步，不并列指向另一个同样锁着的阶段。
- 前端 `nextActionButtons()` 按 `next_action.kind` 挂本地处理器（新建草案 / 提交 / 去审核 / 去发布 / 重新基线 / 刷新来源），
  文案与可用性都由服务端给 —— 这样"下一步是什么"也只有一处口径。
- **服务端的判定只对它被算出来的那个状态有效**：前端按 `项目|草案|状态|修订|变更数` 做 key，
  key 不匹配就当作"还不知道"，**此时不锁按钮**（那是不知道，不是不允许；写操作仍由服务端把关）。
  否则新建草案后会拿旧判定把设计锁住，表现就是"点设计没反应"。
- 读不到接口时：页面写明"读不到治理状态（原因）—— 阶段按钮暂时不锁定，写操作仍由服务端把关"，
  并给「重试读一次」按钮；同一份状态不自动重试（每次渲染都重试＝刷屏）。

本轮四件事都来自同一次反馈：提示框要悬浮、治理状态读不到、设计台/审核台"样式不对"、检索与知识图谱看不到父类。

### 16.1 提示条 = 上层悬浮层（不是页面里的卡片）

**它是什么**：任何提示（切换项目、门禁没放行、操作成功/失败）都渲染到 `body>main>#status`，
这一层是 `position:fixed` 的**悬浮层**，贴右落在标题栏之下，不占文档流、不挤动阶段条与三栏。
**它不做什么**：不再往页面流里插卡片（那样会把阶段条和三栏整体往下推），也不吸附在底栏。

演进史（三次都被用户当面纠正过，别再往回走）：

| 版本 | 做法 | 结果 |
| --- | --- | --- |
| ① | `fixed` 居中 | 压住页头标题 →"位置不合适" |
| ② | 页面流内实体卡片 | →"提示框是在上层悬浮啊，不是改页面样式了" |
| ③ | **悬浮层**（当前） | 贴右、标题栏之下，自动收场，可手动关闭 |

真机读数（1680×950，`probe_final_metrics.py`）：

```

hostRect : [1468, 54, 192, 70]
cardRect : [1486, 66, 156, 46]
headerBottom: 52   overlapsHeader: False
```

卡片本体仍是共用 `.ks-notice`（实心白底 + 左色条 + 图标 + 关闭按钮 + 阴影 + 进场动画），
宿主 `.ontology-workbench__notice` 只留 `padding:0;border:0;background:transparent`，不再自己画一遍。

### 16.2 "读不到治理状态（未找到：stage-availability）"

阶段门禁的**唯一判据在服务端**（`services/ontology_drafts.stage_state()` → `GET …/ontology-drafts/stage-availability`），
前端只渲染。当这次读取失败时，界面按原因分三种说法，而不是丢一句"未找到"：

| 情况 | 界面说明 | 阶段按钮 |
| --- | --- | --- |
| 接口不存在（旧服务） | 明确说是版本/接口问题，写操作仍由服务端把关 | 不锁定，给「重试读一次」 |
| 网络中断 | 说明是连接问题，重试即可 | 同上 |
| 其它错误 | 原文附上，便于排查 | 同上 |

**读不到 ≠ 不许进**：读不到时按钮**不锁定**（写操作照样会在服务端被拦），
同一状态不自动重试（防止刷屏），只给一次显式重试出口。

### 16.3 设计台 + 审核台的视觉统一（按 frontend-design 技能重做）

**问题**：两个页面是两份独立长出来的样式 —— 设计台 125 行里色值全写死（`#203c35` / `#4c6357` …），
审核台用 `--ow-*`，同一个"面板/标题/按钮"在两页的字号、圆角、边框、阴影都不一样。

**做法**（只动视觉，不动结构与功能）：

1. **令牌层**：`style.css` 新增 `--ks-*`（颜色 / 圆角 / 间距 / 阴影 / 字体），两页只许引用令牌。
   颜色语义定死三个：**墨绿＝治理与主操作**，**琥珀＝需要人做决定**，**砖红＝阻断/危险**；
   绿色不再同时充当品牌色、成功色和信息强调色（那样颜色就没有含义了）。
2. **表面层级**：外壳白卡 + 一条发丝线 + 极浅投影；内嵌面板改用 `sunken` 底色分区，**不再框套框**。
3. **字阶**：页标题衬线 22px → 栏标题 19/16px → 正文 12.5px → IRI 与 ID 等宽 11px（标识符要能逐字核对），
   计数类数字用 `tabular-nums`（窄栏里不跳字）。
4. **同类控件一个样子**：设计台与审核台的视图页签统一成同一枚分段控件（灰底凹槽 + 选中白底）。

真机读数：`--ks-line:#dae4de  --ks-accent:#15624b  --ks-ink:#14312a`（两页同源）。
**踩过的坑**：不要写 `.ontology-workbench button:not(.secondary){…}` 这种泛化规则 ——
变更队列的行本身就是 `<button>`，泛化选择器优先级更高，会把整列行背景刷成绿色。

### 16.4 父类：检索与知识图谱都要看得见

层级长在**类**之间（`rdfs:subClassOf`），实体节点本身没有父类，所以由后端补出来：

- **数据源**：`service.ontology_family(project_id)`（按本体版本签名缓存）——
  同一份数据供给两处载荷，两个界面不许各算各的；
- **载荷**：实体节点/记录新增 `class_label` / `class_parents`（直接父类）/ `class_ancestors`（**从直接父类往上的有序链**，

- **顶层类**：返回空列表，界面写「顶层类（本体里没有父类）」，**不编造**父类、也不留空白；
- **非实体记录**（关系/属性）：不挂这些字段，前端不会误显示。

界面两处入口（真机读数）：


## 17. A2：审核台收窄成「收件箱 + 逐项收下」（2026-10-03）

**改了什么**：审核台的「四站阶段条（发现 / 设计 / 校验 / 发布）」整体撤掉，换成两个视图：

| | 改前 | 改后 |
|---|---|---|
| 导航 | 四张阶段卡片（流水线） | **收件箱三格**（机器抽的候选 / 业务方的申请 / 你自己的改动待确认） |
| 审核动作 | 批准 / 要求调整 / 拒绝 | **收下 / 退回让对方改 / 不收**（一键批准 → **一键收下**） |
| 设计 | 审核台里也能改结构（浮动条 ＋子类 / 改父类 / 补定义 / 停用） | 审核台**恒定只读**；改结构只去「本体编辑台」（原「本体设计台」改名） |
| 发布 | 第 5 站：填发布人 → 确认发布 | **没有发布阶段、没有发布按钮**：「收下」就是发布，收完自动发 |
| 校验 | 独立阶段卡片 | 进入「逐项收下」时自动跑一遍，报告摆在变更详情里 |

**为什么**（用户原话）：同一件事曾经有**两个入口**（审核台的浮动条 与 编辑台的「保存并生效」）—— 这是"环节冲突"。
所以审核台只回答"收不收"，改结构一律去编辑台。

### 17.1 怎么验的（真机，只读）

```bash
# 服务先起来（端口 8000，需绕过系统代理）
cd /d/workspace/knowledge_service
NO_PROXY=127.0.0.1,localhost /d/Anaconda3/envs/model_agent/python.exe \
  scripts/verify_workbench_inbox.py --url http://127.0.0.1:8000
```

脚本用真实 Edge 打开真实服务、挑一个草案分布最全的项目（实测 `PG 端到端验收`：12 editing / 1 submitted / 4 closed），
**断言 17 项**，全部 PASS：

- 收件箱三格齐全、计数来自服务端（不是占位「—」）；
- 旧东西真的不在页面上：四站阶段条 ×0 · 发布按钮 ×0 · 发布人输入框 ×0 · 画布上的「＋子类 / 改父类」×0 · 叙事词"四阶段/阶段条" ×0；
- 旧阶段名（design / validate / publish）不会凭空造出视图 → 一律落到 review；
- 编辑中的草案：只给「去本体编辑台」的指路（`[data-go-to-designer]`），点它**真的切到编辑台**；
- 已提交的草案：能逐项收下 + 写清"收完自动发布"，三条决策路（收下 / 退回让对方改 / 不收）都在检查器里；
- 页面无 JS 报错；**没有一个 ≥400 的接口调用**（这条最关键，见下）。

### 17.2 复验挖出的两个真问题（都已修）

**① 决策表单被"迟到的重渲染"覆盖 —— 理由输一半会丢。**
保存上一笔决定的响应回来时会走一次完整的 `renderReview()`，把刚打开的决策表单（正在输入的理由）整个替换掉。
真机表现为"点保存没反应/一直失败"。修法：`saveDecisions` 里**只清掉"这次保存的那条"的表单归属**
（`decisions.some(row => row.operation_id === state.decisionFormOperationId)`），不再无脑 `state.decisionFormOperationId = null`；
检查器重绘前用 `decisionFormOpenFor(operation)` 判断"审核人正开着这条的表单"。

**② 进入「逐项收下」时 `POST /validate` 被发两次，第二次 409 → 操作条变成「刷新并恢复」。**
校验是**写**（会 bump 修订号）。两次渲染并发发起同一个 `expected_revision` → 后到的一个 409，
前端按设计显示「刷新并恢复」，用户看到的是"这一页坏了"。
修法：`ensureValidation()` 加两条约束 —— ① 同一份「变更集合快照」（草案 id + 校验指纹）只校验一次；
② 并发调用共享同一个请求。**key 不能用 revision**：每次决定/校验都会 bump 修订号，用 revision 会退化成"每条决定都再校验一次"。
真机复验：进入视图后 `/validate` **只发 1 次**，无 409。

> 这两条都只有"真机 + 抓接口"才能发现：只跑 mock 单测时它们分别表现为"偶发超时"和"文案不对"。

### 17.3 顺带修掉的

- `ontology-workbench.css`：工具栏按钮原先写成"非设计阶段一律 `display:none` 再逐个放开"，
  而设计视图已被删 → **层级树的「回到根类总览 / 多展开一层」永久点不到**（真机上实测不可见）。现在控件按"有结构视图就显示"给。
- 画布图例：删掉按阶段分叉的旧文案（设计阶段那套编辑手势说明随视图一起消失），点节点＝看详情保留。
- 切回画布视图时会重读一次全图总览，避免"层级视图钻过的那个根"漏进画布视图。
- 服务端文案同步：`select_draft` / `design_reason` / `need_submit` / `publish_reason` / `_next_action` 全部改成
  「本体编辑台 + 收下/不收」口径（**改完必须重启服务**，否则接口返回的还是旧文案）。
- 档案页的决定文案与审核台统一（收下 / 不收 / 退回让对方改）；编辑台、档案、审核台三处的"设计台"字样一并改名。
- 静态契约按新设计重写（不是保旧设计）：三页入口标签、发布不再是阶段、`批准/要求调整/驳回` 一律退场
  （"拒绝"只允许留在注释里 —— 扫描时会跟踪 `/* */` 块注释，别把注释中间行当成用户文案）。

## 18. 知识台账（B1 · 2026-10-03）：实例层的"家"

前面三页管的是**结构**（本体该长什么样、收不收）。知识台账管的是**实例**：已经进来的具体知识长什么样、
要不要纠错、要不要合并重复。**一句话边界：这里管具体的东西，分类不在这。**

| 页面 | 管什么 | 不管什么 |
|---|---|---|
| **知识台账**（原「知识与历史」） | 查实例（三视角）、改一条记录、合并疑似重复、撤销误操作、看一条知识挂在哪一版本体上 | 不改类/属性/关系（去「本体编辑台」）；不审结构变更（去「本体审核台」）；不解析文档（去「来源与构建」） |

### 18.1 怎么用

| 你看到的 | 意思 | 怎么用 |
|---|---|---|
| 顶部四个数字 | `N 实体 · N 关系 · N 原文片段 · N 组疑似重复` | 点数字＝切视角（前三个）或摆出可合并的卡片（疑似重复）；数字来自服务端，读不到时显示 `—` 而不是 0 |
| 三视角页签 | 实体 / 关系 / 原文片段 | 每个视角一句话说明自己在看什么；页签右侧那行字就是当前视角的口径 |
| **挂在哪一版本体上** | `本体 v2 · 2026/2/1（当前）` 或 `（旧版）` | 看到「旧版」＝这条知识是用**老结构**标出来的。要迁移得走「新增新术语 → 迁移 → 停用旧术语」，台账不自动改 |
| **原文断言** | 有几条原文原句在支撑它（两条血缘去重） | 点数字格右侧的小字看口径；显示 0 表示没有找到支撑断言（人工写入或断言未归位） |
| 操作 · 编辑 | 打开记录弹窗（结构化编辑 + 高级 JSON） | 改内容＝产生**新版本**（版本 +1），旧版本仍可恢复；不改动原记录 |
| 操作 · 版本历史 | 同一个弹窗切到历史模式 | 按系统记录时间列历次版本；业务有效期 ≠ 录入时间 |
| 操作 · 撤销这次操作 | 把这条记录**连同那次操作影响到的其它记录**整批恢复到操作之前 | 版本 +1、历史仍可查；撤销前会问一次 |
| 可撤销的操作 | 合并 / 软删除这类"一次改一批"的动作 | 0 条时页面会说明"还没有做过"，不是加载失败 |
| 实体消歧与融合（折叠） | 三步：按名称查找 → 选择保留的实体 → 选择另一个重复实体 | 合并前给出**影响面**（会转移几条关系等），并写明按哪些已读记录统计；合并是不可逆的，撤销靠上面那条 |

**「疑似重复」的口径（刻意很窄）**：只有**名称完全相同（忽略大小写与首尾空白）且本体类型相同**的实体才会被算成一组。
近名重复（"张三" vs "张先生"）走「查重」按钮的语义档，不混进这个数字 —— 数字只放你自己能核对的东西。

## 19. C1：待建模收件箱 + 「结构待定」（2026-10-03）

### 19.1 它解决的是什么

文档里抽出来的概念，本体里可能还没有。以前只有两条错路：**硬塞进本体**（本体被业务噪声污染）
或**直接丢掉**（知识消失，而且没人知道丢过什么）。现在走第三条：**知识照常进来，但标出来** ——
这条知识的状态叫「结构待定」。

### 19.2 用户看到的

- **知识台账**：这类知识的行上有一枚「结构待定」徽标（鼠标悬停能看清**缺的是哪个概念**、
  以及"这条不算正式证据"）；顶上多一个数字「**N 个概念待定**」。数字分三态：
  `读取中` / `读不到`（接口失败，不编造 0）/ 真数字。点这个数字直接跳到审核台的收件箱。
- **本体审核台**：收件箱下面多一节「**待建模的概念**」——按**概念**分组（不是按记录），
  给出"这个概念被几条知识用到""有哪些知识"，以及一句话动作：
  「去「本体编辑台」把这个类建出来；发布新版本体以后，用到它的知识会自动解除「结构待定」」。
  这一节**单列**而不并进上面那三格：那三格按「谁提的请求」分，而"概念还没建模"不是谁的请求。
- **问答**：这类知识**不算证据**，但会**显式列出来**：答案正文会说"当前查询范围内有 N 条知识，
  但它们的类型在本体里还没有（结构待定），不能作为正式证据"，证据面板里单列一块，
  编号用 **P**（`[P1]`）——一眼区别于证据的 `[E1]`。没有正式证据时也不会说成"没有证据"。
- **本体校验**（约束校验）：这类知识**不参与**校验，但校验回执会把它们列出来并说明为什么跳过，
  不做静默忽略。

### 19.3 解除条件（只有一条）

**概念真的进了本体**（在「本体编辑台」把它建成类/关系/属性，保存并发布新版本）之后，状态**自动**变成
「结构待定已解除」，数字自动减一。所以收件箱里**没有"清除标记"按钮** —— 概念没建、标记就还在，
概念建好了、标记自己走。两个清除入口必然打架（这正是前面说的"环节冲突"）。

### 19.4 一句话边界

| 算 | 不算 |
|---|---|
| 可检索、可看原文、可被引用、出现在图谱与台账里 | 不进问答的**正式**证据链（但显式标注） |
| 会被收件箱点名"缺哪个概念" | 不参与本体约束校验 |
| 概念建好后自动解除 | 不计入本体覆盖率（该指标目前还不存在） |

### 19.5 复验怎么做

```bash
# 服务在 8000 上跑着（python -u -m knowledge_service --port 8000）
python scripts/verify_structure_pending.py --url http://127.0.0.1:8000
```
脚本自己造一个临时项目（默认跑完删掉，`--keep` 保留），逐条打勾：
写入收下 → 端点传染 → 收件箱读数 → 可检索 → 校验剔除 → 两个问答入口同口径 → 真页面徽标与收件箱 →
走完整发布链（校验 → 提交 → 逐条收下 → 发布）后数字归零、状态变「已解除」。
**共 30 项，0 跳过**才算过。

### 19.6 这一轮真机挖出的三个坑（mock 抓不到，都已修）

1. `prospective.get(key)` 取的是字符串 `"object_id"` 而不是记录 id → 端点传染记成"(未命名类型)"，
   收件箱里凭空多一组、少一条。**形状对、语义错**的错误 mock 测不出来。
2. 问答有**两个入口**（`/qa` 一次性 JSON 与 `/qa/stream` 流式），各拼一套 `structure_pending` →
   流式那条压根没这个键。口径收进 `answers.pending_block()` / `no_evidence_text()` 两处共用。
3. 台账数字只有两态（有/读不到），加载中的一瞬被读成"服务端没给" → 改成三态。

> 第 2 条是这一轮最值得记的：**"同一件事有两个入口"就是这个仓库反复出问题的地方** ——
> 修的不是那两个入口，是让它们没有第二套口径可写。
