# 本体治理模块拆分设计（三个模块，不是两个页面）

> 日期：2026-10-01（v2，替代 v1 的《本体工作台与本体档案拆分设计》）
> 触发反馈（用户原话）：
> 1. **"本体工作台太重了，然后又要审核又要修改，还能看发布后的数据，这个不对……现在能用，但是很难用。"**
> 2. **"我理解不是本体档案吧，就是本体后续的生产管理是不是要单独做一个模块呢，因为现在从知识写入，然后本体工作台进行审核，然后审核完后，是不是也要有个地方维护生产的本体设计，或者编辑的能力。"**
>
> 第二条是更准确的诊断：缺的不是"档案"，而是**本体设计／维护台**。档案只是配套的第三块。

---

## 0. 结论

整条流水线要分成**四个模块**，各管一段，边界不重叠：

| 模块 | 一句话 | 心态 | 输入 → 输出 |
|---|---|---|---|
| ① **知识写入**（已有） | 把原始资料变成可检索的知识 | 采集 | 文档 → 知识/断言/候选术语 |
| ② **本体审核台**（原"本体工作台"收窄） | 决定这批变更**要不要**进正式本体 | 把关（被动） | 草案 → 批准/拒绝 → 发布或关闭 |
| ③ **本体设计台**（**缺的就是它**） | 主动**设计**正式本体：新增、修改、停用、重构 | 设计（主动） | 设计意图 → 草案 → 交给 ② 审核 |
| ④ **本体档案**（本轮已建） | 已定的事实：版本、目录、Diff、溯源 | 查账（只读） | 只读；唯一写操作是"基于某版本新建草案"→ 进 ③ |

**关键不变量（不变）**：正式本体只能经 **草案 → 逐项审核 → 不可变版本** 进入。
所以 ③ 不是"第二个写入口" —— 它和 ② **共用同一套草案底座**，区别只在*出发点*：
② 处理的是"外部来的变更"（抽取发现、变更建议），③ 处理的是"我自己画的领域模型"。

---

## 1. 现状：一条流水线 + 一个什么都干的页面

```
知识写入 ─→ 发现候选 ─→ 草案 ─→〔本体工作台〕审核 → 校验 → 发布 ─→ 正式本体
                                     ↑
                        还得改结构、看历史、跑 Turtle/SPARQL、看已发布数据
```

本机实测（Playwright 量几何）与用户反馈一致：顶部横幅 165px + 五阶段 58px + 状态条 ≈ 400px
首屏开销；审核页中间是浮层画布观感、底部操作条有遮挡；版本治理是盖在画布上的抽屉；
已发布/已关闭的草案仍能进审核/校验/发布三阶段，进去就撞服务端拒绝（"点回去各种异常"）。

根因不是样式，是**职责混在一页**：一页里同时存在"我改"、"我批"、"我看历史"、'我看已发布数据'四种心态。

## 2. 能力盘点（按代码真实实现列，不凭印象）

### 2.1 已验证存在的写入能力（后端）

| # | 能力 | 后端事实 |
|---|---|---|
| 1 | 新增术语（类/关系/属性） | 草案命令 `create_term`；旧路由 `POST /ontology/terms` |
| 2 | 改父类、多父类 | `add_parent` / `remove_parent` |
| 3 | 关系与属性的 domain / range | `add_domain` `remove_domain` `add_range` `remove_range` |
| 4 | 属性数据类型 | `set_datatype` |
| 5 | 标签与说明（中文/英文标签、描述） | `add_annotation` / `remove_annotation` |
| 6 | 停用 / 恢复术语 | `retire_term` / `restore_term`（停用只影响新版本，历史知识仍可查） |
| 7 | 全量 Turtle 编辑 | `turtle` / `replace_turtle` / `diff_turtle`；另有 `advanced_rdf_patch` |
| 8 | 撤回一条已提变更 | `withdraw_operation` |
| 9 | 影响面查询 | `GET /ontology/term-impact`（改/停用前看有多少知识用到它） |
| 10 | 治理状态机 | 草案 create/commands/submit/validate/decisions/batch-approve/publish/rebase/close；发布不可变 + 校验指纹 |
| 11 | 从知识候选提出本体变更建议 | `ontology-change-proposals` + decision |
| 12 | 查询与校验 | `POST /sparql`、`POST /ontology/validate`、`POST /ontologies`（Turtle 存为草案） |

### 2.2 缺口（用户会要、但系统现在没有的能力）

| # | 缺口 | 现在的替代做法（都很别扭） |
|---|---|---|
| a | 没有"设计台"这个去处 | 在审核台里翻抽屉 / 在旧面板里填结构化表单 |
| b | 术语**改名 / 合并 / 拆分**不是一等操作 | 只能改 label 标注；合并同类只能 Turtle 手写 |
| c | 停用没有**替代指引**（deprecated → 指向替代 IRI） | 代码里有 `DEPRECATION` 常量，UI 与替代字段都没有 |
| d | 约束（SHACL：基数、必填、取值范围）没有可视化编辑 | 只能在 Turtle 里写 |
| e | 没有**整体质量体检**：孤立类、无标签、循环继承、零引用（没有任何知识用到）的类 | `term-impact` 只能一个个查 |
| f | 编辑前没有"这会波及哪些知识/检索"的前置预览 | 只能编完再发布才察觉 |
| g | 没有与外部标准本体的对齐/映射 | 无 |
| h | 没有导出（JSON-LD / OWL / 人读的目录文档） | 只有 Turtle 文本 |
| i | 发布新版本后，已入库知识不会按新本体**受控重分类** | 现状是刻意保留旧版本，但缺"我要重跑"的入口 |
| j | 多语言标签没有管理视图（只能逐个改） | 无 |
| k | 结构对比只有"版本 vs 上一版"，不能任选两版比 | 无 |

## 3. 拆分方案：三页闭环

```
        ┌──────────────────────────────────────────────────────────┐
        │  ① 知识写入（不动）：文档 → 知识/断言/候选术语            │
        └───────────────────────────┬──────────────────────────────┘
                                    ↓ 发现候选 / 变更建议
   ┌────────────────────────────────────────────────────────────────┐
   │  ② 本体审核台（原工作台，收窄）                                 │
   │     发现 → 审核（逐条批准/拒绝）→ 校验 → 发布                   │
   │     只回答："这批变更要不要进正式本体？"                        │
   └───────────────┬────────────────────────────────┬───────────────┘
                   │ 发布（不可变版本）              │ 要求调整 / 撤回
                   ↓                                 │
   ┌──────────────────────────────┐                  │
   │  ④ 本体档案（已建，只读）     │                  │
   │  版本 / 类别目录 / Diff /     │──── 基于此版本 ──┼──→ ③ 本体设计台
   │  Turtle / SPARQL / 发布记录   │      新建草案    │     新增/改/停用/重构
   └──────────────────────────────┘                  │     存为草案（仍走审核）
                   ↑                                 │
                   └──────── 发布出新版本 ────────────┘
                        （③ 的产出最终回到 ④ 成为新版本）
```

**读法**：④ 看现状 → ③ 改（产出的永远是草案）→ ② 批 → 发布 → 回到 ④ 出现新版本。
四者构成一个闭环，没有第二个绕过审核的写入口。

## 4. 每个模块的边界（做什么 / 不做什么）

### ② 本体审核台（原"本体工作台"改名、收窄）
- **做**：看发现候选与证据；对**已存在的草案**逐条批准/拒绝/要求调整（含一键批准）；跑校验；发布；关闭（丢弃）草案。
- **不做**：不做本体设计（新增类、改父类、加约束的入口移去 ③）；不展示版本历史/Diff/Turtle/SPARQL（移去 ④）；不展示已发布数据的目录（移去 ④）。
- 终态（已发布/已关闭）：只读回顾 + 两个出口「去本体档案」「去本体设计台」。
- 界线口吻：**"这一轮要不要过"**，而不是"本体该长什么样"。

### ③ 本体设计台（新增，本轮核心缺口）
- **做**（主编辑器）：
  1. 选基线版本 → 建/开一个草案（设计态）；
  2. 结构化编辑：新增类/关系/属性、改父类、加/删 domain·range、设数据类型、改中英标签与说明、停用/恢复（停用要能指定替代术语）；
  3. 编辑前**影响面提示**（复用 `term-impact`：有多少知识用到它、有没有别的术语引用它）；
  4. 层级重构视图（拖动改父类 + 层级树/关系矩阵看整体结构）；
  5. 高级模式：Turtle 全量编辑（带 diff 预览）；
  6. 存为草案 → 一键提交审核（跳到 ②）。
- **不做**：不能发布（发布是 ② 的动作，单人项目可一键"提交并自审"但仍走同一状态机）；不做知识内容编辑（那是知识写入/知识与历史）；不做历史版本浏览（④）。
- 界线口吻：**"本体应该长什么样"**。

### ④ 本体档案（已建，只读）
- **做**：版本概览；类别目录（类/关系/属性 + 上级类、domain/range、数据类型中文解释、被谁引用）；版本历史与结构对比；Turtle 只读查看 + SPARQL 查询台；发布记录（谁/何时/来自哪个草案/校验指纹 + 展开逐条决定）。
- **不做**：不直接编辑本体；不审批；唯一写操作是「基于此版本新建草案」→ **进 ③**（不是回 ②）。
- 界线口吻：**"现在长什么样、怎么变成这样的"**。

## 5. 与上一版（v1，只有"工作台 + 档案"两页）的差异

我上一版把"改本体"留在审核台，只把"看已发布数据"搬去档案 —— **这没解决用户的核心问题**：审核台依然既要批又要改。差异如下：

| | v1（两页） | v2（三模块） |
|---|---|---|
| 谁来"改本体" | 审核台（抽屉/检查器） | **③ 设计台**（主编辑器） |
| 审核台范围 | 审核 + 改 + 看历史 | **只审核**（+ 关闭/发布） |
| 档案页的"新建草案" | 跳回审核台 | **跳 ③ 设计台** |
| 已发布的目录/版本 | 档案页 | 档案页（不变） |
| 用户"生产本体的设计/编辑" | 仍然没有去处 | 有专门模块 |

已落地的代码（本轮）：④ 档案页（`ontology-archive.js/css` + 菜单入口）。**因此 ③ 设计台是接下来的 P0 缺口**。

## 6. 容易混淆的四组概念（必须分清，否则又会叠在一起）

| 常被混为一谈 | 区别 |
|---|---|
| 知识写入 vs 本体设计 | 知识写入改的是**数据**（文档、断言、实体）；本体设计改的是**结构**（类、关系、属性） |
| 本体设计 vs 审核 | 设计＝主动画模型；审核＝对"已提出的变更集合"做接受/拒绝。同一份草案的两个阶段，但**心态与界面都不同** |
| 审核 vs 档案 | 审核对"还没定的事"，档案对"已经定的事"（账本只增不减） |
| 草稿 vs 正式本体 | 草案可任意改、可关闭；正式版本发布后不可变、不可回滚（要回旧结构只能基于旧版本新建草案重走流程） |

## 7. 实施顺序

- **P0（下一步）**：③ 本体设计台最小可用版 —— 基线选择、草案创建/打开、结构化编辑（术语增改停用 + 父类 + domain/range + 数据类型 + 标签说明）、影响面前置提示、提交审核；并把 ④ 档案页的「基于此版本新建草案」改为落到 ③。
- **P1**：② 审核台收窄（移除改结构入口与版本治理入口，终态只读回顾 + 双出口）；档案页补"任选两版对比"。
- **P2**：缺口 b（合并/拆分）、c（停用替代指引）、e（质量体检）、h（导出）、i（受控重分类）、j（多语言标签视图）。

## 8. 验收标准（真机可核对）

1. 菜单三个并列入口：**本体审核台**、**本体设计台**、**本体档案**（命名可按用户习惯调整）。
2. 审核台里搜不到"Turtle / SPARQL / Diff / 版本治理 / 类别目录"这类"查档案"的字样。
3. 设计台能完成一次真实闭环：选基线 → 新增一个实体类（带中文名、父类、说明）→ 看到影响面提示 → 存为草案 → 提交审核 → 在审核台批准 → 发布 → 档案页出现新版本，且版本对比显示"+1 类"。
4. 设计台里没有"发布"按钮（发布属审核台的职责）；审核台里没有"新增术语"入口。
5. 已发布/已关闭草案上的审核台呈只读回顾，任何点击都不出现英文报错。
6. 浏览器控制台无异常；`pytest` 相关契约全绿。

---

## 9. 明确不做（边界）

- **不做**在档案页直接改本体；**不做**绕过草案的直接写（除已有的受治理 Turtle/术语草案路径）。
- **不做**版本回滚（历史版本不可变）；要回旧结构只能基于旧版本新建草案。
- **不做**物理删除术语（只有停用）+ 历史知识保持可查。
- **不做**跨项目本体合并／继承。
- **不做**多人实时协同编辑（无锁提示、无冲突合并 UI）。
