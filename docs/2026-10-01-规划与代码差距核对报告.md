## 2. 实测断链清单（本次核对的核心产出）

### B1 —— Milvus 语义检索全链路已死，但外表「正常」（P0，最严重）

**这是本次最重要的发现。** 你的 Milvus 是启用的、容器是 healthy 的，但**检索链路 100% 失败并静默降级**。

实测 collection 真实 schema：

```
collection: knowledge_records   row_count: 0
  field: id      type=5(VarChar)
  field: vector  type=101(FloatVector) dim=1024
```

而当前代码 `milvus_store.ensure_collection()` 要求 9 个字段：
`version_id`(主键) / `project_id`(分区键) / `record_id` / `kind` / `type` / `text`(中文 analyzer) / `embedding_model` / `embedding` / `sparse`(BM25)。

三项操作全部实测失败：

| 操作 | 实测异常 |
|---|---|
| 读（`search_dense`/`search_hybrid`） | `MilvusException code=1100: failed to get field schema by name: fieldName(embedding) not found` |
| 写（`upsert`） | `DataNotMatchException: Insert missed an field 'id' to collection` |
| 重建（`rebuild_project`→`delete`） | `MilvusException code=503: no available shard leaders` |

**根因**（关键代码缺陷）：

```python
# knowledge_service/integrations/milvus_store.py:86
if self._client.has_collection(self.collection_name):
    return self          # ← 同名即复用，不校验字段集/维度/analyzer/schema 版本
```

**这个 collection 从哪来的？（已查证，修正了一个我先前的错误推断）**

我最初推断它是"旧版代码留下的"。**这个推断是错的**，查证结果如下：

| 查证项 | 结果 |
|---|---|
| `git log --all -G'FLOAT_VECTOR'` | 220 个提交中，**每一版** `milvus_store.py` 都是 9 字段 schema（`version_id`+`embedding`+`sparse`） |
| `git log --all --name-only` | 历史上 `milvus*` 相关文件只有 `integrations/milvus_store.py`、`milvus_store.py`、`test_vector_storage.py` |
| 全仓库搜 `create_collection` | 只有 `milvus_store.py:106` 那一处（9 字段） |
| Milvus 自有元数据 `created_timestamp` | 解码 = **2026-10-01 12:34:48 CST**（今天） |
| `find volumes -type f`（1345 个文件） | **最早的文件也是 2026-10-01** → 整套栈今天从零建起，无迁移痕迹 |

完整的 `describe_collection` 原始输出：

```json
{"collection_name":"knowledge_records", "auto_id":false, "description":"",
 "fields":[{"name":"id","type":5,"is_primary":true},
           {"name":"vector","type":101,"params":{"dim":1024}}],
 "functions":[], "enable_dynamic_field":true,
 "collection_id":469455090940642595, "schema_version":0}
```

`fields=[id(VarChar 主键), vector(FloatVector 1024)]` + `enable_dynamic_field=true` + `functions=[]`（无 BM25）
—— 这正是 **Milvus quickstart 的 `MilvusClient(uri).create_collection(name, dimension=1024)`**
或 **Attu 新建集合向导** 的默认产物，**不是本项目代码的产物**（本项目 `create_collection` 必然带
`description`、BM25 function、`text` 的 `analyzer_params={"type":"chinese"}`）。

> ⚠️ 为什么这很重要：`docs/2026-10-01-Docker基础设施维护手册.md:180` 把
> 「Milvus：`knowledge_records` 集合（1024 维、COSINE，与应用 `KG_MILVUS_DIM` / 检索集合名一致）」
> 写成了**要保留的既有基线**，`docs/superpowers/plans/2026-09-30-unified-data-services-compose.md`
> 也把「`knowledge_records` is present」当成验证通过条件，`scripts/verify-compose-stack.sh`
> 还断言它「在重启前后必须一致」。**也就是说，一个用错 schema 的同名探针集合，
> 被当成了正式数据来保护**，而应用又「同名即复用」——两者叠加才造成 B1。

于是形成 B1：
- 每次检索抛异常 → `retrieval.py` 捕获 → 日志 `Milvus 排名失败，降级到本地检索`
- API 只返回 `degraded: true` + `语义索引尚未就绪…`，**完全没提「schema 不兼容」**
- `/api/health` 的 `capabilities` 与 `database` 字段都不反映向量后端状态

**删除该集合后的实测（验证根因成立）**

集合删除后，直接调用应用自身的 `MilvusStore.connect().ensure_collection()`，一次成功：

```
fields: version_id(VarChar,PK) project_id record_id kind type
        text(max=65535, enable_analyzer=true, analyzer_params={"type":"chinese"})
        embedding_model embedding(FloatVector,1024) sparse(SparseFloatVector)
functions: ['text_bm25']                      # BM25
indexes:   embedding(HNSW/COSINE) sparse(SPARSE_INVERTED_INDEX/BM25)
           record_id(INVERTED) kind(INVERTED)
```

再注入 1024 维测试向量（不依赖 bge-m3）验证读写全链路：

| 验证项 | 结果 |
|---|---|
| `upsert` | ✅ 2 条写入成功 |
| `search_dense` | ✅ 自身 score=1.000，另一条 0.743 |
| `search_bm25` 中文分词 | ✅ `退款` / `未消费订单` / `过期` 全部命中 |
| `search_hybrid` | ✅ dense+sparse 融合排序正常 |
| 项目隔离 | ✅ 查不存在的项目返回 `[]` |
| `delete` | ✅ 清理成功 |

**结论：建集合与检索的代码本身没有缺陷** —— 之前的全链路失效，100% 由「既有同名错 schema 集合」
+「`ensure_collection` 同名即复用」共同造成。B1 的修复重心因此是 **(a) 加 schema 校验** 与
**(b) 清理并停止把该集合当基线**。

> **另一个重要细节**：即使走 Milvus 的 `chinese` analyzer，`怎样退钱` 对
>「未消费订单可申请退款」仍是 **0 命中**（分词后 怎样/退钱 vs 未消费/订单/申请/退款，无交集）。
> 说明**换述类查询只能靠 dense 语义通道**，BM25 无论分词多好都解决不了。
> 因此 B2（embedding 模型缺失）不修，B1 修好了检索质量也不会好 —— 两者必须一起修。

**连带证据（假成功）**：写入路径在 Milvus 同步失败时，日志仍打印
`写入完成：1 条记录落库并同步向量索引` —— 与规划 F06 描述完全一致，但**你现在的现象比 F06 更严重**：
F06 说的是「偶发失败仅记日志」，实际是「**100% 失败且长期无人察觉**」。

**修复要点**：`ensure_collection()` 必须做 schema 一致性校验（字段名集合 + 维度 + analyzer + BM25 function），
不匹配时**按 `generation`/版本后缀新建 collection 并原子切换**，或直接抛明确错误拒绝启动——**不允许静默复用**。
另：BM25 那条路（`sparse` + 中文 analyzer）本来就是为解决中文分词设计的，schema 修好后 B3 会一并缓解。

### B3 —— 中文关键词检索退化：查询被拆成单字 AND（P0，直接对应「查不准」）

SQLite FTS 建表语句（`repository/core.py:671-673`）：

```sql
CREATE VIRTUAL TABLE record_fts USING fts5(
    project_id, record_id, kind, text, metadata,
    tokenize='unicode61')          -- ← 无中文分词
```

`unicode61` 对 CJK 按**单字**切分，而 FTS5 默认把多词查询当 **AND**。
实测（同一文档，`valid_at=2026-09-01`，过滤 `region.city=北京`）：

| 查询 | hits | 说明 |
|---|---|---|
| `退款` | 1 | 退 AND 款，都在 |
| `未消费订单` | 1 | 五字全在 |
| `北京` | 1 | 命中 |
| **`怎样退钱`** | **0** | 怎/样/退/钱 四字 AND，「怎、样、钱」不在 → 全灭 |

所以「用户自然语言 query → 0 命中」是**必然**，不是偶然。
`smoke_service.py:28` 的断言（`hits == 1`）在 demo 编码器下就是这么挂的：

```
AssertionError: {'hits': [], 'candidate_count': 1, 'active_mode': 'keyword', 'degraded': True,
                 'backends': {'keyword': {'hits': 0}, 'semantic': {'active': False,
                 'error': '语义索引尚未就绪，请先构建语义索引；仍可使用关键词检索和图谱浏览'}}}
```

注意 `candidate_count: 1` 但 `hits: []` —— **过滤找到了候选，词法排名却全军覆没**，两个阶段的语义不一致，
这个对比本身就是很好的回归用例。

规划 §5.4 提到「PostgreSQL 默认全文分词不能直接等价替换中文 FTS」，方向对，但只讲了 PG 侧；
**当前 SQLite 侧就已经是这个病**，且被 FTS5 的 AND 语义放大成「必然 0 命中」。
修复方向：SQLite 侧改 `trigram` 或引入受控中文分词；Milvus 侧修好 B1 后由 BM25 + `analyzer={"type":"chinese"}` 接管。

### B5 —— Windows 系统代理把本机请求也代理了，smoke 直接 502（P1，环境级）

实测：

```
httpx trust_env=True  → POST http://127.0.0.1:8123/api/projects → 502 Bad Gateway
httpx trust_env=False → 200 OK
curl                  → 200 OK
urllib.getproxies()   → {'http': 'http://127.0.0.1:7890', ...}   ← 从 Windows 注册表读到
```

你机器上有本地代理（`127.0.0.1:7890`）。httpx 默认 `trust_env=True`，会走**注册表**里的系统代理
（不只是环境变量），且 `NO_PROXY` 未包含 `127.0.0.1`，于是**对本机服务的请求也被送进代理**。

影响面：
- `scripts/smoke_service.py`（用 httpx）—— 实测复现
- 应用内所有 httpx 出站（`RemoteEncoder.encode`、Semantica/DeepSeek 调用）

修复：启动脚本与测试环境统一设 `NO_PROXY=127.0.0.1,localhost`；
或在 `scripts/smoke_service.py` 里显式 `httpx.Client(trust_env=False)`——**脚本探活本机服务，本就不该看系统代理**。

### B6 —— ~~PostgreSQL 应用角色不存在~~ → **已解决，此处为原误判的更正（P1）**

> **更正**：我最初报告「`knowledge_app` 不存在」是**错的**，原因是第一次查询用了 `\du | head -12`，
> 输出被截断（`knowledge_app` 那一行在 `postgres` 之前，被截掉了）。完整重查结果：

```sql
SELECT rolname, rolcanlogin, rolsuper, rolcreatedb, rolcreaterole, rolbypassrls FROM pg_roles;
           rolname           | rolcanlogin | rolsuper | rolcreatedb | rolcreaterole | rolbypassrls
-----------------------------+-------------+----------+-------------+---------------+--------------
 knowledge_app               | t           | f        | f           | f             | f
 postgres                    | t           | t        | t           | t             | t
```

`knowledge_app` **已存在**，且权限口径完全正确：可登录、非 SUPERUSER / 非 CREATEDB / 非 CREATEROLE / 非 BYPASSRLS
—— 正是规划 §5.1 与 `docker/postgres/initdb/10-app-role.sh` 注释所要求的口径。
`knowledge` 库的 ACL 也含 `knowledge_app=c/postgres`（CONNECT 权限）。

**教训（值得记住）**：`psql -c '\du'` 这类输出**不要用 `head` 截断**——行序不保证，截断会静默丢掉行，
把「存在」读成「不存在」。核对权限/角色一律用显式 `SELECT ... FROM pg_roles ORDER BY rolname`。

**仍然有效的遗留项**：容器日志显示 `database directory appears to contain a database; Skipping initialization`，
说明 `10-app-role.sh` **不是**由 initdb 自动执行的（`volumes/postgres` 的 1345 个文件全部早于脚本挂载）。
所以该角色是**后来手工补跑**出来的。这意味着：
- 任何**新建**环境若忘记挂载 `docker/postgres/initdb`，仍会只有 `postgres` 一个角色；
- 宜在 `scripts/verify-compose-stack.sh` 里加一条断言（`knowledge_app` 存在且无 `rolsuper`），把「手工补过」变成可验证的门禁。

> 附带：手册 §74 说「旧命名卷 `knowledge-postgres-data` 已不再被引用，可手工 `docker volume rm` 释放约 47MB」——
> 实测 `docker volume ls` 里**已经没有这个卷**，该段可删，避免误导。

对等性口径：**表/列**与冻结的迁移前 schema 逐表一致；**索引/约束**按 `表+列+唯一性` 等价（60 个索引定义），
**不比对名字**（PG 会用约束隐式建索引）；**触发器**按行为等价（29 项行为断言）。

## 关键类型映射决策（详细理由见 `0001_core.sql` 文件头）

1. **不透明 JSON 一律 `text`，不用 `jsonb`**。`jsonb` 会**规范化键序并去重**
   —— 实测 `{"k":1,"a":2}` 读回变成 `{"a":2,"k":1}`。而代码里有针对 JSON 内容计算的
   指纹/哈希（`projection_digest`、`fact_key`、discovery 指纹），改用 jsonb 会让
   同样的输入产生不同指纹，**静默破坏幂等与去重**。需要 SQL 内过滤时改建
   `((col::jsonb))` 的表达式/GIN 索引 —— 既有字节精确，又能索引下推。
2. **`CHECK (col IS JSON)` 只保留在 SQLite 原本就有 `json_valid(col)` 的 9 列上**。
   迁移前 SQLite 库已不存在、**没有真实数据可背书**，因此不给其余列凭空加严约束
   —— 否则 PG 会拒绝掉 SQLite 本来接受的写入，这类回归只在生产暴露。
3. **`timestamptz` + 读取层还原成 `utc_now()` 同格式字符串**（UTC + 微秒 + Z），
   使业务层与迁移前逐字节一致，285 个 SQL 调用点不必改时间处理。
4. `record_fts`（FTS5 虚拟表）→ 真实表 + `pg_trgm` GIN（中文无需词典）
   + `to_tsvector('english', …)` GIN（英文明确配置）。

## 本轮发现并已修的真实缺陷

| # | 缺陷 | 后果 | 处理 |
|---|---|---|---|
| 1 | 我把 `ontology_history_repairs` 的 INSERT 守卫写成**无条件拒绝** | 历史修复台账**永远无法追加** | 改为 `WHEN EXISTS(同 repair_key)`，与 SQLite 一致；已在 0001 内修正并用测试锁定 |
| 2 | 我给 12 个列**凭空加了** `CHECK (col IS JSON)`、给 `version` 加了 `CHECK (version >= 1)` | PG 会拒绝 SQLite 接受的写入 | 全部撤除；只保留 SQLite 原有的 9 列 |
| 3 | **集群超级用户口令与 `.env` 漂移** | 迁移无法执行 | 走容器内 trust socket 对齐到 `.env` 声明值（口令不进 argv / 不打印），TCP SCRAM 复验通过 |

> 关于 #3：官方镜像的 `pg_hba.conf` 对**容器内** `127.0.0.1` 是 `trust`，
> 所以「容器内 psql 能连」**不能**证明口令正确 —— 这是很容易误判的假阳性。
> 判定口令是否正确的可靠方法是比对 `pg_authid.rolpassword` 里的
> SCRAM StoredKey 与用该口令推导出的值。

## 必须带进 T03 的两个语义分歧（**PG 比 SQLite 严**）

1. **级联删除会触发触发器**。SQLite 未开 `recursive_triggers`，`ON DELETE CASCADE`
   **不触发**触发器；PostgreSQL 级联删除**会**触发。因此
   `core.py:1124 delete_project` 在 PG 下会被不可变触发器拦住。
   → T03 必须保持「**先删依赖者、再删 projects**」的顺序
   （`delete_project` 本来就是这么写的，但依赖 `delete_counts` 覆盖到 operations/decisions）。
2. **受控删除开关要换实现**。SQLite 用 Python 侧深度计数器
   （`core.py:1076 _allow_ontology_history_delete` → `create_function('ontology_history_delete_allowed')`）；
   PG 对应物是**事务级 GUC**：`SET LOCAL knowledge.ontology_history_delete_allowed = '1'`。
   `_allow_ontology_history_delete()` 改为发这条语句即可；`SET LOCAL` 随事务结束自动失效，
   比手工计数更安全。**前提是调用点必须处于事务内**（`delete_project` 满足）。
   已在 `tests/service/test_postgres_schema.py::_purge_project` 预演并验证通过。

另有一条**结构性结论**（不必写用例）：操作/决定的「多节点 supersedes 成环」与
「替代者指纹不一致」两种守卫，要求新行 id 已被既有行引用，而外键又要求被引用行已存在
—— 二者互斥，故在 INSERT-only 模式下不可达，其唯一入口 UPDATE 已被无条件拒绝。
这两条属纵深防御，不是可测的正常路径。

## 验收中刻意区分的两类判定

- 对等性以**定义**为准（表+列+唯一性），不以**名字**为准 —— 否则会被 PG 的隐式索引名误导。
- 触发器以**行为**为准（同一批写入的接受/拒绝集合），不以 SQL 文本为准 ——
  13 个 SQLite 触发器合并成 9 个 plpgsql 函数后，文本必然不同，但拒绝集合必须一致。
- 有意为之的差异（`record_fts.tokenize` 是虚拟表选项不是列；`schema_migrations`
  多出的 `name/checksum`）在测试里**显式豁免并写明理由**，不做静默忽略。

## 顺带发现的真实生产缺陷：出口代理

排查过程中发现应用有**三处裸 `httpx.Client(...)`**（无 `trust_env=False`）：
`integrations/embeddings.py`、`services/answers.py`、`services/service.py`。

`httpx` 的默认代理解析是：

```python
getproxies() = getproxies_environment() or getproxies_registry()
```

关键在 `or`：**没有代理环境变量时它会去读 Windows 注册表里的系统代理**。
本机实测该代理（127.0.0.1:7890）对 LLM 端点不可靠：

| 调用方式 | 实测结果 |
|---|---|
| 直连 | HTTP 200/400，**0.2s，3/3 稳定** |
| 经系统代理 | **3 次里 2 次** TLS 握手 20s 超时 |

表现是「有时能跑、有时超时」的偶发故障 —— 最难查的一类，因为不可复现，且错误
只会显示成「模型提供商不可用」。

另有一个陷阱值得记下来：只要 `NO_PROXY` 非空，`getproxies_environment()` 就返回
非空，`or` 短路，注册表代理**整体**失效（并不只是 `NO_PROXY` 里列出的主机）。
也就是说「设 NO_PROXY」实际等于「全局不读系统代理」，很容易误判成因。

**处理方式**：把出口代理决策收敛到唯一出处 `knowledge_service/core/net.py`
的 `external_client()`，默认**显式不继承**系统代理；确需代理用 `KG_LLM_PROXY`
指定。同时把三处调用点的错误信息改为保留底层原因（经 `redact` 脱敏）。

## 一个必须说清的取舍：文案为什么没有写成「PostgreSQL」

用户要求把「SQLite 原子落库」改掉。但 `api/__init__.py:69` **当前仍在构造 SQLite
`Repository`** —— 数据此时此刻确实写进 SQLite。

如果只把文案改成「PostgreSQL 原子落库」，日志就开始**说谎**：将来有人排查数据
去向会被引到错误的库上。这比文案陈旧危险得多。

因此改成**从 `repository.backend_label` 如实推导**：现在显示 SQLite（真话），
T03 把应用切到 PostgreSQL repository 时改 `backend_label` 一个值，文案自动跟着变。
换句话说，「不再显示 SQLite」的**真正解法是 T03**，不是改字符串。
