## 3. 动手前必读：硬约束与踩过的坑

### 3.1 设计约束（不可违反）
1. **门禁判据只来自服务端**（`GET /ontology-drafts/stage-availability` 的 `stages.<id>.allowed/reason`）。前端只把它翻译成「能不能点 + 为什么」，**绝不自己推**「哪个阶段能进」。
2. **收件箱按「谁提的请求」分，不按步骤分**：`machine`（机器抽的候选）/ `request`（业务方申请）/ `mine`（你自己的改动待确认）。
   - `mine` 的门禁是**逗号列表** `design,review,publish`：任一阶段规则放行 → 这一类可进（因为它是这一类的后续视图）。
3. **一屏一问**：默认 `machine` 只渲染候选区；`request` 只渲染申请卡；两类不并排。
4. **审核 ≠ 确认**：对别人是「收/不收」，对自己的不可逆改动是「就地弹一次看影响面」。别把两个词混回一锅。
5. **界面引导规则**（用户核心诉求「让傻子都会用」）：一屏一问、长流水折叠 + 内部滚动、字号 ≥11px、首屏 ≤140px。

### 3.2 动手时的坑（本轮真踩过的）
1. **`patch` 工具的多行块替换会搞乱 Python 缩进**：当 new_string 第一行与 old_string 第一行缩进基准不一致时，fuzzy match 会把整块带入错误缩进，`py_compile` 报 `IndentationError`。
   - 对策：多行块替换时，**new_string 第一行必须与 old_string 第一行同缩进**；
   - 出错后用 `execute_code` 跑 Python **按行号精确去/加前导空格**修复（别再用 patch 二次修补）。
2. **新增的内部函数要记得导出**：`window.OntologyWorkbench = {…}`（文件末尾）。本轮 `setInbox` 漏了导出，导致测试 `OntologyWorkbench.setInbox is not a function`。
3. **测试里等「前端状态」而非「mock 状态」**：mock 先变、前端拿到响应才更新 `state.draft`；只 `wait_for_function("mockDraft.status === 'reviewed'")` 会在响应回来前就去切阶段，门禁还没放行 → 假失败。
4. **静态契约测试会把「旧设计」锁成规则**：如旧 `test_ontology_workbench_shell_keeps_four_stages_and_discovery_hooks` 把 4 站阶段条写成了规则。改设计时要**重写**这类用例，不要为了保测试而将就旧设计。
5. **CSS 全局覆盖**：`.ontology-workbench__body :where(...) button` 会把新卡片刷成实心绿；新收件箱卡片必须在 `.ontology-workbench__inbox-item` 重新声明白底/选中/锁定态。
6. **JS 字符串里别混 markdown 星号**（用户可见文案）；注释里的无妨，但保持干净。
7. **`view-switch`（画布/层级树/矩阵）只在 design 阶段显示**；`setModeCopy` 在 design 显示视图说明（`MODE_GUIDE`），其余分类显示收件箱文案。

### 3.3 诚实纪律（写进过技能）
- **不信截图印象，量 DOM 才算**：vision 的每条判断都要能用数字证伪或证实，否则不改。
- 交付物要有**一句话说明它做什么、明确不做什么**（用户核心不满是「感觉不是很明确」）。
- 用户按**真实运行结果**判断完成度，不接受「应该是这样」。
