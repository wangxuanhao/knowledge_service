# 知序 · 全项目整体设计（三层模型）

> 日期：2026-10-02
> 承接《本体治理整体设计（v2）》。v2 只覆盖了**结构层**（本体），本文补上**实例层**（实体/关系/知识）与**消费层**，
> 并回答：实体的编辑该放在哪、实体要不要审批、两层之间怎么互相影响。
> 所有"现状"都来自真机 / 代码实测，标注了文件与行号。

---

## 0. 结论

**整个项目只有两种东西：结构 和 实例。** 现在 13 个菜单项把它们混在一起，所以用户找不到东西。

```
                   ┌──────────────────── 结构层（本体）────────────────────┐
                   │  类 / 关系类型 / 属性 / SHACL 约束                    │
                   │  只经「草案 → 逐项决定 → 不可变版本」改变              │
                   └───┬───────────────────────────────────────┬─────────┘
       新知识带来新概念 │ 待建模收件箱                    新版本 │ 受控重分类
                       ▼                                       ▼
                   ┌──────────────────── 实例层（知识）────────────────────┐
                   │  实体 / 关系 / 原文片段 / 文档                        │
                   │  版本化 + 可撤销，改错可回滚，不审批                    │
                   └───┬───────────────────────────────────────────────────┘
                       │ 检索、问答、图谱、脑图
                       ▼
                   ┌──────────────────── 消费层 ──────────────────────────┐
                   │  把知识用起来看 / 问 / 画                            │
                   └──────────────────────────────────────────────────────┘
```

**判据一句话**：**可逆的不审，不可逆的必审。**
结构变更全局影响且不可逆 → 必须走三道门；实例变更局部影响且可回滚 → 不审批，但必须留痕 + 可撤销 + 有影响提示。

## 1. 三层职责与入口地图

### 1.1 现状：13 个菜单项，按"功能"堆

| # | 菜单 | 实际管什么 | 归属层 |
|---|---|---|---|
| 1 | 项目管理 | 建/删项目 | 运行 |
| 2 | 项目总览 | 统计数字 | 运行 |
| 3 | 检索与交互图谱 | 查 + 看图（**也能改实体**） | 消费（＋实例的编辑入口） |
| 4 | 知识问答 | 用证据答问题 | 消费 |
| 5 | 原文数据源 | 上传 + 读解析正文 | 实例（来源） |
| 6 | 实体脑图 | 以实体为根的树 | 消费 |
| 7 | 知识写入 | 文档 → 知识 | 实例（写入） |
| 8 | 知识与历史 | **实体台账 + 合并 + 版本** | 实例（治理） |
| 9 | 本体审核台 | 五阶段（发现/设计/校验/审核/发布） | 结构 |
| 10 | 本体设计台 | 结构化编辑 | 结构 |
| 11 | 本体档案 | 版本 / Diff / Turtle / SPARQL | 结构 |
| 12 | 后台任务 | 任务队列 | 运行 |
| 13 | 快照 / 评测 | 快照恢复 + 评测 | 运行 |

问题：**结构层只有 3 项，却被切成 5 个阶段；实例层的治理能力散在 3 个页面里，其中 1 个还是消费页。**

### 1.2 目标：4 组 10 入口

```
【项目】      项目管理 · 项目总览
【结构·本体】 本体建模 → 本体审核 → 本体档案
【实例·知识】 知识写入 → 知识台账 → 原文数据源
【消费与运行】检索与交互图谱 · 知识问答 · 实体脑图 · 运行与质量
```

| 现在 | 目标 | 动作 |
|---|---|---|
| 本体设计台 | **本体建模** | 收编「发现候选」（v2 §2） |
| 本体审核台 | **本体审核** | 只剩 逐条决定 + 发布 |
| 本体档案 | 本体档案 | 不变 |
| 知识写入 | 知识写入 | 加"结果三分栏"（v2 §2） |
| 知识与历史 | **知识台账** | 改名 + 升级为实例层的治理中心（见 §3） |
| 原文数据源 | 原文数据源 | 不变 |
| 检索与交互图谱 / 知识问答 / 实体脑图 | 不变 | 消费层 |
| 后台任务 ＋ 快照/评测 ＋ 项目总览 | **运行与质量** | 三合一 |

净效果：**13 → 10**，而且每一层内部只有一个入口对一件事负责。

## 2. 两层的连接点（这是全项目的关键）

结构和实例不是两个孤立的库，它们有两个方向的连接点。**现在两个方向都断的**：

### 2.1 实例 → 结构：待建模收件箱

```
新文档写入 → 抽取出本体里没有的概念 → 进「本体建模」的收件箱
                                      同时用到它的知识标 `结构待定`
```

- **现在**：抽取时遇到本体没有的类型，会走"发现候选"这条旁路，但候选分散在审核台的发现阶段里，**和具体哪条知识有关联却看不出来**。
- **目标**：每条待建模项显示「它来自哪份文档、哪句话、影响几条知识」。

### 2.2 结构 → 实例：受控重分类

```
发布 vN+1 → 提示「改动 3 个类，仍有 128 条知识挂在 vN」→ 用户可选重分类
```

- **现在**：**完全没有**（全库 grep 无此能力）。旧知识永远挂在写入时的 `ontology_id` 上，没人提示你该重跑。
- **目标**：见 v2 §4.1。

### 2.3 消费 → 实例：从图谱直达编辑

**现在已经有**（`evidence-inspector.js:124` 的「编辑这个实体」），做得对，但入口太隐蔽（要点到节点才看得见）。
目标：图谱详情里的「编辑」升级成「**在知识台账里打开这个实体**」—— 点过去是完整的台账视图，而不是一个只有 4 个字段的弹窗。

## 3. 实例层设计：「知识台账」

现在的「知识与历史」其实已经承担了台账职责（`records-view.js` 做了分页、筛选、三步合并向导，做得不错），
但它缺三样东西：**没有"实体"这个视角**、**看不到本体归属**、**撤销入口没接上**。

### 3.1 一屏一个问题

> **「这里管具体的东西：查、改、并重复项。结构（分类）不在这，去本体建模。」**

### 3.2 顶部一行状态

```
128 个实体 · 42 条关系 · 3 个类型待定 · 12 组疑似重复
```

四个数字都可点：
- `3 个类型待定` → 跳到「本体建模」的收件箱
- `12 组疑似重复` → 展开合并向导

### 3.3 三种视角（页签，不是三栏）

| 视角 | 一行里显示什么 | 操作 |
|---|---|---|
| **实体** | 名称 · 本体类型 · **挂在哪一版本体上** · 版本 · 有效期 · 来源 | 编辑 / 版本历史 / 合并 / 软删除 |
| **关系** | 主语 → 谓词 → 宾语 · 类型 · 版本 | 编辑 / 版本历史 / 软删除 |
| **原文片段** | 片段摘要 · 来源文档 · 版本 | 看原文 / 版本历史 |

**关键新增：每行显示"挂在哪一版本体上"**。现在这个信息只在技术详情里（`record-dialog.js:59` 的 JSON），
用户根本看不出"这条知识用的是老结构"——而这正是受控重分类要解决的问题。

### 3.4 实体编辑表单（已有，保留）

`record-dialog.js:59` 已经做对了，直接把它的边界文案固化下来：

> **「这里修改的是图谱中的一个实体，不会修改本体类定义。」**

字段：实体名称 / 实体类型（下拉，选项来自**当前本体**的类）/ 业务生效时间 / 业务失效时间。
保存 = 产生**版本 +1**，旧版本保留（`PUT /records/{id}` + `expected_version` 乐观锁防覆盖）。

### 3.5 合并重复项（已有，保留并升级）

`records-view.js:20-62` 已经是一个三步向导：查重 → 选保留实体 → 选被合并实体 → 确认。
保留它，补两件事：

1. **接上撤销**：接口 `POST /projects/{p}/operations/{operation_id}/undo` **已经存在**（`api/parity.py:194`），
   但 UI 里没有入口。合并完要能一键撤销（现在只在提示文字里说"可在操作历史撤销"，而操作历史入口不完整）。
2. **合并前显示影响面**：会转移多少条关系、多少条来源。

## 4. 实体要不要审批？——不要，这是设计判断

本体有「草案 → 审核 → 发布」三道门；**实例编辑一道门都没有**（`PUT /records/{id}` 改完立即生效）。
这个不对称不是漏洞，是**正确**的，判据就是 §0 那句：

| | 结构变更（本体） | 实例变更（实体/关系） |
|---|---|---|
| 影响面 | **全局**：改一个类，所有用它的知识和检索都变 | **局部**：改一条记录，只有关心它的人受影响 |
| 可逆性 | **不可逆**：版本发布后不能回滚 | **可逆**：版本化 + `/restore` + `/operations/{id}/undo` |
| 是否审批 | **必须**（三道门） | **不审批** |
| 但必须有 | 逐条决定 + 指纹 + 不可变版本 | 留痕（版本历史）+ 可撤销 + 影响提示 |

**推论：给实体编辑加审批是错的** —— 那会让日常纠错变成走流程，用户会绕过它去直接改 JSON。
正确做法是**把"可逆"做扎实**：现在缺的正是"撤销入口没接上"和"改之前不给影响面"。

## 5. 全项目的"一屏一问"总表

| 页 | 一屏的问题 | 主按钮 | 默认折叠 |
|---|---|---|---|
| 知识写入 | 把资料变成知识 | 上传并处理 | 解析高级设置 |
| **知识台账** | 这里管具体的东西：查、改、并重复项 | 编辑所选 / 展开合并向导 | 版本历史、技术标识、操作历史 |
| 本体建模 | 新出现的概念要不要进本体 | 纳入草案 | 校验结论（一行）、影响面 |
| 本体审核 | 这 N 条变更批准还是拒绝 | 发布为 vN+1 | 每条的来源证据 |
| 本体档案 | 本体现在长什么样、怎么变成的 | —（只读） | 版本对比、Turtle、SPARQL |
| 检索与交互图谱 | 找东西、看它连着什么 | 检索 | 图谱与详情 |
| 知识问答 | 基于证据回答问题 | 发送 | 图谱（不预加载） |
| 实体脑图 | 这个实体往下长什么样 | 生成脑图 | — |
| 运行与质量 | 后台在跑什么、质量怎么样 | 刷新 | 任务日志、评测标准答案 |

## 6. 实施顺序（合并 v2 的分期）

| 期 | 内容 | 层 | 风险 |
|---|---|---|---|
| **P0 ✅ 已做** | 终态草案门禁不再撒谎 | 结构 | — |
| **P1** | 三写入口收敛（设计台自审去掉 publish、变更建议文案对齐） | 结构 | 低 |
| **P2** | 界面引导化：进度条、一屏一问、默认折叠、区域标题写用途、首屏 ≤140px | 全局 | 中（纯前端） |
| **P3** | 结构层合并：建模＝发现＋设计；审核台只剩 审核＋发布 | 结构 | 中高 |
| **P4** | 实例层：知识台账改版（三视角 + 本体归属列 + 撤销入口 + 合并影响面） | 实例 | 中 |
| **P5** | 两层连接：待建模收件箱打通 + 受控重分类 + 停用替代指引 | 结构↔实例 | 高（新字段 + 迁移） |
| **P6** | 清理：删掉 `app.js` / `workbench.js` 里被覆盖的死代码（记录列表两套实现） | 全局 | 低 |

**P2 是 P3/P4 的前置**：先有引导化骨架，再往里合并，否则合并只会让页面更挤。

## 7. 明确不做

- 不给实例编辑加审批（§4）。
- 不自动跑存量重分类（v2 §4.1）。
- 不做版本回滚（本体历史版本不可变；实例用 `/restore` 产生新版本，等价于回滚）。
- 不做跨项目本体合并／继承。
- 不做物理删除（本体只停用，知识只软删除）。
- 不做多人实时协同编辑。
