## 2. 一个必须先讲清的判据：两层是怎么耦合的

结构层和实例层不是并排的两个模块，它们**通过两个连接点互相影响**：

```
   结构层（本体）                              实例层（知识）
   类 / 属性 / 关系                       实体 / 关系 / 原文片段 / 文档
        │                                            │
        │  ◀── 连接点①：待建模收件箱 + `结构待定` ────│
        │       新知识带来本体里没有的概念             │
        │                                            │
        │  ──── 连接点②：受控重分类 ──────────────▶  │
        │       本体改版后，旧知识迁到新结构            │
```

**这两个连接点在代码里都还不存在（全库 0 命中）** —— 这是整个项目最大的一块空洞：

| 机制 | 实测 | 没有它的后果 |
|---|---|---|
| `结构待定` / `structure_pending` | **0 个文件命中** | 知识写入时抽出了本体里没有的概念 → 要么硬塞进本体（污染结构），要么丢掉（丢知识）。现在实际上走的是前者：候选堆在"发现"阶段，永远不处理 |
| 受控重分类 / `reclassify` | **0 个文件命中** | 本体出了 v4，旧知识**永远挂在 v3**。用户看得见"这条知识用的还是老结构"吗？看不见 —— 这信息只埋在技术 JSON 里 |

所以顺序上有一条硬约束：**必须先各自把层内理顺，再建连接点**。层内没理顺就建连接点，等于给一个还在变的接口写适配层。

## 3. 实例层规划（用户指出的缺口）

### 3.1 先看家底：实例层其实建得比结构层扎实

实测已建成（`api/parity.py` 逐个接口核对）：

| 能力 | 接口 | UI 状态 |
|---|---|---|
| 改实体/关系（产生新版本） | 记录写入路径 | ✅ 记录弹窗（**2 个入口**：图谱详情卡、知识表格行） |
| 版本历史 / 恢复旧版本 | restore | ✅ 记录弹窗 |
| 软删除 | `POST /projects/{p}/delete` | ✅ 知识与历史 |
| 查重 | `POST /projects/{p}/resolve` | ✅ 三步向导 |
| 别名 | `POST /projects/{p}/aliases` | ✅ 三步向导 |
| 合并重复实体 | `POST /projects/{p}/merge` | ✅ 三步向导 |
| **撤销**（合并/删除） | `POST /projects/{p}/operations/{id}/undo` | ❌ **有接口，UI 无入口** |
| 快照 / 恢复快照 | `POST/GET /snapshots` | ✅ 快照/评测页 |
| 评测 · 导出 | `/evaluate` `/export` | ✅ |
| 子图 · 脑图 | `/subgraph` `/mindmap` | ✅ |

底层也扎实：`record_versions(recorded_at, superseded_at)` 双时态版本、`assertions`（引文 + 字符区间 + 来源文档版本）、
`fact_keys`（事实唯一化）、`merge_operations`（合并可撤销）。

**所以实例层不是"没建"，是"建好了但没地方管"。** 治理操作散在两个页面，全靠"点到一个才看得见"。
实例层缺的是**一个家**，不是能力。

### 3.2 知识台账（新页）

**一屏一问：**

> 「这里管**具体的东西**：查、改、并重复项、撤销误操作。**分类不在这** —— 要改类/属性/关系去本体编辑台。」

三个视角（页签）：**实体 / 关系 / 原文片段**

每行显示（**加粗的是现在拿不到、必须补的**）：

- 名称 + IRI
- **本体类型 + 挂在哪一版本体上** ← 现在只埋在技术 JSON 里，用户看不出"这条知识用的是老结构"
- 版本号 + 业务有效期（`valid_from` / `valid_to`）
- **断言数**（有几条原文在支撑它）← 决定"删了会不会丢证据"

每行操作：编辑 · 版本历史/恢复 · 合并重复项 · 软删除 · **撤销**（新接入口）

顶部一行四个可点数字：`128 个实体 · 42 条关系 · 3 个类型待定 · 12 组疑似重复`

### 3.3 实体要不要审批？——不要，但要把"可逆"做扎实

判据和结构层一致：**可逆的不审，不可逆的必审。**

| | 结构变更（本体） | 实例变更（实体/关系） |
|---|---|---|
| 影响面 | **全局**：改一个类，所有用它的知识和检索都变 | **局部**：改一条记录 |
| 可逆性 | 结构改动要过确认（不可逆的那类） | **可逆**：版本化 + restore + undo |
| 要不要审批 | 别人的请求要；本人的不可逆改动当场确认 | **不审批** |

给实体编辑加审批是**错的** —— 那会把日常纠错变成走流程，用户会绕过它去直接改 JSON。
正确做法是把三件事补齐：

| 该有的 | 现状 | 动作 |
|---|---|---|
| 留痕 | ✅ 版本历史 + `operations` | 保留 |
| 可回滚 | ⚠️ 接口有，**UI 点不到** | **补撤销入口** |
| 改之前给影响面 | ❌ 改一个实体的类型会不会破坏已有关系？没有提示 | 编辑弹窗里加一行影响面 |

边界文案现状已经写对了（`record-dialog.js:59`：「这里修改的是图谱中的一个实体，**不会修改本体类定义**。」）—— 保留。

## 4. 连接点规划（两个 0 命中的机制）

### 4.1 连接点①：待建模收件箱 + `结构待定`

**触发**：知识写入时抽出了本体里没有的概念。

**行为**：**不硬塞进本体**。把用到它的知识标 `结构待定`。

`结构待定` 的确切含义（用户要的"做什么 / 不做什么"）：

- **做**：可检索、可看原文、可被引用、能出现在实体脑图里
- **不做**：**不进正式答案的证据链**（问答引用它时必须显式标注"结构待定"）、不计入本体覆盖率、不能作为约束校验的输入

**收件箱放哪**：**本体审核台**（"要不要收进本体"是审别人的请求，符合 §核心判断）。

**收下之后**：`结构待定` 标记自动解除，那批知识完成一次受控重分类（连接点②的同一条代码路径）。

### 4.2 连接点②：受控重分类

**触发**：本体发布新版本，而旧版本仍有知识挂着。

**行为**：发布后提示 —— 「本次改动 3 个类；仍有 **128 条知识挂在 v3**」→ 可进入迁移面板。

迁移面板按类列出对照：`v3 的「包」 → v4 的「包裹」`，逐类确认或批量确认。

**三条硬约束**（缺一条就会变成灾难）：

1. **默认不跑** —— 不自动改任何数据
2. **不原地改** —— 每条迁移产生新版本（`record_versions` 多一行），旧版本仍在
3. **可回滚** —— 整批迁移写成一条 `merge_operations` 式记录，可一键撤销

**与停用类的关系**：本体编辑台停用一个类时要求"指定替代类或显式无替代"，
那个替代映射**就是**重分类的输入。所以这两件事共用一份数据，不重复问用户。

## 5. 消费层 / 运行层

### 消费层（检索 / 问答 / 脑图）

能力都在，缺的是**双向直达**：

- 图谱点节点 → 右侧详情卡「编辑这个实体」**已经在**了（`evidence-inspector.js:124`）
- 反向缺：**知识台账里点一个实体 → 跳到图谱里定位它**（现在只能重新检索）
- 问答的每条引用应该能一键跳到「原文数据源」的那一段（溯源抽屉已能跳，问答侧要接）

### 运行层（项目与运行）

纯粹是**合并 4 个页面**，不新建能力：项目管理 + 项目总览 + 后台任务 + 快照/评测。
一屏一问：「这里看**跑得怎么样**：任务、快照、评测、项目设置。」

## 7. 界面规则（E：不是一期，是每页都遵守的约束）

来自用户最原始的三句要求："界面不要一直是平铺的"、"要引导的提示来步骤"、"区域功能也要明确是干什么的"。

| 规则 | 现状反例（实测） |
|---|---|
| **一屏一问**：每页/每个阶段只有一个主问题 | 审核台一页同时有"收候选"和"逐项批准" |
| **一屏一个实心按钮** | 多处并列两个主按钮 |
| **长流水默认折叠 + 内部滚动** | 发现阶段中栏 5292px、整页 5721px、底栏按钮在 y=5634 |
| **首屏内容起点 ≤140px** | 实测 389px（页头 114 + 阶段条 60 + 状态条 60 + 黄条） |
| **区域标题写"用途"不写名词** | "对象与草案" → 应写"这里是这次要改的东西" |
| **字号下限 11px** | 全站实测 127 个节点 <11px（9px×69、10px×45、11px×13） |
| **默认折叠**：已完成的步骤显示结果摘要 | 阶段条全是展开的 |

**这些规则要随每一页的改动一起落地，不单独立期** —— 否则就会变成"先做一版再统一改一遍"，正是用户嫌烦的那种返工。

## 9. 风险与不可逆点

| 风险 | 说明 | 缓解 |
|---|---|---|
| **状态迁移 A3** | `ontology_drafts.status` 是 DB `CHECK` 约束（`0001_core.sql:343`），7 个枚举 | 迁移只改约束 + 数据映射；`published → 已收下`、`closed → 已驳回`；**先备份 + 在 `knowledge_test` 上演练** |
| **结构待定 C1** | 引入"什么不算正式证据"的新语义，会改变问答的证据链 | 先只做标记与显示，**不动问答的证据链**，观察一轮再改取证据逻辑 |
| **受控重分类 C2** ✅ | 批量改用户数据 | 默认不跑 / 不原地改 / 可回滚（三条硬约束）——三条**都已落成代码手段 + 界面文案**：空选 422、每条产生新版本、整批一条可撤销操作；干跑与写入共用 `service._timeline_check`（同一口径），真机复验 29 项全绿 |
