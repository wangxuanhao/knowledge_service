# 审核逻辑设计：知识输入 → 审核 → 发布

> 日期：2026-10-02
> 这份是 **A2（审核台收窄成收件箱）** 背后的逻辑设计，回答一个具体问题：
> **「从知识输入开始，一条请求到底怎么走到发布？」**
>
> 它不是新的三层/分期规划（那些在 `完整落地规划.md`、`本体流程再设计-按请求不按阶段.md`），
> 而是把「审核」这条主线抽出来，从第一步到发布一步不漏地写清楚 —— 因为用户关心的
> 正是「写进来之后，谁、在哪、凭什么把它收进本体」。

---

## 0. 一句话

> **审核 = 判断「别人的请求要不要收进本体」，不是「批准我自己改的结构」。**

进而把「审核」和「确认」两个词彻底分开（现在混用，是混乱的根）：

| 词 | 含义 | 用于 |
|---|---|---|
| **审核** | 决定*要不要做*（有人不同意就不做） | **别人的请求**（机器抽的候选、业务提的申请） |
| **确认** | 做*之前*看到代价（已经决定要做，让他看清影响面） | **本人的不可逆改动**（停用类、改类型、改父子）—— 不弹新页面、不进新流程，就地弹一次 |

---

## 1. 两个维度先分清

审核逻辑之所以乱，是因为没分清「谁在改」和「改了什么」。分清了，整条线就顺了。

### 1.1 谁在改（决定要不要审）

| 谁 | 角色 | 要不要审 |
|---|---|---|
| **本人** | 本体负责人，改自己的本体是他的职责 | **不审** |
| **机器** | 知识输入时的抽取，从文档里"发现"新概念 | **审**（收 / 不收） |
| **别人** | 业务方，主动提申请想改本体 | **审**（收 / 不收） |

### 1.2 改了什么（决定走哪条短路径，只对本人生效）

| 重量 | 改什么 | 保存后 |
|---|---|---|
| **标注** | 注释 / 别名 / 显示名 / 描述 / 示例 | 立即生效，版本号不变（修订日志 +1） |
| **新增** | 加类 / 加属性 / 加关系 / 加子类 | 立即生效，版本号 **+1** |
| **动已有的** | 停用类 / 改类型 / 改删父子 / 改 IRI | 保存时**就地弹确认**显示影响面，确认后立即生效，版本号 **+1** |

## 2. 完整流：知识输入 → 审核 → 发布

这是这份文档的核心。一条请求从进入系统到成为本体的一行，完整走一遍：

```
【知识输入】实例层 · 知识写入页
   上传文档 → 文档解析 → 抽取（entity / relation / attribute）
                    │
                    ▼
              产生「候选」
             ├── 本体里已经有这个概念 ──▶ 直接关联到知识（不构成请求，不进审核）
             ├── 本体里没有的新概念    ──▶ 变成「机器抽的候选」＝机器提的请求 ──┐
             └── 证据定位不到的异常    ──▶ 进异常区，人工另看（不是请求）      │
                                                                          │
【审核】结构层 · 本体审核台（收件箱，只剩一句问话：收 / 不收）              │
   ┌─ 机器抽的候选 ─ 收下 ─▶ 进本体（成为新版本）      ◀──────────────────────┘
   │              └─ 不收 ─▶ 驳回；用到它的知识标「结构待定」（C1：可检索、被引用时显式标注，不进证据链）
   └─ 业务提的申请 ─ 收下 ─▶ 进本体（成为新版本）
                  └─ 不收 ─▶ 驳回关闭
                                    │
                                    ▼
【发布】不再是菜单、不再是阶段 —— 是「收下」的结果
   本人改自己的本体： 保存 即 发布（编辑台）
   收下别人的请求：   收下 即 发布（审核台）
   本体只有版本号 v1..vN，「已发布」不是状态，是本体唯一的存在方式
```

三处要点（这是和现状最不一样的地方）：

1. **「发布」消融了。** 它不是一个可以独立去做的动作，而是「收下」或「保存」的结果。
   单独做一个「发布」菜单/阶段会空着（`按请求不按阶段.md` §6 已论证）。

2. **「写入」不在这条线的起点里越界。** 知识写入（文档→知识）是实例层的事，
   它产生的「候选」跨一层进入审核台收件箱，但知识写入本身**不是**审核的一站。
   现状把它和本体四阶段塞在同一页「发现」阶段，正是「三个轴挤一条阶段条」的证据。

3. **收下＝发布，且只产生一个版本。** 现在外部申请的 approve 实际只 `submit()`（不生成版本，
   代码 `api/ontology_changes.py:132`，文案曾经撒谎）。新模型里「收下」一步到底：进本体、版本 +1，没有第二次人工动作。

## 3. 状态模型：7 个 → 2 个（请求的）

现状草案有 7 个状态（`editing / submitted / reviewed / published / closed / stale_base / stale_source`，
DB CHECK 写死，`repository/migrations/0001_core.sql:343`）。新模型砍到只剩「请求」自己的状态：

| 对象 | 状态 | 说明 |
|---|---|---|
| **本体** | **无状态** | 只有版本号 v1..vN |
| **请求**（候选 / 申请） | **待处理 → 已收下 / 已驳回** | 外加一个例外：**需重新基线**（请求基于 v3，本体已到 v4） |

被删的 5 个状态去哪了：

| 旧状态 | 去向 |
|---|---|
| `editing` | 「编辑中」就是「你还没点保存」—— 纯前端，不需要服务端状态 |
| `submitted` | 只有别人的请求才需要「待处理」，本体的改动不排队 |
| `reviewed` | 同上，且它对「逐项批准」这一步才有意义 |
| `closed` | 请求被驳回就是「已驳回」，不设第二个词 |
| `stale_base` / `stale_source` | 合并成请求维度的「需重新基线」 |

> ⚠️ 这一步是 **A3**，要跑 `0005_*.sql` 迁移，不在 A2 里做。A2 只改前端 UI 与交互路径，
> 底层仍走「自动建草案 → 自审 → 发布」（`按请求不按阶段.md` §7 步 3 的要求：先只改 UI，状态机最后拆）。

## 4. 收件箱长什么样（A2 的产出物）

一屏一问，按「谁提的请求」分三格（不是按步骤分）：

| 分类 | 里面是什么 | 收下 = | 不收 = |
|---|---|---|---|
| **机器抽的候选** | 文档里抽出来的新概念，还不是本体 | 进本体（成为新版本） | 驳回；用到它的知识标「结构待定」 |
| **业务提的申请** | 别人要求改本体（只有这一类才叫「审核」） | 进本体（成为新版本） | 驳回并关闭 |
| **你自己的改动待确认** | 你自己改动里，系统不肯替你自动批准的项（高风险/需写理由） | 确认这条变更 | 撤掉这条变更 |

> 第三格是 A1「保存并生效」留下的收尾：可自动批准的已经发布了，剩下的高风险项必须有人逐条确认。
> 它严格说不是「别人的请求」，所以在设计里**单独成格**、措辞用「确认/撤掉」而非「收/不收」，
> 避免和「审核」这个词再混。

每一项都写清「收下 / 不收各会怎样」—— 这是收件箱唯一的解释责任。

## 5. 现状 → 目标 对照（一张表看到全部变化）

| 维度 | 现在 | 改成 |
|---|---|---|
| 入口 | 4 站阶段条（发现→设计→审核→发布） | 收件箱（按「谁提的」分 3 格，无阶段） |
| 状态 | 草案 7 状态 | 请求 2 状态；本体无状态 |
| 审核对象 | 混两件：收候选 + 批自己的改动 | 只收「别人的请求」 |
| 发布 | 2 个发布按钮（设计台 + 审核台） | 「保存/收下」的结果，无独立按钮 |
| 改注释 | 走 4 步、且产生新版本 | 编辑台改字 + 保存（1 步，版本不变） |
| 外部申请 | 点「批准」实际只 submit（文案撒谎） | 收下＝进本体、版本 +1（一步到底） |

## 6. 分步落地（A2 三步）

| 步 | 做什么 | 风险 |
|---|---|---|
| A2-a | 阶段条换成「来源分类条」：三格 + 每格数量 + 收下/不收文案 | 低（样式 + 入口重组，机件不动） |
| A2-b | 动作收敛成「收下 / 不收」，把「逐项批准」包装成「收下」 | 低 |
| A2-c | 删掉 design / publish 视图（它们属于编辑台/档案） | 中（删机器，连带测试） |

**与 A3 的边界：** A2 只改「UI 与交互路径」，状态机（7→2/3）留给 A3 迁移。
这样 A2 可以立刻上线、被用户感知，又不碰数据模型。

## 7. 怎么验证（不靠「应该是这样」）

- 真机走三遍：① 收一个机器候选 → 断言本体版本 +1、知识未标结构待定；
  ② 拒一个候选 → 断言被标「结构待定」、问答引用时显式标注（C1 后验）；
  ③ 收一个业务申请 → 断言只产生一个版本、无「生成本体版本」这类撒谎文案。
- 每一格都读「收下 / 不收」的标题和回执，确认话是真的。
- 跑全量 `python -m pytest -q`（不 `source .env`）。
