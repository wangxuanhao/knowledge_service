# 本体治理整体设计（v2 / 从头设计，不迁就现有结构）

> 日期：2026-10-02
> 起因（用户原话）：
> **"整体的流程呢，具体从知识写入开始，后续的审核，设计，校验，哪些能够合并，哪些必须分开，这块环节设计好……界面不要一直是平铺的，区域功能也要明确是干什么的，现在是都展开，这个给人看太累了，要引导的提示来步骤。让傻子都会用。然后上线一个版本后，版本怎么再优化调整，新的知识再次写入如何审批呢。你可以不参考现在的架构来，整体进行设计。"**
>
> 本文只做设计，不改代码（除已落地的 P0 门禁修复）。所有"现状"陈述都来自真机 / 代码实测。

---

## 0. 一句话结论

**四个环节 + 一个横切能力 + 一个账本。**

```
① 写入  →   ② 建模   →   ③ 审核   →   ④ 发布
（采集）   （发现+设计）  （逐条决定）  （不可逆记账）

        校验 ＝ 横切能力（两边都能随时调，不是一环）
        档案 ＝ 只读账本（不是一环，是一个视图）
```

- 合并掉的：现在的「发现」和「设计」**合成「建模」**。
- 拆掉假阶段的：现在的「校验」**不是环节**，是一项随时可跑的能力 + 两道门禁（提交前、发布前）。
- 合并界面的：现在的「审核」和「发布」**不是两个并列阶段**，是同一页的两步（决定完 → 底部出现发布）。
- 保留不变的核心不变量：**正式本体只能经「草案 → 逐项决定 → 不可变版本」进入，没有第二条写入口。**

---

## 1. 判据：什么能合并，什么必须分开

不看名词，看三条**必须分开**的条件（满足任意一条就不能合）：

| # | 判据 | 说明 |
|---|---|---|
| M1 | **署名不同** | 谁为这件事负责。合并 = 既当运动员又当裁判 |
| M2 | **可逆性不同** | 能反复改的动作，和不可逆的动作，绝不能是同一个按钮 |
| M3 | **失败代价不同** | 改错了最多重画 vs 发错了影响全部检索与问答 |

三条**可以合并**的条件（全满足才合）：

| # | 判据 | 说明 |
|---|---|---|
| C1 | 输入相同 | 同一个东西进来的两种看法 |
| C2 | 心态相同 | 都是"我要创造"或都是"我在评判"，不能一创造一评判 |
| C3 | 中间产物不需要被别人看 | 没有交接点要留档 |

### 逐项判决

| 候选 | 判决 | 依据 |
|---|---|---|
| 发现候选 ＋ 设计 | **合并成「建模」** | C1 输入都是候选术语；C2 都是"我要什么本体"（创造心态）；C3 草案是私产，不需要别人看。现在分开导致"审核台先说要设计，再让设计台设计" |
| 校验 ＋ 设计 | **不能做成阶段，要拆成能力** | 校验是**机器判定**，不是人的动作。做成阶段 = 让用户手动点一下机器。做成能力后：建模时调它看影响面，审核时调它拿结论 |
| 校验 ＋ 审核 | **必须分开** | M3 不同。校验答"**能不能**"，审核答"**要不要**"。机器说能，人也完全可以不要 |
| 审核 ＋ 发布 | **动作必须分开，界面必须合并** | M2：审核可反复、可部分批准、可要求调整；发布不可逆。但现在把它们做成两个并列阶段卡，用户以为要用两次导航 —— 界面该合并成一页两步 |
| 知识写入 ＋ 发现 | **不能合并，但要串成自动流水** | C1 不满足（数据 vs 结构）。但用户不该知道"发现"这个动作存在，写入后自动跑 |

**结论**：4 个环节，不是现在的 5 个阶段；校验从"一环"降为"一能力"。

## 2. 四个环节逐个设计

### ① 写入（采集）

| | |
|---|---|
| **一屏一个问题** | 「把资料变成知识」 |
| **输入** | 上传文档 / 粘贴正文 / API 批量记录 |
| **动作** | 解析 → 切片 → 抽取 → **按当前本体校验** → 落库 |
| **产出** | **三种结果，必须分开显示**（这是整个审批模型的根） |
| **出口** | 自动进入 ② 的收件箱，不需要用户点任何导航 |

产出三分：

| 结果 | 判据 | 去向 | 要不要审批 |
|---|---|---|---|
| **直通** | 用到的类/关系/属性**全在当前本体里** | 直接成为正式知识 | **不要**。它只是填表 |
| **待建模** | 出现了**本体里没有的概念** | 进「建模收件箱」，同时这条知识标 `结构待定` | 要，但审的是**结构**，不是数据 |
| **待修正** | 违反 SHACL（值域/基数/必填） | 进「待修正」队列 | 不要，这是数据问题，不改本体 |

### ② 建模（发现候选 ＋ 设计 合并）

| | |
|---|---|
| **一屏一个问题** | 「新出现的这些概念，**要不要进本体**；进来的话，放在哪一层」 |
| **输入** | 收件箱（待建模候选 + 变更建议）＋ 当前已发布版本 |
| **动作** | 逐条「纳入草案」（自动带父类/domain·range 建议）→ 在画布上调整层级与约束 → 随时点校验看影响面 |
| **产出** | 一份**冻结的草案**（带修订号 + 校验指纹） |
| **出口** | **提交审核**（唯一出口）。提交前强制校验，校验不过不给提交 |
| **不做** | 不发布（M2）；不看已发布版本的历史与 Diff（那是账本） |

关键设计：**「发现」不算一步**。候选是自动来的（写入后自动跑），人只做"纳入还是不纳入"这一个判断。

### ③ 审核

| | |
|---|---|
| **一屏一个问题** | 「这 **N** 条变更，逐条决定：批准、拒绝，还是要求调整」 |
| **输入** | 冻结的草案 + 每条的来源证据 |
| **动作** | 逐条决定；低/中风险、无警告、不需写理由的可以一键批准 |
| **产出** | 全部决定完的草案 |
| **出口** | **底部出现唯一的「发布为 vN+1」按钮** |
| **不做** | 不改结构（改结构是 ② 的事）；不改已发布版本 |

一键批准的口径必须写在按钮旁边（用户反复追问过）：
**只覆盖低/中风险、无警告、无需写理由的变更；高风险与被阻断的必须逐条看。**

### ④ 发布

**不是一页，是一个动作 + 一个确认框。**

确认框里写清四件事：版本号、变更条数（批准 X / 拒绝 Y）、校验指纹、影响面（多少条知识会用到新结构）。
确认后才产生不可变版本 —— M2 要求它必须是独立的、显式的、不可撤销的一步。

### ⑤ 账本（本体档案，不是环节）

版本列表 / 任选两版对比 / 发布记录 / Turtle 只读 / SPARQL。
唯一写操作：**基于某版本新建草案 → 回到 ②**。

## 3. 校验为什么不是环节

现在的「校验」是一个并列阶段卡，用户要走过去点一下机器。这是设计错误。

校验的真实形态：

```
                 ┌───────────────────┐
   ② 建模  ──────▶│  校验（能力）     │◀────── ③ 审核
   随时点，看影响面 │  图完整性         │        自动带上结论
                 │  新写入约束        │
                 │  历史数据影响      │
                 └───────────────────┘
```

- **两道强制门禁**（不通过就走不过去）：提交审核前、发布前。
- **其余时候是按钮**：建模时点一下看"我这一改会波及多少知识"。

界面上它表现为**一行结论**：`校验通过 · 无阻断 · 3 条提醒（点开看）`，而不是一整页。

## 4. 版本上线之后：怎么继续演进

发布 vN+1 之后进入**运行期**。运行期只有三种输入，三套走法，互不干扰：

| 输入 | 谁发起 | 走法 | 会阻塞什么 |
|---|---|---|---|
| **结构要改**（加类 / 改父类 / 停用类） | 人 | ②→③→④ → vN+2 | 不阻塞新知识写入 |
| **新知识进来** | 系统自动 | 直通部分立即落库；新概念进收件箱 | **不阻塞已有知识**（旧知识照常可查可检索） |
| **存量知识要跟着新结构走** | 人 | **受控重分类**（新能力，现在完全没有） | 不阻塞任何东西，默认不跑 |

### 4.1 受控重分类（新增能力，现在是空白）

实测确认：现在**发布新版本后，已入库知识不会按新本体重分类**（全库 grep 无此能力）。
旧知识挂在它写入时的 `ontology_id` 上，这是对的（双时态的本意），但**缺一个"我要重跑"的入口**。

设计：

- **触发点**：发布 vN+1 后，建模页/账本页出现一行提示
  > 「vN+1 改动了 3 个类（新增 2、停用 1）。仍有 128 条知识挂在 vN。**[按新结构重新分类]** / 暂时不改」
- **点开先给影响面**：哪些知识会改、改成什么（重指向新父类 / 替代类）、有多少条会失败（找不到替代类）。
- **跑法不原地改**：产出一份**知识修订**（新版本号），可回滚 —— 和"改本体不可逆、改知识可回滚"的方向一致。
- **默认不自动跑**：旧结构上的知识继续可查。这是双时态的价值，不要替用户做决定。

### 4.2 停用类必须有替代指引

现在停用（`retire_term`）只是个开关，没有"停用后原来用它的知识怎么办"。

设计：停用「优惠方式」时**必须**二选一 ——

- 指定替代类「优惠形式」→ 重分类时把存量知识重指向替代类；
- 显式选「无替代」→ 那部分知识标为"结构已停用"，可查但不再参与新推理。

不允许"什么都不选"就停用。

## 5. 新知识再次写入，如何审批

**一句话：知识不审批，只有"新概念"审批。**

| 新知识的情况 | 是否审批 | 理由 |
|---|---|---|
| 用到的类/关系/属性**都在本体里** | **不审批，直接落库** | 它是在填一张已经批准过的表。审批数据等于审批"用户打了几个字"，没有意义 |
| 引入了本体里**没有的概念** | **审批，但审的是"这个概念要不要进本体"** | 这本质是一次结构变更，走 ②→③→④ |
| 违反了约束（值域/基数） | **不审批，进「待修正」** | 这是数据质量问题（错填、错抽），不是本体该不该改的问题 |

**关键改进**：在新概念被批准之前，用到它的知识标 `结构待定` ——

- 可以检索、可以看原文、
- **不进正式答案的证据链**（知识问答不会拿一个类型还没有定论的东西当依据），
- 一旦对应的本体变更发布，自动转正。

这消灭了现在的混合状态：知识已经进库、类还没定、检索到的东西挂在一个临时类型上，没人说得清算不算正式。

## 6. 界面：从"平铺全展开"改成"引导式单步"

用户原话：**"界面不要一直是平铺的，区域功能也要明确是干什么的，现在是都展开，这个给人看太累了，要引导的提示来步骤。让傻子都会用。"**

### 6.1 七条硬规则

1. **一屏只有一个问题**。顶栏一行大字，内容就是"你现在要做什么"，不是模块名。
2. **一屏只有一个主按钮**（唯一实心色）。其余动作全部降级为文字按钮。
3. **进度条代替阶段条**。4 步：已完成步显示**结果摘要**（可点开回看），当前步高亮，未到步只显示名字。
4. **默认折叠**。凡是不在当前步的内容，一律折成一行摘要，不展开。
5. **区域标题写用途，不写名词**：

   | ❌ 现在 | ✅ 目标 |
   |---|---|
   | 候选术语整理 | 从知识里长出来的新概念 —— 决定要不要进本体 |
   | 发现队列 | 待建模（N 条）：每一条都会变成草案里的一条变更 |
   | 变更队列 | 这批变更，逐条决定批准还是拒绝 |
   | 检查器 | 选中对象的详情与来源（只读） |
   | 本体结构维护 | 改结构请去「本体建模」 |

6. **空态必须给下一步动作**，不留空白页。
7. **不可逆动作二段确认**，确认框里写清"会发生什么"，而不是写"确认吗？"。

### 6.2 首屏预算（实测现在浪费了 41%）

| 区块 | 现在（实测） | 目标 |
|---|---|---|
| 页头横幅 | y=59 起、高 **114px**、内容是营销标语 | **高 ≤ 56px**，内容换成上下文（项目 · 版本 · 草案 · 第几步） |
| 阶段条 | y=201、高 60px，5 个等高卡片，全亮或全灰 | **进度条 ≤ 52px**，一眼看出"在第几步、还差几步" |
| 提示条 + 状态条 | 两条说同一件事，共 ~130px | **合并成一条 ≤ 44px** |
| **正文起点** | **y = 389px** | **y ≤ 140px** |

### 6.3 四个入口的最终形态

| 页 | 一屏的问题 | 主按钮 | 其余内容 |
|---|---|---|---|
| **知识写入** | 把资料变成知识 | 上传并处理 | 结果三分栏（直通 N / 待建模 M / 待修正 K）；解析高级设置默认折叠 |
| **本体建模** | 新出现的概念要不要进本体 | 提交审核 | 左＝收件箱，中＝草案画布，右＝只读详情；校验结论一行 |
| **本体审核** | 这 N 条变更批准还是拒绝 | 发布为 vN+1（全部决定完才出现） | 列表 + 每条的来源证据（折叠） |
| **本体档案** | 本体现在长什么样、怎么变成这样的 | —（只读） | 版本对比默认折叠，展开才看 |

## 7. 现存的三条写入口（必须收敛成一条）

真机 + 代码实测，现在**有三条**能改变正式本体的路径，而设计文档只承认一条：

| # | 路径 | 位置 | 问题 |
|---|---|---|---|
| 1 | 草案 → 逐项决定 → 发布 | 审核台五阶段 | ✅ 唯一合规路径 |
| 2 | 设计台「提交并自审」→ **直接 `POST /publish`** | `ontology-design.js:1305` | 绕过审核台。文档 §8 验收标准 4 明确禁止 |
| 3 | 变更建议「批准并生成本体版本」 | `ontology-workbench.js:1422`，按钮文案见下 | **按钮说的话和实际做的事不一致** |

第 3 条的实测细节：

- 提议创建时**自动新建一个草案**（`api/ontology_changes.py:63`，`source_kind='candidate'`）；
- 点「批准」实际执行的是 `governed.submit(...)`（`:132`）—— 只是**提交进待审核**；
- 但按钮写着 **"批准并生成本体版本"**，成功后前端提示 **"本体变更已批准并生成新版本。"**
- **它没有生成本体版本。** 用户以为发布了，实际停在待审核 —— 最坏的一类不一致：文案撒谎。

**收敛方案**：

- 路径 2：保留「提交并自审」，但**去掉它内部的 publish 调用**，只做到"停在审核台"。发布永远只有一处。
- 路径 3：按钮文案改成「纳入草案并提交审核」，成功后提示"已提交审核，去「本体审核」逐条决定"。或者更好——**变更建议不再单独开草案**，而是**并入建模收件箱**，和候选术语一起排队（第 ② 条的收件箱本来就该是唯一的入口）。

## 8. 与现有实现的映射（哪些能复用）

| 新设计 | 现有资产 | 处理 |
|---|---|---|
| ① 写入 | `document_uploads / chunking / semantica_adapter` | **直接复用**，只加"结果三分栏"的判定与标记 |
| ② 建模 | `ontology-design.js`（1335 行）＋ 审核台的发现阶段 | 设计台**升格为主页**；把发现队列、变更建议并进来；审核台的「发现」「设计」阶段下线 |
| 校验（能力） | `ontology_drafts.validate()` + `validation_report` | **直接复用**，只把它从"一页"改成"一行 + 按钮" |
| ③ 审核 | 审核台的「审核」阶段（`review-plan` / `decisions` / `batch-approve`） | **直接复用**，只把「发布」并进同一页 |
| ④ 发布 | `publish_preflight` / `publish` | **直接复用**，改成审核页底部的动作 + 确认框 |
| ⑤ 账本 | `ontology-archive.js`（498 行） | **直接复用** |
| 阶段门禁 | `stage_state()`（服务端唯一判据） | **直接复用**，把 5 阶段改判 4 环节 |
| 受控重分类 | 无 | **新做**（本文 §4.1） |
| 停用替代指引 | `retire_term` 只有开关 | **扩字段 + 重分类时消费** |

**代价评估**：② 是唯一的大改（合并两页、下线审核台的两个阶段），其余都是"挪位置 + 改文案 + 加一个能力"。

## 9. 分期实施

| 期 | 内容 | 直击用户哪句话 | 风险 |
|---|---|---|---|
| **P0 ✅ 已做** | 终态草案门禁不再撒谎 | "环节的流程上有冲突" | 已全量测试通过 |
| **P1** | 三入口收敛：路径 2 去掉 publish、路径 3 文案与行为对齐（或并入收件箱） | "流程冲突" | 低（两处 JS + 契约测试） |
| **P2** | 界面引导化：进度条代替阶段条、一屏一问、默认折叠、区域标题写用途、首屏预算 ≤140px | "平铺太累、要引导步骤、让傻子都会用" | 中（纯前端） |
| **P3** | 环节合并：② = 发现 + 设计合到设计台；审核台只留 审核 + 发布（一页两步） | "哪些能合并、哪些必须分开" | 中高（动阶段门禁与 4 条契约测试） |
| **P4** | 新能力：写入结果三分栏 + `结构待定` 标记 + 受控重分类 + 停用替代指引 | "上线一个版本后怎么优化调整、新知识怎么写如何审批" | 高（新数据字段 + 迁移） |

**建议顺序：P1 → P2 → P3 → P4。** P1/P2 用户当天就能看到差别；P3 是流程的真正修复，P4 是新能力。

## 10. 明确不做

- 不做版本回滚（历史版本不可变）；要回旧结构只能基于旧版本新建草案。
- 不做物理删除术语（只有停用 + 替代指引）。
- 不做绕过的第二个写入口（本文 §7 的收敛就是删掉多余的两个）。
- 不做多人实时协同编辑。
- 不为了改观感引入前端框架（现有令牌层够用）。
- **不自动跑存量重分类** —— 默认保持旧知识可查，由用户显式发起。
