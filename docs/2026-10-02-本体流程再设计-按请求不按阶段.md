# 本体流程再设计：按「谁的改动」分，不按「走到第几步」分

> 日期：2026-10-02
> 触发（用户原话）：
> **「本体设计台是为了改当前已发布的部分，那么能不能单独把写入，审核，发布，设计(编辑) 这些分别做在不同的菜单，
> 然后不同的环节管理下对应的状态，实现流程呢，还是说你现在的设计更合理呢……我对当前的理解，是本体的设计台
> 就是修改当前版本的，然后直接就修改了，不需要审核，修改人直接改就行了，然后本体审核台同步修改的数据还是怎么，
> 感觉现在为了展示状态已经混乱了，你可以重新设计流程和状态，不考虑当前的设计。」**
>
> 本文不迁就现有结构。但不靠猜：§2 的两条事实是从代码和迁移文件里读出来的。

---

## 1. 诊断：一条阶段条上挤了三个互不相干的轴

现状的「发现 → 设计 → 审核 → 发布」把三件事画成了一条流水线：

| 轴 | 内容 | 它真正是什么 |
|---|---|---|
| **数据状态** | editing / submitted / reviewed / published / closed / stale_base / stale_source | 一条记录的**生命周期**（7 个状态，DB CHECK 约束写死） |
| **工作流** | 发现 → 设计 → 审核 → 发布 | 一个人**要做的动作** |
| **来源** | 文档抽取 / 人工手改 / 外部申请 | 改动**从哪来** |

挤在一起就产生四种病，全都能在真机上看到：

1. **改个注释要过四步**：进设计 → 提交审核 → 逐项批准 → 发布。
2. **审核台上两件无关的事并排**：左边是"机器从文档里抽出来的新概念，要不要收"，右边是"我要批准我自己刚改的结构"。
   这两件事的**决策人、风险、频率完全不同**，却共用一条状态条。
3. **两个家**：设计台的「提交并自审」能发布，审核台也能发布。
4. **状态文案越写越多**：因为每扇门都得解释"为什么锁着、下一步去哪"，而锁的原因来自三个轴的交集 —— 解释是症状，不是病。

**用户要的"分菜单"方向对，但分错了轴。** 见 §4。

## 2. 两条事实（读代码得出，决定了设计的可行边界）

### 2.1 「直接改」已经存在，只是被埋了

`knowledge_service/web/ontology-design.js:8` 的注释：

```
- 不发布。发布是「本体审核台」的动作；这里只有"提交审核"和（单人场景）"提交并自审"。
```

`提交并自审`（`:1252` 起）的实际行为：自动批准所有**可自动批准**的变更 → 直接 `POST /publish` → 回执
"走的是'提交并自审'通道（跳过他人复核，操作人、时间与理由已留痕）"；**但高风险与需写理由的变更仍会拦住它**
（"已批准 N 条，还有 M 条需要逐条处理…已停在审核台"）。

所以"修改人直接改就行"**技术上早就通了**，缺的不是能力，是**它被命名成"自审"、放在次要按钮上、而且只覆盖可自动批准的那部分**。

### 2.2 两个硬约束

| 约束 | 出处 | 后果 |
|---|---|---|
| 本体版本存的是**整份 turtle**（`ontologies(turtle text)`） | `repository/migrations/0001_core.sql:106` | 改一条注释**就是**改了图 → 指纹变 → 必然产生新版本。"标注不递增版本号"需要动存储 |
| 草案状态是 **DB CHECK 约束**，7 个枚举写死 | `0001_core.sql:343` | 状态从 7 个减到 2–3 个必须走迁移（`0004_*.sql`），不是改代码就行 |

## 3. 关键判断：审核的对象是**请求**，不是**改动**

这是整个重设计的一句话。

| | 谁在改 | 要不要人把关 |
|---|---|---|
| **我**（本体负责人）改我的本体 | 本人 | **不要**。这是他的职责，不是需要第三方的审批 |
| **别人**（业务方 / 机器抽取）想改我的本体 | 非本人 | **要**。这才是"审核"存在的理由 |

现状把这两件事做成同一条流水线，于是本体负责人被自己的系统当成"需要被审核的人" ——
**这就是"为了展示状态而混乱"的根**。

顺带把"审核"和"确认"分开，这两个词现状混用：

- **审核** = 决定*要不要*做（有人不同意就不做）→ 只用于**别人的请求**
- **确认** = 做*之前*看到代价（已经决定要做，只是让他看清影响面）→ 用于**本人做的不可逆改动**

不可逆改动的把关是**确认**，不是**审核** —— 不弹新页面、不进新流程，就在原地弹一次。

## 4. 新设计

### 4.1 菜单：结构层 3 个（不是 4 个）

```
① 本体编辑台   打开就是当前正式本体（v3），像编辑文档一样改 → 保存即生效
② 本体审核台   只放**不是你自己改的东西**：机器抽的候选、业务提的申请 → 收 / 不收
③ 本体档案     只读账本：版本、Diff、Turtle、SPARQL
```

**「发布」不再是一个菜单，也不再是一个阶段。** 保存就是发布；审核台里点"收下"也是发布 ——
它是动作的**结果**，不是流水线的一站。把它做成菜单只会空着。

**「写入」不在这三个里。** 知识写入是把文档变成知识，属**实例层**（知识台账/原文数据源）。
现状把它和本体四阶段放在同一页的"发现"阶段 —— 这正是"三个轴挤一条阶段条"最刺眼的证据：
用户在审核本体结构的地方看到"知识写入"的入口。

### 4.2 唯一的规则：按**改动重量**分流

编辑台保存时（而不是进某个阶段时）判定：

| 重量 | 改什么 | 保存后 | 版本 |
|---|---|---|---|
| **标注** | 注释、别名、显示名、描述、示例 | **立即生效**，只记一条修订（谁/何时/改了什么） | 不变（v3 仍是 v3，修订号 +1） |
| **新增** | 加类、加属性、加关系、加子类 | **立即生效**，署名 + 理由留痕 | **+1 → v4** |
| **动已有的** | 停用类、改属性类型、改/删已发布父子关系、改已发布类的 IRI | 保存时**原地弹确认**：<br>「停用「包」会让 12 条知识指向一个停用的类。替代类：[选一个 ▾] / [显式无替代]」<br>确认后**立即生效** | **+1 → v4** |

**用户要学的只有一句：**

> **标注随便改；加东西直接生效；动已有的结构，改的时候当场确认影响面。**

这句话同时回答了"它做什么、不做什么"：

- 它**不做**：不把你拦在审核队列里（你是本体负责人，不是"要改我的本体的人"）
- 它**做**：不可逆的改动必须当场看见影响面才能提交；每次改动署名 + 理由；任一版本可回滚

### 4.3 状态：7 个 → 2 个

| 对象 | 状态 | 说明 |
|---|---|---|
| **本体** | **没有状态** | 只有版本号 v1..vN。「已发布」不是状态，是它唯一的存在方式 |
| **请求**（别人提的） | **待处理 / 已收下 / 已驳回** | 外加一个**需重新基线**：请求基于 v3，而现在已经是 v4 |

被删掉的 4 个状态及其理由：

| 旧状态 | 为什么可以删 |
|---|---|
| `editing`（草案编辑中） | 编辑台直接对当前版本动手，"编辑中"就是"你还没点保存"——**纯前端**，不需要服务端状态 |
| `submitted`（待审核） | 只有**别人的请求**才需要"待处理"，本体的改动不需要排队 |
| `reviewed`（已审核） | 同上；而且它和 `submitted` 的区分只对"逐项批准"这一步有意义 |
| `closed`（已关闭） | 请求被驳回就是 `已驳回`，不需要两个词 |

### 4.4 版本模型：把"标注"从版本号里解耦

这是 §2.2 那条约束的解药，也是"改注释不该变成 v4"的前提。

```
本体 v3
 ├─ 结构（类 / 属性 / 关系 / 父子）────── 变了 → v4        （进档案页的版本列表）
 └─ 标注（注释 / 别名 / 显示名 / 描述）── 变了 → v3.修订N   （只进修订日志，不占版本号）
```

为什么可以这样做：**标注不参与推理**。它不改变任何一条知识的语义、不影响约束校验、不影响检索命中的实体。
而溯源抽屉里冻结的是**当时的标注快照**，所以"当年那个答案引用的注释"依然可复现 —— 不会因为后来改了措辞而失真。

档案页的 Diff 相应地分成两栏：**结构变化 / 标注变化**。现在它们混在一个 Diff 里，
用户看到"版本变了"却分不清"是加了个类，还是只改了个错别字"。

## 5. 走一遍：四个场景

| 场景 | 旧流程 | 新流程 |
|---|---|---|
| 改一个类的注释写错了 | 设计 → 提交审核 → 逐项批准 → 发布（4 步，且产生新版本号） | 编辑台改字 → **保存**（1 步，v3 仍是 v3，修订日志 +1） |
| 加一个新属性 | 同上 4 步 | 编辑台 + 保存 → **v4**（1 步） |
| 停用一个过时的类 | 同上 4 步，且没人提醒"12 条知识会指向停用的类" | 编辑台点停用 → **原地弹确认并显示 12 条受影响知识** → 指定替代类 → 保存 → **v4** |
| 业务方说"我们要加个封禁期限属性" | 外部申请 → 审核台「批准并生成本体版本」（**文案撒谎**，实际只 submit） | 申请出现在**审核台收件箱** → 收下 → **直接成为 v4**（不生成第二个版本） |
| 文档里抽出了新概念 | 混在"发现"阶段，和本体结构编辑共用一页 | 出现在**审核台收件箱**（机器提出来的）→ 收 / 不收；没收之前，用到它的知识标 **`结构待定`**（可检索、不进正式答案的证据链） |

## 6. 为什么不按"写入/设计/审核/发布 四个菜单"分

用户的第一直觉是这么分。诚实说为什么不行：

1. **那是把一条流水线的四段做成四个菜单** —— 用户得知晓"我的改动现在走到哪一段了"，
   改一次要跨四个菜单点。**比现在更累**，只是把病摊得更散。
2. **"发布"分出来会空掉** —— 保存即发布，没有独立的第 4 步可做。
3. **"写入"不属于这一层** —— 它是实例层的事（文档 → 知识）。现状把它放进本体阶段条，
   本身就是混乱的一部分。
4. **按流程分段 vs 按对象分页**：四段式回答的是"系统内部怎么流转"，用户关心的是
   **"我手上这个东西要改，去哪、按什么按钮"**。菜单应该照后者分。

正确的分层轴是 **谁在做（我 / 别人）× 改的是什么（标注 / 新增 / 动已有的）**——
菜单按"谁"分（3 个），流程按"改什么"定（1 条规则）。

## 7. 要动什么、风险多大（诚实）

| 要动的东西 | 为什么必须动 | 风险 |
|---|---|---|
| **标注与结构分开计量** | §4.4；否则改注释也产生版本号 | **最高**。两条路：① 拆存储（结构图 + 标注表，各自指纹）；② 允许 `ontologies` 行原地更新 + 独立修订日志。<br>推荐 ②：改动小、Diff 逻辑不用重写；代价是 `ontologies` 不再是严格不可变 —— 所以**结构**的不可变性必须由修订日志配合保证（结构一改就换新行，只有标注允许原地改） |
| `ontology_drafts.status` 的 CHECK（7 个枚举） | §4.3（7 → 2–3） | 中：需要 `0004_*.sql` 迁移；表形状不变，只改约束 + 数据映射（`editing/submitted/reviewed → 待处理`，`closed → 已驳回`，`published → 已收下`） |
| 编辑台从"对草案动手"改成"对当前版本动手" | 现在没草案时只能只读预览，改不了 | 中：**先只改 UI 与交互路径**，底层仍走"自动建草案 → 自审 → 发布"，把状态机放到最后再拆 |
| 后端 `stage_state()` 整套门禁 | 阶段没了 | 低：判据只有一个出处（`services/ontology_drafts.py`），删比改容易 |
| 审核台收窄成收件箱 | §4.1 | 中：候选与外部申请两套列表要合并成一种"请求"的呈现 |

### 实施顺序（从"立刻能感知"到"动数据模型"）

| 步 | 做什么 | 用户什么时候能感觉到 | 风险 |
|---|---|---|---|
| **1** | 编辑台：把「提交并自审」提成主按钮、改名「**保存并生效**」，标题写明"跳过他人复核，署名与理由留痕" | **立刻** —— "直接改"从隐蔽变显眼 | 低（纯文案+位置） |
| **2** | 编辑台：不可逆改动（停用/改类型/改父子）保存时就地弹确认，**显示受影响知识条数 + 要求指定替代类** | 立刻 —— 从"发送到别处审核"变成"当场看到代价" | 低（前端 + 复用现有 impact 接口） |
| **3** | 审核台：阶段条拆掉，改成**收件箱**（候选 + 外部申请），只剩 收下 / 不收 | 立刻 —— 一页一件事 | 中（前端重写） |
| **4** | 标注/结构分开计量（§7 第 1 行） | 改注释不再产生新版本号 | **高**（动存储） |
| **5** | 状态 7 → 3 + 迁移 | 几乎无感（状态不再被用户看见就是胜利） | 中（迁移） |

**步 1–3 是纯前端 + 文案，可以立刻开始并逐项验证；步 4–5 动数据模型，单独排期。**

---

## 8. 一句话总结

> 现在这条阶段条有 **4 站**、**7 个状态**、**3 个入口**、**2 个发布按钮**，用户的问题是照它来的。
> 新设计是 **3 个菜单**、**2 个状态**、**1 条规则**（标注随便改 / 加东西直接生效 / 动已有的当场确认）、
> **0 个阶段** —— 因为"发布"是保存的结果，不是流水线的一站；
> 而"审核"只对着**别人的请求**，不对着本体负责人自己的改动。
