# 本体流程重构与界面重设计

> 日期：2026-10-02
> 触发反馈（用户原话）：**"从知识写入到本体设计，本体审核工作台，到本体档案，你看下如何设计下呢，感觉现在多个环节的流程上有冲突，页面展示的也很丑陋"**
> 取证方式：真机（`http://127.0.0.1:8000` + 本机 Edge headless）逐页截图 + DOM 几何读数 + 接口读数，
> 项目 `1001_开放`（`92b18226-50dc-49d8-abed-d67bc092b659`，2 个已发布版本、25 实体 / 30 关系、草案 52 条变更）。
> 本文所有数字都是实测值，不是估计。

---

## 0. 结论先说

现在的五个环节**能力上不重叠、归属上全是重叠的**：

| 能力 | 现在有几个入口 | 应该有几个入口 |
|---|---|---|
| 设计本体（新增类/改父类/domain·range） | **2**：本体设计台 ＋ 本体审核台「设计」阶段 | 1 |
| 发布正式版本 | **2**：本体审核台「发布」阶段 ＋ 本体设计台「提交并自审」 | 1 |
| 从知识生成候选草案 | 1（审核台「发现」） | 1（但归属放错页了） |
| 回看已发布版本 | 1（本体档案） | 1 ✅ |

**不是流程画错了，是每个能力长了两个家。** 用户点哪个都对，所以"感觉有冲突"。

界面问题同样实测可量化：

- 首屏 **389px**（视口 950px 的 41%）被"页头横幅 + 阶段条 + 提示条 + 状态条"吃掉，正文从 y=389 才开始。
- 发现阶段整页高 **5721px**，而底栏主操作按钮在 **y=5634** —— 要滚 5.9 屏才够得到。
- 同一个页面在发现阶段是**两栏**、其它阶段是**三栏**（中栏从 5292px 变到 571px）。
- 字号碎到 **小于 11px 的文字节点有 127 个**（9px × 69、10px × 45、11px × 13）。

## 1. 流程冲突：四条，每条都有实测证据

### 冲突 ①：「设计」有两个家

| 家 | 证据 |
|---|---|
| 独立页「本体设计台」 | `ontology-design.js`（1335 行），`[data-tab='ontology-design']` |
| 「本体审核台」阶段 2「设计」 | `ontology-workbench.js:19` 阶段表 `['design','2','设计','画布与层级']`；`:958` `＋ 在画布上新增类`；`:2007` 底栏「新增对象」；`:1940` `create_term`、`:1239` `add_parent` |

两处**写的是同一份草案、同一套命令通道**（`POST /ontology-drafts/{id}/commands`），能力几乎等价。

而《本体治理模块拆分设计》（2026-10-01）§4 已经明确写过：

> **② 本体审核台** … - **不做**：不做本体设计（新增类、改父类、加约束的入口移去 ③）
> ③ 本体设计台 … **不做**：不能发布…

**设计文档已经拍过板，代码没执行。** 所以用户按文档理解流程（设计台 → 审核台），
进到审核台却看到一个同样能改结构的「设计」阶段 —— 这就是"冲突"的来源。

### 冲突 ②：「发布」有两个出口

| 出口 | 证据 |
|---|---|
| 审核台「发布」阶段 | `ontology-workbench.js` 阶段 5 `publish` |
| 设计台「提交并自审」 | `ontology-design.js:1278 submitAndSelfReview()` → `:1305` 直接 `POST /ontology-drafts/{id}/publish` |

设计台的「提交并自审」在校验→提交→批量批准之后，**只要没有剩余待决策项就自己发布**，
跳过整个审核台。这直接违反文档 §8 验收标准 4「设计台里没有"发布"按钮」。

后果：用户问"我该在哪发布"；而且审核台里"发布"这个页面的存在感被稀释成一个可选项。

### 冲突 ③：终态草案的门禁自相矛盾 —— **本轮已修复**

真机读数（修复前，草案 `49bb306c` 状态 `published`）：

```
阶段条：发现🟢  设计⚪(灰)  校验🟢  审核🟢  发布🟢
黄条 ：  "设计 现在进不去 —— 本轮已发布完毕（当前只有已发布/已关闭的草案）…"
```

同一屏上：**设计灰着、黄条说进不去、校验/审核/发布却亮着能点**。

根因在 `services/ontology_drafts.py: stage_state()`：

```python
submitted = bool(has_draft and status in SUBMITTED_STATES)   # SUBMITTED_STATES 含 published/closed
```

`SUBMITTED_STATES = {submitted, reviewed, published, closed}` —— 终态被当成"已提交"，
于是 `validated`/`reviewed` 也跟着为真，三扇门全开。**门后的写操作只认 `reviewed`**
（`publish_preflight` 的状态守卫），点进去必然被服务端 409 拒绝 —— **门禁在撒谎。**

**修复**（`ontology_drafts.py`，2026-10-02）：

```python
terminal = bool(has_draft and status in FINAL_STATES)   # published / closed = 只读账本
submitted = bool(has_draft and status in SUBMITTED_STATES and not terminal)
validated = bool(has_draft and not terminal and (...))
reviewed  = bool(has_draft and status in REVIEWED_STATES and not terminal)
```

终态上只有「发现」可进（它是下一轮的入口），其余四扇门锁住，理由指向真正能干活的地方：
**回看 → 本体档案，再改 → 本体设计台**。

修复后真机复验（浏览器 DOM 读 `disabled`）：

```
发现  disabled=False
设计  disabled=True
校验  disabled=True
审核  disabled=True
发布  disabled=True
```

契约测试：`tests/service/test_ontology_draft_api.py::test_terminal_draft_locks_every_stage_but_discover`
（走完 编辑→提交→校验→审核→发布 全生命周期，逐条锁住结论，并反证"门禁没撒谎"：
再发一次真的被 409 拒绝、版本数不变）。

### 冲突 ④：发现阶段和其它阶段长得不像同一个页面

```css
/* ontology-workbench.css:36-38 */
.ontology-workbench[data-stage="discover"] .ontology-workbench__body{grid-template-columns:minmax(0,1fr) minmax(280px,.38fr)}
.ontology-workbench[data-stage="discover"] .ontology-workbench__library{display:none}
```

左栏「发现队列」在发现阶段被 `display:none`（实测 `height=0`、子节点全 0、`childCount=0`），
版面从三栏变两栏：

| 阶段 | 栏数 | `main` 总高 | 中栏高 | 底栏按钮 y |
|---|---|---|---|---|
| 发现 | **2** | **5721px** | 5292px | **5634** |
| 校验 | 3 | 998px | 569px | 可见 |
| 审核 | 3 | 1200px | 771px | 可见 |
| 发布 | 3 | 1382px | 953px | 可见 |

发现阶段中栏里单独一块 `.ontology-workbench__discovery-run`（"发现任务的结果"）就 **3550px**，
整页 5000px 的候选网格全部展开。

**用户每换一个阶段，栏数、栏宽、页面高度全部变一次。** 这是"很丑"里最硬的一条。

## 2. 目标流程设计：三个阶段归设计台，两个阶段归审核台

### 2.1 一条主链（不重叠、不回头）

```
① 知识写入（不动）
   文档 → 切片 → 抽取 → 知识/断言
        │
        ↓ 知识里出现了本体没有的概念
② 本体设计台  【发现候选 → 设计 → 校验】        ← 三个"我要改本体"的动作都在这
   · 发现候选：从知识里长出来的候选术语（原来的审核台阶段 1，搬过来）
   · 设计    ：结构化编辑 —— 新增/改父类/domain·range/标签/停用
   · 校验    ：图完整性、新写入约束、历史影响
   产出：冻结的草案（带校验指纹）
        │
        ↓ 草案提交（不可再改）
③ 本体审核台  【逐条决策 → 发布】              ← 只回答"这批变更要不要进"
   产出：不可变版本
        │
        ↓
④ 本体档案（只读账本）
   版本 / 类别目录 / Diff / Turtle / SPARQL / 发布记录
   唯一写操作：基于某版本新建草案 → 回到 ②
```

**读法**：一条链，四站，每站只做一件事；②③④ 之间只有"草案"和"版本"两种东西在流动。

### 2.2 为什么「发现」要搬去设计台

「发现」回答的是"**这些从知识里长出来的候选术语，要不要变成我本体里的类**"——
这是**设计决策**，不是**审核决策**。放在审核台，就变成"审核台先说要设计，再让设计台设计"，
用户的第一反应必然是"那审核台到底是审核还是设计"。

搬到设计台后：
- 设计台阶段条 = 发现候选 → 设计 → 校验（3 段）
- 审核台阶段条 = 逐条决策 → 发布（2 段）
- **每一段恰好一个家，没有一段出现在两页。**

### 2.3 每站的边界（做什么 / 不做什么）

| 站 | 做 | 不做 |
|---|---|---|
| ② 本体设计台 | 从候选生成草案；新增/改父类/domain·range/标签；停用与恢复；影响面预览；校验；提交审核 | **不发布**（发布是③的动作）；不看已发布版本的历史与 Diff（那是④） |
| ③ 本体审核台 | 看证据；逐条批准/拒绝/要求调整；一键批准（只覆盖低中风险、无警告、不需写理由的）；发布；关闭草案 | **不改结构**（新增类/改父类的入口全部移除）；不看版本历史/Turtle/SPARQL |
| ④ 本体档案 | 版本概览；类别目录；任选两版 Diff；Turtle 只读；SPARQL；发布记录 | 不编辑、不审批；唯一写操作是"基于此版本新建草案"→ 进② |

**「提交并自审」怎么办**：保留（单人项目确实需要）。但**去掉它内部的 publish 调用**，
只做到"校验 → 提交 → 批量批准 → 停在审核台"。发布必须回审核台点一次 ——
这样"发布"永远只有一个出口，而且自审通道仍然只花两次点击。

## 3. 界面重设计

### 3.1 首屏预算（实测问题 → 目标）

| 区块 | 现在 | 目标 | 理由 |
|---|---|---|---|
| 页头横幅 | y=59 起、**高 114px**、内容是营销标语（"把发现变成可审计的领域语言"） | **高 ≤ 56px**，内容换成**上下文**：项目 · 本体版本 · 当前草案 · 当前阶段 | 首屏最贵的位置不该放 slogan |
| 阶段条 | y=201、高 60px | 高 ≤ 52px，步骤号 + 名称 + 一行状态 | 保留（它是用户理解流程的主轴） |
| 提示条 (`[data-stage-lock]`) | 独立黄条，**和状态条说同一件事** | **与状态条合并成一条** | 实测同一屏三处重复 |
| 状态条 | y=329、高 60px | 高 ≤ 44px | 只留：状态徽章 + 变更计数 + 唯一那一个「下一步」 |
| **正文起点** | **y=389** | **y ≤ 160** | 首屏 41% 被吃掉的直接后果 |

### 3.2 版面：阶段之间不许换骨架

- **所有阶段统一三栏**（左=清单、中=画布/队列、右=检查器），删除
  `[data-stage="discover"] .ontology-workbench__library{display:none}`。
  发现阶段的左栏就放**候选清单**（现在它有数据，只是被藏了 —— 实测左栏 `filters` 里
  来源下拉已经有 `平台基础规则_价格说明.md`，说明元素建出来了、内容也填了，被 CSS 压没）。
- **中栏不许是整页滚动的来源**：长流水（发现任务结果 3550px、候选网格 5000px）一律
  「折叠 + 内部滚动 + 只展开前 12 条」；`main` 总高在**任何阶段都不超过 1.6 屏**。
- **底栏主操作永远可见**：不允许再出现 y=5634 的操作按钮。

### 3.3 字号：从 8 档收到 5 档

实测叶子节点字号分布（workbench + design + archive 三页合计）：
`9px×69`、`10px×45`、`10.5px×4`、`11px×13`、`11.5px×4`、`12px×36`、`12.5px×133`、`13px×6`、17/19/20/22/25 若干。
**小于 11px 的有 127 个节点。**

| 用途 | 现在 | 目标 |
|---|---|---|
| 页标题 | 25px | 22px（衬线，一页一个） |
| 栏/区块标题 | 17–19px | 16px |
| 正文 | 12.5px | **13px** |
| 辅助说明 | 9–10.5px | **11.5px** |
| IRI / ID / 指纹 | 11px | 11px（等宽，唯一允许小于 12 的档） |

**取消 8 / 9 / 10 / 10.5 四档**，一个页面最多 5 种字号。

### 3.4 颜色：只留三色语义

墨绿＝治理与主操作｜琥珀＝待决策｜砖红＝阻断/危险。
现在页面上同时出现 5 种以上绿（深绿横幅渐变、阶段条选中、状态徽章、按钮、浅绿选中态）。
**选中态一律用浅底+描边，不用实心色**（实心色只留给"本屏唯一的主操作"）。

### 3.5 三处具体的"丑"怎么改

| 位置 | 现状 | 改法 |
|---|---|---|
| 设计台首屏 | 黄条 +「正在看：已发布版本…（只读）」+ 三行释义，**三段说同一件事** | 合成一条 44px 的状态条：「当前查看 v2（只读）· 要改点右上「新建草案」」 |
| 档案页「标识 IRI」列 | `urn:knowledge:ontology:92b18226-…:价格类型` 整列溢出 | 列内只显示末段（`价格类型`），完整 IRI 进 `title` + 一键复制 |
| 档案页「上级类」列 | 8 行里 5 行写死"（根：没有上级类）" | 空值留白，列头改成「上级类（空＝根类）」，只在筛选时显示"根类" |

### 3.6 导航

实测侧边栏四个分组里，「建模与治理」**默认是折叠的**（`open=false`，因为当前 tab 是检索页），
用户看不到「知识写入 / 本体设计台 / 本体审核台 / 本体档案」这四个入口。
13 个菜单项不需要折叠：**默认全展开**，并按流程顺序排列：

```
项目          项目管理 · 项目总览
建模与治理    知识写入 → 本体设计台 → 本体审核台 → 本体档案 → 知识与历史
探索与展示    检索与交互图谱 · 知识问答 · 实体脑图 · 原文数据源
运行与质量    后台任务 · 快照/评测
```

## 4. 实施顺序

| 阶段 | 内容 | 代价 | 收益 |
|---|---|---|---|
| **P0（已做）** | 终态起草案门禁收敛（冲突③） | 服务端 ~15 行 + 1 条契约测试 | 门禁不再撒谎；已发布草案只剩「发现」可进 |
| **P1** | 版面骨架统一：删 discovery 的两栏特例、长流水折叠、首屏预算（页头 ≤56px / 正文 y≤160） | 主要改 `ontology-workbench.css` + `ontology-design.css` | 直击"很丑"，不改任何数据流 |
| **P2** | 归属收敛：审核台移除「设计」阶段的写入口；「发现」阶段迁到设计台；设计台去掉 publish | 服务端阶段表 + 两页 JS，**改动最大** | 直击"流程冲突" |
| **P3** | 字号/颜色令牌收敛（3.3 / 3.4）、侧边栏默认展开、档案页三处表格 | 纯 CSS + 少量 JS | 观感最后一公里 |

**建议：P1 → P3（观感）先做，P2（归属）跟着做。** 理由：P1 与 P3 不动任何状态机，
风险低、用户当天就能看到差别；P2 是"流程"的真正修复，但它必须在用户认可新的归属之后再动，
否则会和现有 4 条阶段门禁契约测试打架。

---

## 5. 明确不做

- **不做**版本回滚（历史版本不可变）；要回旧结构只能基于旧版本新建草案。
- **不做**物理删除术语（只有停用），历史知识保持可查。
- **不做**第二个写入口：正式本体只能经「草案 → 逐项决策 → 不可变版本」进入。
- **不做**多人实时协同编辑。
- **不做**为了改观感而引入前端框架（现在是原生 JS + 令牌层，够用）。
