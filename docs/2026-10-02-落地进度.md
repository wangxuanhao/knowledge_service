## A1 ✅ 已完成并真机验证（编辑台：保存即生效 + 不可逆改动就地确认）

**依据**：《按请求不按阶段》的核心判断 —— **审核的对象是请求，不是改动**。
本体负责人改自己的本体是日常职责，不该被拦进审核队列；但**不可逆**的结构改动必须当场看到代价。

> 原 P1-c 是"摘掉设计台的发布按钮"。按上面的判断改成**保留能力、改名并提为主操作**：
> 摘掉按钮只会让用户找不到"我在哪改本体"，而真正的病是这个名字让人看不出它就是"直接改"。

### A1-1 主操作改名并提位

| | 改前 | 改后 |
|---|---|---|
| 文案 | 提交并自审（次要按钮） | **保存并生效**（**主按钮**，非 secondary） |
| 位置 | 排在「提交审核」之后 | 排在「提交审核」**之前** |
| 说明 | "单人项目的一键通道…" | "把这次改动直接生效：提交 → 自动批准「可自动批准」的变更 → 发布为不可变版本。**不做的两件事**：① 不跳过高风险与需要写理由的变更（它们会停下来让你逐条确认）；② 不删除任何历史版本。" |
| 另一按钮 | 提交审核 | **提交审核（交给别人复核）**，title 写明"本次不改变正式本体" |

**回执改成说实话**（三种结局各自说清）：

- 全部可自动批准 → `已生效：发布为 <版本>…这次走的是「保存并生效」：跳过了他人复核 —— 高风险与需写理由的变更如果存在，本来会在这里停下来让你逐条确认。`
- **还有待逐条确认的 → 必须点明"改动还没有生效"**，并说明已跳到审核台、确认完才会发布。
- 失败 → `保存并生效失败：…`

**顺带修掉一个会让文案静默消失的陷阱**：`renderToolState()` 每次都会 `refs.submit.title = …`，
把初始化时写的说明**覆盖回旧文案**。已把两个按钮的说明同步维护在该函数里，并留注释说明为什么。

### A1-2 停用 / 改数据类型：就地确认

**修掉一个用户直接看得到的真 bug：影响面曾经印出「影响面：{}」。**
`api/workspace.py:232` 把统计**平铺在顶层**（`{ontology_id, kind, **term_impact(...)}`），
而旧代码读的是 `result.counts || result.impact` —— 两个字段都不存在 → `{}` → 界面上真的一行空花括号。

改后行为：

- 展开「停用这个术语」即**自动**读取影响面（不再要用户先点一次按钮）。
- 一行人能读懂的话，例如真机读数：`影响面：0 条正式知识（实体 0 · 关系 0 · 属性 0） · 约束 8 处。`
  另有引用时追加"其中 N 条是「关系端点连着它」带出来的"。
- **有引用时**：必须①选「替代方式」②勾「我已看过上面的影响面」，否则停用按钮不可点，
  且 title 直接写出此刻还差什么（用户不用猜）。
- **读不到影响面就不放行** —— 按钮保持不可用，并提示收起再展开重试。这正是"不可逆动作必须先看到代价"。
- **没有引用时不逼用户选替代**：只显示一行说明，直接可停用。
- 替代类走服务端**已经存在**的 `after.replacement`（即 `dcterms:isReplacedBy`），**不新增接口、不改服务端契约**。
- 改数据类型同样处理（它没有"替代"可言，所以只要求确认，不给下拉）。

**视觉复看后的两处加固**（第一次截图复看时 vision 提了两条真问题，都改了）：

   `② 我已看过上面的影响面`，编号把先后与"两个都要"写死。

## A3 ✅ 已完成并真机复验（状态机退场：请求只有 3 种状态）

**① 数据模型：本体没有状态，请求只有三种。**
`ontology_drafts.status` 原来是 7 档（editing / submitted / reviewed / published / closed /
stale_base / stale_source），把三件互不相干的事挤进同一条状态条：① 编辑进度（我还没点保存）；
② 别人的请求走到哪一步；③ 基线 / 来源是否过期。现在只有 `pending`（待处理）→
`accepted`（已收下＝发布）/ `rejected`（已驳回）。

| 原来靠状态记的事 | 现在的落点 | 为什么 |
|---|---|---|
| 已经提交（冻结快照） | **`submitted_at` 时间戳**（0005 新增列） | 它是「什么时候」，不是「哪一种」；submit() 写、**任何一次改动清空**（改了东西就等于撤回提交） |
| 逐条已有决定 | 决定表按 `operation_fingerprint` 匹配 | 改一下草案＝旧决定自动失效，不需要状态帮忙 |
| 要不要重新基线 | **当场推导** `needs_rebase()` | 落成状态就会出现"状态说没过期、实际已过期"（0004 的同类教训） |

**② 阶段从 5 扇门收到 3 扇**：`stage_state()` 只留 发现 / 设计 / 收件箱 ——
校验并进了收件箱（A2）、发布是「收下」的结果而不是一次要用户单独去点的动作。
细分处境改由 `pending_phase()` 推导：`editing`（还没提交）→ `reviewing`（已提交待逐条处理）→
`settled`（每条都有决定，可一键收下）。

**③ 迁移 `0005_draft_status_three_states.sql`（schema 5）**：
editing / submitted / reviewed / stale_base / stale_source → pending；published → accepted；
closed → rejected。**有损且不可回滚**（迁移动器只支持 up）—— 回滚只能「备份后恢复」，
SQL 里写明了这一点，并留了救急用的反向语句。真机行数对照：

| | 迁移前（A0 读数） | 迁移后 |
|---|---|---|
| 真项目 13c51a63 | 13 editing + 4 closed | **13 pending + 4 rejected**（行数不变，只换词汇） |

演练：`scripts/rehearse_migration_0005.py` → **4 项全过**（7 档样本按映射落成 3 档 · 新 CHECK 拒绝旧词汇 ·
重复执行幂等 · 演练行清干净 25 → 25）。

**④ 迁移 `0006_backfill_draft_submitted_at.sql`（schema 6）—— 真机挖出来的 0005 漏项。**
0005 把 submitted / reviewed 并进 pending 时**没有回填 submitted_at**，于是
`pending_phase()` 读成 `editing`：收件箱（`ontology-workbench.js` renderReview）在这种情况下
**整条逐项收下队列都不渲染**，只留一张「去本体编辑台改」的指路卡 ——
**一份已经提交、正在审核的请求被重新丢回编辑台**。

真机读数（0006 执行前）：pending 16 条里有 **2 条有独立证据证明提交过**却 submitted_at 为空 ——
`07b8563f…`（20 条决定 / 17 条变更，validated_at 为空）、`bc449749…`（有校验快照）。
判据只用**已经独立存在的证据**（有校验快照 或 有决定行 —— 这两件事只可能发生在提交之后），
取值 `COALESCE(validated_at, updated_at)`（提交时刻不可恢复，这是近似值；`pending_phase()` 只关心有没有值）。
作用域刻意只收 `pending`：终态行不参与 pending_phase，给它们补一个可能不准的时间戳等于改历史账本而无收益。
执行后复查：**有证据却为空的行 7 → 5，剩下 5 条全是 accepted**（＝作用域外）。

演练 `scripts/rehearse_migration_0006.py` → **6 项全过**（该填的填了 · 拿不出证据的不动 ·
已有值不被覆盖 · 终态一行不改 · 重复执行幂等 · 回滚后真库 25 → 25）。
`EXISTS(决定行)` 这一支的演练需要造合法决定（不可变触发器 + 外键），代价高于收益，
