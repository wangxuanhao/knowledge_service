# 本体建模层（单画布）设计：把三个结构页合并成一张画布

> 日期：2026-10-04
> 触发（用户原话）：
> **「本体编辑、本体审核台、本体档案、知识台账都不好用，流程不要这么多啊……你就简化流程，然后让操作便捷，现在的编辑、审核方式你可以不管了，你设计一个更简单的方案……我看市面上人家就是一个图谱，点击侧边栏可以更改、编辑，然后拖动本体，然后本体可以连线，加个视图按钮就是现在本体编辑展示的内容，编辑都放一个画布上，画布确认的话可以点击校验和审核，审核通过可以点击发布按钮……名称改成本体建模层，知识台账应该是实体层控制吧。」**
>
> 本文承接《2026-10-02-本体流程再设计-按请求不按阶段.md》，在它「审核对象是请求不是改动」的基础上，再往前走一步：**把结构层的三个页面（编辑台／审核台／档案）合成一张画布**。

---

## 1. 结论一句话

结构层只留**一个页面「本体建模层」**（≈ 本体星图·类图谱）：一张画布，左侧列类型/关系/属性三维清单、中间拖拽连线、点类看属性/关系、底部「校验并审核 → 发布」。原「本体审核台」的收件箱变成画布上的**虚线待收下节点**，原「本体档案」的只读账本变成顶栏一个「版本历史」抽屉。**「知识写入」独立成一个入口（≈ 本体生成：上传文档／扫描数据库表／自然语言 → 抽取 → 质检 → 出候选），不占用画布。** 实例层仍是**单独一页「知识台账」**（≈ 实体图谱），按版本显示、不确认版本。

**单用户，没有「别人提交」**：人自己改的 → 画布上直接改；机器抽的（在「知识写入」入口）→ 点「收下」，新概念进建模层画布（虚线待收下）、新实体进知识台账。建模层画布只负责「定结构、发版本」，全在一个页面。

```
┌── ①知识写入（本体生成 · 独立入口）────────────────────────┐
│ 上传文档 / 扫描数据库表 / 自然语言 → 抽取 → 质检 → 出候选   │
│ 抽取过程「思考＋证据」透明可见（分析师对话流）              │
└──────────────────────┬──────────────────────────────────┘
                       │ 收下候选：新概念→本体层 · 新实体→实例层
┌──────────────────────▼──────────────────────────────────┐
│ ②本体建模层（本体星图·类图谱 · 单画布 · 唯一控制结构版本）  │
│ 左：类/关系/属性清单 · 中：画布（实线=已发布，虚线=待收下） │
│ 右：节点详情（属性/关系/规则） · 顶栏：视图切换＋版本历史   │
│ 底栏：校验并审核 → 发布 vN+1                              │
└──────────────────────┬──────────────────────────────────┘
                       │ 发布为 vN+1
┌──────────────────────▼──────────────────────────────────┐
│ ③知识台账（实体图谱 · 另一页）                            │
│ 按本体版本显示实体/关系/属性值；改删不确认版本、留痕可回滚  │
└─────────────────────────────────────────────────────────┘
```

## 2. 诊断：为什么三个页会「流程不可控」

现状结构层被切成三个页面 + 一条阶段条：

| 页面 | 现在管什么 | 用户感受到的问题 |
|---|---|---|
| 本体编辑台 | 主动改结构（新增/改父类/停用） | 改完还要「提交审核」，负责人被当成交给别人审 |
| 本体审核台 | 发现→设计→审核→发布 四阶段 | 一条阶段条挤了三个轴（数据状态/工作流/来源），每扇门都要解释「为什么锁着」 |
| 本体档案 | 只读版本/Diff/Turtle/SPARQL | 查个历史要跳到第三个页面 |

三个页面管的是**同一个对象**（本体结构）、**同一个操作人**（本体负责人）——按《按请求不按阶段》的判据（M1 署名相同 / M2 可逆性相同），它们本来就该合成一页。现状把它们切开，是为了「展示状态」，不是为了「方便操作」。用户的原话「为了展示状态已经混乱了」就是这件事。

**参考图（OntoFlow 类工具）做对了两件事**：① 结构建模就是一张画布，左边点、中间拖、底部发布；② 右侧是 **AI 助手**——自然语言描述需求，AI 生成/调整模型，落到画布上还能继续迭代。不需要「发现/设计/审核/发布」四个站来回跳。

## 3. 单画布怎么设计

### 3.1 布局（三栏 + 顶栏 + 底栏）

| 区域 | 内容 | 取代现在的谁 |
|---|---|---|
| **顶栏** | 页面名「本体建模层」＋当前版本 vN＋**视图切换（图谱/分层）**＋「版本历史」按钮 | 阶段条 + 档案页入口 |
| **左栏** | 「本体类型」树（父子缩进）＋「关系类型」列表＋「属性类型」列表（带数据类型徽标）；底部「＋新建类型／＋新建关系／＋新建属性」 | 编辑台左栏 + 审核台左栏 |
| **中栏（画布）** | 节点=类型，实线箭头=父子，紫色虚线=关系，黄色虚线=待收下候选；点选中类时下方展开它的属性清单 | 编辑台画布 + 审核台画布 + 发现阶段的候选列表 |
| **右栏（节点详情）** | 点选中类时显示：属性定义、允许的关系类型、适用规则、相关实体（对应博文「点一个类，右侧显示属性／关系／规则／实体」） | 检查器 / 详情面板 |
| **底栏（动作条）** | 状态摘要（N新增·N待收下·N冲突·N阻断）＋「校验并审核」＋「发布为 vN+1」 | 阶段门禁按钮 + 一键批准 + 发布 |

### 3.2 三种节点样式（这是「审核」落到画布上的方式）

| 样式 | 含义 | 来源 |
|---|---|---|
| **实线节点** | 已发布的结构 | 当前本体 vN |
| **黄色虚线节点** | 机器抽取的新概念，**待收下** | 知识写入入口抽出（原来审核台的「发现」候选） |
| **选中态（绿色发光）** | 正在编辑的对象 | 点击/从左侧选中 |

「知识写入 → 本体建模」就是这样实现的：在**独立的知识写入入口**输入/上传 → AI 抽取 → 遇到本体里没有的类型/关系，**不进入单独的审核队列**，而是作为一个虚线节点直接出现在建模层画布上，带「待收下 · 来自知识写入」徽标。点它 → 「收下 / 忽略」→ 收下即纳入本版本。

### 3.3 视图按钮

顶栏「图谱视图 / 分层视图」两个页签对应现在设计台的两种画法（力导向图 / 分层带图）。用户要的「加个视图按钮就是现在本体编辑展示的内容」指的就是后者——分层视图保留，但不做成第二个页面，做成画布上的一个开关。

### 3.4 动作条：校验 / 审核 / 发布（0 阶段，3 个按钮）

```
① 画布编辑 / 右侧生成 ──→ ② 校验并审核 ──→ ③ 发布为 vN+1
```

- **校验**＝机器查约束（SHACL / 数据类型 / 父子成环），随时可跑，结果是底栏状态摘要里的「N 冲突 · N 阻断」，**不是独立阶段**。
- **审核**＝人过一眼本次改动（自己改的＋机器抽的），把待收下的候选「收下 / 忽略」。**单用户下没有「别人」**——「审核」不是「审别人的请求」，是「发布前人对机器产出的把关」，就发生在画布上，不跳页。
- **发布**＝生成新版本，是动作的**结果**，不是流水线一站。

## 4. 校验与审核：两层 + 两个点（全流程口径，回答「现有知识还审核吗」）

用户问「有校验吗？后续写入的知识、现有知识又审核吗？开放和非开放、累加、SHACL、domain/range 到底是什么」——这是两层的事，掰开就不乱：

### 4.1 「校验」＝机器自动，全程不需要人

| 层 | 工具 | 什么时候跑 | 查什么 | 不过怎么办 |
|---|---|---|---|---|
| **结构层**（本体） | SHACL | **发布 vN+1 那一刻** | 父子继承成环？属性数据类型合法？SHACL 约束自洽？domain/range 指向存在的类？ | 发布不了，机器拦下提示改哪 |
| **实例层**（知识） | domain / range / 类型 | **每条知识写入那一刻** | 类型在不在本体？关系两端类型匹配？属性值类型对？ | 分流（见下） |

> **属性 vs 关系（本体第三维，别混）：** 关系（ObjectProperty）的 domain/range 都是**类**，查「两端是不是合法类」；
> 属性（DatatypeProperty）的 domain 是**类**、range 是**字面量数据类型**（string/int/float/date/bool），查「值的数据类型对不对、挂在哪个类上」。
> 所以「类 / 关系 / 属性」是本体三维，左栏都要列，机器校验口径不同——这也是知识写入会抽出三种候选（类 / 关系 / 属性）的原因。

### 4.2 知识写入的三种去向（逐条机器分流）

1. **✅ 符合本体** → 直接落库、立即生效，**不需要任何人审核**。
2. **⚠️ 类型不在本体** → 这条知识标「结构待定」（可检索、不进正式证据链）＋ 新概念作为「待收下」虚线节点画到画布。
3. **🚫 类型在、但 domain/range/值类型冲突** → 进「知识审核」，人批准或拒绝（一次性）。

### 4.3 「审核」＝人做、只做两次、只做一次

- 画布上**收下**机器抽的新概念（→ 进本次草案 → 发布后生效）；
- **批准/拒绝** domain/range 冲突的知识（→ 知识审核）。

### 4.4 闭环：待收下 → 发布 → 结构待定自动解除

人收下「封禁期限」→ 校验并审核 → 发布 vN+1 → 所有标「结构待定」的知识**自动解除、正式生效**，不再单独审核。

### 4.5 「开放 / 非开放」是同一个流程的两种表现

- **非开放（约束模式）**＝本体已够全：抽取几乎都走 ✅，机器校验即通过，人只管看结果。
- **开放（探索模式）**＝本体还在长：新概念不断走 ⚠️，**累加**到画布（多次写入不覆盖），人逐步「收下 → 发布」，本体越用越全。

一句话：**现有知识永远不再审核；后续知识写入那一刻机器校验，符合就过、类型缺就「结构待定」（等概念收下发布后自动解除）、约束冲突就知识审核（人批一次）。**

## 5. 实体层（知识台账）：另一页，按版本显示，但不确认版本

用户原话「知识台账这块按照版本显示」＋「知识的删除和修改不用确认版本」——两句合起来才是完整边界。先把「版本」这个词分清楚，它有两层意思，不能混：

| 「版本」 | 谁的 | 怎么产生 | 要不要确认 |
|---|---|---|---|
| **本体版本** v1..vN | 结构（类/关系/属性） | 只在「本体建模层」画布上「发布」产生 | **要**（校验 → 审核 → 发布） |
| **记录版本**（历史） | 实例（实体/关系/片段） | 每次改/删自动 +1 | **不要**（直接生效，可回滚） |

- 本体建模层管**分类**（类/关系/属性，改的是结构），是**唯一控制本体版本的地方**；
- 知识台账管**具体的东西**（实体/关系/原文片段，改的是实例），**删除和修改直接生效**，没有「确认版本」这一步——只自动留历史版本，可撤销。

边界一句话（写死在页面上）：**「这里管具体的东西：查、改、删、并重复项。删除和修改直接生效、可撤销，不用确认版本。结构（分类）不在这，去本体建模层。」**

实体层的编辑**不审批、不确认版本**（判据：局部影响 + 可回滚，见《全项目三层设计》§4），但必须有留痕 + 撤销入口 + 影响面提示。这三条是护栏，不是流程——尤其**软删除 / 合并**这类不可逆动作，改之前要给影响面提示（会转移多少条关系、多少条来源），但那是「看清代价」，不是「确认版本」。

## 5. 两处不能只靠画布消失（诚实交代）

用户说「现在的编辑、审核方式你可以不管了」＋「单用户，为啥还有别人提交这个说法」，这是对的——单用户下没有「别人」，机器（Semantica）是工具不是「别人」。有两个判断不能跟着一起丢掉：

### 5.1 「审核」＝人对机器产出的把关，不是「审别人的请求」

| 谁在改 | 画布上怎么表达 |
|---|---|
| 人自己改结构 | 画布上直接改，改完即改完；只有**不可逆动作**（停用/改类型/改父子）原地弹一句影响面提示 |
| 机器抽取的概念 | 右侧「生成」产出 → 画布虚线「待收下」节点 → 点「收下 / 忽略」 |

两者合流到同一个动作条「校验并审核 → 发布」，不跳页、不排队、没有「别人」。
唯一保留的「审」是**人对机器产出的收下 / 忽略**——因为机器会抽错，这不是多用户审批，是单用户对自己工具的把关。

### 5.2 标注改动不该换版本号（存储约束，单独排期）

现在本体版本存的是**整份 turtle**，改一条注释也是改图 → 必然产生新版本号（`repository/migrations/0001_core.sql`）。「改注释 → v4」正是用户觉得「流程不可控」的一部分。解药是《按请求不按阶段》§4.4 的**标注/结构分开计量**——这是**动存储**的事，不能靠画布搞定，要单独排期，不能在本轮假装画布已经解决了它。

### 5.3 后端治理先保留，UI 先合

底层的 `ontology_drafts` 治理（`stage_state`/`review-plan`/`publish_preflight`）先不动。第一版单画布**走现有 API**：编辑/生成自动建草案 → 「校验并审核」＝校验 + 自动批准可自动批准的变更 → 「发布」＝`POST /publish`。状态机（7→2）和门禁的删除放到最后，避免「UI 合了、门禁还在打架」的中间态。

## 6. 实施分期

| 期 | 内容 | 直击用户哪句话 | 风险 |

| **1** | 新建「本体建模层」单画布页：左清单（类/关系/属性）+中画布+右节点详情+顶栏+底栏；编辑台/审核台/档案入口合并到这一页；校验/审核/发布内联；虚线待收下节点＝知识写入入口抽出、直连画布。**知识写入保持独立入口（本体生成），不进画布** | 「操作都在一个页面」「知识上传和本体星图分开」 | 中（前端重写，底层走现有 draft API） |
| **2** | 实体层：知识台账按版本显示（挂载版本列）+ 撤销入口 + 合并影响面 | 「知识台账按照版本显示」 | 中（复用 `records-view.js`，补列和撤销） |

**期 1、2 是纯前端 + 文案，可立刻开始并逐项真机验证；期 3、4 动数据模型，单独排期。**

## 7. 明确不做

- 不给实例编辑加审批（可逆的不审）。
- 不自动迁移挂在旧版本上的知识（受控重分类另行处理）。
- 不做多人实时协同编辑（同一时刻一人画）。
- 不做物理删除（本体只停用，知识只软删除）。
- 不在这一版重写后端治理（先复用，后拆）。

## 8. 端到端综合评估基线（本体建模层 × 知识写入 × 前端选型 × 流式 × 存储）

**一句话：这是「前端重构」项目，不是「后端重写」项目。后端底座已成熟且正确，缺的都在前端。在现有代码上改，不做 v2。**

| 决策点 | 结论 | 现状依据（代码） | 改动量 |
|---|---|---|---|
| 架构三层分离 | 知识写入 / 本体建模层 / 知识台账 三入口；本体层与实例层两个维度（TBox/ABox） | 现状 10 页混在「建模与治理」一组 | 中（前端菜单重组） |
| 前端选型 | 原生 JS + Cytoscape.js（图编辑），不迁 React/Vue | 44 文件原生 JS，vendor 仅 echarts，无构建，契约测试测真实 DOM | 小（加 vendor 库） |
| 流式抽取 | 阶段流式（非 token 流式） | `ingest_runs.active_stage` + `ingest_stage_outputs` + `GET /ingest-runs` 轮询端点已就位 | 小（前端渲染层） |
| 存储 PG+Milvus | 不动 | `write()` 内 `_sync_milvus()` —— 写入+质检(SHACL)+索引同步 = 同一次操作 | 零 |
| 思考+证据展示 | 现有 `evidence`/`reason`/`classification_reason` 映射成中文思考文案 | 候选已带这三个字段 | 小（字段映射） |

**三个诚实边界：**
1. token 级流式做不到（抽取是 `generate_typed` 结构化 JSON，要拼完整才校验）；「分析师一步步说」是阶段流式，够用。
2. 「改注释不换版本号」要动存储，P3 单独排期，不能靠画布假装解决。
3. 后端状态机 7→2 放最后，先复用现有 draft API 把 UI 合了，避免「UI 合了、门禁还在打架」。

## 9. 版本管理（查看某一版 / 回到某一版 / 发布说明）

用户原话：「你是不是应该有个版本回退的能力，然后可以切换不同的版本的能力……
版本也是需要人手动发布后确认成版本。版本管理发布要写对应的描述，进行确认。」

### 9.1 三条不可动摇的语义

| 语义 | 做什么 | 明确不做什么 |
|---|---|---|
| **查看 ≠ 生效** | 「查看这一版（只读）」把画布切到那一版，顶栏变紫色并写明「历史版本 · 只读」 | 不切换生产版本、不写任何数据、不销毁手上那份草案（横幅会说「改动没丢，点右边回去」） |
| **回退 = 再发一版** | 「回到这一版」以那一版为基线开一份 **revert 草案**，改完审核发布后成为**新版本** | 不改写历史：不删掉后面的版本。所以「回到 v1」是可追溯的，v2/v3 仍在版本管理里，随时能再回去 |
| **发布要有人确认** | 发布说明必填（服务端 `PublishRequest.note` min_length=1）；回退还要**逐条勾选**那条代价警告 | 不是「加了个软提示」—— 空说明 422、纯空白 400、回退没勾 422，都在服务端拦 |

### 9.2 回退为什么必须是一种「显式意图」

服务端有一条老保护：**普通草案的基线必须等于项目当前版本**（否则 409 `stale_base`）。
它防的是「在旧基线上做普通编辑 → 静默丢掉别人后来的改动」，是对的、要留着。

但「我就是要回到 v2」是另一件事。所以回退用独立的来源 `source_kind='revert'`
（迁移 `0007_revert_source_kind.sql`），只对它放行历史基线，并且要求基线**确实是本项目里
存在的某一版**（回退不是一条能指向不存在基线的旁路）。

这条「基线必须是最新版」的假设在服务端有 **四处**，必须逐处放行 —— 只改一处会出现
「能建草案但发不出去」这种最难查的半通状态：

| 位置 | 普通草案 | revert 草案 |
|---|---|---|
| `services/ontology_drafts.create` | 基线 ≠ latest → `stale_base` | 允许，但基线必须存在于本项目 |
| `services/ontology_drafts._check_current`（每次写操作） | 同上 | 跳过（并以 revert 基线作为前置条件的合法取值之一） |
| `services/ontology_drafts.publish_readiness` | `base_outdated` = **error** | 换成一条 **warning**，说清代价：回到 vN 后，它之后那几版的结构改动不再留在当前版本里 |
| `services/ontology_drafts.needs_rebase` | `stale_base` | 返回 None（让人去「重新基线」等于把回退意图抹掉） |
| `repository/core._publish_governed_ontology_draft`（事务内复核） | 基线 ≠ latest → `stale_base` | 只校验基线在项目里存在；`expected_ontology_id` 接受「当前最新」或「回到的那一版」两种取值 |

### 9.3 纯回退（零变更）也要能发布

v1 → v2 加了「设备」；「回到 v1」就是让当前版本重新变成 v1 的结构 —— 这种回退**没有**
任何操作（operation）可审核。与 `git revert` 同构：产生一个新版本，而树等于旧版本。

所以三处「至少一条变更」的门禁对 revert 草案放行，代价由那条回退警告的**勾选确认**担起来：

- `services/ontology_drafts.submit`：`a draft must contain at least one effective operation`
- `services/ontology_drafts.publish_readiness`：`no_operation`
- `services/ontology_drafts.publish_preflight`：`publish requires at least one current approval`
- 前端 `gatePublish`：`approved=0` 时靠服务端返回的 `readiness.revert` 放行（门禁仍只渲染服务端结果，前端不自己推）

### 9.4 版本列表回答四件事

`GET /api/projects/{id}/ontologies` 每一版返回：**第几版 / 什么时候发的 / 谁发的 / 为什么发**。

- 版本号按发布顺序**现算**（1 起）；库里不存序号 —— 存了就会与顺序脱节，而版本号是给人看的（「回到 v2」）。
- 发布说明与发布人取自版本 `metadata.publication.note` / `.actor`（发布时必填）。
- 发布说明功能上线**之前**的版本没有说明，如实显示「（这一版发布于发布说明功能上线之前，没有留下说明）」，不补一句编出来的话。

### 9.5 明确不做

- 不做「把生产切回旧结构」那种一键切换：回退必须留下一次发布记录（审核链不能断）。
- 不改写、不删除任何历史版本。
- 不在回退时自动迁移挂在旧版本上的知识（受控重分类仍是另一件事）。
- 手上有未处理的草案时不许回退：两份草案各自基于不同基线，谁也说不清最后发布的是什么。
