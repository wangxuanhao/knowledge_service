## 一、流程：用户提出的顺序是对的，后端本来就这么设计

用户原话：
> 「是不是先是知识写入，然后出来一个方案，但是不审核，然后到本体建模层，然后本体确认后才是实例层吧，
> 不然本体确认了，然后实例很多不符合规范的 domain range 什么时候审核呢」

### 1.1 三种抽取模式（`models.py` `IngestSettings.extraction_mode`）

| 模式 | 含义 | 写实例吗 |
|---|---|---|
| `ontology` | 按**当前已发布本体**抽取、校验、实体融合 | **写**：合法知识当场落台账 |
| `discovery` | 不看本体，自由发现 | **不写**：只产概念候选（待纳入本体） |
| `documents` | 只存原文、切片、向量 | 不写 |

### 1.2 实例写入的三个契机（全仓核实）

`_materialize_candidates` 全仓**只有一处调用者**（`POST /ontology-discovery/runs/{run_id}/finalize`）：

| 契机 | 触发者 | 写入什么 | 校验 |
|---|---|---|---|
| ① 受控抽取 | 写入页提交 | 合法实例当场落台账 | 抽取时按 `relation_constraint_mode`（advisory/review/strict/off）+ SHACL |
| ② 「提交知识」 | 本体建模层 | 已审核的开放发现候选 → 正式记录（回执：物化 N 条） | 物化时按父本体 SHACL 全量校验，**不合格根本不写**并记 `ontology_validation_failed` |
| ③ 「发布 v_n」 | 本体建模层 | **什么都不写** —— 只造一个本体版本 | — |

> 所以「本体确认后才是实例层」是对的，但**"确认"分两步**：发布（定结构）+ 提交知识/受控抽取（才写实例）。
> 发布本身不产生任何实体。

### 1.3 「没写入的」到底去哪了（四类，各有落点）

| 情况 | 丢了吗 | 现在去哪看 | 怎么处置 |
|---|---|---|---|
| 类型不在本体里（含端点传染） | **没丢**：照常收下 + 打「结构待定」标 | 台账徽标（`records-view.js`）+ 建模层「待建模」 | 纳入本体并发布 → 标记**自动解除**（后端故意不给手动清除：\"两个清除入口必然打架\"） |
| 关系约束 / SHACL 违反 | **没丢**：知识已存，转审核条目（`reviews.py`，落 `accepted_exception` 等处置） | 审核条目 API | 「确认这是例外」/「标记需要整改」 |
| 候选物化校验不过 | 没写入，但**记在案**（`ontology_validation_failed`） | 建模层「候选结果」+ 后端错误记录 | 改结构 →「重新分析当前候选」→ 再提交 |
| 硬错误（端点实体不存在 / 有效区间越界 / datatype 非法） | 整批不写 + 报错 | —— | 不是选择题：修数据/重抽 |

### 1.4 判断：**不新开"实体审核"菜单**

理由：① 四类的处置动作完全不同（改本体 / 定例外 / 重新分析 / 修数据），塞进一个列表等于把分诊丢给用户；
② 本仓已有成熟收件箱形态（结构待定 + 台账徽标）；③ 多一个叫"审核"的入口只会更绕（用户已三次问"必须审核吗"）。

## 二、前端实现现状（2026-10-05 重构后）

写入页当前的实现，替代原先的对话流 + 分类清单：

| 环 | 实现 |
|---|---|
| 输入 | 纯文件上传（`ingest-upload.js`）：多文件 / 拖拽 / 重试 / 25MB 单文件、100MB 单批上限 |
| 解析模式 | 面板顶部 `#ingest-mode-slot` 三档下拉（`workspace.js` 注入）：受控入图 / 开放发现 / 仅文档检索 |
| 结果查看 | 右侧「抽取结果工作区」抽屉（`ingest-results.js`）：按文档汇总实体/关系/属性，运行中每 2s 自动刷新 |
| 提交后 | 留在本页，逐文件结果写进 `#doc-submit-results`，给「想看实时日志可点」的链接（不强制跳转） |

契约：`tests/service/test_frontend_static_contract.py`（静态守卫）+ 浏览器测试（写入页 / 切片预览）。
