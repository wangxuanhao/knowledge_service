## 一、流程：用户提出的顺序是对的，后端本来就这么设计

用户原话：
> 「是不是先是知识写入，然后出来一个方案，但是不审核，然后到本体建模层，然后本体确认后才是实例层吧，
> 不然本体确认了，然后实例很多不符合规范的 domain range 什么时候审核呢」

### 1.1 三种抽取模式（`models.py` `IngestSettings.extraction_mode`）

| 模式 | 含义 | 写实例吗 |
|---|---|---|
| `ontology` | 按**当前已发布本体**抽取、校验、实体融合 | **写**：合法知识当场落台账 |
| `discovery` | 不看本体，自由发现 | **不写**：只产概念候选（待纳入本体） |
| `documents` | 只存原文、切片、向量 | 不写 |

### 1.2 实例写入的三个契机（全仓核实）

`_materialize_candidates` 全仓**只有一处调用者**（`POST /ontology-discovery/runs/{run_id}/finalize`）：

| 契机 | 触发者 | 写入什么 | 校验 |
|---|---|---|---|
| ① 受控抽取 | 写入页「发送」 | 合法实例当场落台账 | 抽取时按 `relation_constraint_mode`（advisory/review/strict/off）+ SHACL |
| ② 「提交知识」 | 本体建模层 | 已审核的开放发现候选 → 正式记录（回执：物化 N 条） | 物化时按父本体 SHACL 全量校验，**不合格根本不写**并记 `ontology_validation_failed` |
| ③ 「发布 v_n」 | 本体建模层 | **什么都不写** —— 只造一个本体版本 | — |

> 所以「本体确认后才是实例层」是对的，但**"确认"分两步**：发布（定结构）+ 提交知识/受控抽取（才写实例）。
> 发布本身不产生任何实体。

### 1.3 「没写入的」到底去哪了（四类，各有落点）

| 情况 | 丢了吗 | 现在去哪看 | 怎么处置 |
|---|---|---|---|
| 类型不在本体里（含端点传染） | **没丢**：照常收下 + 打「结构待定」标 | 台账徽标 + 建模层「待建模收件箱」`/structure-pending` | 纳入本体并发布 → 标记**自动解除**（后端故意不给手动清除："两个清除入口必然打架"） |
| 关系约束 / SHACL 违反 | **没丢**：知识已存，转审核条目 | 写入页「本体约束异常」组 | 「确认这是例外」/「标记需要整改」 |
| 候选物化校验不过 | 没写入，但**记在案** | 建模层「本轮候选结果」 + 写入页「上次提交知识没通过的」 | 改结构 →「重新分析当前候选」→ 再提交 |
| 硬错误（端点实体不存在 / 有效区间越界 / datatype 非法） | 整批不写 + 报错 | —— | 不是选择题：修数据/重抽 |

### 1.4 判断：**不新开"实体审核"菜单**

理由：① 四类的处置动作完全不同（改本体 / 定例外 / 重新分析 / 修数据），塞进一个列表等于把分诊丢给用户；
② 本仓已有成熟收件箱形态（`/structure-pending`）；③ 多一个叫"审核"的入口只会更绕（用户已三次问"必须审核吗"）。

## 二、本次实现

### 2.1 写入页新增「现在这一步」（顶部状态条，`#ingest-flow-step`）

一句话说清：**处在流程哪一步 + 该做什么 + 这一页不做什么**。口径来自服务端，前端不猜：

- 没有已发布本体 → `data-step="no-ontology"`（琥珀）：只会做开放发现、**一条知识都不会进台账**、下一步去建模层；
- 有已发布本体 → `data-step="has-ontology"`：按 **本体 v{n}** 受控抽取 → 合法知识当场进台账；
  版本号取 `GET /ontologies` 最后一版的 `version`（按发布顺序现算，服务端口径）。

### 2.2 「📥 还没落进台账的」分类清单（原「这批原文抽到的知识」）

按"缺什么"分类、**一行一个出口**（不是逐条问）：

| 行 | 动作 |
|---|---|
| 能直接进知识台账 | 一个批量按钮「写进知识台账（N 条）」 |
| 和台账里已有的值冲突 | 「用抽取到的新值替换」/「保留台账里已有的值」 |
| **缺概念，现在收不了（N 条本体里还没有 M 个概念）** | **「把缺的 M 个概念送去『本体建模层』」** ← 本次新增 |
| 本体里还没有的概念（开放发现候选） | 「送到『本体建模层』（N 个）」 |
| 类型不在本体里的知识（结构待定） | 「去『本体建模层』建概念」→ `OntologyWorkbench.openPendingStructure()` |
| 本体约束异常 | 「确认这是例外」/「标记需要整改」 |
| 现在收不了（引用没落库 / 原文改过） | 逐条说清为什么（无动作，不是选择题） |
| 上次「提交知识」没通过的（N 条） | 「去『本体建模层』重新分析」+ 逐条原因 ← 本次新增 |

逐条明细默认收在 `<details>` 里，只有"想单独去掉某条"才在那里点「不要」。

### 2.3 修掉的真问题（都由真机/用例抓到）

1. **服务端枚举漏到界面**：概念状态直接印 `状态 materialized 1`（用户原话"看不懂"）→ 过一层中文映射
   （`待纳入本体 / 已在发现草案里 / 已发布进本体 / 已落进台账`），状态优先级与服务端一致。
2. **已处理完的候选还来问**：1001_开放在旧版里把 55 个**已 materialized** 的概念逐条问"要不要"→
   现在只把 `pending` 的当待办，其余合成一句「另有 55 个…已经处理过，不再重复问你」。
3. **`recordCollected` 缺 `dest` 就整条动作崩**（合成卡片没有 dest）→ 容错 + 给合成卡片补 `dest`。
4. **`conceptId` 过滤误伤**：审核候选没有 `conceptId`（undefined），推送概念时会把整批候选一起摘掉 →
   只在 `conceptId` 有值时才按它过滤。
5. **慢接口没有即时反馈**：`POST /ontology-discovery/drafts` 是**同步跑模型归纳**的（真机实测 >5 分钟未返回）→
   点击即给回执 + 状态行写明"要几分钟、别关页面"，不写"一两分钟"这种假估计。

### 2.4 真机读数（一次性项目，跑完自删）

项目 = 新建 + 只播种一个类「商户」的本体；原文含商户/订单/冷链/退款/平台等概念；模式 = 受控（正式入图）。

- 状态条（发送前）：`现在这一步：按 本体 v1 受控抽取 → 合法知识抽取时当场写进「知识台账」…`
- 分类清单：`缺概念，现在收不了：8 条（本体里还没有 8 个概念）` + 按钮「把缺的 8 个概念送去「本体建模层」」
  （另一次跑出过 `现在收不了：7 条` 逐条列出，同样是"类型还不在本体里"）
- 点该按钮：真机发起 `POST /ontology-discovery/drafts`（服务端开始跑模型归纳）；因同步耗时 >5 分钟，
  探针未等到回执 —— **界面行为正确（即时回执 + 明确说明 + 按钮禁用），慢的是服务端接口本身**。
- 结构待定 `/structure-pending` = 0（这批知识**根本没写进图**：受控抽取下"类型不在本体"的候选不会先入库），
  这解释了两类"缺概念"的区别：① 已入库但类型待定（结构待定）；② 没入库、卡在候选（缺概念）。
