三层分离：知识写入 → 本体建模层 → 知识台账
参考「本体星图」那套系统——本体生成（灌材料）与本体星图（看结构）本来就是分开的，不该塞进同一页。
知识写入 ≈ 本体生成（上传/抽取/质检） 本体建模层 ≈ 本体星图 · 类图谱（看结构/编辑/发布） 知识台账 ≈ 实体图谱（看对象/按版本显示）
① 本体生成

知识写入

Ingest · 独立入口
把业务材料变成结构化知识。这是「建设」动作，跟「看」分开。
  • 上传文档（.txt/.md/.pdf/.docx）
  • 扫描数据库表（映射表/字段）
  • 自然语言描述需求
  • 抽取 → 质量检查 → 出候选
产出候选：新类/关系/属性（要进本体）+ 新实体/关系/属性值（要进台账）。抽取过程「思考+证据」透明可见。
→收下候选
② 本体星图 · 类图谱

本体建模层

Ontology Modeling · 画布
看业务世界的结构骨架：有哪些类、关系、属性。唯一能改结构的地方。
  • 左栏：类 / 关系 / 属性三维清单
  • 画布：拖节点、连线（父子/关系）
  • 点类看：属性、允许关系、规则
  • 校验并审核 → 发布为 vN+1
只管「结构长什么样」。知识写入抽出的新概念在这里以虚线「待收下」出现，收下后发布成版本。
→发布后
③ 实体图谱

知识台账

Knowledge Ledger · 账本
看这套结构在业务里的具体落点：哪些实体、谁和谁有关系、属性值多少。
  • 按本体版本显示实体
  • 实体/关系/属性值：直接改删，自动留痕
  • 可回滚，改删弹影响面
  • 不确认版本
知识写入抽出的新实体/属性值直接落这里。改删无需确认版本，留痕可回滚。
◆那「聊天式分析师（思考+描述+证据）」去哪了？
它不取消，只是不占用本体建模层的画布——它归位到 ①知识写入 这个独立入口里： 上传文档后，抽取过程以「分析师对话流」透明展开（💭 思考 为什么判成类/关系/属性 + 📄 证据 引用原文第几条）， 结果以候选卡片给出，人点「收下」。

这样职责就干净了：知识写入 负责「灌材料、出候选」（可以有聊天的透明抽取）， 本体建模层 负责「定结构、发版本」（纯画布，专注骨架）， 知识台账 负责「看实例」。三个入口，互不越界——这也呼应你上一条「本体层和实例层是两个维度」。
