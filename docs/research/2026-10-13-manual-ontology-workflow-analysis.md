# 操作手册与本体能力差距：流程完整性分析（2026-10-13）

## 范围与证据口径

检查当前离线 HTML 操作手册、旧本体工作台手册、登录权限手册、知识写入事实核实文档以及指定能力差距文档。本文是文档流程审计，未运行服务或重新执行历史测试；代码端事实应结合另一份实现审计。文档对历史测试的记录不等于今天运行环境的实测结果。

引用以仓库根 `D:/workspace/knowledge_service_v2/knowledge_service` 为基准，行号是本次读取时的源文件行号。

## 结论

当前手册有一条可理解的贯通主路径：登录 → 默认本体项目 → 自定义本体 v2 → 受控上传 → 实体/关系/属性核对 → 本体 v3 → 受控迁移 → 业务事实单独修订 → 历史/软删除/恢复。它足以教用户完成一个小型、有本体约束的知识图谱案例，但不足以充当覆盖全部输入模式、例外治理、业务验收和持续运维的完整操作手册。[HTML 手册:15–16, 38–114, 168–255]

**历史文档需按代码分支纠正：** 10-05 事实核实文档的“发布什么都不写”是当时说明；当前受治理的 discovery 来源发布可以原子应用候选实例计划，普通手工建模发布则不自动改业务事实。`review` 模式的审核条目也可在正式事实保存之后生成。[父代理代码审计：services/ontology_drafts_review.py:75–143；repository/core.py:1886–1910；services/service.py:802–828]

指定 `2026-10-12-ontology-capability-gap.md` 不是全套尚未实施的改造计划。表中“当前落地”已包括本体驱动抽取、开放发现工作流、质量门禁、不可变发布、outbox、冻结原文和持久任务；“后续差距”才是后续需补的能力。不能重复把已有能力作为未来收益。[能力差距:6–24]

是否“完整知识图谱项目”应分层回答：建模、抽取、治理、正式事实、检索问答和修订的核心业务链可以存在；有测试、有演示、有本体结构仍不足以证明业务覆盖和答案正确。完整 OWL 推理、自动跨本体对齐也不是所有知识图谱项目的必要前提，应由真实业务需求决定。[能力差距:8, 15, 19–20, 32–40, 50]

## 仍缺的操作闭环

1. **开放发现到正式入图的分支。** 主流程只选择项目本体抽取。另一个事实核实文档区分 `ontology`、`discovery`、`documents`，但它对“发布本体本身不写实例”的绝对表述已不能完整描述当前实现：普通手工建模发布不迁移旧实例；发现来源的受治理发布可以在同一事务应用已审核候选的实例物化计划和 outbox。还存在发现终结/提交知识流程，手册应根据实际入口明确相应回执，不应教用户一律重复提交。当前 HTML 没有逐步示范发现来源的此闭环，也没有教候选物化失败后的结构修改、重新分析、再次处理。父代理代码审计证据：`knowledge_service/services/ontology_drafts_review.py:75–143`、`knowledge_service/repository/core.py:1886–1910`。[HTML:101–114；知识写入事实核实:20–39, 47]
2. **受控摄取的异常分诊。** 手册从提交直接跳台账，没示范抽取结果工作区如何核验、哪些条目需要接受/拒绝/整改。文档已区分结构待定、关系/SHACL 例外、候选物化失败、硬错误整批拒绝；这些情况不能共用“任务完成就是入图成功”的判断。尤其 SHACL `review` 路径可能已经保存知识，再产生例外/整改审核候选；不能把所有待审条目理解为未入图。父代理代码审计证据：`knowledge_service/services/service.py:802–828`。[HTML:101–114；知识写入事实核实:41–53]
3. **业务需求到验收的闭环。** 手册以张三案例讲模型和修订，但没有让用户先定义业务问题、预期答案、必需术语/关系/属性，之后针对这些要求验收。指定差距明确承认产品尚缺“业务问题—本体术语—验收结果”闭环，业务材料的覆盖率、召回率、正确率持续评测集也尚缺。[能力差距:15, 32–34]
4. **真正回答业务问题的操作。** 第 11 章教看回答证据，但没用固定问题展示检索范围/模式、成功答案、缺证据或冲突时的处理；模型存在冻结原文并不能证明答案正确。非流式 JSON 问答也未与流式统一溯源路径。[HTML:257–273；能力差距:14–15, 33–34]
5. **并发与变更失败。** 当前 HTML 排错没有草案基线过期、来源变化、其他管理员先发布、重新基线、迁移选择变化需重预演等完整实例。手册重写设计要求过这些异常，但设计要求不是实际手册已覆盖。[HTML:294–318；手册重写设计:3.3]
6. **内容源持续更新。** 有记录修订和冻结原文说明，但没有完整示范源文档新版本/删除后重新抽取、同一事实多来源冲突、实体消歧/重复融合、存量知识是否重校验、索引失效及补偿的业务操作。不能从本体 v3 演示推定这些链路全部不存在；只能断定手册没教完整流程。[HTML:193–255, 262, 282–287]
7. **质量警告统一处置。** HTML 自己明确当前页面主要展示业务警告，Semantica 警告没有统一逐条确认入口；用户要另查接口中的质量报告。这是已接能力与可操作产品入口之间的真实断点。[HTML:270–271；能力差距:11]
8. **运行验收可执行化。** 当前章说明 API 与状态，但没有从 pending/retry_wait/failed，到定位原因、repair/retry、确认版本和模型/记录指纹一致、再验证检索召回的具体任务案例。[HTML:279–293；能力差距:13]

## 对标后操作会有什么差别

以下是针对“后续差距”的建议操作设计，不是当前已经存在的页面。

| 补齐项 | 现在的操作 | 完成后建议操作 | 预期收益与代价 |
|---|---|---|---|
| 业务问题与可执行验收 | 先建类/关系，再看结果像不像 | 创建项目时记录用例/问题/预期答案 → 映射本体术语 → 固定材料验证 → 发布前后回归 | 前期多一道需求工作，后期少返工；判断“图谱可用”有依据 |
| 统一质量产品入口 | 业务警告看界面，Semantica 报告另查 API | 一张校验报告展示阻断/警告/指标/阈值/版本 → 修复/写理由确认 → 重新校验 | 减少切换、漏确认；高风险修改仍需人工复核 |
| 本体切片召回评测 | 收据能审计选了哪些术语，无法证明没漏 | 固定样本预览术语/预算 → 检查预期术语召回 → 调整别名/映射 → 比较评测后上线 | 减少漏抽与重抽；向量检索和预算优化需有样本证明收益 |
| 两种问答入口统一溯源 | 主页面能审计；JSON 接口尚未统一 | 网页和外部客户端同样保留冻结证据、版本和通道 | 集成和审计更一致，不必在不同入口重复排查 |
| 固定评测持续运行 | 历史测试验证实现修复 | 每次本体/模型/切片规则变更跑覆盖、召回、答案正确性和错误案例 | 把发现错误前移；需业务人员维护样本 |
| 跨本体复用（有需要再做） | 仍需人工语义对齐 | 选择固定版本 → 导入闭包 → 映射 → 冲突审查 → 发布与复测 | 跨域场景可能省建模，简单单域项目反而增加操作复杂度 |
| OWL 推理（有需要再做） | RDF/SHACL/业务约束和子类闭包 | 定义支持的 OWL 子集与推理规则 → 一致性检查 → 查看推导证据 → 单独验收 | 可回答逻辑蕴含问题；不能把占位模块包装为推理，也不保证日常操作更快 |

依据：能力差距:8–20, 32–40。

建议角色分工为业务负责人维护验收问题和预期答案，本体管理员审核结构及影响面，知识运营处理抽取结果/例外/消歧，平台运维处理索引和任务，查看者消费检索问答。**这是工作职责设计，不是当前已实现的新 RBAC 角色**：账号手册目前只有 superadmin/admin/viewer，且明确角色全局、没有项目级权限。[账号手册:80–86, 286–292；HTML:17–36]

## 推荐完整流程与先后次序

业务场景与验收问题 → 项目/本体初始模型 → 输入模式分流 → 抽取/发现与证据核验 → 结构及例外治理 → 本体发布/候选物化或受控入图 → 正式台账及索引对账 → 检索问答业务验收 → 持续文档更新/记录修订/本体迁移 → 固定样本回归。

先修手册（唯一现行版本、三种输入模式、异常分诊、索引与发布完成标准），再补业务问题验收和统一质量入口，再测本体切片召回和统一问答证据。只在确定需求后再做完整推理与跨域复用。这与指定差距文件的优先级相符。[能力差距:19–20, 39–40]

“更完整”主要来自增加业务验收和缺失分支；“更合理”来自分清结构发布、事实写入、异步索引和业务判断；“更高效”要靠统一入口、批量处置和减少返工。尚无用户耗时、返工率或操作次数实测，不能保证性能/操作效率提升，更不能给出百分比。[HTML:164, 282–293；能力差距:9, 11, 13, 15]
