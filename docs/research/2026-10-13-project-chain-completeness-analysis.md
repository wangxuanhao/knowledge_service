# 当前项目链路、操作手册与 ontology 差距分析

日期：2026-10-13。依据当前源码、当前 HTML 操作手册及 `docs/2026-10-12-ontology-capability-gap.md`。

## 结论与核查边界

当前项目具备知识图谱应用的主要功能闭环：项目与权限、本体建模和版本治理、文档摄取、候选审核、正式知识存储、实例治理、检索问答、来源追踪及派生索引补偿。可定位为具备治理能力的知识图谱应用，不能把它认定为已经完整支持 OWL 逻辑推理、跨域本体复用或业务正确性持续验收的平台。

当前 HTML 手册是较完整的受控建模与实例维护教程，但不是覆盖全部模式、分支和恢复操作的完整运营手册。已有第 11、12 章覆盖冻结来源、Semantica 质量检查、身份、任务及异步索引，不应将这些现有内容误报为完全缺失。

本轮为源码和文档核查：代码图谱 MCP 的项目查询持续未返回，终止等待后按本地源码回退。对 `http://127.0.0.1:8100/livez` 和 `/readyz` 的只读请求均无法连接；仓库 AGENTS 指定的 `D:/Anaconda3/envs/model_agent/python.exe` 在当前主机不可用。本轮没有运行全量测试或真实 LLM 摄取。差距文档里的 1596 passed、12 条真实链路通过是历史记录，不是本轮重新取得的结果。

| 环节 | 已有实现依据 | 操作上的限定 |

| 索引补偿与对账 | `ontology_sync.py:50-140` 租约、批写、重试；`:145-164` 核对本体版本、模型、记录指纹 | 本体发布成功不等于 Milvus 已同步；未启用 Milvus 时也不能误判为同步失败，应先看 configured |
| 索引恢复入口 | `api/ontology_drafts.py:102-108` 查询项目索引状态和发起 repair | 使用当前项目的对账结果，而不是只看向量服务进程 healthy |
| 流式问答 | `answers.py:173-184` 持久检索及答案活动、冻结证据摘要；`:220-222` 完成答案留痕；`answer_evidence.py:14-57` 从冻结溯源组装来源 | offered 记录的是当时提供的证据，不能据此自动证明每条结论都正确使用了证据 |
| JSON 问答 | `service.py:894-926` 复用检索上下文、组装证据及回答 | 未走流式入口的持久答案活动和冻结来源摘要路径，两种消费入口尚未完全一致 |

还有一个不能混淆的审核分支：`service.py:802-828` 使用 `shacl_mode='review'`，部分约束异常会作为“知识已保存，请确认例外或标记整改”的 validation 候选。因此手册应区分未入图的候选与已经写入但待整改的异常；不能把所有待审项都视为隔离区。

## 手册的完整程度

以 `docs/知识图谱操作手册.html` 为当前主教程：第 2 章默认本体、第 3 章发布 v2、第 4 章固定材料受控写入、第 5—9 章台账、结构变化、重分类、编辑和恢复，第 10 章版本解释，第 11—12 章来源与运行核查。

这一主线适合教会用户“先有结构，再写事实，再维护和消费”。还应补齐下列可照着操作的分支，而不只是解释概念：

1. 无本体或结构不成熟：创建空项目 → discovery 上传 → 检查候选和证据 → 归纳草案 → 校验审核 → 发布/物化 → 检查 skipped、未处理项和索引状态。
2. 本体已有但知识候选待处理：按实体依赖顺序处理关系/属性，解释拒绝、版本冲突、值冲突、约束例外的去向。
3. 只需文档问答：documents 上传 → 检索就绪 → 问答 → 核对冻结原文，解释为何没有实体关系也是成功。
4. 更新与恢复：本体更新后选择重分类还是重解析；上传失败/取消/重试分别保留了什么；索引异常如何重试及确认完成。
5. 业务验收：准备问题、预期答案、出处、适用时间；检查新版本是否改善答案且未损坏旧案例。

当前手册已经说明 Semantica 警告未统一进入逐条确认入口（HTML:270-271）。这体现的是产品入口还不完整，需要连接页面操作与质量报告，而不是仅增加术语介绍。

旧 `2026-10-01-本体工作台操作手册.md` 与当前 HTML 主线存在历史流程差异；README 已标旧手册过时，但 README 的部分旧审核说明仍与现有认证权限描述矛盾。应给旧文档显著历史标记，指定一个当前入口，并清理相互冲突的说明。

## 对标差距文档：操作会有什么变化

`2026-10-12-ontology-capability-gap.md` 是当前能力与剩余差距清单，不是另一套需要整体替换现有流程的操作规范。其优先项应嵌入现有流程。

| 建议能力 | 当前操作 | 补齐后的操作 | 预期收益与代价 |
| --- | --- | --- | --- |
| 业务问题与可执行验收 | 建类和属性、看校验报告、人工试问 | 先登记业务问题、样本和预期结果，绑定术语；草案/知识版本变更后运行同一组验收 | 减少“结构看着齐，但核心问题答不了”的返工；初期要准备样本，后续可复用 |
| 质量阈值与警告入口 | 查看现有警告，另行核对 Semantica 报告 | 同屏查看质量报告和业务验收结果，按严重程度修复或说明，再发布 | 减少页面/API 来回核对；业务指标应有明确解释，避免以分数替代判断 |
| 本体切片召回评测 | 词法选术语；人工从收据排查 | 固定材料跑召回评测，定位缺失术语；再按结果优化选择器 | 可能减少漏抽与全本体回退；只增加评测不会直接降低推理延迟 |
| 问答入口溯源一致性 | 主页面和 JSON API 留痕不同 | 两入口都输出可追踪的答案标识、冻结来源和版本 | API 消费者也能核对历史原文，减少审计歧义 |
| 外部本体复用 | 自建术语、人工判断映射 | 必要时导入固定版本，审核映射与冲突，再发布 | 跨域需求明确时减少重复建模；会增加导入与映射审核成本 |
| 完整推理 | 层级闭包、SHACL、业务约束与证据问答 | 有明确逻辑需求时增加真实推理器及蕴含结果解释 | 扩展逻辑能力，但增加性能和调试成本，不应作为所有项目必需前提 |

不能把 Semantica competency-question 的名称/关键词覆盖分数直接当作问题已可回答。应分别检查：本体表达能力、事实覆盖、检索命中、答案正确性、出处与时间正确性。SPARQL 断言适用于结构化事实验收；生成式问答还需要预期答案与证据检查。

## 推荐流程与实施顺序

目标流程：业务问题与验收材料 → 选择默认本体/空项目及摄取模式 → 建模或发现 → 结构与事实治理 → 业务验收 → 发布与相关实例处置 → 索引对账 → 检索问答与冻结来源核对 → 错误案例回流。

先补“业务问题—术语—材料—预期结果—版本化验收”闭环、统一两种问答入口来源、补全三种摄取模式和恢复流程的操作教程。再依据业务样本优化本体切片召回和提示词预算。推理器与外部本体对齐按实际需求实施。

结论是：这些补齐会使流程更可验收、更合理，通常降低重复试问、漏抽排查、版本回归及审计成本；它们不保证按钮更少或单次操作更快。本轮没有时间/成本实测，不给出效率提升百分比。建议记录候选处理时间、人工待审量、返工率、术语召回率、问题通过率、证据正确率、token 成本与索引就绪耗时作为前后对照。
