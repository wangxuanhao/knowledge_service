# 上传引导、问答来源与 OWL 推理适配分析

日期：2026-10-13\
目标：让现有知识入图、审核、维护流程更顺畅，同时保持本体建模台可直接编辑，并保证知识可溯源。

## 结论

1. **上传结果页不应增加流程状态机。** 本体建模台的核心仍是画布直接编辑；编辑命令写入草案、校验审核、发布是数据治理边界，不需要再包装成“第 1/2/3 步”页面流程。
2. **上传结果可以增加局部操作建议，但只作为快捷入口。** 已入图知识可“去台账核对”，待确认候选可“去审核/在本体画布定位”，失败任务可“查看日志/重试”。这些按钮由本次结果决定，不增加新状态、不阻止用户直接进入画布。
3. **主页面流式问答的来源链已经较完整；非流式 JSON 问答没有走同一条持久溯源路径。** 两种入口返回的答案可能相同，但可审计能力不同，应优先统一后端组装，再考虑扩充 UI。
4. **完整 OWL 推理现在不适合直接接入生产链路。** 当前系统已经有实用的子类闭包、RDFS domain/range 业务校验和 SHACL；现有数据约束语义、版本/项目隔离和溯源模型尚未为 OWL 蕴含准备好。可做隔离试点，不能把 Semantica 0.7.0 的占位校验器当成 HermiT/Pellet。

## 1. 上传结果与直接编辑建模台

### 现状证据

- 结果抽屉按实体、关系、属性分组，显示“入图/待确认”数量，但每一项只是胶囊展示，没有直接处置或定位动作：`knowledge_service/web/ingest-results.js:207-245`、`:259-287`。
- 空结果文案把“仅文档检索”和“原文没有抽出知识”放在同一句话里，用户无法判断这是主动选择还是抽取结果：`knowledge_service/web/ingest-results.js:252-253`。
- 建模台的编辑入口本来就是直接操作画布，命令写入草案；画布模块明确以 `ctx.sendCommand` 为唯一编辑入口：`knowledge_service/web/ontology-model-canvas.js:11`。
- 建模台主控明确规定“画布编辑 → 草案 → 校验审核 → 发布”，编辑后的草案立即显示在画布上：`knowledge_service/web/ontology-model.js:15-16`、`:113-118`、`:222-250`。
- 历史版本只读是版本安全规则；最新版本或草案仍可直接编辑：`knowledge_service/web/ontology-model-canvas.js:730-732`、`knowledge_service/web/ontology-model.js:456-460`。

### 是否要改“下一步做什么”

不建议增加统一的“当前阶段/下一阶段”状态条，也不建议要求用户按上传、审核、建模、发布顺序逐页通关。那会把一个可直接操作的建模工作台变成向导，并产生新的流程状态维护成本。

建议只在上传结果卡片里增加**由结果触发的上下文动作**：

| 结果 | 建议动作 | 页面影响 |
| --- | --- | --- |
| 已入图 | `去知识台账核对`、`查看来源` | 打开既有台账/证据详情，不新增状态 |
| 待确认事实 | `去知识审核` | 带项目和候选范围定位，不强制跳转 |
| 待建模概念 | `在本体画布定位` | 画布仍可直接编辑，目标节点高亮 |
| 任务失败 | `查看任务日志`、`重试失败项` | 复用既有任务能力 |
| 仅文档模式 | 明确写“按所选模式未抽取图谱知识” | 解释用户选择，不暗示失败 |
| 抽取模式但结果为空 | 明确写“未识别出可入图知识” | 与主动的仅文档模式分开 |

这项属于**建议方案，尚未实现**。在没有代表性上传数据做真机验收前，不应直接改交互。

## 2. 问答来源是否完整

### 已有能力

- 流式问答先创建检索活动，冻结 offered evidence，再生成 `answer_id`：`knowledge_service/services/answers.py:174-184`。
- 回答完成后保存使用关系，并在结束事件返回 `provenance_complete: true`：`knowledge_service/services/answers.py:220-222`。
- 每条证据摘要从冻结的溯源图反查文档、版本、标题、原文、字符位置，并返回 `source_status`、`source_reason`、`provenance_ref`：`knowledge_service/services/answer_evidence.py:9-57`。
- 前端会展示一个或多个来源，并可打开溯源抽屉：`knowledge_service/web/workbench.js:534-564`、`knowledge_service/web/provenance-drawer.js:278-292`。

### 确认缺口

- 非流式 `service.answer()` 复用了同一套 `question_context`，但直接返回检索证据，没有 `begin_retrieval → complete_retrieval → complete_answer`，也没有冻结来源摘要或 `answer_id`：`knowledge_service/services/service.py:894-926`。
- 前端写的“推理路径”是从命中实体出发，沿关系边做无向 BFS；它展示连接路径，不是 OWL 逻辑蕴含：`knowledge_service/services/answers.py:41-77`、`:120-138`，前端说明见 `knowledge_service/web/workbench.js:513-527`。
- `offered` 表示证据曾提供给回答，不自动证明模型的每条结论都由它支持。现有引用检查能发现未知引用，但仍需要业务问答样本判断“引用是否真的支撑结论”。

### 优先改造建议

1. P1：如果非流式 JSON 有外部调用方，让它调用与流式入口相同的溯源应用服务，统一 `answer_id`、冻结来源和完成/失败终态。
2. P1：在来源卡明确显示“来源完整/来源缺失”及缺失原因；避免把“人工写入”和“历史来源缺失”永久合并成一个原因。
3. P2：建立固定业务问题验收集，检查答案、引用、原文定位和版本冻结，而不只检查接口能返回来源。

其中第 1 项会改变外部 JSON 返回结构和持久化行为；需要先确认该入口是否有外部调用方，再实施兼容方案。

## 3. OWL 推理是否适配当前项目

### 当前真正运行的语义能力

- 子类父级闭包和查询扩展已落地，可用父类查询召回子类实例：`knowledge_service/services/ontology.py:300-316`。
- 关系与属性约束是显式业务校验；多个 domain/range 当前按“满足其中任意一个”处理：`knowledge_service/services/ontology.py:318-326`、`:411-446`。
- 数据图可交给 SHACL 校验；这适合“缺字段/类型不合规要报错”的闭世界治理场景：`knowledge_service/services/ontology.py:327-409`、`:447` 之后的 SHACL 路径。
- 项目已有的 Semantica 质量门只包装 `ontology_quality_check`：`knowledge_service/integrations/semantica_ontology.py:33-90`。

### 不能直接接完整 OWL 的原因

1. **domain/range 语义冲突。** 标准 RDFS/OWL 中同一属性声明多个 `rdfs:domain` 或 `rdfs:range` 通常形成交集约束；当前业务实现把多值当作“允许类型之一”。若直接交给推理器，可能把实例推成同时属于多个类。要么先把业务“或”转换成明确的 `owl:unionOf`，要么限制试点本体每个属性只声明一个 domain/range。
2. **开放世界与治理校验目标不同。** OWL 缺少事实通常是“未知”，SHACL/业务审核则需要“缺少即违规”。OWL 适合推导，不能替代现有入图校验。
3. **推导事实还没有版本与来源模型。** 当前记录有项目、本体版本、知识修订和冻结原文。OWL 新推导出的事实需要记录所用公理版本、输入事实版本、推理器版本和证明链，否则会破坏现有可追溯性。
4. **现有 Semantica 接口不是完整推理器。** 安装环境中的 `OntologyValidator.validate` 明确写着 placeholder，HermiT/Pellet 一致性与可满足性逻辑为空：`D:/anaconda/envs/llm_model/Lib/site-packages/semantica/ontology/ontology_validator.py:326-359`。competency question 仅做关键词启发式：`.../competency_questions.py:241-276`。本体对齐只做命名空间与固定分数：`.../reuse_manager.py:154-210`。

### 适合的最小试点

只有出现明确的逻辑需求时再试点，例如：

- 等价类/等价属性带来的查询召回；
- 传递、对称或逆关系的派生；
- 不相交类与不可满足类的一致性检查。

试点必须满足：只读旁路、限定 OWL 2 RL 或更小子集、单项目单本体版本、固定输入快照、推导结果不直接写正式图、每条推导保存证明链，并用真实业务问题对比“现有闭包/SHACL”和“OWL 推理”的增益、误报与耗时。

在这些条件成立前，优先补齐问答来源一致性、业务验收集和上传结果的定位动作，收益更直接，风险也更低。
