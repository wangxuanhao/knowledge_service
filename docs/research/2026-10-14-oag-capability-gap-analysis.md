# 当前项目 OAG 能力与差距分析

日期：2026-10-14（Asia/Shanghai）。方法：优先用 codebase-memory-mcp 发现、读取和追踪；对图谱中行号过时的 service.py 用当前工作区 AST 核对。工作区存在其他进行中的修改，本文分析当前代码，未修改业务实现、未运行服务或复现开源基准。

## 结论与判断口径

若 OAG 指 Ontology-Augmented Generation（本体增强生成），当前项目已实现部分能力，可以定位为“本体治理支撑的图谱与文档混合问答”。本体确实参与建图和可选的类层级召回，但尚未贯穿查询规划、结构化执行、答案验证，因此不宜称为完整的本体驱动推理问答。OAG 没有统一的工程合格标准；此处“完整”是本文采用的目标能力口径，不意味着所有 OAG 必须具备完整 OWL 推理或业务 Actions。

## 核心缺口：本体没有贯穿消费链

### 1. 正式属性没有成为独立问答证据

`answers.question_context()` 的 direct 只取 entity/chunk，found 只加入 relation，最终 evidence 由这两组构成。正式 attribute 的 value/datatype 不被单独纳入证据。原文可能包含这些值，所以不是“所有属性问题都无法回答”，而是无法可靠利用已入图的结构化属性作计算和验证。正式属性已存在，应该补消费链而非重复建表。

### 2. “推理路径”实际是双向图遍历

`answers.py:41` 从任一关系端点走向另一端，输出 from/to/relation，但没有保存此次遍历相对原始主客体是否反向。它可展示连接和扩大召回，不能证明关系反向成立，也未执行传递性、逆属性、业务规则或条件判定。路径也未按问题所需的谓词/方向筛选。优先保留原始 subject/predicate/object 和 traversal direction，并明确展示为“关联路径”，只有执行了有证据的规则才称推导。

### 3. 生成仍以文本提示为主

流式 `answers.py:190` 与 JSON `service.py:943` 都主要向 LLM 提供 question 和 evidence 的 id/text，没有传入本体契约、结构化事实、属性值、执行结果与证明步骤。提示模型“依据证据推理”不等于后端实际执行了可验证推理。

### 4. 缺少 QA 查询规划与执行层

现有链路没有把问题绑定到类型、实体、谓词和属性后，产生可校验的多步骤查询计划。过滤、比较、聚合、排序、日期计算和多跳 join 没有独立算子接入 QA。`formal_writes._Planner` 是写入计划器，不是问答规划器。已有 SPARQL 可作为一个执行工具，但不需要一开始就让 LLM 任意生成查询。

### 5. 来源审计与答案正确性是两件事

`provenance.complete_answer()` 检查引用编号属于 offered 集合，保存 cites，并记录未知编号警告；没有逐结论判断引用是否支持它。流式持久溯源已有较好基础，JSON 入口需要统一。仍应补无引用结论、引用不支持结论、证据矛盾、证据缺失的可判定状态。

### 6. 尚无本次发现的端到端 OAG 质量基准

已有检索、切片、SHACL、来源等功能测试；不能据此证明业务复杂问答准确。图谱搜索未发现 RAGAS/业务 benchmark 主链，搜索结果不足以证明仓库或外部系统绝无评测。应建立固定问题集，分别测答案与引用正确性、数值结果、约束违反、拒答、延迟和 token，并对比普通 RAG、图邻域问答和本体查询。

外部来源、固定源码 SHA 与限制详见 [开源调研](../2026-10-14-oag-open-source-research.md)。

| 项目 | 对本项目最有价值的借鉴 |
| --- | --- |
| [OpenSPG/KAG](https://github.com/OpenSPG/KAG) | Schema 约束构建，独立 Planner/Executor，多步骤依赖，图查询和数值执行器，公开基准。其生成 Python 的数学执行器不等于形式化证明或安全沙箱。 |
| [Microsoft OG-RAG](https://github.com/microsoft/ograg2) | 按本体映射 JSON-LD，用含属性 key/value 的超图组织相关上下文，提供评测配置。适合参考结构化证据，不必整体改成超图。 |
| [Microsoft GraphRAG](https://microsoft.github.io/graphrag/query/overview/) | Local/Global/DRIFT 问题检索策略，尤其全局问题的摘要聚合；这些不自动等于本体规则执行。 |
| [LightRAG](https://github.com/HKUDS/LightRAG) | 检索上下文可检查、来源引用、RAGAS/Langfuse 等质量与运行观测。 |

`ontology-driven-dev` 是业务软件建模与生成路线，不应作为本体问答能力的主要对标；本地已有 2026-10-10 专门调研，本轮外部访问未独立验证。

## 建议实施顺序与验收

1. **P0：补结构化证据。** 将正式属性、类型、主谓宾方向、本体/事实版本、有效时间与断言原文共同传给生成器；统一 JSON/SSE 的溯源服务。验收：问“实体金额/截止日”能引用对应属性和原文，不靠模型从无关 chunk 猜。
2. **P0：避免把路径当证明。** 保留方向与反向遍历标记，正式/待定边界在路径中一致生效；引用检查扩展到逐结论支持。验收：A 采购 B 不被当成 B 采购 A；证据不足会明确说明。
3. **P1：最小类型化查询计划与确定性执行器。** 先支持实体属性查询、条件过滤、比较、计数/求和、日期运算、限定谓词的多跳 join；每步保存输入、输出、事实来源。验收：计算答案可独立复算，计划类型或谓词不合法时拒绝执行。
4. **P1：业务评测和消融。** 从实际业务确定问题、期望答案、证据和时间版本，覆盖别名/父子类、反向关系、属性、计算、多跳、无解和冲突。功能测试与问答质量评测分开报告。
5. **P2：按明确需求增加规则/OWL 子集。** 例如逆关系、传递关系、业务期限或赔付规则。推导事实保存公理/规则版本、输入版本与证明；暂不直接写正式事实。发布本体变化后的索引与缓存一致性应复用现有治理再做核对。

不建议直接接完整 OWL 推理器：`ontology.py:411` 对多个 domain/range 按任意一个满足，与标准 RDF 多 domain/range 的交集语义存在差别；`pyshacl` 的 RDFS inference 用于校验，并非问答证明服务。先明确治理约束、逻辑蕴含和业务规则的不同语义。

若用户目标是 Palantir 式业务操作型平台，还需要另评估对象级权限、Action/Function、审批、幂等和执行审计；这些不是本轮知识问答型 OAG 必须一次性补齐的要求。
