# Ontology Playground 对当前知识服务的借鉴分析

日期：2026-10-15。范围：源码调研与改造建议；没有实施业务代码修改，没有运行浏览器或服务测试。

## 结论

可以参考 microsoft/Ontology-Playground 的交互组织方式，尤其是类与属性的可视化设计、术语选择与图谱高亮、自然语言入口与解释联动。当前项目已有更完整的事实版本、证据与本体治理流程，建议在这些流程之上改操作体验，而不是整体替换为演示应用。

参考项目下载到 `D:/workspace/references/Ontology-Playground`；固定 commit 为 `9ec82ec6605de15dd50c2254a169986c0b2bd7cc`。外部项目的具体实现和许可证以同目录调研文档 [源码分析](2026-10-15-ontology-playground-source-analysis.md) 为准。

**最重要的区别：参考项目主界面 NL2Ontology 是前端规则与示例响应，不是 LLM 执行真实业务查询。可选 Azure OpenAI 本体生成 API 是另一项能力。** 不应把它的界面表现当作完整自然语言图数据库查询能力。

## 三种借鉴路线

| 路线 | 好处 | 成本与不足 |
|---|---|---|
| 在现有原生 JS 前端渐进增强（推荐） | 能复用草案、事实写入、权限、历史与证据，先解决编辑困难 | 需要抽出共用编辑器与画布操作适配接口 |
| 将参考项目界面整体移植 | 可以较快接近演示外观 | 需要适配前端栈和数据模型；演示查询、存储不能承担现有治理责任，移植不是直接接上接口 |
| 先只新增自然语言查询侧栏 | 对既有页面影响较少，可先验证问题覆盖 | 台账编辑与图谱维护的障碍仍在，且要明确查询计划与失败行为 |

## 本体建模：左侧术语、中央画布、右侧属性、下方变更

建议保留现有草案/审核/发布机制，增强一套稳定的操作：

- 左侧按类、关系、属性检索术语；中央展示类继承和关系类型；右侧编辑名称、说明、父类、适用类、值类型及约束。
- 点选节点看详情；从一个类发起“添加关系”再点目标类；添加属性时默认归属当前类。已有两步点击连线可以继续使用，拖线是后续交互增强。
- 未发布修改在画布突出显示；变更清单展示改了什么、影响哪些已有知识、哪些约束不通过。
- 用户在画布修改的是草案；审核与发布完成后才成为正式本体。发现来源发布可能附带经过治理的实例物化计划，不能概括成所有发布永远不涉及实例写入。
- 移动节点是视图布局；修改父类、关系或属性才是语义变更。两种保存不要混在一起。

以上是建议，尚未形成经过用户确认的实施规格。

## 知识台账：以实体为中心维护，保留关系与属性的独立查询

建议主路径是“搜索一个对象 → 选择它 → 在侧栏维护”，而不是要求用户理解记录 JSON。

1. 台账默认实体清单，展示名称、类型、主要属性、来源数、更新时间与治理状态；关系和属性视角保留，便于跨实体查错与批量维护。
2. 同一对象详情提供属性、关联关系、原文依据、修订历史四个区域。每项属性和关系保留独立记录标识与版本。
3. 新增实体用本体中的类选择器；新增关系从当前实体发起，选关系类型和目标实体；修改属性按数据类型使用文本、数字、日期、枚举等控件。枚举/必填等规则应读取实际约束，不能仅凭 OWL domain/range 宣称所有业务约束都满足。
4. 新增、修订、软删除、恢复、融合复用既有服务，并携带已有版本号。版本冲突时展示服务端最新内容，允许用户比较后重试。
5. 融合时展示两实体的属性冲突、相关关系、证据来源和预期影响，选择保留者后提交；操作历史承担撤销，不让用户手工修 JSON 恢复。
6. 台账、主图谱使用同一详情与编辑组件。台账中“在图谱定位”和图谱中“在台账查看”继续保留。

台账目前只先取最多 1000 条并在客户端搜索、分页；因此不能用局部加载的表格总量进行全量维护判断。后续应补服务端搜索、分页、稳定排序和全量计数。[`records-view.js:417–442,499–506`]

## 主知识图谱：可以有类似交互，但维护的是事实实例

优先加这些直接操作：选实体看同一侧栏；在实体菜单新增关联实体/关系；点击边修订或软删除关系；在实体详情新增/修改属性；展开和收起一跳邻居；选择两个实体发起融合预览。属性默认在实体卡内展示，需要比较时才展开为值节点。

服务端已经会生成 `virtual: true` 的属性展示节点与边；它们只是视图投影，不能把虚拟 ID 作为实体/关系记录 ID 保存。编辑应转回原属性记录或所属实体。[`services/explorer.py:185–208`]

本体与主图谱可以共用选择、缩放、搜索、高亮和侧栏交互习惯，但各自调用本体草案操作和事实修订操作。客户端不得因画布支持删除就绕过权限、版本、证据、约束或审计。

关于渲染库：先复用已有 ECharts 完成侧栏、菜单和真实写入闭环；若实际需求包含频繁框选、拖线、局部布局、复杂边编辑，再评估主图谱迁到已在项目中使用的 Cytoscape。迁移前验证平行边、自环、中文标签、属性投影、大图性能与现有时间/类型筛选，不以演示观感代替验证。

## NL2Ontology / NL2KG 的建议实现

需要区分三个入口，即使最终出现在同一对话框里：

| 用户示例 | 实际意图 | 执行结果 |
|---|---|---|
| “哪些类型有生效日期？” | 查本体结构 | 术语清单、解释、在本体画布高亮 |
| “适用于平台 A、当前有效的规则有哪些？” | 查真实事实 | 按平台与时间范围执行，返回记录、来源、可探索子图 |
| “给规则增加生效日期属性” | 建模变更建议 | 生成待确认草案操作、差异与影响，再走审核发布 |

### 是否一定需要 LLM

固定问法可以用词典、别名和规则识别，不需要 LLM。参考项目主界面就是这种方式。但开放中文表达、同义词、复杂条件与多跳语义，建议使用 LLM 负责生成受限制的结构化计划；真正查询、计数和写入仍由后端确定性代码完成。

建议链路：用户问题 → 意图分类 → 取当前项目适用本体术语/别名/约束 → LLM 生成结构化查询计划 → 校验术语、类型、项目权限与范围 → 执行 → 返回记录、证据与图谱高亮 → 可选 LLM 根据真实结果解释。

结构化计划只允许定义好的字段，如 `intent`、`entity_type_iri`、`predicates`、`filters`、`valid_at`、`known_at`、`applicability`、`hops`、`limit`。项目标识与权限范围由服务端绑定，不能由模型提供。歧义时先询问用户，例如“规则”对应哪个类、“有效”按哪个日期判断。

这里的计划格式是建议新增的接口，**不是当前已有能力**。第一版适合支持术语查询、类型过滤、属性条件和一至两跳关系；统计与更复杂连接需明确实现和测试后再开放。可以由后端编译成既有 scoped/graph 查询，或受限 SPARQL；不能把模型输出未经校验直接作为 SQL/Cypher 执行。

执行要明确资源预算、最大跳数、最大返回记录数和超时；精确 COUNT 应在完整授权范围计算，不能对检索 Top-K 或已加载 1000 行做计数再称为全量结果。查询回执应展示实际解释、使用的范围、是否截断及错误原因。

自然语言修改另走命令建议链：生成原子操作 → 展示差异和影响 → 用户确认 → 既有写入/审核。LLM 没配置时保留表单、筛选、固定模板查询，不使用示例答案伪装成功。

### 如何验证它确实可用

建立一组真实中文问题，覆盖本体术语、实体过滤、属性范围、关系路径、平台适用范围、有效时间/认知时间、同名歧义、无结果和越权情况。对查询记录 ID、聚合值、范围和证据检查，而不是只检查回答通顺；修改建议还要检查不会直接发布或绕开事实版本。

## 补充：路径循迹值得优先引入

参考项目实际实现是“选择两个实体类型 → 前端 BFS 求一条有向最短路径 → 展示关系链与跳数 → 图谱高亮”。无需 LLM，且不是实例数据查询；细节见配套源码分析的 Path Finder 章节。

建议在当前系统区分三个用途：

| 用途 | 路径节点/边 | 回答的问题 |
|---|---|---|
| 本体结构路径 | 类与关系类型 | 两类对象在模型中如何连接？ |
| 实例关系路径 | 真实实体与事实关系 | 两个具体对象通过哪些已记录事实相连？ |
| 证据溯源 | 事实、断言、文档片段与原文 | 这条关系为什么被记录，依据在哪里？ |

实例路径中的每条边应能点击查看关系记录、来源原文和修订信息。示例“平台 A ←适用于— 规则 R —要求→ 材料 M”只是操作说明，实际展示必须由当前范围内的事实计算得出。结构上可达不意味着存在实例路径；最短路径也不意味着最可信或因果关系。

当前问答已有 `services/answers.py` 的 `_reasoning_paths`，从检索种子沿提供的关系做有限跳 BFS，再返回链条。这是可复用的展示/计算基础，但不是已经完成的任意两点寻路接口。该函数把关系两个端点都作为可遍历方向，且为每个到达节点保留一条首次到达路径；不能把其输出直接宣称为遵循关系方向的完整推理证明。[`knowledge_service/services/answers.py:43–88`，本次实际文件核对]

第一版建议支持“设为起点/终点、最大跳数、按关系方向/忽略方向、路径链、整条高亮、点击边查证据”。忽略方向只改变搜索方式，显示仍保留原始关系箭头，并标出逆向经过；无路径应表述为“当前范围和跳数内未找到”，而不是“没有关系”。项目、权限、平台适用范围、有效时间与认知时间要与查询一致。服务端按完整授权范围寻路，不能只在浏览器已加载的子图上断言不可达。

多条路径、指定必经点、排除关系、逐步播放和影响范围分析可以在基本闭环后追加。逐步播放属于我们可新增的交互建议，不是参考面板现有能力。LLM 只需在用户自然语言说“平台 A 与材料 M 有什么关系”时辅助解析起终点和条件，路径本身由图算法求得。

## 推荐顺序

1. 先建设台账与图谱共用的实体详情/表单编辑器，解决用户现在最难完成的维护动作。
2. 给现有本体画布与主图谱补齐可理解的操作菜单、变更预览和写入反馈。
3. 接入真实的本体结构查询和受约束的自然语言事实查询，并让查询结果驱动画布定位/高亮。
4. 最后再根据实际编辑需求评估图谱引擎统一和自然语言建模建议。

下一步若进入实施，应先确认第一阶段的交互规格与验收场景。本调研不承诺已有任意自然语言查询、完整 OWL 推理或大规模图编辑能力。
