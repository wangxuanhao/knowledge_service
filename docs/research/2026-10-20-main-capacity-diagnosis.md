日期：2026-10-20。以下是两次单次诊断，不能作为 P95 验收或与前一天结果直接比较得出提速比例。

项目：**容量验收 · 15万实体 / 30万关系（保留测试）**，ID `46249548-2189-4ad7-8f23-70ee2bcc7f6f`。迁入主应用后有 150,001 个实体、300,000 条关系，原容量库保留。原有 8 个项目与 2 个账号未修改，未复制认证表。Milvus 采用独立集合代际，450,001 个向量已做逐行回读核对。详见 [迁移核验](2026-10-20-retained-capacity-migration.json)。

在项目内搜索“真实大库编辑验收实体”可测试受本体治理的编辑、修订和历史；本次诊断完成一次成功保存，r4 → r5。大量合成夹具并非完整绑定本体的业务事实，不能用任意夹具代表治理编辑。数据和同类复用的真实模型向量用于容量测试，不能用于业务语义相关性验收。

## 一条正式实体修改为什么慢

实际 PUT 返回 200，客户端用时 **102.888 秒**。模型已经预热。

| 阶段 | 秒 | 含义 |
| --- | ---: | --- |
| 规划时的全项目快照 | 34.292 | 读取当前记录、构造 Python 对象、计算权威指纹 |
| 执行时重新取快照 | 29.887 | 为保证执行前权威状态未变化，再次处理全项目记录 |
| 预留操作时间 | 13.090 | 包含读取 450,004 个历史时间戳，读取/物化本身 9.723 秒 |
| 暖态模型编码 | 0.289 | 本次不是冷启动模型拖慢 |
| 时间线检查 | 2.499 | 执行前一致性检查 |
| 正式计划准备 | 1.546 | 写入准备 |
| 实际执行变更 | 0.102 | 不含重新快照、预留时间等治理工作 |
| 同步推动向量投影 | 12.211 | 远端调用、重试及投递等待尚未逐一划分 |

两次全量快照合计 **64.179 秒，约占 HTTP 时间 62.4%**。这是单条修改仍按项目总规模工作的主要证据。SQL `execute` 累计 6.013 秒，结果 `fetchall` 物化累计 32.226 秒；JSON 读写累计 21.182 秒。这些是嵌套计时，不能再与上表相加；不能把全部时间归为数据库执行或 JSON。

锁需要区分“等锁”和“拿着锁做事”：首次服务锁等待只有 10.8 微秒，但持有约 97.058 秒；仓储锁等待累计 0.197 秒。PostgreSQL 表锁语句执行约 4.1 毫秒，事务 advisory 锁约 2.1 毫秒。本次 141 个 PostgreSQL 观察样本未见 Lock 等待、阻塞 PID 或未授予锁，因此没有证据把这次修改解释为锁表等待或事务冲突。系统确实使用事务及表锁保护正式写入；长事务仍可能影响其他并发访问，不能由这一次样本推断并发没有风险。

观察采样间隔中位数 0.631 秒，最大 6.361 秒，无法排除短暂等待。HTTP 进入路由前约 5.824 秒、投影推进内部约 12.211 秒仍需更细边界。详见 [写入阶段数据](2026-10-20-main-governed-put-summary.json)。

## 全量图加载卡在哪里

同一主应用项目完整加载 **150,001 个实体和 300,000 条关系**，首次可见 5.413 秒，全部完成 **77.516 秒**。92 个请求均为 200，完整 ID 定位能打开真实详情，未出现脚本错误。详见 [浏览器阶段](2026-10-20-main-full-graph-client-phases.json) 与 [服务端汇总](2026-10-20-main-full-graph-summary.json)。

| 直接测得的阶段 | 秒 | 可得出的结论 |
| --- | ---: | --- |
| 服务端 92 个请求 HTTP 累计 | 65.478 | 本次请求顺序执行；加载的大部分时间在等待响应 |
| 仓储 RLock 获取等待累计 | 32.725 | 是应用进程内部共享锁的等待 |
| 最慢实体页 HTTP / 其中仓储锁等待 | 26.657 / 26.256 | 该页主要被应用锁挡住，并非该页绘图或 JSON 解析 |
| SQL execute 累计 | 20.137 | 包含驱动等待、数据库处理和传输，尚未细分 SQL 计划/IO |
| 浏览器 JSON.parse 累计 | 0.446 | 不是本次加载的主要瓶颈 |
| 布局 worker 往返累计 | 0.180 | 不是本次加载的主要瓶颈 |
| Renderer.sync 累计 | 1.831 | 包含 1.759 秒边位置计算，不能重复相加 |

图加载这次没有同步 PostgreSQL 锁观察，也没有记录应用 RLock 的持有者。日志里有同时发生的 450,001 行全量查询，但只凭时间相近不能指认某个 API 或后台任务就是持有者。下一步需要记录持锁线程和调用栈。不能把应用 RLock 等待叫成 PostgreSQL 锁表，也不能直接归咎于 Milvus。

浏览器 draw 的 CPU 提交计时不等于 GPU 完成时间。本次能完整绘制、定位，不代表全量加载速度已达标。前一天隔离的 5 次加载 P95 为 48.187 秒，30 秒目标未通过；今天单次 77.516 秒也不能替代该验收结论。

## 电脑资源的影响

写入期间应用 RSS 峰值约 5.132 GiB，主机可用内存最低约 1.929 GiB，内存使用率最高 93.9%，CPU 最高 99.4%。另外的 Milvus 观察发现 HNSW 索引构建仍在进行，CPU 和内存使用较高。资源竞争可能放大延迟，但没有做受控资源对照，不能证明电脑配置或索引构建是唯一根因。Windows 页文件用量不证明发生了磁盘换页。

当前直接证据支持：**优先改造单条治理写入中的全项目工作，以及跨请求共享仓储锁；再量化数据库分页查询与索引资源竞争。** 更换电脑不能替代对这些随项目规模增长的工作量的处理。

## 后续优化顺序与保护条件

1. 定位图加载期间的持锁调用，将只读长查询改为独立一致性快照或专用读连接。保留项目、本体、历史时点、端点与权限过滤，避免只为缩短锁而改变可见数据。
2. 将单条正式写入的权威校验从全量对象快照改为有明确定义的修订水位及受影响记录校验。必须证明能发现并发修改和本体基线变化，不能直接删除校验。
3. 优化历史时间戳预留，先证明所有合法时间表示和跨表范围一致，再考虑数据库聚合或单调水位；不能直接用字符串 MAX 取代现有语义。
4. 明确提交与投影就绪的边界，利用现有 outbox 展示同步进度与重试；数据库成功、Milvus 尚未就绪时应如实提示，不能静默改成关键词或本地向量。
5. 优化分页 SQL 与资源调度后，在同一数据、硬件和后台负载下重跑完整图、单条编辑、并发编辑和长期交互验收，报告 P50/P95 及失败率。

以上是下一阶段的优化工作，不是本次已经完成的性能修复。当前生产变更聚焦于界面对齐和视图交互修复，诊断包装未作为生产路由交付。
