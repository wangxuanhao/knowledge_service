# 页面缓慢：数据库、接口与渲染核查

核查环境：`llm_model`，现有 8100 服务，普通项目 `53264f57-4e9f-4cd5-a0f9-5a6f20181391`。测量时使用已认证只读接口；未修改普通项目业务数据。浏览器图谱创建的是读取会话。

## 结论

存在数据库侧的多余计算，但没有证据支持把所有页面缓慢归结为 PostgreSQL 整体性能差。已确认的主要问题是：多处前端同时持有加载职责；隐藏组件读取和轮询；启动依赖运行诊断；选择器触发所有项目统计；文本 JSON 反复解析；发现概览重复读取历史。

普通项目实际只有 67 条当前记录、4 份文档、28 个实体。另一个保留的容量项目有 450001 条记录；旧项目选择接口会聚合所有项目，所以它确实会把容量数据的统计开销带进普通页面启动。其他范围查询已按当前项目限制，不能将所有慢接口都解释成容量项目影响。

Docker 恢复后，独立数据库 `SELECT 1` 八次为 2.29–6.81ms，八次流水线合计 5.17ms；稍后有其他验证负载时十二次为 2.46–18.08ms。确认连接到业务库 `knowledge` 且目标项目存在，检查时阻塞连接和 idle-in-transaction 均为 0。该结论只覆盖采样时刻。查看的热查询已有索引；小型 assertions 顺序扫描约 0.4ms，没有必要据此增加索引。驱动耗时不等同于 SQL 执行时间，EXPLAIN 也不包含完整结果输出和客户端调度。

## 已修复

| 位置 | 原行为 | 本轮实现与验证 |
|---|---|---|
| 启动 | 项目列表两次；先等 health 中的 Milvus 探测 | 项目选择一次；独立公开鉴权策略，约 5–6ms；既有未认证遮罩保留 |
| 项目选择 | 全部记录/本体分组统计 | `include_counts=false` 只读目录；默认管理接口保持统计兼容 |
| 台账 Apply/Reset | scope 事件和 click 各触发一遍 | 唯一 scope 事件，真实模块探针各一次主分页 |
| 批次组件 | 隐藏时三次初始化读取，每两秒再读详情/items | 隐藏请求为 0；可见列表不逐项扇出；显式详情才读取和轮询；离开/切换/关闭取消且拒绝旧响应 |
| 本体建模 | 主控、目录渲染器分别读取草案目录；隐藏切项目也挂载 | 主控一次目录读取，目录仅渲染；保留多草案显式选择与发布硬校验 |
| 运行页 | 先加载旧分区再加载目标；无消费者也读全局 jobs | 先选目标再激活；只有后台 watcher 才读全局 jobs；真实控制器回归覆盖离开再返回 |
| 上传辅助 | 隐藏时读取词表，旧项目响应可能覆盖 | 实际打开上传时读取；项目/请求代际/可见模式共同校验 |
| OCR 能力 | 每次重读约 31.75MB 模型并校验哈希 | 按模型/清单/配置/运行包身份复用；实际引擎初始化仍强校验 |
| 资料摘要 SQL | 一份大文档重复转换文本 JSON 十次 | 同一行解析一次；四轮结果完全一致，202–382ms → 16–51ms |
| 发现概览 | 草案逐份查运行，生命周期再读一次历史 | 同一快照复用运行清单；相同路径 SQL 14 → 9；缺失引用维持原有查找/错误语义 |

台账网络里的四次 records/page 包含当前 kind 的 50 行主分页，以及三个其他 kind 的计数读取；后者不是相同查询的重复发送。本轮主分页重复已删除，多 kind 专用计数聚合仍属于后续设计。

## 实际耗时与边界

停止测试负载后的最终串行两轮（30 次请求均为 200）：

| 接口 | 两轮耗时 |
|---|---|
| 鉴权策略 | 2.7 / 4.1ms |
| 轻量项目目录 | 20.7 / 23.5ms |
| 台账实体分页 | 53.6 / 47.3ms |
| 资料摘要 | 102.0 / 75.6ms |
| 本体读取 | 27.4 / 25.1ms |
| 草案目录 | 35.4 / 33.2ms |
| 发现概览 compact | 318.5 / 205.0ms |
| 重分类计划 | 108.6 / 50.1ms |
| 筛选字段 facets | 79.9 / 83.4ms |

这轮说明普通项目在当前修复版本和较低负载下，主要读取已回到几十至几百毫秒。下面保留的较慢采样反映启动和并行验证负载的影响；没有将不同环境轮次当作严格的代码前后对照。

在一轮串行采样中，台账分页 118/167ms，资料摘要 219/263ms，轻量目录 43/83ms。另一轮重启后的采样出现明显波动：台账 241/246ms、资料摘要 363/1934ms、发现概览 1649/2922ms。两轮均全部 HTTP 200。不得只选最快一轮宣称全部页面已达标，也不能将 Docker 恢复产生的变化全部算作代码收益。

服务隔离剖析的最后一轮：资料摘要 126ms、实体页 56ms、发现概览 669ms。发现概览仍是主要慢项之一，虽然已删除五次 SQL，仍有九次查询及兼容历史计算。

真实 Chrome 页面核查无 pageerror，进入资料库一次目录请求、台账一次主分页、模型一次草案目录。资料库/台账分别静置六秒均为零请求。图谱首批实测 24 实体、30 关系，状态 paused（尚未请求剩余孤立实体），三次绘图为 0.2/5.6/11.7ms；不能把首批当成全量完成。该轮页面大部分长任务小于 200ms，图谱首批最长 298ms；模型首屏约 4.9s 主要等待接口，未发现对应多秒绘图长任务。此轮同时存在其他验证负载，属于当前运行表现，不是无负载性能承诺。

仍需继续按设计收敛的模块：发现生命周期专用读取模型、草案编辑共享预览上下文、台账计数聚合、dashboard 来源聚合和本体索引水位摘要。运行概览中的 Neo4j 检查也可能约四秒；它是连接诊断，与 PostgreSQL 分页性能应分别计时。

### 最后并发与浏览器复核

重点页面再次核查：资料库首屏约 615ms、台账首屏约 624ms、本体建模约 1551ms、图谱首批约 1009ms。四个页面无脚本错误，静置仍无额外请求。该轮台账 Apply/Reset 辅助请求曾出现 2.9/3.3s，不能用单接口耗时替代页面验收。

因此补做了真实台账七接口的串行/并发重放。批量来源请求使用当前可见实体的真实 ID，所有请求均 200。串行两轮总计 489/606ms，六路并发两轮总计 274/196ms，未复现连接池并发阻塞。浏览器资源计时复测中，系统网络设置下台账进入、Apply、Reset 最慢请求分别 182/165/287ms，筛选字段 224ms。禁用浏览器代理的对照中则为 302/208/248ms；没有稳定证据将波动归因于代理，所以未修改系统代理配置。

整体证据支持“已确认并修复的应用读取冗余 + 首次加载/运行负载下的波动”，不足以认定 PostgreSQL 缺索引或持续锁阻塞。首次挂载与秒级波动仍保留为性能边界，不宣称所有页面在任何负载下均低于 500ms。
