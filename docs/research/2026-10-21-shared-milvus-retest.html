结论

新方案在两个普通项目上已跑通：显式构建、原生关键词/语义/混合检索、已验证的筛选范围、项目隔离、单条修改后增量追平均有现场证据。不能据此宣称 15 万实体大库已通过完整性能认证。

本轮未修改应用架构代码；新增 HTTP 复测脚本及证据。当前还存在构建等待超时、健康检查接口不兼容、单写耗时波动，以及大库写入的全量快照路径。

方案与现场对齐

  • PostgreSQL 仍为权威源，schema 实际/期望均为 24。计划文档的“23/待迁移”已过时。
  • 唯一集合 knowledge_vectors；21 个固定列，按当前目录增加可空筛选列；目录仍混入技术字段，需要收敛。现场最终 37 列，dynamic 字段关闭，向量 1024 维。
  • 当前检索走 Milvus 排名和条件，再对有限命中回填 PostgreSQL；120 个正式基线请求均声明 _backend=milvus、degraded=false。
  • 启动后集合仍为 0 条，未建索引的关键词搜索返回 503 并明确提示向量化；未建项目的受控修改没有 Milvus 投影 envelope 或 dense 事件数据。
  • 只显式处理两个普通项目；保留的容量项目没有向量化，权威源仍为 150001 个实体、300000 条关系。

构建和修改：仍有问题

  1. 首项目首次构建约 135.9 秒（任务内部报告 134.87 秒）。该阶段包含字段准备、模型冷启动、编码、加载和校验。现有任务日志只显示统一阶段，没有足够细分计时，不能把全部耗时归为 Milvus 或数据库。
  2. 对照项目首次构建失败：create_index / wait_for_creating_index timeout in 20s。保留失败任务，随后通过同一显式入口重试，约 14.8 秒成功（任务内部 11.83 秒）。需要区分 RPC 等待预算与异步索引状态，并在显式任务中提供可恢复进度；不能靠自动重建所有项目掩盖。
  3. 小项目修改存在波动：未建索引时修改 1.330 秒、恢复 0.759 秒；建好后修改 0.855 秒、恢复 10.086 秒。每项仅 1 次，不作为写入 P95。并行读取另一个普通项目约 0.065 秒。需要继续细分主库写入、编码、Milvus upsert/flush 和队列追平。
  4. 健康检查误报：真实检索成功后，/api/health 仍因 MilvusStore.collection_dim 方法缺失而报告集合未就绪。页面如果使用这个状态，会显示错误的不可用提示。定位：services/runtime_capabilities.py 的旧接口调用。

编辑和恢复均产生正常历史版本，旧版本 CAS 提交返回 409。修改后的新版本已通过关键词检索验证；恢复后的规范内容与修改前一致。构建代次保持 1，索引已追平权威水位。

bf_ 与平台状态的字段边界

bf_ 是应用给 metadata 平铺列自动生成的名字，后缀由字段路径和类型生成；它不是 Milvus 强制的命名。metadata.title 目前映射到 bf_c9bc0d332084202b2993。平铺是为原生标量过滤，哈希命名是处理路径合法性和跨项目类型冲突的实现选择。

platform_mode 是既有适用范围规则的固定辅助列，与 platform_values 配合：specific 为指定平台列表，all 为全部适用，unknown 为未说明。只存列表会让 all 和 unknown 的空数组产生歧义。页面应显示指定平台、通用、未说明，而非原始 mode 列名。

当前自动发现仍把 synthetic_fixture、model、provider、extraction_method、ontology_slice.* 等技术/测试信息带入字段目录。这不符合“只纳入真实业务筛选维度”的边界。provider 筛选复测只证明过滤机制可用，不证明该字段应作为业务维度。建议收敛字段准入并显示可读映射；本轮未擅自清空或重建共享集合。

机器、数据库与 15 万节点边界

独立资源采样 148 次、PostgreSQL 采样 139 次；可用内存最低 5.44 GiB，服务 RSS 峰值 2952 MiB。主机 CPU 中位占用 99.8%，峰值 100%。本轮有明显主机 CPU 竞争，无法据此给出隔离环境下的 SLA。

采样中阻塞后端峰值 0、未授予锁峰值 0；未观察到锁表/事务冲突引起的等待。这不是对所有未采样时刻的保证，也不等于没有应用锁或 Python 全量处理。

容量项目每页读取 20 实体，20 次均成功，P95 0.099 秒。未重新测试全量 15 万节点图形加载、15 万向量构建、容量项目单条修改、并发吞吐和检索质量。

静态审计发现的大库写入风险仍在：service.write 规划读取完整项目快照，execute_formal_write_plan 执行再读完整快照并比对指纹；_reserve_record_operation 仍取回全部历史 recorded_at 后在 Python 求最大值。定位 core.py 的 1121、1153、842 行附近，以及 service.py 的 210 行。它们与 Milvus 是否共用一个集合无关；即使记录全在一张表，重复全量取回、解码和指纹仍会随数据量增大。这一结论来自当前源码，不能伪装成本轮大库写入计时。
