# 30 万节点：纯 CPU 加载、持久缓存与 Hindsight 对照

日期：2026-10-27。范围：性能诊断与独立测试夹具；未将缓存、加载器或渲染方案接入产品。

## 先回答“存起来下次打开会快吗”

**完整数据快照有帮助；只保存坐标帮助很小。** 当前稳定 ID 布局本身约 0.25 秒，主要时间花在分页反复构建数据、对象恢复和 CPU 绘图。完整快照绕过了大量小分页；IndexedDB 仍须反序列化对象、重建绘图资源并重新绘制，不能等同于秒开。

**现有方案尚不能判定满足纯 CPU 的 30 万节点交互要求。** 两档数据都完整显示了 30 万节点，但连续相机交互帧间隔 P95 为 68–79 ms，高于本次用于对照的 33 ms 目标。这个目标是测试建议值，不是用户已经确认的最终验收标准。

## 测试边界与 CPU 证据

- 本机 CPU 为 Intel Core i5-1340P（12 核 / 16 逻辑处理器）。使用未修改的 `knowledge_service/web/full-graph.js` 中 `GraphDataset`、`Renderer`、`SessionLoader`。测试文件位于 Git 忽略目录 `.benchmarks/graph-cache-assessment/`。
- 独立 Edge 测试进程带 `--disable-gpu --use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader`；实际 GL renderer 为 **SwiftShader Device (Subzero)**，即 CPU 软件 WebGL。没有更改用户浏览器配置。
- 合成数据通过本机磁盘文件和 HTTP 提供，包含 ID、名称、类型、版本、端点和全部关系；不是生产数据库性能测试。合成顺序 ID 的压缩率偏高。
- “新页面首次加载”没有清空操作系统文件缓存，不称作磁盘完全冷启动。浏览器重启测试确实关闭并重新启动专用浏览器进程、复用测试 profile。
- 当前产品 API 开启认证，匿名项目读取返回 401；未绕过认证，也未向业务库写入数据。因此真实 PostgreSQL 查询、业务鉴权、部署网络、真实标签长度与端点分布仍未验收。
- 每次完整恢复检查实体/关系数量、索引数量、坐标长度和首尾 ID；首帧计时包含 `gl.finish()` 和两次 rAF。检查不是逐条内容校验和，也不覆盖真实数据的所有异常。
- 帧间隔来自短时相机连续变化；内存是 JS heap，不是浏览器总 RSS，也不证明 30 分钟稳定性。所有秒数为本机短测结果，不能推广成所有 CPU 的承诺。

关系更多那档单次重启恢复反而较快，帧间隔也较小，反映采样、GC 与调度波动，**不能解释为关系越多越快**。快照生成是本次合成夹具的离线准备时间，不含真实业务数据库导出或拓扑布局。

现有每批 400 条加载器在相同合成本机 HTTP 下，两档均在 90 秒期限内未完成：

| 目标规模 | 截止时已加载节点 | 已加载关系 | 请求数 | 结果 |
|---|---:|---:|---:|---|
| 30 万 / 60 万 | 274,001 | 274,000 | 688 | 90.141 s，未完成 |
| 30 万 / 150 万 | 300,000 | 321,200 | 806 | 90.178 s，未完成 |

快照测试与分页路径的数据规模相同；这说明当前小分页、重复构建与上传路径值得优化，不证明真实服务端全量导出能达到本机夹具的速度。

## 持久缓存失效验证

在 1,000 节点控制组中，对水位、布局版本、范围、用户、项目、策略版本的变化，以及权限撤销、权威校验失败、坐标截断，共 9 项，均在绘制前返回缓存未命中或拒绝。原型每次先做权威校验，不能仅凭本地缓存显示旧权限下的数据。

这是**测试原型的行为**，产品尚无这套持久缓存；也不意味着已实现生产版本的一致性、退出清理、容量淘汰和损坏恢复。

## Hindsight 的加载与缓存机制

固定研究版本为本机 `ghcr.io/vectorize-io/hindsight:1.1.0`，官方 commit `a5a619b5ca59c5c39e0f96be6f7a31fabd136bd5`。更多绘图源码依据见[前一份研究](2026-10-26-hindsight-graph-rendering-research.md)。

- 首页请求 200 个节点；Memories 默认请求 1,000 个节点。“加载更多”增加 limit 后重新读取。不能把 bank 存储量当成浏览器实际显示量。
- `graph-cache.ts` 使用模块级 Map，最多 9 份查询结果，30 秒内视为新鲜，过期后先显示旧值再后台刷新；会预取相邻类型，并复用相同查询的进行中预取请求。这是**页面运行期内存缓存**，该模块没有 IndexedDB 或图快照磁盘持久化。
- DataView 对后台相同结果保留原对象，避免不必要的布局。其 `sameGraph` 比较总量、边数、表格 ID/文本；本项目不能直接照搬它作为版本或权限一致性校验。
- Canvas 2D 空闲分支最多绘制 6,000 条边，标签按缩放和避让规则显示；每帧仍扫描所有已加载节点。悬停分支的关联边没有这一上限。

固定源码：[graph-cache.ts](https://github.com/vectorize-io/hindsight/blob/a5a619b5ca59c5c39e0f96be6f7a31fabd136bd5/hindsight-control-plane/src/lib/graph-cache.ts)、[DataView](https://github.com/vectorize-io/hindsight/blob/a5a619b5ca59c5c39e0f96be6f7a31fabd136bd5/hindsight-control-plane/src/components/data-view.tsx)、[Constellation](https://github.com/vectorize-io/hindsight/blob/a5a619b5ca59c5c39e0f96be6f7a31fabd136bd5/hindsight-control-plane/src/components/constellation.tsx)。

## Hindsight 实际界面的纯 CPU 扩容测试

使用本机实际 Next.js Memories/DataView 页面与原组件，仅在独立浏览器中将图 GET 转向独立本机 HTTP 压缩文件，不改 Hindsight 的服务、数据库或组件代码。额外禁用硬件 Canvas；CDP 确认 `2d_canvas=disabled_software`、`gpu_compositing=disabled_software`、GL 为 SwiftShader。

本实验采用最小图响应，没有真实记忆正文/表格元数据，也没有测详情编辑；目标是检验原组件随节点数扩大时的 CPU 成本。请求到 HUD 包括本机 HTTP 传输、gzip 解压、JSON 解析、组件准备与首次绘图提交，不含真实 Hindsight API/数据库读取耗时。解码到 HUD 用于观察组件准备与首次 CPU 绘图。HUD 来自 Canvas `fillText` 的实际调用，证明绘制命令执行，不能单独等同于合成器完成呈现或已可稳定交互。

两者页面 viewport 均为 1280×1000；本项目图容器约 1229×760，Hindsight Canvas 为 1166×700。布局、载荷字段及特效也不同；本项目测相机交互，Hindsight 测默认持续动画。结果用于各自的规模可行性诊断，不能当作严格同负载的渲染器排名。

最初发现测试工具直接注入的 gzip 响应不会执行 HTTP 自动解压，造成页面无数据；已用独立 fetch/JSON.parse 复现。改为解压 JSON 注入后可以绘图，但 74 MiB 数据经过测试协议又引入了明显传输开销。因此最终改用真实本机 gzip HTTP，并重新跑完全部 4 档；结论只采用 `results-http.json`，早期注入的超时及请求计时不纳入比较。

| 返回的节点 / 关系 | 首次请求至 HUD | JSON 解码完成至 HUD | 空闲帧间隔 | 后续 rAF 样本 | JS heap |
|---|---:|---:|---|---:|---:|
| 1,000 / 2,000 | 0.311 s | 0.227 s | P95 16.8 ms | 294 帧 | 17.0 MiB |
| 10,000 / 20,000 | 1.224 s | 1.105 s | P95 100.1 ms | 55 帧 | 56.5 MiB |
| 50,000 / 100,000 | 5.705 s | 5.399 s | P95 416.6 ms | 19 帧 | 176.8 MiB |
| 300,000 / 600,000 | 38.550 s | 36.839 s | 观察到 1,499.9–1,633.3 ms；样本不足，不报 P95 | 3 帧 / 2 个间隔 | 904.8 MiB |

各档解析结果均核对了完整返回量，HUD 均报告所有节点可见、0 标签；1,000 节点档画 2,000 条边，其余档位均只画 **6,000 条边**。默认远景没有同时展示节点名称。鼠标保持在 Canvas 外，避免触发未限流的 hover 关联边分支。3 档较小数据截图成功；30 万档截图在 5 秒期限内未完成，记录为 `screenshot_error`，不能宣称截图或稳定交互验收成功。

30 万档的 HUD 为 `300000 memories · 300000 visible · 0 labels · 6000 links · zoom 0.02x`。观察期为短时默认动画，没有测拖拽、深度缩放、真实详情读取或长期探索。1,000 节点早期探针曾出现较大帧间隔波动；最终表仅保留这次完整 HTTP 重跑，避免挑选最快结果或将单次短测当成稳定性能承诺。

结果说明 Hindsight 的默认小规模概览、页面缓存与视觉规则值得借鉴；**它当前的 Canvas 逐节点准备与持续绘图，在本机纯 CPU 的 30 万节点实验中没有提供流畅交互能力的证据**。不应把该产品常规页面的快，推断成原组件直接扩容到 30 万就会快。

## 建议与尚未证明的部分

1. 优先采用版本化完整数据快照，减少小分页与累计重建；同页切换保留对象和绘图资源。坐标可一并保存，但当前布局耗时并不是主要瓶颈。
2. 浏览器持久缓存作为加速层；服务端仍负责当前权限、数据水位与范围校验。按用户/项目/范围/策略/水位/布局版本区分缓存，数据或权限变更时拒用旧结果。
3. 纯 CPU 的持续交互需要另做绘图方案验证：按视口与缩放控制细节，空间索引限制拾取候选，远景可评估预生成密度图/多级图块，近景显示真实节点与关系。数据层仍完整保留 30 万节点；若采用聚合或边预算必须明确标注并可展开，不能用截断数据冒充全量。
4. 不直接复制 Hindsight 的持续 Canvas 动画和全节点扫描，不把它的 6,000 边预算当成本项目完整关系绘制的性能证明。图块、分级绘制和空间索引在本次尚未实现或测得达标。

用户要求先测试再确认实现。本次没有部署缓存，没有更换生产绘图器，也没有继续改本体扩展开关及局部/全量视觉样式。
