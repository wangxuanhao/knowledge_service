## 原因与修复

`LocalEncoder` 原本在第一次 encode 中导入 SentenceTransformer、加载本地权重，并在整个过程中持有编码器锁。冷启动成本由首个语义请求承担，后来的语义检索和问答继续等待同一把锁。热态复测正常，因此只测试热态会漏掉原故障。

现在应用 lifespan 启动一次后台预热；模型初始化状态使用独立的短锁。交互查询在等待编码器锁之前检查状态，初始化期间立即说明准备状态；关键词检索仍按原路径执行，不自动更换检索模式。加载失败保留脱敏错误，避免每个查询重新导入或加载；已加载模型的短暂推理失败仍可通过原 encode 路径恢复。

健康检查只读取准备状态，不加载权重；日志新增依赖导入、权重加载和预热总耗时，便于以后区分冷启动、索引请求和其他慢阶段。

## 依赖导入进一步分解

“依赖导入”对应 `from sentence_transformers import SentenceTransformer`，尚未读取 BGE-M3 权重。在新的独立进程中，仅执行该导入实测 40.20 秒；另一轮带 cProfile 的分段测量合计 48.28 秒：

| 连续、不重叠的阶段 | 版本 | 耗时 |
| --- | --- | ---: |
| PyTorch 导入 | 2.8.0 | 12.10 秒 |
| Transformers 的 AutoModel / AutoTokenizer 导入 | 4.55.0 | 28.16 秒 |
| SentenceTransformers 其余导入 | 5.2.3 | 8.01 秒 |

这些测量与原服务的 63.99 秒来自不同进程、不同运行时负载，且 cProfile 本身有开销，不能视为原请求每个阶段的精确分账。

已验证的加载开销包括：

- 导入日志记录约 4,173 个模块。SentenceTransformers 的包入口同时导入交叉编码器、稀疏编码器、训练器等模块，超出当前稠密向量查询所需的功能。
- Transformers 4.55.0 的 `create_import_structure_from_path` 会扫描模型目录、读取源码中的导出定义，构造动态导入映射；本次剖析该路径累计约 9.43 秒。
- 整体出现 18,295 次文件状态查询（约 9.31 秒）、7,014 次最终路径解析（约 3.70 秒）、3,712 次代码文件打开（约 3.21 秒）。这些系统调用的开销贯穿多个库，不能再与上表阶段累计时间相加。
- 单独导入实验没有读取模型权重；原服务约 6.13 秒的权重加载是另一个阶段。未把某种安全软件、网络问题或硬件故障认定为上述系统调用开销的原因。

因此，几十秒属于依赖初始化过重的性能问题。后台预热消除了用户请求承担冷启动及锁排队的问题，尚未缩短上述依赖导入本身的成本；本轮只做测量，没有升级或替换共享 conda 环境中的依赖。
