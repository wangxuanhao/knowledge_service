# 空本体草案的阶段门禁设计

## 背景

本体工作台在项目尚无草案时，仍允许用户点击“设计”。前端随后请求草案列表；列表为空时只更新左侧列表，主画布继续停留在“正在加载草案…”，形成永久加载假象。

## 目标

- 草案列表已确认为空时，仅允许停留在“发现”阶段。
- “设计 / 审核 / 校验 / 发布”按钮在无草案时禁用，并向辅助技术暴露原生禁用状态。
- 空草案结果必须收敛到明确空态，不能保留加载提示。
- 从发现阶段成功生成草案，或选择已有草案后，后续阶段立即恢复可用。

## 非目标

- 不在点击“设计”时隐式创建草案。
- 不改变草案 API、草案生命周期或后端权限规则。
- 不重构本体工作台的阶段架构。

## 交互与状态设计

前端状态增加草案可用性：初始为未知，草案列表加载成功后变为有或无。未知状态不把“加载中”当成永久业务状态；列表明确为空后，同步禁用所有依赖草案的阶段按钮。

切换项目时，草案可用性必须重置为未知，避免沿用上一项目的门禁状态。

`setStage` 同时保留程序化门禁：即使外部代码直接请求进入非“发现”阶段，只要已知没有草案，也保持在“发现”阶段并给出“请先生成草案”的提示。这避免只依赖按钮的视觉禁用。

当草案列表为空且非“发现”渲染路径已经开始时，主画布显示可执行的空态提示，并清空加载态。创建草案或成功选择草案后，草案可用性改为有，阶段按钮解锁，按现有流程进入设计。

## 数据流

1. 打开工作台并加载发现数据、候选数据和草案列表。
2. 根据草案列表设置草案可用性并同步阶段按钮。
3. 无草案：保持发现阶段；后续阶段按钮禁用。
4. 有草案：后续阶段按钮启用；首次进入时沿用现有自动选择第一份草案逻辑。
5. 新建草案成功：立即标记为有草案并进入设计。

## 错误处理

草案列表请求失败仍沿用现有错误提示，不把请求失败误判为“没有草案”。只有成功响应且列表为空时才进入明确的无草案状态。

## 测试

在现有 Playwright 浏览器契约测试中让草案接口返回空列表，并断言：

- “设计 / 审核 / 校验 / 发布”均为禁用状态。
- 触发禁用按钮不会切换离开“发现”。
- 直接调用 `setStage('design')` 也不会绕过无草案门禁。
- 主画布不出现“正在加载草案…”。
- 现有有草案场景仍可进入设计并加载层级。
