# Knowledge Service 傻瓜级操作手册重写设计

## 1. 背景与目标

现有 `docs/知识图谱操作手册.html` 已覆盖登录、用户管理、知识写入、本体建模、知识编辑、软删除和提取审核等功能，但第 5～7 章没有形成可连续执行的业务流程，截图也存在中文标注乱码、红框遮挡控件、裁切缺少上下文等问题。

本次重写的目标不是增加产品功能，而是让第一次使用系统的读者能够只看手册完成一次完整操作，并理解每一步完成后本体、实体脑图、知识台账和版本信息分别发生什么变化。

## 2. 内容原则

1. 全书使用同一个连续案例：员工“张三”从“员工”重分类为“产品经理”，所属“产品部”。
2. 每个操作步骤固定回答四件事：在哪里、点什么、填什么、成功后看到什么。
3. 本体结构与实例知识分开讲述，避免把“新增类”误写成“新增实体”。
4. 版本名称统一：软件使用“服务 v1.1.0”，结构使用“本体 vN”，单条知识使用“记录修订 rN”；若当前界面仍显示 `vN`，手册明确注明它是该记录自己的版本，而不是本体版本。
5. 只记录当前产品真实能力。属性在本体画布中挂在类详情下，不绘制成节点；实体脑图当前不展示属性分支；知识台账可以切换到属性视角。
6. 每章都提供“完成标志”和“常见误解”，使用户可以自行判断是否操作成功。

## 3. 章节结构

### 3.1 起步部分

- 封面和阅读说明：说明适用服务版本、完整案例和三类版本。
- 系统概览与启动准备：保留现有部署、登录和项目概念，但压缩与主流程无关的说明。
- 角色和权限：使用实际角色“超级管理员 / 管理员 / 只读用户”。贯通案例由管理员账号执行；只读用户只能查看消费层，不能创建项目、写入知识或建模。

### 3.2 主流程部分

主流程只有一条确定路径，不在“新写入”和“迁移”之间留下二选一：

1. 超级管理员创建“管理员”账号，退出后由该管理员登录；后续主流程全部使用管理员账号。
2. 在“项目与运行 → 项目设置”创建项目，知识建模方式固定选择“加载默认本体 · 直接构建正式图谱”。创建完成时系统自动发布默认本体 v1。
3. 进入界面实际名称“本体建模层”，在默认 v1 上新增类“员工”“部门”、属性“工号”“入职日期”和关系“隶属于”，经“校验并审核”后发布为本体 v2。
4. 使用固定文件 `manual_employee_v2.txt`，解析模式固定选择“使用项目本体 · 正式入图”。文件正文固定为：“张三是一名员工，工号是 E001，入职日期是 2025 年 1 月 6 日。张三隶属于产品部，产品部是一个部门。”
5. 打开抽取结果；合法记录直接入图，待确认记录全部进入“知识审核”并逐条接受。最终验收不依赖某个固定抽取计数，而以台账中能查到两个实体、一条关系和两个属性为准。若实际走查不能稳定产生这组结果，则不得发布截图，必须调整固定材料或把无法稳定演示的记录移出主流程。
6. 在实体脑图和知识台账核对 v2 初始结果；台账分别查看实体、关系和属性三类独立记录。
7. 返回“本体建模层”，在 v2 基础上新增“产品经理”，父类为“员工”，发布为本体 v3。
8. 对比发布前后：本体画布新增类，但实体脑图和知识台账中的实例不会自动改变。
9. 执行受控重分类，把依据本体 v2 的既有记录迁移到本体 v3。此步骤只更新本体归属并为实际迁移的每条记录产生新修订；因为“员工”在 v3 中仍有效，“张三”的类型仍保持“员工”。
10. 在知识台账编辑“张三”实体，把类型从“员工”改为“产品经理”，单独产生该实体的新修订。
11. 对比迁移和编辑前后：脑图关系保持存在，实体类型变为产品经理，台账能分别查看各记录的修订号与本体归属。
12. 编辑“工号”属性，演示只有该属性记录产生新修订；随后软删除并撤销一条关系，查看结果和历史记录。

### 3.3 附录与排错部分

开放提取、确认性提取、实体类型关闭等不属于贯通案例的能力移到附录，优先级低于核心流程。常见问题重点回答：发布后数据为什么没变、为什么脑图没有属性、为什么记录版本与本体版本不同、为什么旧本体知识仍存在。

排错说明至少覆盖：未选项目或无权限、空项目尚无本体、没有可选父类或关系端点、校验失败、发布未就绪、草案基线过期或版本冲突、没有旧版本记录、没有可迁移目标、预演被拦截、选择改变后必须重新预演、知识写入失败或待审核、空台账、撤销成功和撤销失败。每项固定写“看到什么、原因、下一步”。

## 4. 贯通案例与状态变化

案例初始状态由手册前置步骤实际创建，不依赖预置数据：

- 创建项目时自动得到默认本体 v1；不把它写成用户手工发布的自定义版本。
- 在默认 v1 上发布自定义本体 v2：包含“员工”“部门”、“员工”的“工号/入职日期”属性，以及“员工—隶属于→部门”关系。
- 按本体 v2 写入实体“张三”“产品部”，关系“张三—隶属于→产品部”，属性“工号=E001”“入职日期=2025-01-06”。
- 实体、关系、两个属性是相互独立的知识记录，各自拥有记录 ID 和修订号；不能用“张三的版本”代替整组知识的版本。

第二次建模操作只新增“产品经理”并设置其父类为“员工”，随后发布本体 v3。

发布后的完成标志：

- 本体建模层能看到新类，原有属性详情和关系边保持不变。
- 实体脑图没有自动多出“产品经理”节点。
- 知识台账中的既有记录仍各自保持原修订号，并依据本体 v2。

迁移后的完成标志：

- 受控重分类后，各条被迁移记录依据本体 v3，但“张三”仍为“员工”。
- 随后单独编辑“张三”实体，其类型才变为“产品经理”，并产生该实体自己的新修订。
- 关系早在本体 v2 下写入，因此脑图仍显示“张三—隶属于→产品部”；重分类本身不创建这条边。
- 台账继续显示实体、关系和属性记录；实际参与迁移的每条记录分别产生自己的新修订，未参与迁移的记录不会跟随实体一起升级。
- “张三”实体的旧修订 / 本体 v2 以及迁移修订 / 本体 v3 仍能在历史记录中查看。

## 5. 截图与标注规范

### 5.1 截图来源

- 所有编号操作必须使用服务 v1.1.0 的实际运行界面截图；示意图只能解释概念，不能冒充操作截图。
- 统一使用 Chromium 内核浏览器、1440×900 CSS 视口、100% 页面缩放、DPR 1、PNG 格式；每张原图旁保存截图条件记录。
- 同时保留无标注原图和最终标注图，便于检查标注是否遮挡原始信息。
- 截图只保留完成当前任务所需的界面上下文；涉及左侧导航、项目选择或版本归属时必须保留对应区域。

### 5.2 标注方式

- 使用圆形编号 `① ② ③` 标记操作顺序，中文说明放在截图下方的步骤表中，避免字体乱码和长文字压住界面。
- 红框只圈定目标控件，边框与控件保留至少 6 像素间距；验收时在原图与标注图叠加对比，检查框内控件文字和输入值均完整可见。
- 单图最多标记三个连续动作；超过三个动作拆图。
- 不用半透明色块覆盖输入值、按钮文字、版本卡片或结果内容。
- 每张图都配“这张图做什么”和“完成后应看到什么”。

## 6. 页面呈现

手册继续交付为单个可离线打开的 HTML 文件，样式、脚本和图片均内嵌。核心页面能力包括：

- 左侧章节目录和当前位置高亮。
- 顶部“完整流程”进度导航。
- 操作步骤卡片、完成标志、注意和原理四类视觉区块。
- 发布前后与迁移前后的对照表。
- 三类版本关系示意和贯通案例时间线。
- 基础打印样式，确保分页时截图与图注不被拆开。更多视觉美化放在核心流程验收之后。

不引入外部 CDN、外部字体或网络图片，避免离线打开时样式和中文标注失效。

## 7. 验证标准

1. HTML 在无网络环境下可以打开，目录、锚点和内嵌图片正常。
2. 所有中文标注可读，不出现方框或乱码。
3. 每个编号都能在相邻说明中找到唯一对应步骤。
4. 所有红框不遮挡控件文字、输入值和结果信息。
5. 主流程从创建项目到迁移后查看脑图、台账可以连续执行。
6. 全文搜索不存在把本体版本和记录修订混为一谈的表述。
7. 明确说明属性在三个页面中的不同呈现：本体详情、脑图不显示、台账属性视角。
8. 明确说明发布本体不会自动修改实例知识。
9. 验证 HTML 标签闭合、内嵌资源可解析，并在浏览器中抽查桌面宽度和打印布局。

## 8. 范围边界

本次只修改操作手册及其必要的内嵌图片资源，不改变本体、脑图或知识台账的业务实现。只有在目标服务 v1.1.0 实际界面完成走查并取得截图的能力，才能成为编号操作。实际界面不存在的版本筛选、迁移入口或属性展示只能放在“当前不支持”说明中，不能成为步骤、完成标志或截图项。
