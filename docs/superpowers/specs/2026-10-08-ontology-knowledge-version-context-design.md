# 本体—知识双版本上下文设计

## 1. 背景与结论

当前系统已经分别保存本体历史和知识记录历史：

- `ontologies` 保存项目内不可变的本体发布记录；新数据在 `metadata.version` 保存本体结构版本号，早期数据缺失时按发布时间顺序回填。当前 `/ontologies` 接口仍用发布行序生成展示号，本能力必须把它收口到同一权威口径，见 4.3。
- `record_versions` 保存每条知识的双时态修订；`version` 是该记录自己的递增修订号，`version_id` 是不可变修订标识。
- 实体、关系、属性记录的 payload 已包含 `ontology_id`，受控重分类会生成新记录修订并把新修订关联到目标本体，旧修订继续保留。
- 本体建模页已经可以只读预览历史本体，也可以从历史本体派生新草案；知识台账已经显示本体归属，但没有统一版本筛选和知识修订时间线。

本设计保留现有存储模型，采用“两条独立版本轴、显式关联”的语义：

- 本体使用“本体 vN”。
- 单条知识使用“修订 rN”，不再称为“知识 vN”。
- 每个知识修订通过 `ontology_id` 固定关联其创建或迁移时依据的本体发布记录。
- 项目的最后一个已发布本体是“当前生效本体”；历史本体始终只读。

不创建全局“知识库版本”，也不在查询时用任意本体动态解释未关联的历史知识。

## 2. 现有架构落点

项目是单进程 FastAPI 服务：

1. `knowledge_service/api/knowledge.py` 暴露项目知识、本体历史、图谱和记录历史接口。
2. `knowledge_service/services/service.py::KnowledgeService.scoped` 是知识可见范围的统一入口，负责双时态、软删除、类型和端点完整性过滤。
3. `knowledge_service/repository/core.py` 负责 PostgreSQL 的 `record_versions` 与 `ontologies` 持久化。
4. `knowledge_service/services/reclassify.py` 负责旧本体知识到当前本体的只读计划、预演、执行与可撤销操作。
5. 前端是 `knowledge_service/web/` 下的原生 JavaScript：
   - `ontology-model.js` 保存本体画布状态和历史预览状态；
   - `ontology-model-panel.js` 渲染版本管理抽屉；
   - `records-view.js` 渲染知识台账；
   - `record-dialog.js` 渲染单条知识详情；
   - `workspace.js` 渲染交互图谱与实体脑图；
   - `workbench.js` 提供全局 `wb` 状态和页签切换能力。

Milvus只参与语义向量检索，不参与版本归属与历史计算。本能力的权威数据仍全部来自 PostgreSQL。

## 3. 目标

### 3.1 用户目标

用户必须能够：

1. 一眼区分当前生效本体、正在查看的本体和知识自身修订。
2. 切换到任意本体版本并只读查看结构。
3. 查看当前仍关联该本体的知识数量、类型分布和迁移状态。
4. 从本体版本直接跳转到已经按该本体筛选的知识台账。
5. 在知识详情中查看该知识的完整修订时间线，以及每个修订关联的本体版本。
6. 明确理解“发布本体不会自动改写知识；迁移会产生新修订”。

### 3.2 非目标

本次不做：

- 全局知识库快照或整库发布版本。
- 自动迁移全部旧知识。
- 改变现有受控重分类的审批、预演和撤销规则。
- 把属性改为本体画布节点或给实体脑图增加属性分支。
- 用历史本体直接编辑或覆盖当前本体。
- 修改 Milvus collection 或向量索引结构。

## 4. 版本语义与不变量

### 4.1 三类版本名称

| 名称 | 示例 | 含义 |
|---|---|---|
| 服务版本 | 服务 1.1.0 | 软件发布版本，仅在系统信息中出现 |
| 本体版本 | 本体 v3 | 项目级结构发布记录，包含类、关系、属性和约束 |
| 知识修订 | 修订 r4 | 单条实体、关系、属性或原文片段的修订序号 |

### 4.2 数据不变量

1. 已发布本体不可变；预览历史本体不写数据。
2. 已保存的知识修订不可变；修改或迁移必须新增修订。
3. 一个知识修订最多关联一个 `ontology_id`。
4. 结构化知识（entity、relation、attribute）没有显式 `ontology_id` 时由现有写入逻辑关联当前本体；显式指定项目内历史本体仍用于历史导入、普通修订和受控治理，并继续按该本体校验。本能力不收紧现有写入权限。兼容历史数据可以暂时没有 `ontology_id`，界面显示“未知本体”，不能猜测版本。
5. 发布本体不会批量改写知识。
6. 受控重分类产生 `rN+1`，新修订关联当前本体；旧修订保留原 `ontology_id`。
7. 当前知识是每个 record id 在所选双时态范围内可见的修订，不等于“属于当前本体的知识”。

### 4.3 本体版本号的权威口径

本体发布记录由不可变 `ontology_id` 唯一标识；面向用户的结构版本号按以下顺序解析：

1. 优先使用 `metadata.version` 的正整数值。
2. 旧发布记录没有该字段时，按项目内 `created_at, id` 的稳定顺序回填为第 N 个结构版本。
3. 纯标注发布可以复用同一个结构版本号；此时版本列表显示“本体 v2 · 标注修订”，并用 `ontology_id` 短标识区分两条不可变发布记录。

`GET /ontologies` 必须直接返回解析后的 `version` 和 `version_reused`，本体版本管理、知识台账、重分类标签和新增上下文接口全部使用这两个字段，不能在各前端页面再次按数组下标编号。历史项目的回填规则与 repository `_current_ontology_version` 保持一致。

## 5. 交互设计

### 5.1 本体页面版本上下文条

本体建模页标题下增加上下文条：

```text
当前生效本体：v3    正在查看：v2（历史·只读）    关联知识：128 条
```

规则：

- 默认查看当前本体。
- 通过版本管理选择历史本体后，画布进入只读预览，显示黄色历史版本提示。
- 历史预览期间禁止新建类、改父类、连关系、编辑属性和发布。
- “退出历史预览”恢复当前本体和原有草案上下文。
- “基于此版本创建草案”沿用现有 `forkFrom` 行为；不提供“切换生产版本”或“覆盖当前版本”。

### 5.2 版本管理详情

每个本体版本详情保留发布信息和现有两个操作，并增加“关联知识”区域：

- 当前仍关联：当前可见修订的 `ontology_id` 等于该版本。
- 实体 / 关系 / 属性：按 kind 分组统计；document 与 chunk 不计入本体知识影响。
- 待迁移：当前仍关联旧本体，且受控重分类计划给出可迁移处置。
- 迁移阻塞：当前仍关联旧本体，但计划为 `unmapped`。
- 已迁出：曾有修订关联该版本，但当前修订已经关联其他本体。
- 历史修订：所有关联该本体的知识修订数，包含已被后续修订取代的记录。

区域内提供“在知识台账查看”按钮。按钮切换到知识台账并携带选中的 `ontology_id`；不触发迁移。

### 5.3 知识台账版本筛选

台账增加本体归属筛选器：

- 全部本体（默认）
- 本体 vN（当前）
- 本体 vN（历史）
- 未知本体（仅兼容历史数据）

筛选的是当前可见知识修订的 `ontology_id`，不会把已经被取代的历史修订混进主表。主表版本列改为两行：

```text
修订 r4
依据本体 v3（当前）
```

状态徽标使用：

- 当前：关联当前生效本体。
- 待迁移：关联旧本体且受控重分类计划中有可用目标。
- 迁移阻塞：关联旧本体但没有可用目标。
- 迁移状态未知：关联旧本体，但受控重分类计划读取失败，前端不得猜测处置。
- 未知本体：没有可识别的 `ontology_id`。

不引入“兼容”状态。现有后端没有独立、稳定的兼容性判定；把“类型仍存在”直接显示成兼容可能误导用户忽略属性或约束变化。可迁移的 `carry` 仍显示“待迁移”，并在重分类抽屉中解释它只变更本体归属。

### 5.4 知识修订时间线

知识详情增加“修订历史”页签，调用现有 `/records/{record_id}/history` 接口，按修订号倒序显示：

```text
r4 · 本体 v3 · 2026-10-08 11:30 · 当前
r3 · 本体 v2 · 2026-10-07 16:20 · 已取代
r2 · 本体 v1 · 2026-10-06 09:05 · 已取代
```

每个节点展示修订号、不可变 version_id 的短标识、记录时间、本体版本、类型和删除状态。点击历史节点只读展示该修订内容，不允许直接保存；要修改必须回到当前修订并产生新修订。

### 5.5 图谱和脑图

本阶段只增加本体归属范围，不改变图的节点模型：

- 默认仍展示当前双时态范围内的最新知识。
- 从本体历史详情进入图谱或脑图时，携带所选 `ontology_id`。
- `KnowledgeService.scoped` 先按本体归属过滤，再计算 entity id 集合；关系或属性的主体不在范围内时继续按现有规则剔除，避免悬空边。
- 页面明确显示“知识范围：本体 vN”，并提供“一键恢复全部本体”。

## 6. 后端设计

### 6.1 扩展统一 Scope

给 `knowledge_service/models.py::Scope` 增加：

```python
ontology_scope: Literal['all', 'ids', 'unknown'] = 'all'
ontology_ids: list[str] | None = None
```

请求校验规则：

- `all`：`ontology_ids` 必须为 `None`，不限制本体归属。
- `ids`：`ontology_ids` 必须是非空、去重后的字符串列表，只保留这些本体发布记录关联的知识。
- `unknown`：`ontology_ids` 必须为 `None`，只保留缺少 `ontology_id` 或 `ontology_id` 不属于当前项目任何发布记录的知识。

不合法组合返回 422，不能静默忽略字段。`KnowledgeService.scoped` 把该条件应用在软删除过滤之后、entity id 完整性计算之前；`unknown` 模式从 repository 的项目本体列表得到合法 id 集合。

这样 `/records/query`、`/graph`、`/mindmap` 等复用 Scope 的接口可以保持同一过滤语义，不在前端各自实现不同版本规则。

### 6.2 本体知识上下文接口

新增只读接口：

```text
GET /api/projects/{project_id}/ontologies/{ontology_id}/knowledge-context
```

返回：

```json
{
  "ontology": {
    "id": "...",
    "version": 2,
    "is_current": false,
    "created_at": "..."
  },
  "current_bound": {
    "total": 128,
    "by_kind": {"entity": 60, "relation": 40, "attribute": 28}
  },
  "migration": {
    "pending": 93,
    "blocked": 35
  },
  "history": {
    "revision_count": 190,
    "record_count": 141,
    "migrated_away": 13
  }
}
```

计算规则：

- `current_bound` 只统计当前可见、未软删除且 kind 为 entity/relation/attribute 的修订。
- `migration` 复用 `Reclassify.plan()` 的分组判定，只汇总 `from_ontology_id` 等于目标版本的组；`pending` 是这些组中 `migratable=true` 的 `record_count` 之和，`blocked` 是 `migratable=false` 的 `record_count` 之和，不是分组数量。目标本体是当前版本时两项都为 0。重分类计划不可读时两项返回 `null`，前端显示“—”和“迁移状态未知”。
- `history` 从 `record_versions.payload->>'ontology_id'` 聚合；`migrated_away` 是曾关联该版本但当前可见修订已关联其他本体的 record id 数。
- 不返回整批知识正文，避免版本管理抽屉加载大量数据；查看明细走台账过滤。
- 项目或本体不存在时使用现有 404/KeyError 处理；本体不属于项目时不得泄露其他项目统计。

聚合逻辑放在新的 `knowledge_service/services/version_context.py`，SQL历史聚合放在 repository 的窄方法中，避免继续扩大 API 路由函数和 `KnowledgeService.scoped` 的职责。

### 6.3 性能与一致性

- 当前知识明细继续通过 `/records/query` 分页读取。
- 上下文接口只返回聚合数字。
- 首版不新增数据库表；如果真实项目的聚合查询超过既有性能预算，再单独增加 `(project_id, payload->>'ontology_id')` 表达式索引迁移，不在本能力中预先优化。
- 接口一次请求内在 repository 事务/连接上下文中读取本体列表、当前记录和历史聚合，允许普通 read-committed 快照，不承诺跨请求一致。

## 7. 前端状态与导航

在全局 `wb` 中增加轻量版本上下文：

```javascript
wb.versionContext = {
  ontologyId: null,
  ontologyVersion: null,
  source: null // 'ontology-history' | 'ledger' | 'graph'
}
```

规则：

- 切换项目必须清空版本上下文。
- 本体历史预览更新该上下文。
- “在知识台账查看”写入上下文并调用现有页签切换函数。
- 台账筛选器变化同步上下文；选择“全部本体”清空它。
- 图谱和脑图读取该上下文，并在 Scope 中发送 `ontology_ids`。
- 页面刷新后不持久化版本上下文，避免用户下次进入时误以为仍在当前本体。

## 8. 错误与空状态

- 没有项目：保持现有“请先选择项目”。
- 项目没有本体：显示“尚未发布本体”，不显示 v0。
- 上下文接口失败：版本结构仍可查看，关联知识区域显示“读不到关联知识”，不得显示 0。
- 本体 id 未知或跨项目：显示版本不存在并退出历史预览。
- 旧记录没有 `ontology_id`：显示“未知本体”，允许在台账筛选，但不能归入任一版本。
- 记录历史加载失败：当前记录详情仍可用，历史页签显示可重试错误。
- 受控重分类计划不可读：待迁移和阻塞显示“—”；旧本体记录逐行显示“迁移状态未知”，不得根据前端猜测。

## 9. 测试策略

### 9.1 服务与仓储测试

- Scope 按单个和多个 `ontology_id` 过滤。
- Scope 的 `all`、`ids`、`unknown` 三种模式及非法字段组合；`unknown` 同时覆盖缺失 id 和跨项目/失效 id。
- 过滤后不会留下悬空关系或属性。
- 上下文统计区分当前关联、历史修订和已迁出记录。
- 迁移前后：旧本体的 `current_bound` 减少、`migrated_away` 增加，新本体的 `current_bound` 增加。
- 未映射组计入 blocked，可迁移组计入 pending。
- pending 与 blocked 断言按各分组 `record_count` 求和，不按分组数计数；计划不可读时返回 null。
- `/ontologies`、版本管理、台账和重分类对结构版本号使用相同的 metadata 优先与旧数据回填规则，标注修订不会被错误编号为新的结构版本。
- 跨项目 ontology id 返回 404，不泄露统计。
- 未知 `ontology_id` 历史记录不归入任何正式版本。

### 9.2 前端契约与浏览器测试

- 本体历史预览显示当前/查看版本并保持只读。
- 版本详情显示关联知识统计，接口失败时不编造 0。
- 跳转台账后本体筛选正确选中。
- 台账使用“修订 rN”和“依据本体 vN”，不再把记录版本显示为裸 `vN`。
- 记录详情时间线显示每个修订对应的本体版本。
- 切换项目清空本体筛选。
- 图谱/脑图请求携带 `ontology_ids`，恢复全部本体后不携带。

### 9.3 回归测试

- 现有本体版本管理、历史预览、从历史版本派生草案不变。
- 现有受控重分类的 plan/preview/apply/undo 全部通过。
- 不带 `ontology_ids` 的现有 Scope 请求结果不变。
- 全量 `python -m pytest -q` 通过，并用运行中的 8100 服务做健康检查和关键页面冒烟验证。
