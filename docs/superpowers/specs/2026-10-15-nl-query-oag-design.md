# 第 5、6 模块：多平台规则文档查询与 OAG 增强规格

日期：2026-10-15。状态：已按用户确认范围推进首批实现；实施与验证记录见对应计划。通用精确统计、自动规则判定与外部业务库仍为后续独立范围。

## 1. 业务目标与调整结论

项目当前管理多个平台的业务规则文档，不接入订单、交易、客户等外部业务数据库。现有 PostgreSQL 是项目内部的知识权威存储，不代表用户已经提供外部业务数据，也不是本期需要新增的数据源。

用户目标是：**找得准、平台不混、比较有依据、每个结论能回到原文**。属性较难提取，必须采用“原文证据为基础，本体、实体、关系和属性逐步增强”的方式。没有抽出属性，仍能完成条款问答、分平台比较、条件与例外解释及原文溯源；精确筛选、穷尽枚举和统计则取决于结构化数据质量与覆盖范围，不能保证无属性时等价可用。

本规格替代初稿“以通用 NL 查询计划、属性条件与全量聚合为首期主线”的设计。第 5 模块定位为面向规则文档的自然语言检索、查询理解与比较；第 6 模块定位为现有 OAG 的证据组织、解释、有效性控制和溯源增强。复用同一问答链，不另建平行系统。

用户新增要求：失效内容可以作为可查看、可追溯的历史参考输出，但不能作为当前有效规则回答的依据。历史时点查询需按指定时点重新判断有效性。

| 能力 | 当前实现 | 处理方向 |
|---|---|---|

| 平台与时间 | Scope/Search 已有 applicability、valid_at、known_at、本体范围；支持平台分组 | 复用既有三态和双时态，不另造范围语义 |

| 时间来源 | IngestSettings 在未显式给 valid_from 时可回退到 published_at，并标记 effective_time_source | 发布日期推定生效须明确标注，不得宣称经过业务确认 |
| 模型输入 | answer_messages 提供正文、适用范围、发布日期、有效期，未传整份 metadata | 加入必要的、服务端判定的有效性与证据用途，不直接倾倒任意 metadata |
| 本体辅助 | ontology_expansion 默认关闭；structure_pending 只适用于 entity/relation/attribute，文档和切片不参与 | 无本体、无抽取、抽取待定时，合格原文切片仍可作为文档证据 |
| 属性 | 独立 attribute 尚未完整进入问答检索 | 作为可选增强接入，不能成为基础文档问答的验收依赖 |
| 路径 | 平台分组返回空 reasoning_paths；非分组 BFS 可双向走边，found 限 200 而 paths 另遍历 relations | 统一成有方向和来源的可选关联路径；无图也能回答原文问题 |
| 溯源 | SSE 冻结证据与来源；JSON 共用上下文和提示但未走同等活动保存链 | JSON/SSE 统一运行与证据契约 |
| 引用检查 | complete_answer 检查是否引用 offered 编号 | 保留引用检查，增加证据资格约束；引用合法不等于结论语义正确 |
| SPARQL | 本地 SELECT/ASK，最多输出 1000 行 | 保留已有能力，不强行接入首期普通条款问答 |

- `knowledge_service/services/answers.py`：answer_messages、question_context、_reasoning_paths、stream_events。
- `knowledge_service/services/service.py`：public、scoped、search、answer。

## 3. 本期范围与不纳入的能力

本期必须提供：规则条款检索、单平台问答、多平台有来源的比较、前提/例外上下文、原文定位、当前/历史有效性区分、JSON/SSE 一致的证据用途。查本体术语与关联路径利用已有知识作为辅助，不是所有请求的必经步骤。

属性能力保留为增强：有可靠值时用于展示和明确范围内筛选；缺失时回到原文证据，不强填、不把缺失当否定、不声称已列全。自动抽取不强制开启；允许沿用既有审核和人工维护流程，不新建一套属性审核系统。

暂不实施：外部业务库接入、通用 SQL/SPARQL/Cypher 生成器、任意多步 Agent、完整 OWL 推理器、业务规则自动判定、通用数值聚合、自然语言自动修改本体/知识。初稿 query-plans/query-runs API、八算子计划、全量聚合成员持久化和固定七天运行保留要求移出首期；后续确有精确查询需求再独立设计。

## 4. 查询理解与共享处理链

继续使用现有知识问答入口，默认自动识别“查条款、比平台、查历史、看关联、查本体”；这些是内部路由意图，不要求新增五套页面。明确问题直接执行；平台名、时间或对象有歧义时再澄清。

处理链：问题及显式范围 → 轻量查询理解 → 分平台/时点检索 → 上下文和来源补全 → 服务端证据资格划分 → 问答或比较 → 引用检查 → 冻结结果与原文定位。

轻量理解只形成 intent、平台/业务/对象候选、主题、比较维度、as_of、known_at、是否展示历史参考。复用用户显式筛选及既有可靠精确匹配；LLM 可建议术语和候选，不能凭猜测产生硬过滤，更不能扩大身份授权。不强制要求问题先绑定完整 IRI 或生成持久化查询计划。

明确区分模型角色：LLM 可理解问题、从证据归纳比较项、组织表达；服务端决定权限、适用范围、有效性、证据是否可参与回答。未配置模型时保留 evidence_only，不伪装生成了比较或推理结论。

依赖方向保持 api → services → repository。JSON 与 SSE 共用运行、资格分类、证据编号与终态逻辑，路由仅处理参数和传输；不把新增逻辑堆进巨型 service.py。

## 5. 找得准：原文、条件与例外

检索以条款/切片为基础，本体术语、实体别名、关系辅助召回。针对多平台比较保留各平台独立配额与空组，不能由单个平台占满 top-k。邻近上下文、来源补全与后续重排同样受平台、项目、本体范围和时点约束。

命中一条“7 天内”时，优先补同文档版本内的标题、适用对象、起算点、条件和例外；若预算或切片边界无法补齐，显示“上下文可能不完整”，不能拼成完整规则。例外不一定在相邻切片，不承诺只取前后一段就完整；先使用已有结构与相邻切片，必要时受限检索同版本相关条款。

原文证据是否可用，依据访问资格、平台、有效性、版本及可追溯来源判断；不要求它已经抽成实体/关系/属性。结构待定抽取记录继续单列，不作为正式结构事实；其合格来源切片可以独立进入文档证据，不能通过引用原文把未经审核的抽取字段升级为正式属性。

文档标题、文本声称的截止日期与平台名可辅助核对，不能未经审核自动改写规范有效期或平台字段。无结构化值时可回答“原文写明……”，不能声称已执行全库数值筛选。

## 6. metadata、有效期与证据用途（首期重点）

### 6.1 规范字段与时间语义

每项命中与证据保留 record_id/version_id、metadata 中对业务有用的允许字段、顶层 valid_from/valid_until、published_at、effective_time_source、来源版本及 assertion_refs（如有）。source_id 不是派生实体来源的唯一依据，来源关系沿用 assertions 与冻结溯源。

一次请求固定 as_of：用户明确历史日期则取该时点，否则取请求开始时的当前时点。known_at 表示“系统当时知道什么”，与业务生效时间不同。用户只说“2024 年的规定”时，仅改变 as_of；known_at 默认固定为本次请求的当前知识时点，表示用目前掌握的资料回看历史，允许后来入库但在该历史业务时点有效的资料。只有明确要求重现“系统当时已知内容”或显式指定 known_at 时才限制系统知识时点，不能自动令 known_at=as_of。区间沿用 [valid_from, valid_until)：到失效边界即不再有效。日期仅给到日时须明确业务时区和边界，解析不唯一则澄清。

服务端输出 validity_status、validity_basis、answer_eligible、exclusion_reasons；answer_eligible 在本契约中特指“能支撑本次 as_of 的有效规则结论”，包含明确历史时点的回答；另用 usage 表示 effective_basis / qualified_quote / reference。资格还同时受权限、平台、结构状态、冲突和来源要求约束，不能仅看日期。

- effective：有足够规范信息支持在 as_of 时有效，且无撤销/冲突证据。缺省结束时间本身不证明永久有效。
- expired：valid_until <= as_of，或在 as_of 已有经审核的业务撤销事实。
- not_yet_effective：valid_from > as_of。
- unknown：有效性信息不足；包括只有发布日推定生效、来源未知或待人工核对。可显示推定时间，但不能包装成已确认有效。
- conflict：规范时间、经审核状态或不同来源之间矛盾，不能自动选“最新”消解。

新增业务状态如需支持，实施时须定义唯一的类型化字段及映射规则；任意 metadata.status（当前也可能是上传处理 ready/failed）不能当作规则失效状态。record superseded_at 是系统版本替代，不等于规则业务失效；不得混用。入库审核可明确确认发布即生效，但不能全局自动等同。

### 6.2 回答依据与参考内容分离

| 证据用途 | 展示与溯源 | 是否进入结论生成依据 |
|---|---|---|
| answer_evidence：符合范围、as_of 有效、可追溯的原文/事实 | 正文依据卡，可定位原文 | 是 |
| historical_reference：as_of 已失效 | 独立历史参考区，标注失效时间与原因 | 否 |
| future_reference：尚未生效 | 独立参考区，明确生效时间 | 否 |
| uncertain_reference：有效性未知/冲突 | 单列“有效性待核对”，提供原文与缺失信息 | 未知项默认仅允许带限定语的原文说明；冲突项只展示冲突，不支撑当前有效规则的确定结论 |
| 结构待定、平台未知 | 沿用待定/范围未知分区 | 不自动支撑平台特定的正式结论 |

有效性未知不等于失效。缺日期不能阻断基础文档问答：建议默认允许说明“文档写明……，生效状态待核对”，但不能断言“该平台当前规定为……”。只有缺少确认有效依据时，明确“未找到在该时点确认有效的依据”，同时给出可核对原文，不误报“系统没有文档”。另提供严格策略：未知项只展示摘录、不参与生成。用户已确认默认策略：“允许依据原文回答，但明确标注有效性待核对，不宣称当前有效”。严格策略仅作为可选配置，不作为存量问答的默认门槛。P0 呈现待核对原因及既有维护入口，不静默过滤到空。

失效/未来/冲突参考条目不能混入生成当前结论的 LLM evidence 消息，相关原文由确定性界面/响应结构展示；参考 ID 使用独立 R/F 前缀，不能加入答案的 E 引用允许集。有效性未知项若采用建议默认策略，可进入独立 qualified_quote 输入，以 U 编号仅支持带“文档表述、有效性待核对”标识的说明段，不得支撑当前规则比较单元；严格策略下不进入生成消息。接口明确区分 E 的当前依据用途与 U 的限定引用用途，不能只用一个“可引用”布尔值。若答案引用 R/F、编造编号或把 U 用于当前有效结论，资格审计不能标为通过；采用确定性摘录降级或明确失败，流式已发 delta 标记为草稿，done 给出最终可用内容和审计状态。首期对 U 的说明由固定标识分区渲染，无法可靠校验的自由文本退回摘录，不承诺通用语义证明。引用 E 合法仍不代表结论语义正确。

### 6.3 失效参考如何检索

保留默认有效范围查询作为回答通道；增加受限参考通道，按同一身份、平台、主题、知识时点检索失效/未来/待核对内容，返回独立配额与分页/截断状态。参考命中不得挤占有效依据配额。用户可关闭参考展示；关闭后不执行该通道。

现有 valid_at 查询会排除失效记录，因此需要显式设计仓储/检索的参考读取，不得偷偷把 include_unknown 当“包含失效”，不得拿当前时间查询结果冒充全历史。原生投影不支持该范围时回退权威读取并记录降级；尚无适配时明确参考不可用，不能宣称没有历史内容。

### 6.4 实体、来源和上下文的有效性

同一实体可能被多个文档提到：实体顶层时间或 metadata 不能替代每条 assertion / 文档版本的适用性。有效文档与失效文档指向同一实体时，仅合格来源支持当前结论，失效来源独立留作参考，不能因实体命中就全部注入提示。

相关切片、例外补全、路径上的每条边都需独立资格判断。来源失效不能因附着到有效实体而恢复资格；主体无效也不能仅凭有效来源把该结构事实升级。仅有过期规则时不推测它今天仍适用。

用户查“2024 年当时的规定”时，以 2024 年 as_of 判断；今天已失效但当时有效的条款可以作为该历史回答依据，并明确历史范围。当前问答中看见历史参考与主动历史查询是两种用途，不能混为一谈。

## 7. 比较有依据

按平台分别获取依据，再生成统一比较维度：适用对象、前提、要求、时限及起算点、例外、生效范围。维度可从原文归纳，不要求已经保存为属性。每个当前有效规则比较单元有本平台、该时点合格 E 引用；共用规则明确说明适用性。未知有效性的原文可另作“文档表述比较”，必须整表明确为待核对，不与当前有效规则比较混合。

一边没有依据时写“未检索到确认有效的依据”，不能写“该平台没有此要求”。原文描述不等价、起算点不同或版本冲突时明确区别，不强行归一化。对“哪些平台……”默认返回已找到证据的平台与搜索范围，不宣称穷尽；穷尽枚举需要额外覆盖保证。

失效内容可在历史参考中单独展示，不能补齐当前比较表的缺项。若用户要做两个历史版本比较，分别声明时点并按各自有效性取依据，不以当前结论模式混用。

## 8. 属性与图谱作为可选增强

属性状态区分：缺失、候选待审核、已接受/人工维护。只有既有治理认可且有效的值可用于结构化筛选；候选显示原文和待核对状态，不强行填值。缺属性不影响合格文档问答，抽取失败不阻止原文入库与检索。

优先可维护时限、金额、适用对象等少数高价值字段，并保留限定条件、起算点、单位和来源。“7 天”不能脱离“申请/处理/自然日/工作日”等语境。属性与来源原文矛盾时显示冲突，暂停据其给出确定筛选结论。

后续属性筛选结果必须显示“已维护属性范围内”；只有对应对象、属性、有效性和覆盖契约明确时才能称完整结果。不能拿属性缺失判定不符合，也不能把切片数当规则数。文档数量等内部对象统计只有独立完整执行并说明口径后才可精确输出，top-k 数量永不当总数。

路径为可选关联解释：逐边包含原始 subject/object、遍历方向、关系与节点版本、来源及有效性。默认有向，显式无向时标反向；限定跳数和数量，并仅使用合格集合。无路径返回明确状态，不能阻断原文回答，更不能把关联当业务证明。主画布的当前显示 BFS 与后端知识查询范围分别说明。

## 9. 结果契约、界面与 API

保留现有 /qa、/qa/stream，内部共用运行服务。兼容保留 answer、evidence、structure_pending 等字段；新增 as_of、known_at、platform_groups、historical_references、future_references、uncertain_references、coverage_warnings、eligibility_summary。evidence 继续表示 E 类回答依据，参考区及限定引用使用独立命名空间；有效性未知与适用范围未知分开记录，不复用含混的 include_unknown 作为统一开关。

必要时新增向后兼容的历史参考展示参数，不改变 /search 的默认有效期语义。参考通道先限定用于本期问答/比较；全面历史浏览不在本期承诺范围。接口字段默认值、上限和事件扩展在实施计划中具体确定；本规格不强制新建 query-plans/query-runs。

来源项包含 document_id、document_version_id、record_version_id、片段起止位置、quote、平台、规范有效期、时间来源、用途与排除原因。源正文与引用来自冻结版本，不能点击后跳到当前替换版本；来源缺失显式提示，不能伪造文件引用。只返回经权限允许的业务 metadata；不把内部运维/提供商字段直接输出给模型。

界面先展示本次时点的回答及其依据，再展示历史/未来/待核对分区；失效/未来/冲突参考标注“未参与本次回答”，实际参与限定说明的 U 标注“仅用于文档说明，未作为已确认有效规则依据”。用户可选择历史日期、展开原文或定位相关实体。没有有效依据时状态提示仍可显示参考原文；不能用过期条款生成一段貌似当前有效的答案。

SSE 保留 evidence/delta/done/error，delta 为生成中草稿；done 仅在资格与引用检查及持久化完成后发出，取消/超时/失败进入唯一终态。JSON 与 SSE 相同输入需有等价的证据范围、资格分组和最终语义，不要求两次 LLM 文本逐字相同。

## 10. 一致性、预算与权限

项目授权、平台/业务/对象、本体范围和 known_at 贯穿初始召回、来源、相邻上下文、参考通道、路径及点击原文。历史参考不放宽授权，不暴露不可见节点存在性；applicability 不等于访问权限。重新打开运行与原文需重新鉴权。

固定本次读取时点和可复现记录/文档版本；投影只负责可支持的召回，权威记录负责资格判定。无法验证同一版本时回退或显式不完整，不静默更换为最新版本。以短事务或历史版本冻结读取，不为模型生成保持长事务。

沿用已有 k、分平台配额、hops 和后端超时，增加独立参考配额和总上下文预算。不能照搬初稿任意“最多 3 个平台”限制：超出单次比较预算时分批处理并显示覆盖范围，不能默默遗漏用户选中的平台。每个平台的有效依据不被参考项挤占。预算不足、参考暂不可用、上下文被截断时明确返回，不以超时表示“没有规定”。

本期不新增永久运行成员索引或七天保留承诺；溯源沿用既有保留治理。模型输入与文档内容均视为数据，不允许其中指令改变权限或工具范围。

## 11. 分期实施与验收

| 阶段 | 交付 | 验收重点 |
|---|---|---|
| P0：问答依据和参考分离 | 统一 JSON/SSE 资格、有效性与溯源；历史/未来/待核对分区；原文不依赖抽取 | 失效内容可查看但不进入当前答案依据；缺属性与结构待定不连带屏蔽合格原文 |
| P1：条款检索与平台比较 | 上下文/例外补全、平台独立配额、逐项引用、缺项提示、历史查询 | 平台不混，每个比较结论可回原文；无属性也能完成 |
| P2：可选知识增强 | 有来源的实体/路径定位；已有可靠属性展示与受限筛选 | 不影响基础问答；方向、覆盖范围、单位、有效性明确 |
| 后续独立规格 | 精确全量查询/统计、规则执行、按需外部业务数据接入 | 有具体需求和数据完备性依据后另行设计，不作本期前置条件 |

以下案例必须纳入固定回归集；业务文案可用合成规则，不能依赖真实模型临场抽取才能通过。离线契约测试与真实模型质量评测分开，真实评测记录模型版本、范围、证据和成本。

| 场景 | 必须满足 |
|---|---|
| 只有文档切片，无实体/属性/本体 | 有明确平台及有效性、来源时正常问答并引用 |
| 属性抽取失败、候选待审核、结构待定 | 原文仍可用；不自动升级候选事实 |
| 相同主题分属平台甲乙 | 分别取证，不跨平台补答案 |
| 通用规则、未知平台规则 | 明确适用性，未知不当平台特定依据 |
| 两平台比较一边缺依据 | 明确缺项，不声称没有此规则 |
| 条件/例外在邻段或另一条款 | 同版本受限补全，无法补齐则提示 |
| valid_until 恰等于 as_of | 已失效，只入参考区，不进入生成消息 |
| 尚未生效、有失效参考、完全无有效依据 | 分别标记；输出状态提示和参考，不生成当前规则结论 |
| 无日期、仅发布日期、metadata.status=ready | 可带限定语说明原文或按严格策略展示摘录；不误判已有效或已失效 |
| 两个来源时间冲突、被审核撤销 | 单列冲突/失效，不按更新时间自动选赢家 |
| 同一实体有有效和失效来源 | 当前答案仅引用有效来源，失效来源独立展示 |
| entity 有效但补充 chunk 或关系失效 | 补充项不能绕过资格进入依据 |
| 仅指定历史 as_of、未指定 known_at | 按当前知识回看历史，后来入库且历史有效的资料可参与 |
| 同时指定历史 as_of 与 known_at | 仅用该知识时点可见版本，不混入后来才被系统知道的资料 |
| 参考接口不支持或投影滞后 | 权威回退或明确不可用，不能假报没有历史内容 |
| 引用失效参考 R、编造 E、将 U 当当前依据 | 资格/引用检查拒绝通过，确定性降级或失败 |
| 所有属性缺失，问哪些平台满足数值条件 | 可给原文支持的发现与限制，不宣称全量结果 |
| 相同条款多来源、top-k=5 | 不按来源/切片重复算规则，不将 5 当总数 |
| JSON/SSE、断流、取消、持久化失败 | 分组和语义一致，终态可追踪，不提前 done |
| 越权文档、跨平台路径、恶意原文指令 | 不扩大可见范围，不泄漏或执行指令 |

首期阻断项：平台/权限泄漏、失效或未确认有效依据支撑当前确定结论、引用无法定位实际版本、无属性导致基础问答不可用、比较缺项被伪造成规则不存在。检索质量以人工标注的条款命中、例外覆盖、比较单元引用支持及有效性资格准确性评估，不用 LLM 自评或引用编号合法替代。

## 12. 已确认事项与参考

已确认：多平台规则文档为核心；不接外部业务数据库；增强现有 OAG；属性可选；业务规则判定后续；失效内容可看但不支撑当前有效规则答案；未维护有效期的存量文档允许依据原文回答，必须标注有效性待核对，不宣称当前有效。用户原先选择的“精确查询”在本背景下首先落实为条款定位准确、平台与时间准确、引用准确，不继续扩大成缺乏数据基础的通用业务数据库查询。

已有业务问题类型足以推进实施，不把补齐属性或等待用户提供 3–5 个问题作为阻塞条件。具体案例可在回归集使用合成规则，并逐步替换为用户认可的真实样例。业务撤销状态的规范字段、日期边界和存量有效期核对方式必须在对应实施任务中明确，不能任意猜测 metadata 键名或日期语义。
