## 1. 要解决的问题与设计取舍

目标是让使用者完成“上传资料 → 形成可用知识 → 提问/查关系 → 回到原文核实”，并能理解每一步的处理状态和版本依据。界面围绕这条链路组织，项目管理负责项目本身，不承担知识消费筛选。

三种方案的比较：

| 方案 | 收益 | 代价/不足 |
| --- | --- | --- |
| A. 只把顶部 Metadata 条搬到侧栏 | 改动小 | 仍共享隐形条件；上传、任务与版本关系仍然分散 |
| **B. 按使用任务组织导航，筛选按页归属（推荐）** | 复用现有服务，把资料、知识、本体、索引、问答串起来 | 需要拆开全局 scope、调整导航与页面入口，分批验证 |
| C. 整套切换到 GraphRAG 或 Semantica Explorer | 可以复用更多上游界面/流程 | 与现有 PostgreSQL 权威存储、本体治理、双时态和来源审计有冲突，迁移范围过大 |

采用 B。导航重组必须保留所有既有治理能力，并提供可发现的入口；本体编辑与实体维护是完整工作区。先补齐现有能力的使用闭环，再建设可验证的 Local/OAG、消融实验和社区 Global/DRIFT。本文是统一产品蓝图；第 10 节明确分批边界。

## 3. 导航与页面职责

左上保留当前项目切换器，用于快速切换及进入当前项目概览/备份。账号上方固定“管理”分组，明确列出“项目管理、人员管理”，不再把创建、改名、删除项目与账号维护只藏在下拉中。业务导航空间不足时单独滚动，管理入口保持可达。管理页属于工作空间范围；人员当前为全局账号/角色，不暗示已实现项目成员 ACL。详细操作和保护规则见[项目与人员管理设计](2026-10-19-project-and-people-management-design.md)。

左侧导航按实际工作组织，分组使用轻量文字，不重复堆放大面积说明卡：

| 分组 | 入口 | 页面第一任务 |
| --- | --- | --- |
| 使用知识 | 知识问答 | 输入问题、看回答、核对证据 |
| 使用知识 | 检索与图谱 | 找片段/实体/关系，查看局部关联；脑图作为实体详情中的视图 |
| 管理资料 | 资料库 | 找到来源文档、添加文件、看原文和处理结果 |
| 管理资料 | 知识台账 | 维护正式事实、查看候选与问题、核对来源和修订 |
| 管理资料 | 本体建模层 | 处理发现候选、改类型与约束、校验和发布 |
| 运行与质量 | 构建与任务 | 看处理队列、失败、索引同步，定位问题 |
| 运行与质量 | 质量评测 | 保留抽取质量；新增检索与问答消融（执行后端待建设） |
| 管理（固定入口） | 项目管理 | 查找、创建、进入项目；设置抽屉内改名、备份入口与删除 |
| 管理（固定入口） | 人员管理 | 管理全局账号、角色和启用状态；编辑、口令重置与删除保留守卫 |

知识台账内有“知识维护 / 融合与消歧 / 操作历史”三个稳定入口；实体、关系、属性、片段仍是知识维护中的视角。质量评测内区分“抽取质量”和“检索与问答消融”；后者为新增执行能力，接通前只在设计预览中展示计划形态。

用户与权限仍是系统管理入口；只读账号仅显示已有授权的消费入口，保留服务端权限校验。不因导航重组扩大资料或管理权限。

新建项目表单先收名称，提交显式指定 `ontology_mode: "discovery", use_default_ontology: false`，防止服务默认装入通用本体。创建完成进入资料库空态，主按钮“添加文件”；已有可检索资料的项目默认进入知识问答。受控/发现/文档三种处理路径移至资料上传按批次选择，已有领域本体通过本体建模层导入/编辑/发布后供受控处理使用；不由项目初始化方式锁定后续任务或编辑能力。具体契约以[项目与人员管理设计](2026-10-19-project-and-people-management-design.md)为准。

项目概览只显示：资料是否可检索、图谱是否有正式知识、是否有待处理事项、最近构建是否异常。每一项提供一个能解决当前问题的入口。数量作为辅助信息，整个概览固定为全项目口径。

## 4. Metadata 筛选的出现位置与交互

### 4.1 默认收起的页内侧栏

删除公共顶部 Metadata 大面板。适用页面在自己的工具栏放一个“筛选”按钮，打开内容区左侧的筛选栏；全局导航始终保持导航职责。宽屏侧栏约 280–320px，窄屏为抽屉，关闭后把焦点送回触发按钮。筛选栏默认关闭，不自动挤压图谱或问答首屏。

没有条件时只保留“筛选”按钮。应用后，按钮显示已应用条件数量，并在当前结果/输入区旁展示可移除的短标签，如“平台：美团”“业务时点：2025-09-01”“高级条件 2 项”。收起侧栏不隐藏已生效条件。

侧栏使用“编辑中 → 应用”的两阶段状态。取消/关闭保留已应用范围，不让未提交的输入悄悄影响请求；重新打开恢复已应用值。底部是“应用”和“清空本页筛选”，清空直接更新本页结果。JSON 无效时阻止应用并定位错误，旧的已应用范围仍有效。

### 4.2 页面与字段矩阵

| 页面/对象 | 是否有内容 Metadata 筛选 | 普通控件 | 不应出现的控件 |
| --- | --- | --- | --- |
| 知识问答 | 有，默认收起 | 平台、业务、适用对象、业务时点；更多字段折叠 | 图谱实体/关系类型、索引重建、并发数 |
| 检索与图谱 | 有，默认收起 | 平台、业务、适用对象、业务时点；其他 Metadata | 项目管理操作 |
| 图谱画布内部 | 类型是局部视图条件 | 实体类型、关系类型、方向、跳数、标签/布局 | 用图谱类型偷偷限制全部原文检索 |
| 资料库 | 有，按来源文档解释 | 标题、文件格式、处理状态；平台/业务/对象和其他文档字段 | 实体/关系类型、本体草案状态 |
| 知识台账 | 有 | 实体/关系/属性/片段视角、类型、状态、来源字段；本体归属和历史查看单列 | 解析参数 |
| 上传与文件详情编辑 | 没有查询筛选 | 编辑这份资料的来源范围、时间、业务字段 | “应用筛选”按钮 |
| 本体建模层 | 没有通用 Metadata 筛选 | 本体版本、草案、术语种类、名称、校验问题等本页条件 | 平台/来源字段的全局条件 |
| 项目列表/设置/概览 | 没有 | 项目名称查找；概览全项目统计 | 内容 Metadata 条件 |
| 构建与任务 | 没有 | 任务类型、状态、创建时间、所属文档/批次 | 平台/实体类型等内容字段 |
| 知识备份 | 没有 | 备份名称、时间、类型 | 内容筛选；“按筛选结果备份” |
| 抽取质量评测 | 不用通用侧栏 | 本次评测单独指定知识范围、标准答案 | 继承上次问答/资料库条件 |

资料状态/文件格式属于资料列表自身条件；任务状态属于任务条件。后端尚无相应列表能力时，不能对分页的一页结果冒充全库筛选，需先补列表接口或标明仅筛选已加载项。

### 4.3 状态与语义边界

- 筛选状态按“项目 + 页面”保存到当前登录会话。切到新项目使用该项目本页状态，首次进入默认不限；退出登录清除。问答、检索图谱、资料库、台账各自独立。
- 检索结果与其展开的图谱共享基础内容范围。画布类型/布局只作用于图谱；脑图继承显式打开它的实体与内容范围。跨页时只有用户点击“基于此范围提问”等明确动作才复制兼容条件，目标页显示复制后的标签。
- 旧版全局条件如非空，只迁入当前活动且兼容的页面一次；不复制给所有页。不支持的条件保留在迁移摘要中，提示用户处理，不能静默删除或转换成“通用”。
- 不限、通用、未知三者分开。空平台条件表示不限制查询；文档平台“未知”不等于“全部平台适用”。保留现有 applicability 协议及服务端证据资格判断。
- 默认不添加业务时间硬过滤，仍可看历史/未来/待核对资料；问答对“当前有效规则”的判断仍由服务端进行。设置业务时点不自动改变系统知识时点。
- “系统历史时点”和“本体归属”放在历史/版本入口，默认当前系统状态、全部本体归属；不默认只看最新本体，也不将无本体的文档证据排除。
- 原有嵌套 AND/OR JSON 能力保留于高级条件；显示名称改为“更多字段”，系统字段默认不列出，已应用的系统条件仍能看到并删除。
- 每次提交固定一份范围；项目切换、条件改变后旧响应不能覆盖新结果。问答消息保存提交时范围，改筛选只影响下一次提问，不删除已有对话，不重新解释历史回答。
- 内容资格由服务端裁决。前端本页状态隔离不能代替项目、权限、时态和来源校验。

## 5. 资料库、上传与处理结果

### 5.1 统一入口与列表

“添加文件”是资料库唯一主要写入入口。原“知识写入”和“原文数据源”收进同一资料流程；批次队列、上传组件和来源阅读器继续复用。项目概览、空态里的添加按钮都进入这一入口。

列表以文档为单位，默认每行显示：名称/格式、平台范围、最近处理状态、原文检索状态、知识处理摘要、更新时间。选择文档后展示“原文 / 提取知识 / 处理记录 / 修订记录”。原文中的引用位置与知识详情互相可跳转，详情保留返回当前列表的路径。

文档是否可检索、事实是否已确认、向量是否同步分别显示；不要用一个“完成”包住所有状态。没有明确数据时显示“待核验”，不根据任务 100% 推断各项均已就绪。

### 5.2 上传的三个步骤

1. **选择文件**：拖放或浏览，显示逐文件大小、格式和错误；数量、大小、ZIP 和 OCR 支持从服务能力读取。先不展示并发/阈值/原始 JSON。可以移除文件，浏览器重复选取提示不等于服务端去重。
2. **核对资料信息与处理方式**：平台、业务、适用对象、发布时间/有效期；批量默认值可逐文件覆盖，继承值与覆盖值有区别。普通业务 Metadata 使用字段编辑，JSON 是高级入口。查询侧栏的条件绝不自动写入文档。
3. **确认并处理**：摘要列出文件数量、处理用途、实际本体版本、可选高级配置；主按钮“开始处理”。提交后进入本批次详情，可继续浏览其他页面。

处理方式用用户结果表达，同时保留准确的服务模式：

| 用户选项 | 实际服务行为 | 本体与界面规则 |
| --- | --- | --- |
| 图谱增强 → 按已有本体抽取（非开放） | 基于明确发布的本体受控抽取，类型、关系和属性按既有词汇映射 | 仅限定本批抽取；不支持的术语进入未映射/待处理说明，不自动转开放。之后仍可手工新增/修改本体或发现父类 |
| 图谱增强 → 开放抽取（候选发现） | 有本体时复用已有词汇并发现增量；无本体时建立首版候选 | 新类/关系/属性先映射、编辑、校验和审核，不直接改正式本体。之后同样可继续手工建模 |
| 仅文档问答 | 解析/切片，保留文档检索证据；不做实体关系抽取 | 不要求先建本体，不显示无意义的本体选择 |

对已有项目沿用原偏好；无已发布本体或模型不可用时给出具体原因与可选择路径，未经用户选择不把受控任务改成开放发现，也不把图谱任务静默降成仅文档。受控提交固定当前展示的 `ontology_id`；版本读取失败阻止受控提交，已有未发布草案只显示一条提示。详细类/谓词列表通过“查看本体”打开，避免在上传首屏展开一大块。

“有本体”不等于“只能受控提取”，也不关闭手工编辑。上传第二步中，图谱增强下必须显式保留上述两条路径；有本体时沿用既有偏好，无本体时受控提取不可选，并说明首版发现流程。仅文档问答不出现这些本体设置；切换回图谱增强时恢复用户已选路径。确认页、运行记录和任务详情均显示实际处理路径、来源与基线身份。

### 5.2A 已有本体的持续建模闭环

本体页提供“从资料继续建模”，资料详情提供“从此资料继续建模”，已完成的发现任务提供“处理发现候选”。资料已解析时复用其版本与候选，不要求重新上传。手工新增/编辑类、关系和属性继续保留，是否启用自动发现不影响手工编辑。

操作链：选择来源修订 → 固定本次发现基线/配置 → 创建或复用发现运行 → 新增/复用/冲突候选分组 → 编辑新术语或映射既有术语 → 暂缓/不采纳并记录原因 → 草案中继续调整 → 校验、逐项/安全集审核 → 发布。发现运行完成与草案发布是不同状态。

已有未发布草案时，默认保留原草案，新发现建立独立来源草案；列出“来源草案 / 目标草案 / 基线 / 冲突”，经显式预览后合入。不能用新发现覆盖用户未提交的手工编辑；也不能假定两个同基线草案可以直接拼 Turtle。基线已变化则阻断合入/发布，提供重基线与重新校验。草图为便于体验，可将已确认示例候选加入当前草案，但必须标为本地演示，不把跨草案合入记为已有实现。

本次源码复核：`OntologyDiscoveryWorkflow.create_run` 在存在已发布本体时仍执行归纳，将最新发布的 Turtle 传入 `_normalize_induction_candidates` 和 `_induce(...baseline_turtle=baseline)`，并保留基线快照和并发变化检查。因此“已有本体后继续发现”是现有后端能力，不应被界面隐藏。当前请求 `DraftRequest` 只有 name / infer_hierarchy，候选取自项目级 `_candidates`；尚无精确文档/候选集合或用户预期基线字段。新设计中的来源选择需新增服务端 scope/manifest 与相应资格校验；选择基线需新增预期发布 ID 校验，不能靠前端筛选冒充真正约束。已有已处理候选身份与 source fingerprint 机制应复用，避免重复派生。

术语映射复用已有稳定 IRI，不因为名称相近就新建重复类；它与实体实例的身份融合分开。候选的新建/映射/排除决定必须保留来源、原因和预期修订，新增关系/属性先处理端点和所属类型。目标字段/协议超出当前 `DraftReview`（excluded_candidate_ids / excluded_terms / term_labels）时，列为命令或映射契约扩展，不能仅画选择框就标为已支持。

高级处理设置默认折叠：切片策略、属性抽取、关系约束、消歧、自动融合与并发。保留现有默认值及禁止隐式自动融合的边界；“预览切片”放在此处，明确只预览首文件且不触发模型/写入。

### 5.3 批次与结果是不同对象

批次详情顶部为一行完成统计及异常入口，下方为文件表：文件 → 当前阶段 → 可用产物 → 本体依据 → 错误/下一步。批次设置在提交时固定，后续发布新本体不会改写排队中的任务。

每个文件以三个真实状态维度展示，不画会误导为全体串行的单一长进度条：

- 来源处理：待上传/已上传/解析中/原文可用/解析失败。
- 知识处理：未启用/抽取中/候选待确认/正式知识已写入/部分失败。
- 派生索引：待同步/同步中/已就绪/失败；社区摘要仅在后续真正接通后出现。

这些是目标读模型，阶段一不得从任务文本解析猜测；现有接口信息不足的条目标为“待核验”，阶段二补后端聚合。文档原文已具备证据资格时可供文档问答，不因图抽取未完成而一概禁用；当前实现若写入/索引尚未可用，页面按实际状态说明，不能只靠前端宣称渐进可用。

文件完成后的操作依结果决定：原文可用 → “查看原文”；有候选 → “处理待确认知识/进入本体建模”；有正式事实 → “查看提取知识”；局部失败 → “查看失败项/重试失败项”；具备检索资格 → “基于这份资料提问”。最后一项精确限来源版本需要服务端真实支持，阶段一无对应范围协议时仅提供“前往问答”，不能靠把文件名填进问题冒充硬筛选。

### 5.4 同名文件、重跑与来源新修订

这些动作必须区分：新文档、新内容修订、以相同来源重跑提取。仅凭文件名不判定同一来源，不将模型重跑记成“文件 v2”。

阶段一只呈现已有记录修订和已有任务历史，不新增“替换已有文档”按钮。阶段二实现完整来源用例后再提供“上传新修订”：显式选择要更新的来源，固定内容 hash、来源修订和处理配置，保留旧原文与引用。相同内容允许明确重跑提取；新修订的去重、撤回旧断言、更新投影必须由服务层统一处理，不能在前端改 ID 拼装。

规则内容发生业务换版时，与“纠正同一条记录”区分，沿用已有新逻辑 ID/有效区间约定；不能用系统 rN 直接推断一条旧规则业务失效。

## 7. 版本关系：用对象与依据解释，不另造“项目 vN”

### 7.1 显示规则

| 对象 | 用户看到的名称 | 变化含义 | 出现位置 |
| --- | --- | --- | --- |
| 来源文档 | 文档修订 rN；业务版本/有效期另列 | 同一逻辑来源的记录修订；不自动等于新政策版本 | 原文详情、引用、处理输入 |
| 本体 | 本体 vN + 发布日期；碰撞时加短 ID/标注修订 | 已发布结构/标注的不可变身份 | 本体页、受控上传依据、事实详情 |
| 事实 | 知识修订 rN + 依据本体 | 同一记录的系统修订；业务有效期单列 | 知识详情、历史抽屉 |
| 处理运行/批次 | 处理时间、用途和状态；详情可复制运行 ID | 执行动作，可对同一来源多次重跑 | 文件处理记录、任务 |
| 语义/图/社区索引 | 当前可用/待同步/构建中/失败；详情显示代次、模型和同步水位 | 可重建派生产物；不改变权威事实历史 | 构建与任务，问答异常提示 |
| 知识备份 | 备份名称、创建时间、内容边界 | 存档，不是本体发布/索引代次 | 项目菜单的知识备份 |
| 历史回答 | 回答时间、当次范围、引用来源修订 | 固定当次证据；新索引不改写旧回答 | 对话消息详情、证据抽屉 |

本体无归属显示“未绑定/未知”，不能猜成当前本体。文档/事实修订前缀统一 r，只有本体正式发布使用 v。没有服务端稳定代次/水位时显示“状态未知”，不得在前端用时间或数组下标造代次。

### 7.2 一个能读懂的例子

假设“退款规则”文档修订 r2 以本体 v3 处理，产生实体 A 的知识修订 r1。此后：

1. 发布本体 v4：新任务可以采用 v4，已存在的 A 仍依据 v3；若需迁移，执行已有受控重分类，保留审计。
2. 纠正文档得到 r3：旧回答仍引用 r2 的冻结原文；r3 的正式提取必须经历新处理和治理，不能把 r2 的事实直接标成 r3 产生。
3. 重建索引：新索引消费符合资格的记录修订，索引换代本身不产生“本体 v5”或“知识修订 r2”。

详情用“来源 → 处理依据 → 产生知识 → 检索状态”纵向关系展示，而非将四个版本号无说明地横排。

### 7.3 备份的诚实边界

现有 `Explorer.snapshot` 保存当前记录及本体目录；`restore_snapshot` 保存恢复前备份，再写入目标记录的新修订并处理当前多出记录的删除标记。它没有恢复本体目录的发布状态，也没有打包原始文件、配置、索引和任务。

因此名称使用“知识备份”。恢复确认应明确恢复的是记录、会产生新修订、会保存恢复点、会触发派生同步，以及不包含哪些对象。保留现有确认流程，不添加没有服务端支持的“完整项目回滚/差异预览”。若旧知识与当前治理约束不兼容，展示服务端失败原因，不承诺必能恢复；历史备份不默认复制成可随意切换的在线知识版本。

## 8. GraphRAG 与 OAG 的可用能力边界

产品目标是“文档证据为基础，图谱关系与本体契约逐步增强”。当前已有文档/结构化命中、合格证据组织、可选本体词项扩展、回答与引用核对；正常分组问答的路径目前为空。目标 Local 链须实际补齐：实体定位 → 范围内事实与邻域读取 → 同版本原文补全 → 证据组织 → 回答与引用核对。无图事实时仍可做文档说明；有图路径也不能宣称是业务规则证明。

问答的主入口始终是一个输入区。普通用户不需要先理解 Basic/Local/Global/DRIFT；“检索设置”中的高级策略只列实际接通且可用的模式，每条回答可查看当次实际策略、范围、有效性和证据。未配置模型时明确提供证据查找，不把切片拼接展示成模型已经生成回答。

| 能力层 | 内容 | 采用策略 |
| --- | --- | --- |
| 当前可复用 | 文档/混合检索、图谱浏览、实体关系维护、本体发布、候选治理、来源/双时态与证据问答 | 先打通闭环；当前状态以运行验证为准，不能只凭文档宣称全部可用 |
| 本轮补齐的产品契约 | 页内范围、来源页整合、版本解释、任务/索引入口、就绪状态 | 第一、二批按第 10 节交付 |
| 后续 GraphRAG 增强 | 社区划分、层级报告、Global 归纳、DRIFT 深入探索、策略质量对照 | 单独设计构建产物/失效/范围验收后上线，不仅新增几个模式按钮 |

社区能力优先探索从 PostgreSQL 中已治理事实导出可重建投影：复用 Semantica 0.7 的社区能力，或使用 GraphRAG 的 BYOG 工作流；用同一业务样本比对后选择适配器，不再产生第二套权威实体/本体。构建 manifest 至少固定来源/事实修订、所涉及本体 ID、范围、算法/模型配置与产物 schema。

社区报告是聚合后的内容：生成时混入其他平台/权限/历史来源，事后隐藏引用无法消除正文污染。Global/DRIFT 只能使用输入范围满足当前请求的报告；任意动态 Metadata 条件没有匹配产物时回退合格文档/局部检索，并说明原因。来源撤回或范围收紧立即影响读取资格，依赖社区报告失效，不能等定时重建才阻止使用。

Semantica 的 `truth_filter` 在 0.7.0 只支持 local；GraphRAG v3.2.0 的默认增量按 title 判断新增且未处理删除。来源逻辑 ID、内容/metadata 指纹、撤回、证据资格与失效由本项目服务层负责，不能照搬这些入口后宣称同步完成。官方依据见参考笔记，后续实施固定版本并再次核验。

## 9. 布局与异常状态

延续现有青色品牌，主工作区采用浅色干净底色、清晰字号和轻边框。去掉重复的“大标题 + 英文说明 + 长段解释 + 四张导航卡”；页头只保留当前任务、简短状态、一个主要动作。帮助放在具体字段旁或详情中。

资料与任务使用紧凑列表，用户点一行再看细节；日志默认折叠。图谱和问答保留内容面积。1280px 以上可并列内容与详情；1024px 优先抽屉；768px 及以下单列，筛选/详情用可关闭抽屉，不出现横向溢出。侧栏与证据抽屉冲突时只保留一个覆盖层，保留返回位置、焦点和滚动。

空项目显示“添加文件”；缺本体仅阻止需要正式本体的动作；缺模型说明可用的检索/提取范围；索引落后显示同步状态与恢复入口。任何降级均展示实际执行模式。网络错误保留用户已输入内容，旧项目/旧范围响应不得串入当前页。

## 10. 实施分批与验收

### 第一批：完整能力入口、本体编辑体验与范围隔离

以现有契约能够支撑的前端交互和读写接线为范围：

1. 删除公共筛选横条，拆出独立范围状态/编辑器；更新所有 scope 消费者和 apply/reset 监听，避免问答隐藏条件、跨页清空和无关请求。
2. 按第 3 节归属调整导航与入口；用同一资料入口承载已有上传和阅读功能，任务/索引独立归位；不增加空壳能力。
3. 统一 rN/vN 及实际本体依据展示；知识备份、抽取评测更正名称和范围；将技术大表单改为对象详情与结构化编辑，同时保留高级入口。
4. 沿用原生 JS/CSS 和现有模块边界，不引入新前端框架；修改资源必须 bump `index.html` 的版本并同步相关契约。
5. 完成本体目录、图/表单联动、类型属性展示、关系/继承、变更/校验/版本入口；保留完整台账、融合/消歧和操作历史。将第 12—15 节的每一项既有能力列入入口清单与验收，不以草图中未画完为删除依据。

恢复术语、冲突选值/消歧审核等存在契约缺口的流程，在第二批修复并验证前保持明确的不可提交/未完成状态。第一批可以设计其表单与可见入口，但不能据此记为链路验收通过。

对本批次的关键验收：

- 项目设置、概览、任务、上传、本体、备份都不出现内容筛选横条；问答的生效条件始终可见。
- 问答平台 A 不影响资料库/项目统计；资料页清空筛选不清聊天、不请求图谱；跨页复制范围只有显式动作才发生。
- 检索/图谱共用内容范围，图谱类型只限制图谱；高级嵌套 JSON、系统字段保留、三态范围和时点语义不回归。
- 非空旧筛选迁移、刷新、切项目、退出登录、慢响应和条件编辑未应用均有行为验证。
- 受控上传请求绑定界面展示的本体 ID；无本体/读失败/未发布草案/批次排队后发布新本体时行为清晰。
- 文件结果与事实引用不拿最新本体替代实际历史归属；同 vN 多发布身份可区分。
- 验证 Node 契约与有意义的浏览器行为，检查 1440/1280/1024/768 宽度；后端行为未改变时不重复跑全量数据库测试，新增范围接线依赖的接口做定向验证。不得并行运行两个 PostgreSQL pytest 会话。

### 第二批：来源与处理的完整用例

先修复现有交互契约缺口：恢复术语的来源版本/字段、融合属性冲突选值、消歧复核队列与审核合并的 winner 参数桥接，以及多个精确同名候选的歧义处置。随后独立补来源逻辑身份/文件新修订、精确来源问答范围、资料列表服务端条件、文件可用状态读模型和来源变更依赖失效；为索引构建增加服务端幂等/活动任务复用。没有对应契约时不开放新增按钮或承诺。复用现有上传、断言、溯源、任务与事务 outbox。

持续建模同时补齐精确发现来源/候选 manifest、用户预期本体基线、发现运行的任务化入口与草案切换/合入协议；优先接通现有“项目候选 + 当前发布基线”的真实流程，再开放精确来源和跨草案合入选项。复用 source fingerprint 和已处理候选标识，不另造一套无审计的“立即应用”。

验收以单份及批量真实规则资料为主：上传 → 标注平台/有效期 → 原文阅读 → 待确认/正式事实 → 按明确范围问答 → 冻结引用 → 来源修订/撤回 → 新旧回答及索引资格核对；验证同名不同内容、同内容重跑、多来源同事实与部分失败恢复。原文可用与图谱可用分别验证。

### 第三批：真实 Local/OAG 增强与消融实验

接通正常问答分支的实体/邻域/路径及证据读取，明确定义图谱与本体辅助开关的执行范围；以固定资料和问题集完成第 15 节的查询侧消融。实验运行、范围 manifest、逐问题结果和成本记录由服务端持久化。当前 `ontology_expansion=false` 只关词项扩展，不能冒充关闭全部本体辅助。

### 第四批：社区与全局问答

独立规格/实施计划，固定算法与依赖版本；先做一个范围明确的社区构建和 Global 工作流，再评估 DRIFT。使用相同固定业务问题对照文档检索、局部增强与社区模式的证据正确性、范围隔离、有效性、延迟、token 成本及失败恢复；不能只凭主题回答更长就通过验收。

前一批不以完成社区能力为前提；每批都验证实际使用路径。设计确认后生成对应实施计划，再修改产品代码。

## 12. Semantica 底层职责与“本体解析”的准确含义

| 环节 | 当前实现 | 修订目标 |
| --- | --- | --- |
| PDF/DOCX/HTML 文件解析 | `DocumentParser` → `semantica.parse.DoclingParser`，记录解析器/版本/页表信息 | 保留 Semantica 接入，统一错误、OCR 能力、原文偏移及解析收据 |
| TXT/Markdown 正文读取 | 内置 UTF-8 读取，并非调用 Semantica | 统一在资料处理入口管理，保留轻量读取事实；不在界面宣称所有格式均由 Semantica 完成 |
| 实体、关系和属性语义抽取 | Semantica provider 与本项目受控/开放适配 | Semantica 作为算法依赖，结果进入候选/断言和正式写入规则 |
| 从资料归纳本体 | `ontology_discovery._induce` 调用 Semantica `OntologyGenerator` | 保留候选归纳、类/谓词/属性归一化、冲突隔离及基线版本绑定 |
| 已有标准本体文件解释 | 当前公共入口只接收 Turtle，`Ontology` 使用 RDFLib，随后建立本项目术语/约束索引；多格式 OWL/imports 闭包尚未接通 | 通过统一的本体导入/解析适配接入处理链；RDFLib 保留标准图和未支持三元组，不把 OWL 压成 Playground 的简化 JSON |
| 本体质量与实例校验 | Semantica quality check + RDFLib/pySHACL + 项目业务约束 | 区分语法错误、SHACL 违规、语义风险与质量建议，只有真实通过的检查才能显示通过 |

“本体解析”需要同时覆盖资料中的语义结构发现与标准本体文件解释：前者已有 Semantica 归纳链，后者目前不是完整的 Semantica 端到端解析功能。目标以 Semantica 的解析/抽取/本体能力为主要算法底座，通过明确适配统一接入；标准 RDF 解析与 SHACL 保留必要内核。不能仅把 RDFLib 入口换名就声称增加了 Semantica 能力。

Semantica 输出通过项目服务写入 PostgreSQL；本体、事实、来源、审核和版本仍由项目统一治理。Milvus/Neo4j 是可重建投影。未发布的建议不直接成为正式术语，底层库的自动合并/推理建议不绕过人工决策、范围与版本守卫。

## 13. 完整本体编辑器：参考 Playground 的联动，保留项目治理

### 13.1 布局和展示

参考项目真实 Designer 是“左表单 + 右 Graph/RDF 预览”；浏览页另有 Inspector。采用本项目现有三栏工作区并补齐内容，而非原样搬入其英文演示规则：

- **顶栏**：当前草案/基线发布、保存状态、版本记录、导入/源码、撤销/重做。已发布/历史版本只读；“编辑”创建或进入基于该版本的草案。
- **左栏**：类/关系/数据属性目录、术语搜索、添加入口、继承树和发现候选入口。类型卡片可展开属性摘要，属性显示名称、值类型、直接/继承来源。
- **中央**：类继承与业务关系图。提供紧凑圆点图、带属性摘要的类型卡片图及 RDF 源码视图；圆点图取自参考的显示方式，画布属性卡是本项目设计增强。继承用独立的虚线箭头，关系保留真实方向和类型；属性可作为类型卡片中的字段，避免全展开为节点。
- **右栏**：选中对象的查看/编辑检查器，类、对象属性、数据属性与继承使用对应表单。宽屏常驻，中屏/小屏使用用户已认可的抽屉；不会与路径、证据抽屉互相遮住。
- **底栏**：本次变更、风险、校验问题、审核与发布；点问题定位对象和字段，点变更看前后值及影响。默认只占一行，详细清单按需展开。

画布移动/布局保存独立于本体语义修改；缩放、布局、标签开关不产生本体发布。草案内撤销与重做只处理编辑操作，已发布历史不可由客户端撤销栈删除。

### 13.2 编辑对象和字段

| 对象 | 显示/编辑内容 | 提交边界 |
| --- | --- | --- |
| 类 | 中文标签、规范名称、说明、稳定 IRI、多个父类、状态、属性列表 | 保留身份；增删父类先看继承环/影响，不静默改实例归属 |
| 对象属性/关系类型 | 名称、说明、domain/range、方向、现有约束；选起点和终点建关系 | 与继承操作分开；1:N 展示须来自实际约束，不能自行推导 minCount=1 |
| 数据属性 | 名称、所属类、XSD 值类型、说明、约束；显示继承来源 | 数字/日期/枚举等控件读取真实约束；同名类/关系/属性冲突阻断或隔离 |
| SHACL/约束 | 必填/最大数量/枚举/模式/值域等当前支持的字段，复杂形状看源码 | 服务端执行真实校验，未支持的 OWL 表达保留并提示，不能静默丢弃 |
| 停用/恢复 | 原因、影响、替代术语；恢复选择来源发布和明确字段 | `restore_term` 必须携带 source_ontology_id + selected_fields；不得仅发 target_iri |

所有编辑走现有结构化草案命令。导入先保留原始标准图和导入差异；Semantica 生成的候选先进入预览、映射与冲突处理，不“应用”即覆盖生产本体。模板借鉴的是交互，不套用 Fabric 的 26 字符/仅英数字/每类强制标识等应用约束。

### 13.3 版本、审核与迁移

版本记录可查看结构/标注差异、发布时间、稳定 ID、来源草案及相关治理记录。当前已有草案相对基线的差异和整版本 revert；任意两份历史发布的比较尚需独立补读模型/比较契约，前端不能仅更换两个下拉框就宣称实现。相同 vN 的标注修订仍保留不同发布身份。历史查看不切换线上指针；从历史回退创建新草案，经校验/审核后再发布。

发布确认展示变更、风险、校验、候选物化计划（如有）与索引后续同步。现有知识继续标记原本体依据；需要迁移时走已有受控重分类，明确受影响知识、前置版本与失败原因。不得把所有发布概括为“仅改结构”，因为发现发布可能带经过治理的事实物化计划。

## 14. 实体维护、融合、消歧和撤销的固定入口

### 14.1 维护路径

台账默认显示实体清单，保留关系/属性/片段视角。点实体打开同一对象抽屉，包含“属性 / 关联 / 证据 / 修订历史”。图谱节点也使用这套详情；关系与属性有自己的记录 ID、修订和来源，不把虚拟展示节点当作可写实体。

列表工具栏明确提供“新增实体”；对象主操作是“编辑实体”，并提供“新增关系/新增属性”；更多菜单保留别名、软删除与恢复。创建/修订用本体驱动字段表单，高级 JSON 继续可用。提交携带预期修订号；冲突时显示最新内容供比较，不静默覆盖。

实体类型编辑继续从该记录绑定的本体选择可用类，保留现有同本体范围内的类型纠正能力；跨本体发布的迁移另走受控重分类。不能因引入新版编辑器而把所有类型修改一律禁用。

### 14.2 融合与消歧

台账页内常驻“融合与消歧”入口，实体详情可发起该流程。内容包括疑似重复组、按名/别名查重、人工选择两个实体和待消歧复核队列。

融合步骤：选保留实体/待并实体 → 比较类型与属性、关系、来源和业务范围 → 检查兼容性 → 选择冲突字段处理 → 展示影响 → 确认。相似度只是候选线索。服务端仍检查稳定类型 IRI、业务区间和 applicability；不同本体版本在满足兼容条件时可以融合，不能恢复成“必须同 vN”的旧限制。

SHACL maxCount=1 的冲突已有 `governance.merge` 的 `attribute_winners` 选择契约，前端需明确选获胜属性，不凭显示顺序默认选择；消歧复核的合并 DTO/路由目前还缺此参数桥接，需同时补齐。其他冲突按后端实际能力阻断/转复核，不能承诺任意冲突都会自动消解。合并后来源断言和旧修订继续可追溯，关系按真实治理规则重定向。

现有精确同名/别名快路径会取首个合格候选，多个候选时尚未强制复核；`auto_merge=false` 只控制语义相似合并档，不能当作关闭全部精确对齐。改造要求多个精确匹配先显式选择或进入歧义复核；说明唯一标识对齐、别名对齐、语义融合分别采取了什么规则，不把任何同名都自动当作同一对象。

复核队列显示候选依据、评分、来源差异和已有决定，分别提供合并、保持独立、驳回候选三个动作。拒绝候选不自动删除来源，不合并也不代表数据错误。

### 14.3 操作历史与恢复

“操作历史”集中展示融合、别名、软删除/恢复及可撤销状态。撤销先读取当前依赖和预期版本，展示将恢复的对象/关系；已有后续修改导致不可安全撤销时明确解释，允许回到对象详情处理。不会承诺任意时间都可撤销，也不直接删除审计记录。

## 15. 检索与问答消融：单独的真实实验能力

用户同时需要实体融合治理和能力消融评测。它们分属台账与质量评测。现有抽取 P/R/F1 继续保留，新增检索与问答实验，不用一个分数混合全部目标。

### 15.1 冻结实验与配置

一个实验固定：项目及访问资格、来源/知识修订 manifest、业务/系统时点、平台/对象范围、本体发布身份、索引代次、问题集/期望证据、模型/prompt/编码器配置、top-k/上下文预算、随机性和缓存冷热策略。不能一组资料多、一组资料少却把差异全部归因于图谱。

冻结的是实验输入与配置，不冻结访问权。执行、读取结果与导出时重新检查当前身份/授权和来源撤回资格；操作者由服务端认证上下文写入，不接受客户端伪造 actor。已撤回资料或已失去权限的证据不得因存在历史 manifest 而继续暴露。

| 对照组 | 实际执行要求 | 当前接入状况 |
| --- | --- | --- |
| 关键词/向量/混合基线 | 各自真实检索，保留命中证据版本 | 现有模式；需新增统一实验运行与记录 |
| 混合 + 图谱局部增强 | 范围内实体/邻域/路径进入上下文 | 正常问答分组分支尚需接通，不因图浏览存在就标已实现 |
| 混合 + 本体辅助 | 明确词项/类层级扩展和允许的本体上下文 | 已有 ontology_expansion 仅覆盖部分辅助；完整实验开关需定义 |
| 完整增强，去图谱 / 去本体辅助 | 一次改变一个指定因素，记录实际跳过环节 | 新增策略契约；关闭不影响权限、有效性、来源资格和正式知识校验 |
| 社区 Global/DRIFT | 匹配范围的社区/报告真实参与检索 | 后续能力，缺产物时标不支持，不给虚构指标 |

关闭图谱必须阻止图上下文/邻域/路径读取和入模，不是仅隐藏画布。关闭本体辅助须约定移除哪些召回/上下文环节，不能关闭治理、授权或证据资格校验，也不能以 `ontology_expansion=false` 代替整个 OAG 的消融。

构建侧可增加“融合/消歧前后”对照，但必须从同一冻结抽取输入建立隔离的派生实验图，固定别名、候选与决策策略，不撤销/重写生产融合记录来制造实验组。此项在查询侧实验完成后独立建设。

### 15.2 报告与证据

结果按问题配对展示：命中的文档/事实版本、遗漏证据、答案与引用、平台/时点越界、拒答原因、实际执行策略和降级。聚合指标包括证据 Recall@k/Precision@k（有标注时）、引用支持性与有效性、答案正确/拒答判定、延迟 P50/P95、token/成本。缺少标注或用量收据时显示未评测/不可用，不记成 0 或满分。

配置、运行和结果分离；可取消长实验、重试失败项、查看每组未完成状态并导出可审阅报告。模型评分只作辅助，争议项进入人工复核。成本/质量结果均来自实际运行，不以演示值或框架论文成绩替代本项目测量。

## 16. 能力保留与验收底线

实施计划必须把“旧入口 → 新入口 → 服务契约 → 行为验证”逐项登记，至少覆盖：实体/关系/属性 CRUD 与历史；别名查重、重复组、融合、冲突选值、消歧复核与撤销；本体类/关系/属性/继承/SHACL、草案/校验/审核/发布、版本查看/回退/术语恢复与受控迁移；上传/断言/原文/问答引用；三种检索与显式本体扩展；抽取评测及新消融框架的能力状态。

草案重基线/来源刷新、安全批量确认、按本体版本查看关联知识，以及索引状态核验/修复均需保留可到达入口和各自守卫，不能因导航收拢而遗失。

上版草图没画出的能力不作为删除理由。改后的正常用户路径必须能找到并完成原操作；发现已有契约错配则记录修复和验证，不把“按钮存在”当作链路已经可用。设计预览的表单与本地操作不计为这些产品能力已接通。

## 19. 最终澄清：抽取策略与持续建模是两个维度

用户明确表示关注的是开放抽取和非开放抽取的逻辑，不是按类型设置复杂的新增白名单，也不是发布后锁死本体。上传每次明确选择抽取方式并记入运行；切换方式不改变项目今后能否建模。既有 `extraction_mode=ontology/discovery/documents` 继续作为真实协议，本体编辑不由这个开关控制。

| 维度 | 按已有本体抽取（非开放） | 开放抽取 |
| --- | --- | --- |
| 本批资料 | 映射已发布的类/关系/属性；记录不能映射的内容 | 可发现新词汇；先生成候选并处理映射/冲突 |
| 正式本体 | 本批不自动扩展结构 | 候选归纳为草案，校验和审核后才能发布 |
| 后续手工编辑 | 可新增、修改、停用、恢复类/关系/属性，均走草案 | 同样可操作 |
| 发现父类 | 独立操作，可基于当前草案调用 | 同样可操作，不要求再上传资料 |
| 发布之后 | 发布记录不可变；创建或继续新草案增改，再发布 | 相同规则；已有知识保留实际本体依据 |

“非开放”约束词汇扩展，不等同于把 `relation_constraint_mode` 的所有校验自动设为 strict；现有 advisory/review/strict/off 是另一套关系约束处置参数，应保留在高级设置并如实记录。实体消歧与 `auto_merge` 也独立，模式切换不默许自动融合。

### 19.1 补回的建模操作

- **发现父类**：本体页固定入口，至少两个有效类、可编辑草案及当前基线满足条件才运行。当前已有实现仅在已有类之间建议继承；保留已有边，跳过重复/环，模型失败给明确失败状态，过期修订/基线拒收。实际已有服务将建议编译进草案命令，再进入审核发布；新增“逐条预览后采纳”属于交互/接线增强。草图显示本地示例建议及采纳/不采纳，不伪装成模型实测。
- **插入/新增**：集中菜单承载新建类、为选中类添加子类、新建关系、新增属性；创建上级概念后可连接已有子类。这里的“插入”指手工结构编辑，不默认为删除旧边并自动在两类间插入中间类。
- **画布连线**：保留选子类再选父类、以及选关系起点再选终点的两步流程，确认后写草案；表单编辑仍可用。多父类不被替换成单父类。
- **不完整定义**：既有服务允许尚未设置 domain/range 的关系/属性；目录仍显示，注明未指定端点，不把“画不出线”当作关系不存在。新草图中部分必填端点表单不能作为删除这个既有能力的依据。

完整逐项对照见 [能力、入口与验收清单](../../research/2026-10-19-full-capability-ui-parity.md)。其中未完成的草图交互与未实现的产品链路分别标记；该清单作为后续实施验收的基线，不以截图或检查数量替代能力覆盖。

## 20. 15 万实体与完整检索的追加约束

用户要求两项都满足：全库检索与同一图谱绘制 15 万实体。局部邻域和聚合总览只作为补充，不替代全量模式；类型卡片是本体结构展示，不是实例大图方案。详情、编辑、证据、历史、融合和撤销在列表、局部图、全量图中使用相同真实 ID 与服务契约。

完整性包括功能入口、检索语义/范围、运行可用性和规模，分别验收。当前代码有 Neo4j/Milvus 原生加速，也仍有全范围权威回退、未分页选择器和图证据缺口；不能用快路径或几个模式名称代表所有请求都已完整可用。依据本次磁盘审计更新状态，不沿用旧索引的行号或把所有检索概括为全量预载。

全量模式需独立的数据会话/分页清单、WebGL 渲染与布局/解码 Worker、逐层显示标签、错误恢复，以及基于实际边数/硬件的容量验证。先做隔离 15 万技术验证，再集成共享编辑器；未验证前，草图已标明“全量模式尚未验证”。具体数据契约、待验证目标和必过行为见 [补充规格](2026-10-19-search-graph-scale-and-capability-acceptance-design.md)。
