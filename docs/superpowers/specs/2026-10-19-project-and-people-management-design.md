# 项目管理与人员管理：可发现的管理入口

日期：2026-10-19。范围是信息架构、操作设计和本地交互草图；未修改生产页面、账号或权限后端。

## 1. 结论与方案选择

推荐左侧固定“管理”分组，直接列出**项目管理、人员管理**。上方仍按当前项目呈现知识业务；左上项目下拉用于快速切换。管理入口放在账号上方且不随业务导航滚出视野，业务区空间不足时独立滚动。管理页标题与面包屑标明工作空间范围，不能让人以为人员角色只影响当前项目。

| 方案 | 优点 | 代价与判断 |
| --- | --- | --- |
| 固定管理分组，两个独立页面（采用） | 不用猜账号菜单或项目下拉；列表与操作可以完整展开 | 多两个导航项；用分组和全局面包屑区分工作范围 |
| 合并到一个“设置”页面 | 主导航较短 | 入口含义含糊，项目和账号操作仍需二次寻找 |
| 继续放在下拉和账号菜单 | 视觉最轻 | 当前反馈已说明发现性不足，不采用 |

不增加与任务无关的统计大卡，也不在管理页显示内容 Metadata 筛选。人员页只提供姓名/账号、角色、启用状态条件；项目页只查找项目名称。

## 2. 已核对的能力边界

| 能力 | 当前实现 | 设计处理 |
| --- | --- | --- |
| 项目列表、创建、读取、改名、删除 | [projects.py](../../../knowledge_service/api/projects.py) | 汇入项目管理；概览和备份保留 |
| 创建时的 metadata、ontology_mode、可选默认本体 | 同上及 [models.py](../../../knowledge_service/models.py)；更新请求仅支持 name | 表单先收名称，但创建请求必须显式传 `ontology_mode: "discovery", use_default_ontology: false`，避免服务默认装入通用本体；抽取路径在上传时选择 |
| 用户列表、创建、展示名/角色/启用状态修改、口令重置、删除 | [users.py](../../../knowledge_service/api/users.py)、[user-admin.js](../../../knowledge_service/web/user-admin.js) | 保留完整操作，将原来的隐蔽入口改为人员中心 |
| admin / superadmin / viewer | [auth.js](../../../knowledge_service/web/auth.js)、[security_middleware.py](../../../knowledge_service/api/security_middleware.py) | 管理员和超级管理员能进入管理页；只读用户保留切换项目，不能写入 |
| 项目成员、项目角色、按成员限制项目访问 | 未见成员关系或项目 ACL 接口 | 明确列为独立后续能力；不摆可点击的“管理项目成员”假入口 |
| 邮件邀请、部门、团队、项目归档 | 本次未见相应接口 | 不加入此次操作承诺 |

当前人员管理是**全局账号与系统角色**。项目 ID 划分数据空间，不等于已经实现按人员控制项目访问。页面重排不能替代后端鉴权。

用户路由文件说明声称 admin 不能“查看”超管，但当前 GET 清单直接返回 `users.list_users()`，前端也会列出受保护账号；不能声称已有清单隐藏规则。本设计暂保留该受保护行，不展示其编辑操作。修改超管、授予超管的限制由后端守卫实施。

## 3. 项目管理页面与抽屉

列表每行：项目名、当前项目标记、来源资料数量、本体状态、进入项目、设置。数量和状态必须来自真实接口；无数据时显示“待获取”，不能根据处理进度推断可用。草图只从示例数据计数，正式接入如列表字段不足需补汇总接口，避免逐项目拉全量知识。

主按钮“创建项目”。填写名称 → 提交 → 创建成功后进入该项目资料库空态 → “添加文件”。生产接入请求明确为 `{name, ontology_mode: "discovery", use_default_ontology: false}`，不能只提交名称：现有模型默认 `use_default_ontology=True`，路由缺省 mode 为 ontology，省略两项会加载默认本体。这里选择空项目作为初始化策略，不限制以后逐批选择抽取方式。

不要求用户创建项目时先理解本体、索引或抽取参数；首份资料上传时选择图谱增强/仅文档，以及开放/非开放抽取。已有领域本体通过本体建模层的导入/编辑/发布流程先建立，再供受控上传选择。创建后仍可继续编辑本体。原创建时的模式选项移动到实际资料处理和本体建模入口，功能不删除。

“设置”打开右侧抽屉，包含名称、项目概况、项目概览和知识备份入口；删除放在抽屉下方。保存只提交项目名称，不能暗示描述、所有者或默认抽取配置可以更新。名称校验遵循服务契约；前端空值检查不能被描述为服务端项目名唯一约束。

删除先确认项目名和影响，输入项目名后提交；服务端成功后再移除列表。删除当前项目则清除其当前页面/问答上下文，并进入剩余项目或“暂无项目”状态；不可继续使用已删除 ID。PostgreSQL 删除与外部派生投影清理的回执分开展示：`deleted` 成功但 `cleaned` 异常时提示清理待处理，不能回滚假象或直接宣布全链路已清空。

## 4. 人员管理页面与抽屉

列表每行：展示名/登录账号、系统角色、启用状态、编辑。当前账号显式标记。创建按钮叫“添加人员”，抽屉标题/说明明确创建登录账号；字段为唯一登录账号、可选展示名、系统角色、初始口令。admin 可选 viewer/admin，superadmin 才可选择最高角色；用户名冲突展示 API 409，不丢其他输入。当前没有邮件字段，因此不展示“发送邀请”。

“编辑”打开右侧抽屉：账号不可改名，可改展示名和被允许的角色；账号启停、重置口令为次操作，删除放在下方。保存角色降级、停用与删除前显示后果并确认。停用保留账号，删除物理移除并释放登录名，不能混用。重置口令要求两次输入一致；不回显旧口令或存储草图口令。自己的口令沿用个人账号入口。

角色保护继续服从现有服务：

- admin 能管理普通 admin/viewer，不能创建、提升为或修改 superadmin。
- superadmin 可授予最高角色；任何人都不能降级、停用或删除已有 superadmin。
- 当前登录账号不能降级、停用或删除；自己的展示名仍可修改。
- 只读用户不展示写入控制；直接访问管理 API 仍由服务端拒绝。隐藏按钮不是安全边界。

成功反馈说明更改的对象和字段；正式接入时如遇 403/409/404，保留未提交输入，解释原因，刷新角色/目标状态后重试。人员页切换项目仍保持全局范围，不能将列表绑定当前 project_id。

## 5. 项目成员权限的后续方案

如果需要“甲只能访问 A 项目，乙能编辑 B 项目”，应建设项目成员子页与服务端成员关系：在项目设置里增加“成员与权限”，明确项目可见性及读取、资料维护、本体编辑/发布、治理、构建等授权。届时系统管理员和项目内角色分别建模，设计迁移后的存量项目可见范围并覆盖所有读写接口、异步任务和证据访问。该阶段需要单独设计与验收，当前草图不将其做成已生效配置。

## 6. 草图范围与接入验收

交互文件：[工作流草图](../mockups/2026-10-16-workflow-preview.html)，独立模块：[management JS](../mockups/workflow-management-preview.js)、[management CSS](../mockups/workflow-management-preview.css)。支持 `#projects` / `#people` 直达。现用 admin 示例，支持本地创建/改名/切换/删除项目及账号创建/编辑/启停/口令确认/删除；重载恢复示例。没有真实 API、真实邀请或真实账号更改。草图未模拟 viewer/superadmin 登录身份，角色矩阵属于生产接入验收要求。

正式接入验收：两个入口在桌面和移动导航都可发现；长导航滚动时管理入口可达；项目切换器仍可快速切换；列表搜索与状态过滤语义准确；项目创建空态、改名同步、删除当前/最后项目可完成；账号重名、口令校验、角色降级、停用与删除语义清晰；自身与超管保护不可绕过；viewer 无写入并且 API 拒绝越权；错误与投影清理回执正确；两个管理页面无 Metadata 筛选。
