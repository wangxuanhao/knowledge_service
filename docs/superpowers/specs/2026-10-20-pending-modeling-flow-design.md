# 候选进入本体、手动建模与版本发布设计

日期：2026-10-20。状态：设计提案，待用户评审；本次不实施生产代码。

最终核对：静态设计复审通过；八组 DOM 场景以及 Edge 桌面/390px 五步界面检查通过。额外覆盖“勾选但未加入”的候选不能随纯手动变更发布；正式结构、发布快照与下一轮清单均按实际加入绑定生成。浏览器记录见 `../../research/2026-10-20-pending-modeling-browser.json`。这些检查只验证交互稿，不证明真实服务已具备选批、预演或事务契约。

交互稿：`../mockups/2026-10-20-pending-modeling-flow.html`。其中所有数据与交互均为静态演示。

## 1. 目标与选择

用户应始终知道：现在看的是什么、打算加入哪些内容、写到哪份草案、与哪个正式版本相比、是否已经发布、后续如何继续调整。

推荐采用 **“待建模清单 → 选批 → 加入草案前预览 → 草案内调整 → 审核与发布”**。保持已认可的浅色本体建模台、中央结构画布、左侧术语目录、右侧检查器、底部变更清单，只补齐候选进入与版本边界。

比较过的另外两种方案：

| 方案 | 好处 | 代价与结论 |
| --- | --- | --- |
| 顶栏“待建模”侧栏，选批后预览加入草案（推荐） | 同一工作区能看见目标结构与候选；发布前可继续手工调整；入口明确 | 需要补齐服务端选批、预览和目标草案契约 |
| 独立“待融合”页面，再返回建模台 | 大批量处理空间更大 | “融合”容易被理解为实体去重或直接改正式本体，切页丢失目标结构上下文 |
| 候选自动进入草案，再统一审核 | 点击少 | 用户无法明确控制插入范围；草案易受后续抽取污染；不采用 |

主入口名称用 **待建模（数量）**，说明文字为“来自抽取的候选术语”。“待融合”可作为用户口头表达，但不作为系统动作名；系统中的实体去重、事实确认与本体术语建模是不同任务。

## 2. 四类对象与两套版本

| 对象 | 展示单位 | 主要动作 | 不能暗示的含义 |
| --- | --- | --- | --- |
| 候选事实 | 实体/关系/属性陈述、来源与证据 | 查看证据、确认或排除事实 | 抽取成功即正式知识 |
| 候选术语 | 实体类型、关系类型、属性名称，聚合来源事实 | 新增术语、映射已有术语、暂缓、处理冲突 | 候选节点已属于正式本体 |
| 草案变更 | 稳定操作 ID、目标 IRI、修改前后、来源、审核决定 | 手动改、撤销、校验、逐条审核 | 已保存草案等于发布 |
| 正式本体 | 版本快照、术语稳定 IRI、发布人/说明/时间 | 查看、比较、基于当前版本继续建模 | 发布后永久禁止建模 |

顶栏固定显示“当前正式本体 v3”“工作草案 D-024 · 修订 r8 · 基于 v3”。本体版本 vN、草案修订 rN、实体记录修订必须有完整名词；不能共用一个无前缀“版本”徽标。历史版本预览必须带“只读预览 · v2”，退出后回到原草案，不自动创建新草案。

开放/严格抽取控制抽取方式与未命中术语的处理，不控制正式版本能否被覆盖。正式快照不可原地修改；基于当前版本可以持续建模并发布下一版。

## 3. 插入前：建模台与待建模清单

### 3.1 顶栏与画布

- 固定版本区展示正式版本、工作草案、草案修订与基线；无本体时显示“尚未发布 · 首版草案”。
- “待建模 4”打开宽侧栏，不直接执行生成、模型推理或写入。
- 候选默认不进入正式树。开启“显示候选”时仅为虚线预览，图例写明“候选，尚未加入草案”。
- 右上保留“手动新增”“发现父类”“版本管理”；底部保留“本轮变更”“审核与发布”。

### 3.2 清单信息

清单以候选术语为行，按类型/关系/属性筛选，同时显示：显示名与规范名称、推荐动作、目标父类或关系端点、来源文档数量、涉及候选事实数量、证据可用性、冲突原因、目标草案绑定。默认不勾选任何项。

同名不等于同义。命中已有术语时默认显示“建议复用”，需核对稳定 IRI 与种类；跨种类冲突必须单独处理，不生成本体操作。证据不可解析的项保留诊断，不能用绿色“可加入”掩盖问题。

选择可分页保留，但底部必须写“已选 2 项（含其他页 1 项）”；全选只选择当前筛选中可处理的项，提供清空选择。筛选后仍显示选择总数与完整已选清单。刷新来源后原选择失效项要逐条说明，不能静默替换成新集合。

每个候选可查看证据抽屉：原文引用、文档版本、片段、抽取批次、术语归纳理由、受影响事实。展示置信度不替代人工判断。

## 4. 插入哪些内容：加入草案前预览

点击“预览加入草案”才进入预演；还未保存。预演固定以下上下文：项目、目标草案 ID、目标草案修订、正式基线 ID、来源快照、选中候选与映射、父类/端点调整。

目标草案必须明确选择：继续当前可编辑草案，或基于当前正式版本创建新草案。存在其他草案时不能静默附加；草案已收下/驳回时只能回看或新建下一轮。

预览分三块：

1. **结构前后对照**：新增节点/边用实线预演和“新增”标签；移动父类显示旧父类→新父类及删除/新增的边。关系展示 domain/range；属性展示所属类、datatype 与约束。保留所有既有父类，除非用户明确选择替换。
2. **本次变更清单**：逐项列“新增术语”“复用已有”“修改层级”“跳过冲突”，展开可读稳定 IRI、原子操作、证据与依赖。排除某项时连带项必须可见，不能留悬空关系/属性。
3. **事实与发布影响**：显示关联事实数量、写入模式与预计跳过原因。加入草案不会确认事实。现有发现发布可能联动事实物化，预览和最终发布确认必须明确显示，不得声称“只改本体”或“所有事实必然写入”。

主按钮“加入草案（2 项）”；副按钮“返回选择”。“生成建议”不是“加入草案”。父类推断采用独立“发现父类”，明确需要模型推断且允许失败降级；已人工选择的层级不可被建议悄悄替换。

### 4.1 只有术语复用时：独立事实确认

当本批全部候选都能复用已有正式术语、没有新增结构操作时，不要求用户制造空草案或执行一次“发布”。从清单的“核对映射与事实”进入：

1. 核对显示名、规范名称、种类与稳定 IRI。例如将本批可确认是企业实例的“采购方”主体映射至示例 IRI `https://example.org/ontology/Enterprise`（`owl:Class`）。采购方也可能表示角色，需用本批证据确认，不能仅按词义相近自动合并。
2. 明确勾选映射确认，再预演事实写入影响。逐条列来源事实、预计新增/复用/跳过与理由；本体变更数为 0，当前正式版本和工作草案修订保持不变。
3. 用户另行确认本批事实范围，再执行对应 `ready_to_finalize → finalize_run` 的发现完成意图。该动作是事实处理，不称作“发布本体”。
4. 返回事实回执，逐条显示实际新增、复用、跳过、诊断与来源；请求键、来源快照和正式基线随回执保留。重复确认或结果未知后的重试应返回同一结果，不能重复创建事实。

交互稿的采购方示例有 3 条事实：F-B01 企业身份明确，模拟新增 1 条；F-B02 已有 E-017，模拟复用 1 条并关联证据；F-B03 仅称“甲方”，因 `missing_entity_identity` 模拟跳过 1 条，保留证据与诊断。回执 FR-001 显示 v3→v3，不创建本体版本，也不修改 D-024 修订。之后若其他流程发布 v4，回执仍记录处理时的 v3，同时展示当前版本，不能把历史回执改成 v4。

这条路径与“有结构变更的发现草案在发布时联动事实物化”分别展示。当前后端已有无结构变更的 finalize 能力；将用户精确选批、人工映射及逐条预演贯穿到该能力仍需补齐契约，静态稿不表示已上线。预演后正式基线或来源变化时回到核对映射，不能沿用旧确认直接执行。

## 5. 插入后：草案投影与手动修改

提交成功后显示“已加入草案 D-024 · 修订 r9；尚未发布”，给出实际新增/复用/跳过结果，定位新节点。正式版本仍显示 v3。待建模清单中该批标记“已进入 D-024”，提供回到草案；不能继续显示为可重复加入的待项。

画布显示“v3 + 当前草案”的投影；新增为浅青色与“草案新增”文本，修改为“草案调整”文本。颜色之外必须有可读标记；正式树可随时切换回“仅看 v3”。底部每条变更保留来源、动作、前后值及撤销入口。

### 手动能力应保留并整合

| 入口 | 操作 | 预览与保护 |
| --- | --- | --- |
| 选中类型→新增子类 | 在指定父类下新增类型 | 展示 IRI/规范名称冲突；不默认改其它子类 |
| 选中父子连线→插入中间父类 | 例如 企业→供应商 变成 企业→交易主体→供应商 | 明确列新增类、新增两条边、移除原一条边；其他父类不动；环路校验 |
| 检查器→父类 | 增加或移除一个父类 | 保留多父类；显示受影响继承关系 |
| 检查器→属性 | 名称、说明、datatype、domain 等 | 标量属性与对象关系分开；显示继承来源；不把继承属性重复新增 |
| 关系检查器 | 名称、domain、range、方向等 | 明确结构语义变更和事实影响 |
| 发现父类 | 对当前草案请求建议 | 独立建议清单，逐条采纳到草案；失败不妨碍手动建模 |
| 变更清单→撤销 | 撤销选定变更或本批 | 先展示依赖与来源绑定影响；不误当成删除正式术语 |
| 版本管理→基于当前版本继续建模 | 发布后开启下一轮草案 | 自动带当前正式基线，前版可回看 |

手动修改与候选导入共用草案操作账本和校验。已提交后继续改会使相关校验/审核决定过期，界面立即提示“内容已变更，需要重新校验/审核”；不能保留旧的“可发布”绿灯。

### 5.1 空草案也能直接手动建模

“草案可编辑”由草案存在且请求为 pending 决定，与是否已导入候选无关。空草案的“手动新增”应可用，能直接保存类型、属性或关系操作；已有正式结构时可据此选择父类、domain、range。完全空本体没有类目标时，属性/关系的端点必须先建立，不能伪造目标。

“发现父类”根据当前正式结构叠加草案后的实际类型目标放行；有目标类即可请求建议，不要求先导入某个候选。无目标类时展示“先新增实体类型”的原因与入口。静态稿列出目标，不执行模型请求。

审核与发布以实际操作账本非空、当前指纹决定和服务端 readiness 为准，不以“已导入候选”作为前置条件。只有手动变更时，涉及候选事实数显示 0，不生成虚构来源或事实处理计划；发布成功仍保留草案账本与正式版本，下一轮沿用已发布手工术语。

## 6. 审核与发布：清楚但不再增加后端状态

持久请求状态沿用 `pending → accepted / rejected`。界面显示的“待建模、已加入草案、待校验、待审核、可发布、基线变化”是从事实投影得到的进度与门禁，不新增等价状态机。

“审核与发布”面板展示：修改前后的结构、服务端逐项风险分类、错误和修复入口、警告确认、每条当前指纹上的审核决定、当前基线是否变化、来源快照是否变化、发布说明、事实写入影响。

建议用户动作分两层，但沿用后端现有提交与发布命令：

- “校验并准备审核”执行现有校验/提交；错误定位回检查器。
- 审核按服务端 `review-plan` 的 safe/manual/blocked 展示；安全项批量确认必须明确列出集合。高风险变更逐条审核并说明理由。不得把批量批准在界面上称为“已发布”。
- “发布本轮变更”只在服务端 `publish-readiness` 准备就绪时可点。按钮下写具体阻断原因和下一步。
- 最终确认显示实际版本策略：结构改动通常发布下一版；纯注释改动可能复用结构版本号。不能固定承诺每次 vN+1，仍需显示新的发布记录。
- 若发现草案附有事实物化效果，确认区显示“同时处理 X 条候选事实，预计新增/复用/跳过…”，发布结果分别报告本体与事实。无结构变更但已有术语可复用时，走明确的事实确认/完成发现路径，不制造空本体版本。

发布后显示“当前正式本体 v4 · 发布成功”，草案为只读历史请求。提供“查看版本差异”“查看事实处理结果”“基于 v4 继续建模”。索引同步如异步进行，单独显示任务进度与重试，不将数据库发布成功与索引查询就绪混为一谈。

## 7. 转换/动作矩阵

| 当前可见情境 | 用户动作 | 实际对象变化 | 下一步与可恢复性 |
| --- | --- | --- | --- |
| 有候选，未选批 | 打开待建模、筛选、看证据 | 无写入 | 保留当前草案视图 |
| 已选可处理候选 | 预览加入 | 只读预演，不改变草案 | 可改映射/父类/范围；返回不丢选择 |
| 预演与基线/来源均一致 | 加入指定草案 | 原子写入候选绑定与草案操作，增加草案修订 | 展示实际结果；以批次/命令键去重 |
| 已加入 pending 草案 | 修改属性/层级/关系 | 追加或替换草案操作；新修订；旧校验/决定可能失效 | 返回变更清单与定位 |
| pending 草案有未决定项 | 校验、提交、逐条审核 | 校验快照、指纹、审核决定 | 仍为 pending；按服务端门禁推进 |
| 内容/来源/基线均有效且决定完整 | 发布本轮变更 | 原子发布正式本体；请求 accepted；依效果计划处理事实 | 保留发布回执、事实结果和幂等键 |
| 待处理但决定不采纳 | 驳回/关闭请求 | 请求 rejected；保留账本与理由 | 候选是否回到待建模按来源绑定投影，不能只改前端计数 |
| 无新增结构、可复用已有术语 | 查看事实处理预览→确认 | 当前本体版本不变，按既有 finalize 物化合格事实 | 回执区分复用/新增/跳过，允许幂等重试 |
| accepted/rejected 历史草案 | 继续建模 | 新建基于当前正式版本的 pending 草案 | 历史请求保持只读 |
| 正式基线或来源变化 | 查看差异→重新基线/刷新来源 | 明确产生新草案修订与冲突报告 | 重新预览/校验/审核，不盲目重试 |
| 加入/发布超时，结果未知 | 查询结果或重试同一请求 | 相同幂等键恢复原结果 | 不生成第二份草案或重复操作 |

## 8. API 与服务能力对照（以当前工作树源码核实）

代码索引返回的源码区间已有偏移，本设计以有界文件检查纠正。下列为函数名证据，避免依赖旧行号。

| 能力 | 现有证据 | 设计落点/差距 |
| --- | --- | --- |
| 发现清单、候选图和来源 | `api/ontology_discovery.py: overview/candidate_mindmap`；`services/ontology_discovery.py: _candidate_source_reference` | 复用来源证据；UI要区分术语聚合数和事实数 |
| 发现运行→统一草案 | `services/ontology_discovery_workflow.py: OntologyDiscoveryWorkflow.create_run` | **缺口**：目前请求仅 name/infer_hierarchy，基于全项目候选；不支持显式选批或目标既有草案 |

| 重新基线与来源保护 | `OntologyDrafts.needs_rebase/rebase`；`RevisionConflict/StaleBase/StaleSource` | 用中文差异说明和恢复动作；失败保留用户选择与表单 |
| 校验、提交、逐条审核 | `api/ontology_drafts.py: validate/submit/decisions/review_plan/batch_approve` | 风险和门禁唯一来源为服务端；恢复手工审核，不靠一个“收下”隐藏全部步骤 |
| 发布与重复请求 | `DraftReviewPublishMixin.publish_preflight/publish/publish_readiness`；`repository/core.py: _publish_governed_ontology_draft` | 已有预期修订/预期本体/指纹/警告确认/幂等键；**缺口**：选批加入也需对应去重与回执 |
| 发现发布时事实物化 | `DraftReviewPublishMixin._publication_effect_plan`；`OntologyDiscoveryWorkflow.finalize_run` | 当前已经耦合，必须如实展示。**若要独立控制“只发布本体/另行确认事实”，需新增服务端策略与权限/审计契约，本次不假装存在** |
| 结构版本策略 | `publish_preflight` 中 `reuse_version=is_annotation_only(approved)` | 发布界面展示服务端决定的结构版本策略；纯注释不保证 vN+1 |

推荐新增的服务端契约应包含：候选选择快照、映射/父类选择、目标草案与 expected_revision、expected_ontology_id、源指纹、预演 token/指纹、依赖闭包、实际事实影响计划；确认加入使用同一预演指纹与幂等键，在事务中复核。端点名称留到实现计划确定。

## 9. 失败、并发与发布结果

- 草案修订变化：提示“其他修改已保存，当前为 r10”，提供刷新差异并保留原选择；禁止覆盖。
- 基线变化：显示 v3→v4 的变化和“重新基线”，重建预览后再确认；不能静默把候选塞到旧基线。
- 来源变化/候选已处理：明确哪些项已被另一批处理，哪些仍可用；返回实际跳过结果。
- 批次部分冲突：加入前清楚决定“排除冲突后继续”或“返回修改”；加入动作本身应原子成功或失败，不留半批。
- 网络超时：保留命令/发布幂等键与请求回执入口，先查再恢复；用户刷新后仍能从服务端恢复上下文。
- 索引失败：发布回执保持成功；单列“索引同步失败→重试”，不重复发布。

## 10. 设计验收场景

1. 从清单加入两项前能看到“新增类型供应商、属性注册资本”、目标草案、基线、来源和涉及事实；返回时选择保留。
2. 新增后正式本体仍是 v3；草案节点有文字标记；待建模清单可追溯至 D-024。
3. 将企业→供应商改为企业→交易主体→供应商时，两侧结构和四项原子图编辑可核对，其他父类保留。
4. 手动新增属性和关系，以及请求父类建议仍可在草案继续进行；发布后“继续建模”创建下一轮。
5. 跨种类同名冲突不能选入；证据和隔离诊断保留。
6. 审核过的操作被修改后，发布按钮立即显示需要重新校验/审核的原因。
7. 发布确认能区分结构发布和事实处理；全部术语复用时不伪造新结构版本；纯注释遵循版本复用策略。
8. 并发修改、来源变化、双击加入/发布与超时重试不产生重复草案/操作/事实。
9. 从“采购方”复用入口核对已有类型和稳定 IRI，未确认映射不能进入事实预演，未确认事实范围不能 finalize；确认后回执准确显示新增 1、复用 1、跳过 1，本体 v3 与草案修订不变，重试仍为同一 FR-001。
10. 只复用路径预演后若基线变化，阻止执行并要求重新核对映射；已完成回执保留处理时版本、源快照、跳过原因，后续建模不改写该回执。
11. 空草案无需导入任何候选，可手动新增类型、修改该条目、核对父类建议目标，再审核发布；事实数始终为 0。属性与关系也可直接写入操作账本；发布后历史只读，下一轮仍能看见已发布术语。

交互稿用于评审入口、列表、前后预览、草案结果、手工编辑和发布文案；上述原子性、校验、权限和并发约束需要后续实现与测试，不由静态稿证明。

### 交互稿的范围与状态核对

- 加入前提供“继续当前草案 / 基于当前正式版本新建草案”的明确选择，确认后使用选定的草案 ID、基线与修订显示结果。
