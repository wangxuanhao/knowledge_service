# 知识写入与本体建模的统一操作规范

日期：2026-10-20。状态：操作设计，尚未按本文改造生产页面或写入接口。

本规范承接 `2026-10-20-pending-modeling-flow-design.md`，把用户日常路径、入口与草案使用规则收敛为统一约定。旧交互稿中的选批、预演、指定草案并非现有生产能力。本次设计不把这些能力标记为已上线。

## 1. 用户只需先判断一件事

**我要补充具体知识，还是修改描述知识的结构？**

- 具体知识：某个客户、某笔订单、某条关系、某个属性值，进入资料处理与知识审核。
- 结构：客户类、订单类、客户与订单之间允许的关系、金额字段及约束，进入本体建模。

草案承载一轮结构修改；它还可以关联依赖这些结构修改的候选事实，但不是所有文档、事实或上传任务的容器。

| 对象 | 用户去哪里处理 | 管理的内容 |
| --- | --- | --- |
| 处理批次 | 资料库 → 处理批次 | 哪些文件、处理方式、抽取所用发布、进度、失败与结果 |
| 待确认知识 | 资料详情 → 提取知识，或知识台账 → 知识审核 | 具体事实、映射、来源证据、确认与排除 |
| 工作草案 | 本体建模 → 本轮修改 | 新增、修改、停用、恢复结构定义，以及明确加入的候选依赖 |
| 正式本体版本 | 本体建模 → 版本管理 | 已发布结构、发布身份与历史 |

## 2. 三种方案比较与选择

| 方案 | 操作影响 | 结论 |
| --- | --- | --- |
| 资料、事实、结构全部进入草案 | 所有上传都需要版本发布；普通事实与结构审核混淆 | 不采用 |
| 手工建模与开放发现各自独立建草案 | 后端现状接近此方案，但用户难以判断当前修改位置 | 不作为统一日常路径 |
| 批次管理写入，结构修改汇入明确的工作草案 | 复用已有定义时直接治理事实；确需改结构时明确关联草案 | 推荐；保留原有治理边界并补齐衔接 |

## 3. 日常路径 A：补充已有类型的知识

例：正式本体 v3 已有“客户”类，资料新增“张三是客户”。

1. 资料库点击“添加文件”。
2. 选择“按已有本体抽取”，确认确切正式发布。
3. 查看处理结果：新增、复用、待确认、未通过分别显示。
4. 有待确认事实时核对映射和证据；通过校验的正式事实在知识台账查看。

结果：增加或修订事实，本体仍为 v3，不因上传而新建本体草案。无法映射的事实保留诊断，提供“申请补充结构”入口，不偷偷扩充正式本体。关系约束的 advisory/review/strict/off 与开放/按本体的词汇策略仍是不同设置。

## 4. 日常路径 B：从资料中发现新结构

例：正式本体 v3 有“客户”，本批资料提出“企业客户”及“统一社会信用代码”。

1. 资料库“添加文件”，选择“开放抽取”。抽取结果先保留为候选。
2. 批次结果显示两组任务：可复用现有结构的候选、需要补充结构的候选。不得仅按显示名称相似就确认复用。
3. 复用组核对正式术语身份与事实范围后，执行“确认写入知识”；不制造空草案或新本体版本。
4. 需补结构组点击“完善本体结构”，在右侧抽屉查看候选、来源和依赖事实。选择要处理的内容，再预览加入。
5. 明确目标：继续当前已选可编辑草案，或基于当前正式版本另建草案。没有草案时在实际确认加入时自动新建；打开清单和预演不落草案。存在多份未选择草案时，必须显式选择，不能偷偷挑第一份。
6. 预览显示结构前后、实际新增/复用/冲突、目标草案及修订、关联事实范围。确认“加入本轮修改”后，画布显示草案结果，可继续手动编辑。
7. 审核与发布确认区明确展示“本体结构变更”和“同时处理的关联知识”。发布成功后分别报告正式本体发布、事实新增/复用/跳过、索引同步进度。

结果：有结构变更时发布新结构；符合最终获批结构和来源校验的关联事实按明确确认的范围处理。不能声称所有候选都会入库，不能让没有加入本轮的候选随手工修改发布。

## 5. 日常路径 C：手动维护结构

例：用户已确定需要“企业客户”这个类，不必先上传资料。

1. 本体建模使用唯一通用入口“新增定义 ▾”，选择“实体类型 / 关系类型 / 属性字段”。
2. 填写定义并保存。已有明确选中的可编辑草案时沿用；没有时基于当前正式发布自动创建。无正式本体时以空基线创建首版草案。
3. 当前项目有多份可编辑草案且未明确选中时，第一次保存前选择目标；之后在该工作区继续沿用。
4. 查看“本轮修改”，核对新增、修改、停用、恢复的前后值与影响。
5. 校验、审核、发布。没有关联候选时显示“关联知识 0 条”，只发布结构。

结果：新增结构定义。不会因为手工发布而自动确认历史积压候选。发布后可从资料结果中的“用新版本核对候选”发起明确的后续处理；新上传批次也可选择新发布。

## 6. 入口与页面收口

### 6.1 本体建模

固定上下文：

```text
正式本体 v3 · 已发布                         [查看正式版本]
本轮修改 D-024 · 修订 r8 · 基于 v3 · 未发布   [本轮修改 8] [审核与发布]
```

无草案时显示“当前没有未发布的结构修改；保存第一项结构调整时自动建立”。历史预览带“只读”，保留原工作草案选择。

| 现在容易混淆的入口 | 规范后的入口 |
| --- | --- |
| 目录、画布、详情多处通用新建类/关系/属性 | 顶部一个“新增定义”菜单；选择种类后共用同一个表单与写入接口 |
| 选中类后为它增加内容 | 保留“新增子类 / 为此类新增属性 / 新增关联关系”；明确预填对象和目标草案，不作为另一套创建流程 |
| 手动画布连接 | 保留“编辑继承 / 连接已有类型”；确认框写明本次将新增或修改哪个定义 |
| 新建草案、选择、关闭混在术语工具区 | 收进“本轮修改 → 草案管理”；另开一轮修改是显式高级操作 |
| 草案、源码与发现 | 拆为“待完善结构”抽屉、“本轮修改”与“高级 → RDF 源码 / 导出” |
| 草案术语显示“生效，可用于抽取” | 分开显示“草案中启用 / 草案中停用”与“已发布 / 未发布”；草案定义不能作为正式抽取依据 |

不删除既有草案、历史、源码能力、手工编辑能力或审核记录。

### 6.2 资料库与知识台账

资料库继续使用“添加文件 / 处理批次”抽屉。每个批次结果明确展示本体依据、事实处理结果和结构待办。

需补充结构的事实行可跳转到其关联草案；草案变更可返回来源文档、证据和批次。尚未关联时显示“未加入本轮修改”，不能显示成已保存。

知识台账集中展示具体实体、关系、属性值及其事实审核。草案目录不再承担普通事实审核入口。

## 7. 草案规则与用户可见状态

| 动作或情境 | 草案规则 |
| --- | --- |
| 打开建模页、查看源码、切换布局 | 不创建草案 |
| 上传文件或抽取完成 | 管理处理批次与候选，不因上传本身创建结构草案 |
| 第一次保存结构变更 | 明确目标后沿用或自动创建工作草案 |
| 从资料候选确认加入结构修改 | 明确目标和范围后写入该草案及候选绑定 |
| 仅复用正式术语写事实 | 不新增本体草案和本体版本 |
| 已审核后继续编辑 | 当前校验及相关审核决定按新指纹失效，重新校验审核 |
| 其他人发布新版本 | 工作草案显示基线变化，重新基线并处理冲突，不自动覆盖 |
| 发布完成 | 该草案成为只读历史；下一轮结构保存基于新正式发布建立新草案 |
| 关闭草案 | 说明原因并保留审计；候选不得丢失，需重新核对来源和绑定后才可再次加入 |

“待完善结构、未发布、待审核、可发布、基线变化”是从真实服务状态推导的显示，不新增等价持久状态机。工作草案指针是当前用户工作区的明确选择，不强制整个项目只能有一份草案。

## 8. 后端必须补齐的契约

当前代码的发现生成请求未携带目标草案，手工草案与发现草案分别创建；发布效果只支持自身发现运行的绑定。仅改前端按钮不足以实现本文。

1. 把“归纳建议 / 加入指定草案 / 确认复用事实”区分为明确意图。预演无写入，最终加入必须带项目、目标草案、预期修订、正式基线、来源快照、选择集合与请求身份。
2. 同一目标草案接收手工与多批候选时，操作、候选绑定、来源引用和事实发布效果必须在同一事务中完整更新。不能把发现草案的单一 publication_effects 字段直接覆盖到手工草案，不能丢掉先前批次的效果。
3. 只按最终获批的有效操作计算候选依赖。拒绝、撤销、替换或停用操作会使依赖事实重新判定，冲突和跳过原因可回查。
4. 只复用已有正式术语的候选走事实确认，不以未发布草案术语伪装正式映射。
5. 保留 CAS、来源和基线检查、审核与操作指纹、逐项警告、幂等及原子发布。发布前基于实时权威状态校验。
6. 保存草案、读取画布、审核状态和完整发布校验保持分离；本次整合不能恢复之前“保存一直等校验”的阻塞。
7. 发布回执分列本体发布结果、实际事实结果与索引投影状态。Milvus 仍为向量后端，不增加回退路径。

## 9. 迁移与交付次序

先补指定草案加入和多来源发布效果契约，再改前端入口与回执；不可先让按钮宣称已经加入选中的草案。

已有手工/发现草案按真实身份保留，继续编辑、发布或关闭。不会自动跨草案合并。用户初次进入时能查看旧草案并明确选择工作草案；来源不完整的旧候选显示诊断，不能强行迁入。

本规范不改变开放/按已有本体的选择权，不锁住发布后继续建模，也不把所有新增事实强制变成本体发布。

## 10. 必须验收的操作故事

1. 已有客户类，按本体上传张三资料：事实可追踪，本体版本和草案数不因上传增长。
2. 开放抽取全部可复用：确认后写事实，无空草案、无虚构新版本。
3. 已有手工草案，再加入新批次结构建议：明确使用同一草案 ID，原操作与审核审计保留，修订增加，旧校验失效。
4. 同一草案加入两批候选，再手工补属性：两批绑定都存在，预演和发布回执能逐批解释事实结果，未选候选不被处理。
5. 同一请求重试与并发加入：不会重复建类、建草案或写事实；陈旧修订返回冲突且不留下部分修改。
6. 来源撤回、基线变化、依赖操作被拒绝：阻止陈旧加入或发布，保留诊断与原有工作。
7. 空项目直接手工建类：首项保存准备首版草案，可继续加关系和属性，事实数为 0，发布后继续下一轮。
8. 纯手工发布新类：历史候选仍待处理；明确用新正式发布核对后，可走复用确认。
9. 多份已有草案：未选时明确选择；选中后所有一般结构写入的表单和回执显示同一目标。
10. 草案新增术语显示未发布；普通抽取只选择已发布身份；历史事实不因新本体发布自动迁移。
11. 重复通用新建入口已收口，且子类、属性、关系的上下文快捷编辑、源码、版本、父类发现仍可使用。
