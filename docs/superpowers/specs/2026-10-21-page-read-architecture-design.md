# 页面读取与响应性能设计

## 目标与现状

针对首次进入先露出业务页再跳登录、交互图谱、本体建模、资料库和知识台账缓慢，统一页面读取职责，删除无关请求，保留双时态、来源证据和本体发布校验语义。沿用 FastAPI、PostgreSQL、原生 JS，不迁移框架。

普通项目 `53264f57-4e9f-4cd5-a0f9-5a6f20181391` 实测 67 条当前记录、137 个历史版本、4 份文档、28 个实体。450001 条记录属于单独容量测试项目，不能用其规模解释普通页面慢。

上轮已实现鉴权遮罩、独立只读连接、分页资料元数据、断言批量读取、候选定向读取和页面响应代际保护。本轮仍复现：启动项目列表两次；台账 Apply/Reset 各两次主分页；隐藏批次组件三次初始化读取、每两秒两次轮询。复现命令 `node .benchmarks/page-request-count-audit.cjs`，修复前四项均 RED。

普通项目 13 个接口两轮共 26 次 HTTP 请求均 200；compact discovery 4048/4398ms，资料摘要 2313/1089ms，实体页 976/997ms。独立服务剖析 discovery 4748ms 中驱动 execute 4540ms（12 次）；资料摘要 989ms 中 execute 985ms（8 次）。EXPLAIN 的服务端执行时间明显较短，但不含完整结果传输、TOAST/输出序列化成本，因此尚不能归因于索引、磁盘或网络中的某一项。JSON 解码仅毫秒级。当前环境 Docker 引擎停止，恢复后须重新测量，不能将停服视作页面耗时。

## 方案选择

推荐在现有模块内逐步统一生命周期和专用读取模型。只继续加各处分支保护，改动小但重复加载仍会再生；全量改 SPA、引入统一响应缓存或 BFF 的成本高，且不能自动删掉重复调用。本方案先修可复现路径，再逐个收敛后端重计算。

## 页面请求边界

| 页面/动作 | 必需数据 | 禁止顺带加载 |
|---|---|---|
| 启动 | 公开鉴权策略、会话、项目选择列表一次 | Milvus 现场探测、OCR 校验、隐藏项目卡片/批次/草案列表 |
| 资料库 | 当前范围的来源摘要页，展开才读正文 | 所有历史正文、批次详情与 items |
| 知识台账 | 当前 kind 分页、可见行来源断言、治理摘要 | Apply/Reset 的第二条加载路径、全量 records/query |
| 本体建模 | 当前发布摘要、发现状态、草案目录一次、所选草案画布 | 渲染器自行读草案目录，隐藏模型重建 |
| 交互图谱 | 当前范围图或候选图，过滤面板展开才读字段 | 隐藏面板全量图和批次轮询 |
| 运行任务 | 所选子视图的一次加载，批次列表 | 先加载旧子视图、未展开批次的逐项读取、无消费者的全局 jobs |
| 批次详情 | 可见详情与当前 items 页 | 关闭后轮询、暂停/需人工处理状态无限轮询 |

## 生命周期与一致性

页面持有加载所有权。项目变化先使旧代际失效，再清理状态；只有可见页面读取。应用/重置通过唯一 `workspace:scope-changed` 事件触发，去掉额外 click loader。导航先确定页面和子视图，再加载目标一次。目录和画布渲染消费页面状态，不在 render 中发请求。

进行中的读取使用 AbortController（对支持 signal 的模块），离页、项目切换取消；仍保留代际检查，防止已经完成的旧结果覆盖新项目。共享目录去重键必须包含项目、完整 normalized scope、资源和修订身份，不能只按项目缓存。失败释放 in-flight 锁，显式刷新与写成功后重新读取。当前没有跨页面共享的数据不引入全局缓存。

批次列表与详情分开。只有可见的批次详情读取 items；后台服务器继续执行已提交任务。关闭抽屉只停止浏览器轮询，不取消任务；重新打开恢复读取。轮询只覆盖有自动进展的状态，暂停、中断、待人工处理、完成和取消停止；项目切换使在途结果失效。

## 后端读取设计

1. 公开鉴权策略返回配置布尔值，不触发数据库、Milvus 或 OCR；保留 health/readyz 诊断用途与现有鉴权 fail-closed。
2. 项目选择接口提供轻量目录选项，默认项目管理接口仍返回计数，保持兼容。轻量目录使用独立只读视图，避免共享 writer 锁。
3. OCR 能力读缓存模型身份校验结果，按清单、模型文件 stat、配置和运行包版本失效；实际引擎初始化仍强校验。禁止在每个页面能力请求中重读约 31.7MB 模型。
4. 复合读取在同一只读快照中验证项目一次。来源、台账和重分类逐步删除内部重复 get_project；标量计数使用专用聚合，不通过 limit=1 记录页取总数。
5. compact discovery 仍须返回正确生命周期，但无需解码每份旧草案的完整历史、所有本体 Turtle。先剖析投影和数据体积，再用专用生命周期输入替代，保留旧草案兼容性。
6. 草案画布视图应从共享 preview context 得出，stage/readiness 复用操作历史；发布时仍执行精确验证、权限检查、CAS 和源指纹校验，不能被编辑态缓存替代。
7. dashboard 只做范围聚合，文档成功计数通过 assertions 的多对多来源关联计算。facets 限定字段/样本扫描策略须另行定义可解释截断，不能静默改变完整计数。
8. ontology-index GET 的全量 reconcile 改为事务水位/模型身份摘要；精确重算保留为显式操作。历史版本按不可变 ID 直接读取和缓存 presentation。

第 1–3 项和前端已复现冗余为本轮可独立验证的修复切片；第 4–8 项为整体设计中的后续定向优化，逐项满足一致性回归后才能宣称完成，不在一次性能补丁中重写治理系统。

## 验证与验收

结构硬约束：一次事件最多一个相同主查询；隐藏页面无列表/详情扇出；关闭后无批次 timer；项目 A 的旧结果不能写入项目 B；显式刷新可重试；启动策略无需外部依赖；未认证业务区保持遮罩。

正确性守卫：已知时间/有效时间半开区间、include_unknown 与 applicability/null 语义、当前与历史来源事件、端点可见性、用户权限、草案版本和发布硬校验均不退化。台账不同 kind 的计数不是重复请求，暂保留直至专用聚合落地。

验证顺序：真实模块 VM 请求计数 RED→GREEN；针对可见/隐藏、离页重开、同项目新旧请求的前端测试；公开鉴权策略与 OCR 缓存失效测试；单一 pytest 会话；正常项目 HTTP 串行两轮与页面网络/长任务实测。客户端等待、SQL 服务端执行、响应解码和浏览器渲染分别记录。Docker/服务未恢复则明确记录未完成实测，不能用 VM 测试冒充浏览器表现。

暖态目标（设计预算，非现状保证）：鉴权策略 50ms、普通分页 300ms、首屏内容 500ms、标量辅助 500ms；实际以同环境前后采样报告，超预算必须记录 SQL 次数、等待和响应体大小。容量项目另列，不混入普通项目结论。

## 本轮落地范围（2026-10-21）

已按本设计实现页面所有权、轻量鉴权策略/项目目录、OCR 身份缓存。模型目录由主控读取并行复用；运行页先选子视图再加载；无后台 watcher 时不读全局 jobs；上传范围词表仅在上传界面读取且拒绝旧响应。批次列表与显式详情分离，离开、关闭、切项目会取消/失效请求，暂停和待人工处理状态不轮询。

数据库侧额外修复了两处已实测的冗余：来源/候选文档的文本 JSON 在物化投影中只解析一次；发现概览复用一份运行历史，避免逐草案查询和生命周期再次查询，同一路径 SQL 次数由 14 降至 9。来源投影四轮新旧结果完全一致，原查询 202–382ms，修改后 16–51ms。这个投影对照隔离了 SQL 写法影响；不同轮次 HTTP 同时受运行负载影响，不能把环境恢复后的所有提速算作代码收益。

仍未实施的整体设计项：专用多 kind 计数聚合、草案编辑 preview context、dashboard 来源聚合、ontology-index 水位摘要、不可变本体 presentation 缓存，以及完全取消所有旧模块在途请求。它们需要各自的正确性回归，不属于本轮已修复声明。暖态目标仍是验收预算，现有页面尚不保证全部达标。
