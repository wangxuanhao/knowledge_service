# 图谱、检索与问答的统一时间语义

用户已认可 Semantica 时间对标建议，并要求问答与检索筛选一起考虑，随后要求继续。实现沿用现有页面、原生 JS 和双时态 API。

## 范围与语义

- 业务有效期使用 `[valid_from, valid_until)`；缺起点显示“未知”，缺终点显示“未设结束时间”，不补写当前时间。
- 共享筛选提供“全部业务时间 / 当前有效 / 指定日期”，默认全部。当前有效在应用筛选时固定为一个明确 UTC 时点，并显示该时点；重新应用可刷新。它不是后台自动走动的时间窗。
- 指定日期为空或无效时禁止应用，保留此前已应用条件；不能静默清空时间限制。
- 有时间筛选时，用户可控制是否包含生效时间未知的记录，默认包含；全部业务时间不排除未知，且说明日期未知不代表已确认有效。
- 系统历史时点 `known_at` 独立于业务时点 `valid_at`。当前图谱“知识时间”明确改称系统修订时间，默认当前系统版本。历史语义/混合检索仍按既有能力明确拒绝，不能偷偷切换模式或清空历史日期。
- 检索与问答使用同一个页面归属筛选组件。移除问答独立 `qa-as-of` 日期入口，防止覆盖共享条件；保留历史/未来参考开关，说明参考不属于有效规则依据。
- 问答提交时只读取一次范围，传输请求、提交注记、历史保存及重试复用同一份冻结范围；以后改筛选不重写旧回答的范围。
- 包含未知时间关闭且存在业务时间条件时，问答参考补读也不能重新引入时间未知资料；历史和未来参考仍由既有参考开关独立控制。问答仍会核对来源文档的有效性，不能把未知或仅发布时间推定的资料当作确定有效规则依据。
- 检查器增加可证明的时间来源（显式维护、发布时间推定、原文抽取、来源继承或未知）；只展示现有 metadata/来源证据能证明的标记，缺少标记时不猜测。原文日期和系统记录时间分列。

## 实现边界

复用 `WorkspaceContext` 的规范范围 `valid_at / known_at / include_unknown`，不向 API 添加 UI 模式字段；存储仍为现有 PostgreSQL 双时态结构，不迁移或回填旧数据。当前有效可以在关闭或重开编辑器后恢复成显示该固定时点的指定日期模式，文案需明确当前时刻是在应用时固定。

纯时间选择、校验和来源文案收敛在小模块，视图调用共享逻辑；不在大型工作台脚本内复制计算。原有范围草稿/应用、项目与页面隔离、复制到问答和检索模式兼容检查保持一致。

## 验收

1. 全部时间请求 `valid_at=null`，不因当前时钟隐藏历史或未来记录。
2. 当前有效固定应用时刻；指定日期按浏览器本地输入转换为 UTC；清空无效日期不覆盖已应用范围。
3. 有效期开始边界命中、结束边界不命中；未来、失效和未知资料能按所选条件区分。
4. 平台/业务/对象、Metadata、本体/种类、业务时间、系统时间和未知开关可组合，切页或复制范围不会丢条件。
5. 问答发送时间与历史注记一致，生成前异步保存期间修改控件也不改变已捕获请求；旧历史保持提交时范围。
6. 问答关闭未知时间后，参考补读不重新引入未知资料；确定性规则证据仍只接受已经核对有效的资料。
7. 新前端资源有版本号，既有 Node 契约、Python 时间/问答回归和真实浏览器交互验证通过；不并行运行 pytest 会话。
