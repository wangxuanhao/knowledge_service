# 主流程待办与控件可辨识性

用户在上一轮方案实施后指出：候选与需要加入草案的内容藏在“继承导航与项目候选”中；草案选择像标题，下拉框不明显，并要求整体检查项目体验。本次属于已批准交互的修正与扩展走查，在现有 checkout 上继续，保留所有既有修改，不提交、不操作真实业务数据。

## 直接反馈的落地设计

- 建模左栏增加始终可见的“候选与草案待办”区域，放在术语目录和继承目录前。进入页面即可看到来自几份资料、几条待核对、几条已加入草案等待发布，以及对应明确动作。继承折叠区只负责层级导航，不再承载关键待办；切换卡片/继承/术语视图都不隐藏待办。
- 已发布/未发布、已加载草案/需要选择草案、候选加载中/读取失败/数量未知/暂无候选分别呈现真实状态。查看草案复用现有模型/工作区，不自动选择多份草案或创建草案，历史只读及权限守卫保持。
- 候选抽屉的草案去向改为两个显式、可点击的选项：“新建一份草案”和“加入已有草案”。已有草案才使用独立、带标签的草案选择框；新建选项旁说明确认时才创建。选择只改变现有 controller.target，不新增写入路径或修改确认语义。
- 全站原生单选下拉框具有明显边框、与纸面不同的控件底色、足够大的箭头区、hover/focus/disabled 状态，文字留足箭头空间。文本输入框、标题说明、选择控件视觉可区分。沿用现有青绿色主题，保留原生键盘/读屏行为、多选框、checkbox/radio、侧栏深色项目选择和紧凑布局。

## 全项目走查中确认的问题

在资料/候选/草案/任务及检索/问答/台账/项目设置中完成源码走查；真实浏览器工具因无法确认当前窗口 URL 而中止，本轮不继续操作用户浏览器。页面验证仅使用仓库的离线确定性测试，不当作真实业务全流程验收。

同轮修复不改变业务规则的明显误导与失效交互：

1. 台账不提供实际上无效的“全部类别”；保留当前按单一类别的表格与查询，选择值始终与实际 kinds 一致。
2. 切换项目立即清空知识备份列表；读取与恢复操作都绑定来源项目，丢弃迟到响应，防止 A 的卡片出现在 B 下。
3. 项目创建/设置在当前弹窗内显示字段和网络错误，保留输入；字段错误聚焦对应字段。
4. 问答发送前可见“仅展示依据 / 生成模型答案”的当前选择，复用唯一 generate 控件，保留现有默认 generate=false。只读用户遇到索引错误时得到管理员修复说明，不被引导到不可执行的构建动作。
5. 资料处理记录区分正式待审核事实与发现候选：正式候选进入项目知识审核，并如实说明是当前项目范围；发现候选继续使用准确 run/document 范围。不能用当前文档的模式冒充历史运行模式。
6. 任务完成卡片有发现候选时显示下一步，使用真实结果中的 run/document 身份；缺少身份只提供明确标为项目范围的入口，不伪造精确范围。
7. 首次本体审核操作保留既有校验→提交→服务端允许项批量批准行为，但增加可见说明，明确会批量批准哪些内容，未获准项仍需按定义审核。
8. 发布反馈将版本、关联知识和索引状态分开说明；索引状态仅来自本次回执，提供已有构建任务入口，不把页面刷新成功冒称为索引就绪，不自动构建或发布。

资料库按“待核对/草案待发布”跨资料筛选需要可信的逐资料人工待办读模型，列为后续产品增强；本轮不从处理完成状态猜造待核对统计。

## 验证与交付

用有意义的 Node 行为回归先复现隐藏待办、目标选择、台账值不一致、跨项目迟到结果、弹窗错误与候选误路由，再修复。对现有 UI 文案/资源版本契约作最小同步，保留以前的未提交修改。离线真实 JS/CSS 在桌面、平板、手机与键盘路径下检查首屏待办、标题/表单层级、草案选项、深色侧栏选择器、错误位置和边界；只使用合成数据。全量 Node、必要前端静态契约及独立规格/质量审查后交付。没有后端更改则无需重启业务服务，核对本地静态资源与缓存版本即可。
