# 从规则知识图谱到本体驱动平台：总体设计方案

日期：2026-09-09。范围：源码核查、公开资料对标、产品与技术设计；不实施应用改造。

## 1. 结论与定位

你的判断基本成立，但“完全没有本体”不准确。项目已有手工维护的领域本体、抽取类型约束、RDF 投影与部分校验；当前主线仍是“规则文档 → 实体关系抽取 → 知识图谱 → 图增强检索问答”。尚未形成可由业务人员生成、配置、审核、发布、迁移和治理的本体平台。

当前的本体编辑功能是带备份的 TTL 源码编辑，不等于完整的本体管理。也不能把安装 Semantica、接入 Neo4j，或把类别画成图，等同于拥有 Foundry Ontology。

建议目标：**先做规则知识领域的本体驱动知识平台，再按真实业务需求增加可执行的对象和动作。** 保留现有 16 Web、17 抽取和检索入口，分阶段替换内部能力，不大规模重写前端，不照搬整个 Foundry。

本方案中的 Open Foundry 暂指公开仓库 [syzygyhack/open-foundry](https://github.com/syzygyhack/open-foundry)。同名项目可能不止一个，若你指另一个仓库，需重新核对该部分。

## 2. 现有能力：有基础，但没有统一闭环

以下为静态源码审查结果，不代表已运行端到端测试，也不代表检查了每一份存量数据。

| 能力 | 源码证据 | 判断 |
|---|---|---|
| 本体定义 | `ontology/meituan_ontology.ttl` 包含类层级、对象属性、数据属性和两个 SHACL Shape | 已有领域模型，不是零基础 |
| 本体来源 | `docs/图谱设计.md` 说明由实体关系分析材料反向归纳；TTL 指向该设计 | 手工整理的领域本体，未发现项目级自动生成、审核发布流程 |
| 抽取约束 | `apps/17_rule_demo_semantica_api.py:167` 从 TTL 派生类型白名单 | 部分接入，但关系仅与硬编码列表取交集，新增关系不会自然进入抽取 |
| 模型展示 | `apps/16_kg_web_server.py:171` 等仍维护 CLASS_GROUPS、CLASS_DESC、PRED_DESC | 页面元数据与 TTL 分散维护，存在不一致风险 |
| 编辑 | `apps/16_kg_web_server.py:1035`、`:1047` 读取和保存 TTL，语法解析、备份、原子替换 | 文件维护工具；没有不可变版本、项目绑定、兼容性检查与审批 |
| 校验 | `kgcore/ontology_owl.py:635` 检查 domain/range 与祖先类型 | 轻量自定义检查，不是完整 OWL 推理或 SHACL 执行 |
| 抽取后回检 | `apps/17_rule_demo_semantica_api.py:742` 定义回检，`:1529` 命令行调用 | 16 的 Web 抽取分支未完整复用此流程；仅降低置信度也不等于禁止错误入库 |
| RDF/SPARQL | `kgcore/ontology_owl.py:232` 构造数据集，`:280` 过滤谓词 | 有查询基础，但 `_KNOWN_OBJECT_PROPS` 硬编码会过滤新增谓词 |
| 对象身份 | `apps/16_kg_web_server.py:334` 用实体文本作 ID、按文本去重 | 同名异物易合并；重复事实的多来源证据未完整保留 |
| 图结构 | `apps/16_kg_web_server.py:677` 使用 `nx.DiGraph` | 同一对节点的不同关系可能在运行时覆盖，迁移数据库前就应修正 |
| 检索问答 | `apps/16_kg_web_server.py:1828` 组合向量召回、邻域扩展与证据 | 已有图增强 RAG；不宜直接宣称具备所有 GraphRAG 社区汇总或全局检索能力 |
| 治理和动作 | 当前检查的主链路没有完整注册、版本发布、对象动作与权限闭环 | 是下一阶段的平台层建设，不是换皮即可完成 |

几个必须先解决的具体断点：

- 新增一个类或关系，需要同时影响抽取、校验、展示、RDF 与查询，不能要求人工修改多处列表。
- `entity_type_whitelist` 只取叶子类：新增子类可能让父类退出抽取白名单。应显式配置 `extractable`，不要根据树结构隐式决定。
- TTL 声明了必填标题等 SHACL 约束，但当前导出数据未完整填充这些属性。不能直接开启严格校验就宣布完成，应先完成映射和存量质量报告。
- RDFS domain/range 本质上具有类型推导语义，不直接等同于业务的闭世界输入校验；多个 domain/range 也不是简单“满足一个即可”。业务约束应单独定义并明确执行语义。[RDFS 标准](https://www.w3.org/TR/rdf-schema/)、[SHACL 标准](https://www.w3.org/TR/shacl/)

## 3. 三类东西要分清

| 层次 | 本项目例子 | 作用 |
|---|---|---|
| 本体/模型 | RuleDocument 有标题、版本、生效日期；RuleClause 属于 RuleDocument | 定义可以表达什么以及怎样表达 |
| 对象与事实 | 某份规则第 3 版、第 4.2 条、该条款对应某类违规 | 保存有身份、有来源、有状态的数据 |
| 检索与应用 | 查询某日期有效规则、回答处罚依据、审核抽取建议 | 使用数据完成任务 |

本体可以先由专家定义，也可以由数据归纳和 LLM 提议，通常是两者结合。图谱可以采用 schema-on-read，不是必须先建完整本体；但生产知识平台需要一个可治理的已发布模型来约束正式数据。

### Unknown 不等于“本体缺失”

Unknown 可能来自：抽取未给出类型、原始类型未声明、归一化丢失、关系端点没有对应实体、不同来源分类冲突、旧数据未迁移。本次不能仅凭标签确定某条实体的具体根因。

设计上保留 `raw_type`、`mapped_type`、`resolution_status`、`reason_code`、模型和提示词版本、证据位置。状态至少区分待分类、未声明类型、冲突、端点待解析、已确认；Unknown 只是前端兼容显示，不再作为正常业务类。

不能为了让校验通过，依据关系 range 强行把“直播账号信息”改成 Actor。可能是抽取错、关系选择错，也可能需要新关系表达内容适用范围。必须展示原文、模型建议和冲突原因供审核。

## 4. 对标：借鉴什么，不照搬什么

### Palantir Foundry：学习运营型本体

Foundry 将本体定位为连接业务数据与真实对象的运营层，包含对象、属性、链接，也包含动作、函数及安全机制。值得学习的是“模型 → 数据绑定 → 受控操作 → 应用复用”的产品闭环，不只是本体图形界面。[官方 Ontology 概述](https://www.palantir.com/docs/foundry/ontology/overview/)

它的 Action Type 描述一次受规则控制的对象/属性/链接变更，可配置参数、校验及副作用。对我们而言，将来可对应“确认抽取事实”“发布规则版本”“提交人工审核”，而不是把任意 CRUD 接口改名为 Action。[官方 Action Types](https://www.palantir.com/docs/foundry/action-types/overview)

阶段内不追求完整数字孪生、任意业务应用搭建器、通用函数沙箱和企业全域连接器。当前先做好规则知识模型；没有真实事件源时，不声称具备处罚执行与业务闭环。

### Open Foundry：参考 schema 驱动的工程组织方式

该仓库描述了由领域 schema 驱动 API、授权、动作、版本和审计的路线。README 明确标注 pre-1.0，并声明未经过独立安全审计或监管验证。适合作为架构参考和受控验证对象，不应仅凭功能列表当作成熟生产底座。[项目 README](https://github.com/syzygyhack/open-foundry/blob/main/README.md)

其 PostgreSQL+AGE、消息系统、身份与关系授权等组合，与本项目 Python/Neo4j 方向并不相同。借鉴单一模型来源、事务动作和变更日志，不直接搬入整套服务集群。README 还明确指出默认开发部署禁用了真实治理执行，使用允许全部操作的替身与模拟管理员；本地示例跑通不能作为鉴权有效的证据，不能暴露到不可信网络。[部署警告](https://github.com/syzygyhack/open-foundry/blob/main/README.md#run-the-stack)

### Semantica：采用算法组件，不等同于管理平台

官方模块包括 ontology、reasoning、provenance、change_management、graph_store 等。它不只是实体关系抽取库，但模块存在不意味着本项目已经接入。[官方模块目录](https://docs.getsemantica.ai/modules/)、[官方源码](https://github.com/semantica-agi/semantica)

本地安装版本为 0.6.7；检查到 ontology 目录存在生成、类推断、属性生成、OWL、校验、能力问题与版本相关代码。当前项目主要利用抽取组件，未把这些能力接成管理工作流。尤其本地 competency question 检查包含词语与类/属性名称匹配的启发式实现，不能当作“业务问题确实可回答”的验收依据。

建议通过适配器试用：本体草案生成、候选类/属性归纳、对齐建议；用独立测试验证质量、中文效果、异常行为和成本。注册中心、权限、发布、迁移和审计归项目自身管理。固定依赖版本，不在本次方案阶段升级。

## 5. 领域模型：先把规则知识表达准确

现有 Platform、Merchant、User、Violation、Penalty 词汇可以复用，但概念、角色和事件需要逐步拆分，不宜整套推倒重来。

第一阶段建议模型：

| 对象类型 | 核心内容 | 与现有模型的关系 |
|---|---|---|
| RuleDocument | 稳定业务 ID、标题、版本、生效/失效时间、来源 | 扩充现有规则文档 |
| RuleClause | 条款号、正文、所属文档版本、适用范围 | 将条款成为可引用对象 |
| ViolationType | 违规分类定义，而不是具体违规发生记录 | 明确现有 Violation 的知识分类语义 |
| PenaltyPolicy | 处罚方式、额度/时长范围、条件与例外 | 明确现有 Penalty 的政策语义 |
| RuleCondition | 适用主体、业务场景、次数、严重程度等条件 | 避免所有规则压成一条 triggers 边 |
| Evidence | 文档版本、页码/段落、字符区间、原文摘要与校验值 | 与对象/关系事实分别关联，多对多 |

示例关系：

```text
RuleDocument ─hasClause→ RuleClause ─definesViolation→ ViolationType
                               ├─hasCondition→ RuleCondition
                               └─specifiesPenalty→ PenaltyPolicy
上述对象及事实 ─supportedBy→ Evidence
```

“商家”这样的泛称是角色/类别提及，不自动变成真实商户实例。之后接业务数据时再增加 Organization、Person、Account、RoleAssignment，并明确主体在何种上下文、何时扮演角色。

第二阶段才考虑 ViolationIncident、PenaltyDecision、AppealCase：它们需要真实事件、审核和执行数据。规则文档能定义“什么情况下可以处罚”，不能证明“某商户已经违规并受到处罚”。

条件先支持有限、可解释的字段和操作符，复杂未结构化条件保留原文并标记人工判断。不要让 LLM 在没有规则引擎和业务授权时直接执行处罚。

## 6. 本体如何生成、配置与管理

### 6.1 生成：模型建议进入草稿，不直接修改正式本体

```text
业务目标与能力问题 + 样本文档/数据 + 领域模板
  → 候选类、属性、关系、约束、映射及证据
  → 人工合并/拆分/重命名/拒绝
  → 样本抽取试运行与质量报告
  → 审核发布 → 项目绑定版本
```

首先定义能检验的问题，例如“在指定日期，某类违规适用哪些处罚，分别由哪条规则支持？”这会倒逼版本、条件和证据建模，而不是追求自动生成更多类别。

提供两种抽取模式：正式模式只产生已发布模型允许的事实；探索模式允许提出新类型/关系，但进入候选队列，不污染正式数据。每条建议展示支持与反例、现有模型重用建议、置信度及预计影响。模型自报置信度不能作为自动发布依据。

### 6.2 配置：以结构化表单为主，TTL 为高级入口

配置对象类型、属性类型/枚举/单位/必填、链接端点/方向/基数、身份与去重规则、抽取描述/示例、数据映射、质量规则、显示名称及权限。

区分“允许被抽取”“允许生成实例”“抽象父类”，避免叶子类规则绑死业务。类 ID 与显示名称分离，中文改名不改变身份；命名空间按领域配置，不固定美团。

### 6.3 管理：发布必须可复现

生命周期：Draft → Validated → InReview → Published → Deprecated。已发布版本不可修改；编辑产生新草稿。项目绑定明确的 ontology_version；任务执行期间固定 schema、映射、提示词和抽取器版本。

发布检查：引用完整性、继承循环、属性/链接合法性、约束可执行性、样本校验、现有数据影响、API/查询兼容性。删类型、改属性类型、加必填、缩小范围通常需迁移计划，不能仅替换文件。

并发编辑通过 revision/ETag 检测冲突。回滚模型指针不代表数据自动回滚；迁移要保存前后修订、映射和可恢复快照，对不可逆转换明确阻止或要求专项方案。

### 6.4 单一来源的演进

短期继续以 TTL 为权威来源，先消除分散白名单并为项目保存快照。注册中心成熟后，切换为 PostgreSQL 中的结构化 OntologySpec 修订作为权威，统一生成支持范围内的 TTL、SHACL、抽取 schema、校验器与 UI 元数据。

不是把任意 OWL 无损转成普通 JSON 表单。先声明支持的模型子集；导入不支持的公理时，保留原始扩展并标记只读/不执行或拒绝发布，不静默丢弃。切换后不得让 TTL 和数据库成为两个可独立编辑的真相源。

## 7. 系统架构与数据库选择

建议保持一个模块化后端加异步 Worker，不急于拆微服务。

```text
现有 Web + 本体工作台
          │
API / 身份验证 / 项目权限
          │
本体注册 │ 数据接入与映射 │ 对象事实 │ 查询问答 │ 受控动作
          │
PostgreSQL（权威修订、事务、审计、任务、Outbox）
          ├── 幂等 Worker → Neo4j（图与向量查询投影）
          ├── 校验 Worker → RDF/SHACL 报告
          └── 文件/对象存储（原文、快照、模型附件）
```

| 组件 | 负责什么 | 不负责什么 |
|---|---|---|
| PostgreSQL | 用户关联、组织项目、角色、模型版本、映射、规范对象/事实修订、审核、审计、任务与 Outbox | 不把复杂多跳查询硬塞入业务表 |
| Neo4j | 对象关系查询、邻域扩展、图分析；经验证后承担向量检索 | 不替代本体生命周期或认证系统 |
| 文件/对象存储 | 文档原件、解析产物、大附件、备份 | 不作为并发业务元数据数据库 |
| Worker | 抽取、校验、导入、索引、迁移、投影重建 | 不在 HTTP 请求线程执行长任务 |
| 身份提供方 | OIDC 登录、会话及身份管理；是否引入独立服务按部署复杂度决定 | 不自动决定本项目每条数据的访问权 |

为避免跨库双写，建议 PG 保存规范数据与修订事件，Neo4j 作为可重建读模型；同一事务写数据、审计和 Outbox，Worker 按事件 ID 幂等投影。查询返回 projection_version；更新后需要即时可见的场景等待水位或读取 PG，不能把最终一致性伪装为即时一致。

这不是把 Neo4j 降为摆设：多跳关系和图检索仍由它承担；只是将需要与审核、权限、动作原子提交的权威写入集中在一个事务边界。若选择 Neo4j 作为对象权威库，则必须另行设计跨库变更协调，不能两边任意写。

初期保留 FAISS 兼容现有数据，迁移验证后可统一到 Neo4j 向量索引；是否另选 pgvector 或专门向量库，由目标版本的过滤能力、数据量、召回率、延迟和运维需求实测决定。**不必一开始同时部署三套数据库，也不必为向量独立选库。**

数据库支持的具体索引能力、版本和许可证应在实施选型时按官方文档核验，本方案不指定未经验证的版本组合。

## 8. 数据、权限和问答闭环

### 核心记录

- `ontology / ontology_version / schema_item`：模型、不可变修订和稳定类型 ID。
- `project_ontology_binding / mapping_version`：项目绑定与字段/抽取映射。
- `source_document / source_revision / evidence`：版本化来源及定位。
- `mention / extraction_claim`：原始提及与待审主张，保留原始类型和来源。
- `object / object_revision / relation_fact / fact_evidence`：稳定对象身份、关系事实及多来源支持。
- `proposal / review / validation_report / migration_run`：治理过程。
- `action_definition / action_run / audit_event / outbox_event`：受控变更和可靠传播。

每条跨项目记录包含 project_id；需要租户时增加 tenant_id 并统一约束。关系用独立 ID，不能只用起终点；去重键必须包含关系类型和必要业务维度。同名实体合并需身份策略与可撤销审核。

### 权限不是只加登录页

起步角色：管理员、本体设计者、审核者、数据编辑者、只读使用者；项目作用域和操作权限分开。发布与高风险动作按需要禁止自审。先实现可测试的项目级隔离，再扩展对象/字段敏感级别。

所有入口检查权限：列表、详情、导出、图扩展、向量检索、SPARQL、问答、缓存与后台任务。证据在送进 LLM 之前过滤；不能生成答案后才删引用。缓存键含项目、权限版本和数据版本。用户输入不得直接成为无限制 Cypher/SPARQL 或任意函数执行。

### 从图增强 RAG 到本体感知问答

问题识别 → 选择可访问的本体/数据版本 → 有限查询计划 → 属性过滤、关系查询和文本召回 → 证据校验 → 有引用的回答。

例如“该规则何时有效”优先查结构化版本属性；“为什么适用”组合条件与原文证据。未结构化或证据冲突时明确说明，不由 LLM 补造事实。问答只读默认不执行动作；如需动作，单独显示参数、权限、影响与确认过程。

## 9. 前端信息架构：保持现有系统，新增真正可操作的工作台

保留项目、文档、实体、图谱、问答和测评页面。把目前本体页面升级为“本体工作台”，不再把实例数量统计当成模型定义。

| 页面/标签 | 用户任务 |
|---|---|
| 概览 | 查看当前绑定版本、发布状态、覆盖率和阻断问题 |
| 对象与属性 | 左侧类型树，中间表单，右侧实例样本与影响；区分定义属性和观测到的属性 |
| 关系与约束 | 编辑端点、方向、基数、必填与校验规则，预览正反例 |
| 数据映射 | 配置来源字段/抽取字段到对象属性、主键与关系端点，预览转换结果 |
| 候选与质量 | 审核新类型、Unknown、冲突、孤立端点；定位原文并批量处理 |
| 版本与发布 | 差异比较、影响分析、试运行报告、审核和项目升级 |
| 动作（后续） | 配置已限定的业务操作及执行记录，不先建设任意代码平台 |

样式延续正常业务系统：信息密度适中、表格和表单优先、状态与版本常驻可见。关系图只辅助理解，不承担所有编辑操作。编辑实例类型和编辑类型定义应有不同入口与明确影响提示。

## 10. 渐进实施顺序

| 阶段 | 工作包 | 完成标志 |
|---|---|---|
| P0：保真与统一 | 备份/恢复演练；统一模型加载；16/17 共用抽取后处理；修正多关系覆盖；保留原始类型与多来源；项目模型快照 | 现有流程不退化，新关系不在任一路径静默消失 |
| P1：本体管理 MVP | PG 注册中心；结构化类型/属性/关系编辑；基础映射；校验试运行；候选审核；不可变发布；项目版本绑定；必要登录与权限 | 用户不改 Python/TTL，即可完成一个领域模型版本发布与绑定 |
| P2：生产数据底座 | 规范对象/事实修订、Neo4j 投影、异步任务、幂等导入、审计、权限全链路、备份监控 | 索引可重建、失败可重试、跨项目不可越权、数据能恢复 |
| P3：语义检索与受控动作 | 模型约束查询计划、有效期过滤、证据冲突处理、有限动作框架与必要业务源接入 | 能完成真实业务闭环，而不仅是展示知识图谱 |

P1 先支持对象、属性、关系与有限约束，不做任意 OWL 逻辑、不做无限制函数沙箱、不做整套 Foundry 克隆。只有样本需求和数据规模明确后再给工期、成本和性能承诺，不用主观百分比评价“生产成熟度”。

建议代码边界：把 16 逐步收敛成路由层；新增 `ontology_service`、`ingestion_service`、`object_service`、`query_service` 和 `projection_worker`。现有 17 与 Semantica 封装为 ExtractorAdapter；底层类型不直接暴露给前端。首阶段可以仍在一个 Python 进程/代码库内分模块。

## 11. 验收用例与迁移保护

1. 新增 `governsContent` 后，不修改 Python 白名单，抽取配置、页面、校验、图查询和 RDF 均能识别。
2. 新增子类型不会隐式禁用父类型抽取；必须由显式配置决定。
3. 模型 v2 尚未发布或项目未升级时，绑定 v1 的任务结果与查询不受影响。
4. 缺失必填标题产生可定位的校验报告，严格导入阻断，探索导入进入隔离区；不是只降置信度。
5. 同一对对象可以同时保留两种关系；同一事实有两份证据，不因去重丢失来源。
6. 同名不同主体不被自动合并；Unknown 能查到原始输出和原因，审核修正有历史可追踪。
7. 图投影任务中断后重试不重复生成对象；索引落后明确显示；索引可从权威数据重建。
8. 用户不能通过问答、向量、导出或查询语言看到其他项目受限信息，连证据摘要也不能泄漏。
9. 修改或撤回文档版本后，关联事实和索引按策略失效；历史回答可以追溯当时版本。
10. 回滚演练同时验证 schema、对象修订、原文与索引恢复，不仅验证 TTL 文件存在。

正式动工前冻结基线：备份代码、TTL、项目 manifest/graph/corpus、向量索引和原始文档；保存校验值、依赖版本、当前样例问答与查询结果。转换先在副本执行，旧数据只读保留，按项目迁移，不一次覆盖所有项目。

## 12. 推荐决策

先批准 P0 + P1 的产品范围，而不是先购买或部署一堆数据库。最小成果应是：**创建本体草稿 → 配置对象属性关系 → 文档映射与试运行 → 审核发布 → 项目绑定 → 按同一模型抽取与检索**。

Neo4j 是重要的图数据能力；PostgreSQL 是治理与事务基础；Semantica 是可替换的算法工具箱。真正需要自主建设的核心，是把它们连接起来的本体生命周期、数据身份、证据、权限和受控变更流程。

本方案使用 research 技能组织一手资料核查；产品设计建议是基于本项目源码与业务场景的推导，并非声称各对标产品采用相同内部架构。
