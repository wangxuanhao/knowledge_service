# 演讲稿：从规则文本到可问答的知识图谱

> 汇报时长参考：约 8–12 分钟；每节建议配 1–2 屏演示。
> 可直接照读，也可删减加粗句。配套系统文档：`docs/16_Web服务_现状与使用指南.md`。

---

## 开场（30 秒）

各位好。我今天汇报的是：**怎么把美团/大众点评这类海量规则协议文本，自动变成一张"能查、能问、能追责"的知识图谱，并给出带出处、可回滚、可评测的落地系统。**

业务痛点很直接：审核与风控规则有成百上千份、条款互相引用、不断更新，靠人肉翻文档既慢又容易漏。我们希望做到：**问一句业务问题，系统从图谱和原文里找出证据，再给出一句话结论和出处**。

整个项目分五步讲：**数据从哪来 → 实体和关系怎么构建 → 图谱与向量怎么成型 → 网页上怎么用 → 怎么保证正确与可回滚。**

---

## 一、数据从哪来：原始规则文本（1 分钟）

**一句话：先有"原材料"，即平台规则协议原文。**

- 原材料是 `.md/.txt` 的规则文档，放两个目录：`data/rule_demo`（小样）和 `data/rule_txt`（批量全量）。
- 命名自带业务分层，例如 `业务规则_美团外卖_…_商户食品安全违法平台停止服务规范.md`。
- 我们平时调 17 号脚本整批抽取，产出到 `data/rule_demo_output/run_<时间戳>/`；Web 里点"📥 载入数据"即可一键把每个 run 建成一个"项目"。

**演示提示**：可切到「📄 数据源」页，点开任意项目，直接看到这批原文长什么样、一共多少字、被抽出了多少实体和关系。

---

## 二、实体与关系是怎么构建的（核心，3 分钟）

**一句话：分块 → LLM 受约束抽取 → 归一消歧去重 → 构图。** 这里按"实体怎么来"详细讲。

1. **标题感知分块（structure-aware split）**
   长规则不能一刀切。我们按章节标题把正文分块（块约 8000 字、重叠 400），保证"一条完整规则/一个处罚条款"尽量落在同一块里，避免被硬切两半——这是抽取质量的关键地基。

2. **LLM 抽取实体（受本体白名单约束）**
   用 17 引擎（semantica 原生 NERExtractor + 关系抽取，标题感知分块、自动偏移校正、JSON 稳定）。
   每个实体都必须落在**本体定义的类型**里，比如：
   - 主体：平台 Platform、商家/商户 Merchant、用户 User、履约服务、外部组织；
   - 规则与条款：RuleDocument / 章 / 节 / 条；
   - 治理：违规行为 Violation、处理措施 Penalty、救济途径 Remedy；
   - 数据与交易客体：个人信息、商品/订单/资金结算等。
   也就是"抽什么"不是模型随便定，而是由 `ontology/meituan_ontology.ttl` 这本体文件（唯一要手改的说明书）约束的。

3. **LLM 抽取关系**
   在已抽实体的基础上抽"主-谓-宾"，谓词同样是白名单：如 `规则禁止 prohibits`、`违规触发处罚 triggers`、`平台处置 handles`、`商户实施违规 commits`、`条款归属 partOf` 等，并做 domain/range 约束回检——平台只能处置违规，商户才能实施违规。

4. **归一 + 消歧 + 去重**
   同一实体在不同文档写法不同：卖家、店铺、商户、商家。我们做**别名归一**：可人工标注"某名是某实体的别名"；合并两个近似实体（向量相似 + 类目一致自动并入）；重复三元组去重。这一步决定图谱里是不是"同一个人只有一个节点"。

5. **构图成环**
   实体→节点，关系→有向边，存成 networkx 图，落盘 `graph.json`，同时每个节点/边都带上：**类型、置信度、来自哪份文件、命中的原文条款**——为后面"每个答案都能溯源"做准备。

**演示提示**：切「图谱」页点节点看详情（出/入边 + 出处条款）；切「实体」页看别名与合并；切「🧬 本体」看这些类型/谓词哪来的。

## 三、图谱与向量如何成型（1 分钟）

**一句话：图负责"关系链路"，双路向量库负责"语义召回"，两者一起打包成一个可离线复用的"项目"。**

- **实体向量库**：把"名称+类型+上下文片段"编码进 FAISS，解决"名称不完全一致也能搜到"；
- **原文段向量库**：把整段条款原文编码，命中任意相关句子；
- **项目包**：`data/projects/<项目名>/` 下统一放 manifest（元信息+来源全文+别名+统计）、graph.json、实体/段 JSON 和向量索引——离线可迁移、重启可重载。

## 四、网页上能做什么（2 分钟）

8 个入口，覆盖"体检→浏览→治理→问答→更新"：

- **看板**：项目总览，实体/关系/来源分布一眼看完；
- **图谱**：力导向图浏览与语义检索，图例中文、颜色按类型统一；
- **实体**：按类目管实体，可增删、加关系、**别名与合并治理**；
- **本体**：看类型/谓词字典（来自 TTL）；
- **数据源**：看这个项目背后的原始文档与统计；
- **脑图**：以任意实体为根向下展开关系；
- **问答**：端到端 LLM 问答（下面重点讲）；
- **增量**：把新文档并入已有项目，并带**版本快照与一键回滚**。

### 重点演示：问答是怎么答的
1. 多通道召回证据：实体向量 top-k + 命中原文段落 + **段落里出现的实体回灌补漏**，再沿图的出/入边扩展取"关系证据"；
2. 把证据编成 `[1][2][3]…` 编号上下文，让大模型**只依据证据回答**、逐条标出处、证据不足就明说（不编造）；
3. 流式输出，答案下方可展开证据、可一键跳回图谱定位那条实体与关系。

**演示提示**：在「问答」页问一句，如"平台对售假商户会采取哪些处理措施？"，指出答案里带 [n] 编号、点开能看原文——这就是"可审计的问答"。

### 重点演示：增量与版本
新规则来了不用重建整库：选已有项目 + 上传一篇文档 → 后台任务逐分块抽取并实时打日志 → 别名/向量消歧对齐后**合并进原图**；写入前自动存一份完整快照，"📎 增量"页能列版本并**一键回滚**（可反复回退）。切页面任务不中断。

## 五、正确性、运维与评测（1 分钟）

- **溯源**：每个节点/关系带来源文件与原文条款；每个问答答案可回溯到证据编号。
- **日志**：服务落盘日志（每个接口耗时 + 未捕获异常）与 stdout 镜像，出问题能定位是模型还是并发。
- **健壮性**：后台写索引与前台检索已加锁防并发段错误；任务跑在服务线程，页面切换不影响。
- **评测"尺子"**：用 18 号脚本建 gold 标准答案，跑 `eval` 得到实体/关系/三元组的准确率、召回率、F1——改一版引擎就能对分，避免"感觉变好了其实更差"。

## 结尾与下一步（30 秒）

一句话总结：**从"规则文本"出发，经过受本体约束的 LLM 抽取与消歧，构建"图+向量"项目，在网页上提供可溯源问答与增量治理，并用 gold 评测兜底。**

下一步方向：
1. **全局问答（Global Search）**：Leiden 社区检测 + 社区摘要，回答"整个规则体系层面"的问题；

## 可能的提问与应答要点

- **"为什么不用纯 RAG 检索文本，而要建图？"** 文本 RAG 答"单条事实"够用，但"违规→处罚→申诉→法律依据"这类**跨条款的关系链路**和"某条规则被哪些场景引用"，图结构天然能多跳推理，也方便治理与归并。
- **"抽取错了怎么办？"** 三层兜底：本体白名单过滤 + 置信度保留 + Web 人工别名/合并/删除；还有 gold 评测监控漂移。
- **"数据敏感/保密？"** 全本地模型（bge-m3 本地向量），LLM 走自有/受控通道；落盘均可加 ACL 与审计链（待做项）。
