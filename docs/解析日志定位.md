# 解析任务日志定位

在“后台任务”查看逐任务日志；同样的日志会输出到启动终端，以 `[task:任务ID]` 标记。每条包含 UTC 时间戳和任务运行秒数。数据库保存每个任务最近 2000 条日志。

## 应当看到的步骤

1. 文档标题、字数、项目 ID，原文收据 ID。
2. 切片策略、长度、重叠、总片数，以及项目本体版本。
3. 每片的序号、原文起止位置、字符数。
4. 抽取模块加载、实体抽取器初始化、LLM 实体抽取开始与结束、实体数。
5. 关系抽取器初始化、LLM 关系抽取开始与结束、关系数；无实体或关系类型时明确记录跳过。
6. 消歧融合、已有实体更新数量、知识与本体校验、向量化、PostgreSQL 落库。
7. 完成或失败。失败保留最后阶段、异常类型、代码位置；只有成功才标记 100%。百分比表示阶段估计，不是模型处理比例。

## 长时间没有完成

每 30 秒记录“仍在等待当前步骤”，附上工作线程最近 8 层的文件名、行号和函数名，不包含局部变量、正文或模型请求体。

- 抽取器初始化：可能在加载 NLP 模型或依赖。
- LLM 抽取：可能在建立连接、等待响应、内部重试或响应解析；结合执行位置区分。
- 向量化：检查本地 embedding 模型加载和计算。
- 等待锁／PostgreSQL：检查另一个写入操作或数据库锁。

等待诊断不是自动超时取消，也不表示任务有实际进展。当前没有实现硬性总任务超时；Semantica 内部每次 HTTP 尝试和 token 用量尚未单独拦截记录。不要仅凭心跳认定任务正常。

## 安全与重启

不记录完整提示词、LLM 响应或 API Key，环境中的密钥值会脱敏。不要开启 HTTP 请求正文调试后直接分享日志。

旧式单文档任务与批次任务的恢复入口不同。任务卡若显示 interrupted，请先核查原文收据；批次任务按下面的检查点流程继续。强制停服前保存的原文收据可能仍显示 processing。

## 批次、检查点和 OCR（2026-10-14）

在「知识写入」的批次卡核对申请/实际并发与状态计数。详情分页显示文件的 `stage`、`failed_chunk_ordinal`、`error_code`、自动重试次数和 `next_retry_at`；下载失败明细用于逐文件排查。排查时保留项目 ID、批次 ID、条目 ID 和固定来源版本 ID，不分享令牌或供应商原始异常正文。

- `retry_wait`：临时模型或 OCR 错误正在退避；到时自动继续。
- `needs_attention`：自动重试耗尽、配置不兼容、附件缺失或 OCR 低置信度。先处理公开原因，再选择恢复方式。
- `interrupted`：核对服务和租约状态，使用「从断点继续」复用成功切片。
- OCR 失败：先用「查看原文与 OCR」打开固定来源，核对文字、置信度与坐标框。忽略图片必须填写原因并留下审计记录。

切片配置、文件、本体、模型或解析器版本变更会使旧检查点不兼容，应整份重新处理；旧尝试与固定来源仍保留。可用 `scripts/generate_ingest_fixture.py` 生成确定性知识包，`scripts/verify_ingest_batch.py` 在隔离项目验收。完整操作与真实截图见 [批量知识写入与断点续跑运维说明](2026-10-14-批量知识写入与断点续跑运维说明.md)。
